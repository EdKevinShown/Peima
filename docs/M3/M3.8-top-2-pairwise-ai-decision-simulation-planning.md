## 一、主流程（重新定义顺序）

以下顺序为 **产品语义上的用户主路径**；**Full RRM** 与 **M1.3 校准** 不在此路径上阻塞用户。

| 步骤 | 名称 | 职责 | 备注 |
|------|------|------|------|
| **1** | **条件硬筛** | 年龄、城市、性别意向、关系目标、硬性偏好、红线等；**不通过者不进 6 人池**。 | 与现网硬 gate 一致；无硬筛通过则无后续。 |
| **2** | **人像 / 长相匹配** | 在硬筛通过人群中生成 **6 人候选池**；人像用于吸引力、照片质量、风格偏好等 **排序/分层**。 | **不**单独决定最终对象；输出进入下一步的 **池 + 排名元数据**。 |
| **3** | **20 维关系画像筛选** | 从 6 人池筛出 **Top 2**；输出 **`relationshipShortlistTop2`**（见 §二）。 | Top 2 仅为 **待 AI pairwise 模拟的候选**；**不是** Final Match。 |
| **4** | **Top-2 Pairwise AI Decision Simulation** | 输入 Top 2；**1～2 次** LLM 调用（目标 **30～90 s**）；输出 **`aiPairwiseDecision`**（见 §三）及 **`winnerCandidateId`**。 | **未来**参与「最终展示对象来源」的 **AI 决策层**；本轮仅契约与规则。 |
| **5** | **Final Match** | 仅展示 **二选一后的 1 人**；若 AI 失败/超时，**fallback** 到 **20 维静态第一**（见 §六）。 | 不写 **`MatchResult`** / 不改 **`finalScore`** 为本轮交付；接入需 **独立门禁 PR**。 |
| **6** | **Full RRM diagnostic** | **后台**异步；admin / shadow / M1.3 calibration；**不**改变用户已看到的 Final Match。 | 与 `ai-simulation-v1` / M4.1 类诊断对齐语义；**静默不替换** UI 已展示对象。 |

**确认（对应交付清单 §1）**：主流程为 **硬筛 → 人像 6 人池 → 20 维 Top2 → AI 二选一 → Final Match**；Full RRM 为 **并行诊断层**。

## 二、`relationshipShortlistTop2` 契约（20 维 → Top 2）

**目的**：在 **6 人池** 上产生 **可复现、可审计、最小必要字段** 的 Top 2 静态短名单，供 Pairwise AI **唯一输入**（除 viewer 上下文外）。

**建议根类型名**：`relationshipShortlistTop2`（JSON 列或 API 子对象均可；字段名可团队统一 snake_case）。

```typescript
// 规划契约 — 非运行时代码
relationshipShortlistTop2 = {
  schemaVersion: 1,
  sourceVersion: "relationship-shortlist-top2-v1",
  viewerUserId: string,
  poolId: string,
  generatedAt: string, // ISO-8601
  /** 指纹：viewerUserId + poolId + candidateUserIds[0,1] 有序 + staticRank + 规则版本哈希（实现时定义算法） */
  shortlistFingerprint?: string,
  candidates: [
    {
      candidateUserId: string,
      staticRank: 1 | 2,
      staticCompatibilityScore: number, // [0,1] 或产品约定标度；文档化即可
      axisScoresSummary: Record<string, number> | Array<{ axisKey: string; score: number }>, // 20 维摘要：聚合/桶化，非原始问卷全文
      majorStrengths: string[], // 短句，上限条数实现时固定
      majorRisks: string[], // 短句或结构化 risk tags
      dealbreakerPassed: boolean,
      visualPoolRank: number | null, // 在 6 池中的 rank；无则 null
      reasonSummary: string, // 可复现的筛选理由（规则 id + 关键因子）
    },
    {
      candidateUserId: string,
      staticRank: 2,
      // ... 同上
    },
  ],
};
```

**硬约束**

| 约束 | 说明 |
|------|------|
| **`candidates.length === 2`** | 否则 **不走** Pairwise AI，直接 **fallback**（见 §六）。 |
| **隐私** | **不**含完整隐私画像、**不**含可识别长文；仅 **AI 决策必要摘要** 与 **已脱敏/已摘要** 的 20 维信息。 |
| **可复现** | `sourceVersion` + 规则版本 + 输入池 fingerprint + **确定性 tie-break**（实现时写清）。 |
| **无假候选** | `candidateUserId` 必须来自 **当前 pool 真实成员** 且 **已过硬筛**。 |

## 三、`aiPairwiseDecision` 契约（Pairwise AI 输出）

**目的**：单次（或受控两次）LLM 的结构化 **决策提案**；**默认**不写入 **`MatchResult`**，**不**影响 **`finalScore`** / worker 排序。

```typescript
aiPairwiseDecision = {
  schemaVersion: 1,
  sourceVersion: "ai-match-pairwise-decision-v1",
  viewerUserId: string,
  poolId: string,
  candidateAUserId: string,
  candidateBUserId: string,
  winnerCandidateId: string,
  loserCandidateId: string,
  decisionConfidence: number, // [0,1]
  decisionScoreA: number,
  decisionScoreB: number,
  dimensions: {
    conversationFit: number,
    emotionalSafety: number,
    conflictRepair: number,
    progressionFit: number,
    longTermFit: number,
    riskControl: number,
  },
  candidateA: PairwiseCandidateBlock,
  candidateB: PairwiseCandidateBlock,
  decisionReason: string, // 短摘要，非长对话
  fallbackUsed: boolean,
  appliedToFinalScore: false,
  appliedToWorkerRanking: false,
  generatedAt: string,
};

// 共享块
type PairwiseCandidateBlock = {
  conversationFit: number,
  emotionalSafety: number,
  conflictRepair: number,
  progressionFit: number,
  strongRisk: boolean,
  suggestedAction: "stop_or_step_back" | "slow_down" | "maintain" | "continue_lightly" | "soft_progress" | string, // 实现时与产品枚举对齐
  progressionWindow: "closed" | "weak_open" | "open" | "strong_open" | string,
  reasonSummary: string,
};
```

**说明**

- **`appliedToFinalScore` / `appliedToWorkerRanking`**：固定 **`false`** 于本契约；若未来接入写入，需 **新门禁 + 新 PR**。  
- **本步性质**：**decision proposal**；与 **Full RRM** 的 `rrmSimResult` **分离命名空间**，避免诊断工具误读。

## 四、AI 模拟范围（Pairwise 专用，非 Full RRM）

**只做「紧凑」pairwise 评估**，**不**生成 **7 场景** 完整 transcript，**不**输出长对话原文，**不**复用 Full RRM 的 **慢 payload**（`transcript_lite` v2 全量模拟）。

**建议模块映射（prompt 设计层面）**

| # | 模块 | 说明 |
|---|------|------|
| 1 | **开场顺滑度** | 短 rubric + 静态摘要推断，非逐轮对话生成。 |
| 2 | **情绪安全 / 尊重风险** | 与 **strongRisk**、尊重相关信号对齐；**不得**用未校准 D_pre 顶格 **单独否决**（见 §九）。 |
| 3 | **轻微分歧修复** | 单维度或双场景 **摘要级** 判断。 |
| 4 | **推进节奏** | 与 `progressionFit` / `progressionWindow` 提案一致。 |
| 5 | **长期目标初步适配** | 轻量，不等同 Full RRM 长期场景全家桶。 |
| 6 | **strong risk** | 布尔 + 短因；供 **§五** 规则消费。 |

**输出控制**：JSON schema **强校验**；失败 → **`fallbackUsed: true`** + 走 §六。

## 五、决策规则（Rule + AI fusion）

**输入**（每条候选 + 全局）：`staticRank`、`staticCompatibilityScore`、`decisionScoreA/B`、`strongRisk`、`suggestedAction`、`progressionWindow`、`decisionConfidence`。

**规则草案（实现时编码为纯函数 + 单测）**

| # | 条件 | 结果 |
|---|------|------|
| **R1** | **仅一方** `strongRisk === true` | 该方 **不得** 为 `winner`；winner = 另一方（若另一方通过其它硬性检查）。 |
| **R2** | **双方** `strongRisk === true` | **无 confident match**：进入 **fallback / 静态 Top1 / 或 admin review**（产品择一；默认 **fallback 静态 Top1** 需显式产品确认）。 |
| **R3** | `decisionConfidence` **高** 且 `|decisionScoreA − decisionScoreB|` **≥ 明确阈值**（如 0.12，可调） | `winnerCandidateId` = **AI 胜出方**。 |
| **R4** | 分差 **小**（低于阈值）且 confidence 非高 | **保留 20 维静态第一** 为 winner（**稳定性优先**）。 |
| **R5** | AI **失败 / 超时 / schema 校验失败** | **fallback** = **20 维静态第一**；`fallbackUsed: true`。 |
| **R6** | `suggestedAction === stop_or_step_back` **仅一方** | 该方不得为 winner（与 R1 可合并实现）。 |

**与 AI 的关系**：LLM 产出 **提案分数与理由**；**最终 winner** 由 **规则层** 裁定，避免模型漂移一票否决静态安全结论。

## 七、并发策略：一次 Pairwise vs A/B 各跑一次

| 维度 | **方案 A：单次 pairwise prompt（同时比较 A/B）** | **方案 B：A、B 各一次 compact，再本地比较** |
|------|-----------------------------------------------|---------------------------------------------|
| **延迟** | **最低**（1 次网络往返） | 2 次调用；可 **并发**，仍可能 > A |
| **偏见** | 对比框架可能引入 **序偏差 / 锚定**；需 **严格 JSON schema + 候选顺序随机化或双序跑分**（实现项） | 单候选评估 **较稳定**、可审计 |
| **成本** | 低 | 中高 |

**推荐（对应交付清单 §4）**：**MVP 采用方案 A**，与 **30～90 s** 目标一致；**实现时**加入 **顺序鲁棒性**（例如：随机 A/B 标签 + 校验 `winner ∈ {A,B}`，或 **双序一致性检查** 作为 M3.8-M5 增强）。**方案 B** 作为 **M3.8-M6+** 或 **高争议样本** 的可选路径。

| 方案 | 描述 | 优点 | 缺点 |

|--------|------|

| 单测（mock Prisma + builder） | `apps/api/test/ai-pairwise-top2-shortlist.service.spec.ts` |

**输入与门禁**

- `previewPool` 必须存在且 `userId === viewerUserId`，`items` 非空；否则 `RelationshipShortlistTop2Error` **`POOL_NOT_FOUND`**。
- **Viewer** 必须有 **`user_profile`**；否则 **`VIEWER_PROFILE_REQUIRED`**（不伪造画像）。
- 池内项按 **`candidateUserId` 去重**（保留 **`rankInPool` 最小** 的项）。
- 候选：`candidateUserId !== viewer`；**`displayMode === "full"`**（与 preview shortlist v0 eligible 一致）；存在 **`User`** 与 **`UserProfile`**；**`passesPreferenceHardGate`**（与 `@peima/shared/matching/preference-hard-gate` 一致）。**`dealbreakerPassed`** 在契约中恒为 **`true`**（未通过硬闸者不会进入 Top2）。
- 通过上述门禁者 **&lt; 2** → **`INSUFFICIENT_ELIGIBLE_CANDIDATES`**。

**排序（静态）**

1. **`staticCompatibilityScore` 降序** — 基于现有 **`computeG1rProfileScalarScore`**（`post-pool-dimension-g1r.ts`，与 worker profile 标量同构），映射为 **0–100** 整数；对 **`marriageExpectation` / `childrenIntent` / `riskPreference`** 轴若 **\|Δ\| &gt; 0.55** 各扣 **2** 分（上限仍 clamp 在 0–100）。
2. **平局**：**`rankInPool` 升序**（保留池内展示顺序）。
3. 再平局：**`candidateUserId` 字典序**。

**`axisScoresSummary` / strengths / risks**

## 二十、M3.8-M4B planning note（Pairwise WaitingPage / Fallback UX）

**状态**：**M3.8-M4B 仅规划** — 定义等待语义、超时与 fallback、Final Match 接入门槛、viewer API 草案、前端 UX 草案、与 Full RRM 边界；**本轮不改代码**、**不写 `MatchResult`**、**不改 `finalScore`**、**不接 `FinalMatchPage`**、**不让 Pairwise 静默替换已展示对象**、**不进入正式 M4**。

### 20.1 用户等待阶段定义

**语义**：关系画像筛选已完成，正在进行最后一轮 **AI 二选一（pairwise）** 关系模拟。

**建议主文案**（可 A/B 微调语气）：

> 正在进行最后一轮 AI 关系模拟，通常 1 分钟内完成。

**进入条件（逻辑上同时满足）**：

- 6 人池已生成（当前业务下的 preview pool / 等价阶段）；
- **20 维 Top2** 已生成（`RelationshipShortlistTop2` 已就绪）；
- **pairwise job** 已存在且状态为 **`queued` 或 `running`**（或已触发创建、等待 worker）；
- **Final Match 尚未展示**（未提交「最终一人」的 viewer 可见结论）。

**退出等待**（进入下一 UX 分支）：`succeeded` 且通过 **§20.4** 门槛 → 可进入「最终一人」提案阶段；`failed` / 前端超时 → **§20.3** fallback；`running` 过久由 stuck recovery 回到 `queued` 时，等待页仍视为「进行中」，直至超时或成功。

### 20.2 等待时间策略

| 指标 | 建议值 | 说明 |
|------|--------|------|
| **P50 体验目标** | 30–40 秒 | 文案「通常 1 分钟内」与工程目标一致；worker poll 间隔（如 10s）与 LLM 延迟叠加后仍应多数落在此区间 |
| **P90 体验目标** | ≤ 90 秒 | 与前端最长等待对齐，避免「无限等」预期 |
| **前端最长主动等待** | **90 秒** | 硬顶；超时即走 fallback（见 §20.3） |
| **轮询间隔** | **3–5 秒** | 平衡 DB 压力与体感；可与 `GET .../jobs/:jobId` 草案对齐 |
| **超时后** | fallback | 不允许全页 **5 分钟** loading；可与后端 stuck recovery（如 15m）解耦 — **用户可见**以 90s 为准 |

**注意**：后端 `STUCK_TIMEOUT_MS`（如 15m）用于 reclaim **running** job，**不**等于用户等待上限；用户层 **90s** 单独产品化。

### 20.3 Fallback 策略比较与推荐

| 方案 | 行为 | 优点 | 缺点 |
|------|------|------|------|
| **A** | 超时 / `failed` 后 **直接 static Top1** | 用户必有可展示结果；实现简单 | AI 失败时参与感弱 |
| **B** | 超时后仍阻塞或强提示「稍后再看」 | 尊重 AI 完成机会 | 易引发焦虑与流失 |
| **C（推荐）** | **双阶段**：前端 **90s** 内只等 pairwise；超时 **用 static Top1 展示最终一人**，**后台 pairwise 仍继续**；若之后 job `succeeded`，**不静默替换**已展示对象，仅 **admin diagnostic / 审计日志** 记录「晚到结果」 | 兼顾 SLA 与数据完整性；符合约束 **「不让 Pairwise 静默替换已展示对象」** | 实现与观测面稍复杂（需记录 `displayedSource: static_pairwise_timeout` 等） |

**推荐**：**方案 C**。与 M4A 异步 job 模型一致：超时仅影响 **首屏 Final 提案来源**，不取消后台 job。

### 20.4 Pairwise 结果何时可成为 Final Match（门槛草案）

以下全部为 **后续实现** 的准入条件；**M4B 不实现**。

1. **Job 成功**：`ai_pairwise_decision_jobs.status === succeeded`。
2. **契约有效**：`AiPairwiseDecision` 通过 `parseAndValidateAiPairwiseDecision`（与现 validator 一致）。
3. **身份绑定**：`winnerCandidateId` / `loserCandidateId` 与 Top2 中 `candidateA` / `candidateB` 一致（与现有 **winner_binding** 语义一致）。
4. **`strongRisk`（产品闸）**：
   - 若 **`winnerCandidateId` 对应块 `strongRisk === true`**：**不得**将该 winner 作为 Final Match 展示 winner；
   - 若 **仅 loser strongRisk**：可按规则仍用 winner（需在实现 spec 中写清文案与合规）；
   - 若 **两侧均 `strongRisk === true`**：进入三选一产品分支（本轮只定方向）：**no-confident-match**（空态+解释）/ **static fallback（Top1）** / **admin review 队列** — 推荐默认 **static Top1** + 标记诊断，避免用户卡死。
5. **`decisionConfidence`**：建议阈值 **`>= 0.55` 或 `>= 0.6`**（实现时二选一并配置化）；低于阈值 → **staticRank 1**。
6. **分差过小**（可选闸）：若 `|decisionScoreA - decisionScoreB|` 低于某 epsilon，视为「无明确偏好」→ **staticRank 1**（具体阈值实现阶段再定）。

**小结**：Final Match 的「可展示 winner」= job 成功 + 校验通过 + winner 非 strongRisk + confidence（及可选分差）通过；否则走 static / no-match 分支。

**输出（完整 proposal，admin / tests）**：`schemaVersion: 1`，`sourceVersion: pairwise-final-match-proposal-v1`，`recommendation` ∈ `pairwise_winner_eligible` \| `static_top1_fallback` \| `no_confident_match` \| `pairwise_unavailable`；含 `candidateUserId`、`fallbackCandidateUserId`、`reasonCode`、`reasonSummary`、`pairwiseJobStatus`、`decisionConfidence`、`decisionScoreGap`、`winnerCandidateId`、`staticTop1CandidateUserId` 等（**viewer 路径不得**把 confidence / gap / strongRisk / raw scores / dimensions 透出）。

**Gate 规则（评估顺序概要）**

1. `jobStatus !== succeeded` 或 `decision == null` → **`pairwise_unavailable`**，`candidateUserId` = static Top1。
2. `candidateA/B` 与 shortlist Top2 顺序绑定不一致，或 `winnerCandidateId` 不在 Top2 → **`pairwise_unavailable`**（`invalid_decision_binding`），`candidateUserId` = static Top1。
3. 双方 **`strongRisk`**：`strongRiskPolicy === no_confident_match` → **`no_confident_match`**；否则 → **`static_top1_fallback`**。
4. 仅胜方 **`strongRisk`**：`no_confident_match` policy → **`no_confident_match`**；否则 → **`static_top1_fallback`**。
5. `decisionConfidence < minConfidence` → **`static_top1_fallback`**。
6. `abs(scoreA - scoreB) < minScoreGap` → **`static_top1_fallback`**。
7. 以上均通过 → **`pairwise_winner_eligible`**，`candidateUserId = winnerCandidateId`。

**说明**：fallback 到 static Top1 **不等于** AI 失败；`no_confident_match` 仅为 proposal 状态，**不写**最终结果；pairwise **不**静默替换已展示对象（须由上层路由 / 写入策略保证，见 §二十）。

### 一、Final Match 生成来源分层（产品语义）

| 分层代号 | 语义 | 触发条件（概要） | 候选来源 |
|----------|------|------------------|----------|
| **A. `static_final`** | 静态最终主路径 | pairwise **不可用**（queued/running/failed、无 decision、绑定非法）、**超时**（如 90s）、**低置信** / **小分差** / **strongRisk fallback**（见 §二十二 gate → `static_top1_fallback` 或 `pairwise_unavailable`） | **20 维 Top2 的 `staticRank === 1`**（`staticTop1CandidateUserId`） |
| **B. `pairwise_final`** | AI 二选一通过闸后的最终来源 | pairwise job **`succeeded`**；**`buildPairwiseFinalMatchProposal`** 输出 **`recommendation === pairwise_winner_eligible`**（即 confidence / score gap / strongRisk 等 gate 已通过） | **`winnerCandidateId`**（与 proposal 的 `candidateUserId` 一致） |
| **C. `no_confident_match`** | 无可靠 AI 胜者（proposal 层） | 双方 `strongRisk` + policy `no_confident_match`，或单胜方 strongRisk + 同 policy 等（见 §二十二） | **MVP**：不单独做「无匹配」空态产品页；**默认仍走 A**（static Top1）+ **诊断 / admin**；可选 **admin review**、**稍后再试**、未来 **显式 rematch** 流程（须用户主动触发，**非**静默写库） |

**与 M7 proposal 的映射**：`pairwise_winner_eligible` → 才允许映射到 **B**；`static_top1_fallback` / `pairwise_unavailable` / 超时 → **A**；`no_confident_match` → **C**（MVP 默认回落 **A** + 旁路记录）。

### 二、写入时机方案比较（A / B / C）

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A** | Waiting 内等 pairwise（如最多 90s），**过闸后**再写 **`MatchResult`** | 用户看到的 Final 与 **真实 AI 二选一** 一致 | 等待链路复杂；写入须 **幂等、强门禁、防晚到替换** |
| **B** | **先**写 static 的 **`MatchResult`**；pairwise **只**写 proposal / 诊断，**不**改已写结果 | **安全**；实现简单 | 产品上 AI 更像「解释层」，除非后续再显式「升级」展示（不推荐静默） |
| **C** | 新建 **`FinalMatchCandidateProposal`**（或等价 JSON sidecar 表），**先**持久化 proposal，**不**直接写 **`MatchResult`** | **安全过渡**；可 shadow / 对账 / 回滚 | 多一层存储与状态机 |

**推荐的最小生产路径（与产品倾向对齐）**

1. **短期（推荐）**：**方案 C 的「sidecar / proposal 持久化」** + **方案 B 的用户可见结果** — 即 **先 static 或先只记 proposal，用户可见 Final 不与晚到 pairwise 绑定**；**不**在 Waiting 内强依赖「写完 MatchResult 再跳转」作为唯一路径。  
2. **与「方案 A 的 shadow」等价物**：在 **未**打开写 `MatchResult` 的 flag 前，将 **若启用 pairwise 会选谁** 写入 **sidecar / shadow 字段**（不改变用户已选或已展示的 `candidateUserId`）。  
3. **再进入方案 A 的变体**：仅在 **Final Match 尚未对用户提交（未展示 / 未冻结）** 且 **feature flag** 打开时，由 **专用、幂等 endpoint** 将 **B** 写入 `MatchResult`（见下文 Phase 3）。

### 四、已展示对象不可替换原则（硬性）

**英文（contract 用语）**  
**Once Final Match is shown, a late pairwise result must not silently replace it.**

**中文**  
一旦最终匹配对象**已经展示给用户**（或已处于产品定义的 **「已冻结 / finalized_for_viewer」** 状态），**晚到的** pairwise `succeeded` + `pairwise_winner_eligible` **不得**通过任何后台路径 **静默** 修改 **`MatchResult`** 或替换前端已渲染的最终对象。

**晚到结果仅允许**：

- **admin diagnostic**（审计、排障）；  
- **shadow report**（Phase 2 对账）；  
- **未来显式 rematch / 重新生成**（须 **用户主动** 触发、独立流程与文案）；  
- **禁止**：无用户感知的 `PATCH` / worker 偷偷更新 `MatchResult`。

实现时建议增加明确状态位（规划）：例如 **`final_match_presentation_frozen_at`** 或 **`match_result_source_locked`**（**本轮不建字段**，仅语义约束）。

### 三、Final Match 冻结点（Frozen）

**产品语义**：一旦用户处于 **「已看到最终 1 人」** 或后端已 **提交不可回退的最终展示承诺**，即视为 **frozen**，**晚到 pairwise success 不得覆盖**。

**冻结为真的判定（OR，实现时择可落库子集）**

1. 客户端路由已进入 **`FinalMatchPage`** 且服务端已记录 **`finalMatchRouteEnteredAt`**（规划字段，**本轮不建**）；或  
2. **`MatchResult`**（或等价行）已被 **读接口标记为已展示**（如 `displayedAt` / `finalizedAt`）；或  
3. 已存在 **`finalMatchDecisionMeta.frozen === true`** 且可选 **`frozenAt`**；或  
4. 业务定义的 **「finalize 成功响应已下发给客户端」** 且客户端 ACK（可选，复杂度高，**MVP 可不用**）。

**当前无字段时**：M3.8-M11 起优先在 **meta 侧车（方案 B）** 或 **独立 `FinalMatchDecision` 行（方案 C）** 写入 **`frozen` / `frozenAt`**，**避免**仅依赖「是否写了 `MatchResult.candidateUserId`」推断（可能与 static 预写竞态）。

**原则**：**Once frozen, late pairwise must not silently replace the shown candidate**（与 §二十四 · 四一致）。

### 六、Finalize 规则（服务端顺序概要）

1. **Job 缺失或非 owner** → **404**（与 viewer pairwise 一致，防枚举）。  
2. **`queued` / `running`** → **409 或 202 `pending`**（**不**写 `MatchResult` / meta 终态）；body 含 `retryAfter` 可选。  
3. **`failed`** → **`static_fallback`**；`selectedCandidateUserId = staticTop1`；记录 `fallbackReason`。  
4. **`finalSourceShadow` 缺失** → 若 `succeeded` + `decisionResult` + `shortlistSnapshot` 可 **重建 shadow**（调用与 M9 相同 builder）；否则 **static_fallback**。  
5. **`proposalRecommendation === pairwise_winner_eligible`**：  
   - **`enabled`**：`selected = shadowSelectedCandidateUserId`（应等于 M7 winner）；  
   - **`shadow` / `proposal_only`**：`selected` **仍规划为 staticTop1**（用户可见不变），meta 记录 **「若 enabled 会选」**（可与 `finalSourceShadow` 对齐）。  
6. **`pairwise_unavailable` / `static_top1_fallback` / `no_confident_match`** → **`selected = staticTop1`**（MVP `no_confident_match` 同 §二十四）。  
7. **已 frozen** → **不覆盖**任何已展示/已提交字段；返回 **`already_frozen`**（HTTP **409** 或 **200** + 业务码，团队统一）。  
8. **任意持久化路径**须 **幂等**（见下节）。

---

### 七、Fallback 规则（与 M7 / M9 / Waiting 对齐）

- **90s 超时**（未 `succeeded`）→ **staticTop1**；finalize 若对未完成 job 调用 → **pending** 或 **static_fallback**（产品二选一，**推荐 pending** 直至 job 终态或用户放弃）。  
- **failed / 低置信 / 小分差 / strongRisk fallback** → **staticTop1**（理由写入 `fallbackReason` / `reasonCode` 桶）。  
- **`no_confident_match`（MVP）** → **staticTop1** + **诊断 / admin**。  
- **late pairwise success** → **仅** admin / shadow / 显式 rematch；**finalize** 在 frozen 后 **拒绝**更新。

---

### 八、幂等性（`viewerUserId` + `poolId` + `pairwiseJobId`）

- **唯一键建议**：`(viewerUserId, poolId, pairwiseJobId)` 上的 **finalize 结果**（meta 行或 `MatchResult` 上 JSON 子文档版本）。  
- **重复调用**：若已存在 **同一 finalize 版本** 的 meta → **返回已有**（HTTP **200** + `idempotentReplay: true`）。  
- **已 frozen 后重试** → **不**写不同 `selectedCandidateUserId`；返回 **`already_frozen`**。  
- **同一 pool 多 job**：仅允许 **与当前会话绑定的 `pairwiseJobId`**（如 session 或 **最近一次 Waiting 写入的 jobId**）通过校验，**禁止**随意换 job 绕过冻结。

- **`queued`/`running`** → **`pending`**，**不**写表。  
- **`failed` / shadow 缺失**：由 **`buildPairwiseFinalSourceShadowRecord`** 复算 → **`static_fallback`** meta，**写表** `frozen=true`。  
- **`pairwise_winner_eligible` + `proposal_only`/`shadow`**：`selectedCandidateUserId = staticTop1`，**`wouldChangeStaticResult`** 反映 shadow。  
- **`MODE=enabled`**：返回 **`status: disabled`**，**不**写表（本轮不启用真写）。  
- **同 `(viewerUserId, poolId)` 已有行**：**`already_frozen`**，返回 **已存 meta**（**晚到 pairwise 成功不替换**已 finalize 侧车）。  
- **幂等**：重复调用与首次冻结后调用均返回同一逻辑结果。

**前端串联（M3.8-M12A）**：见 **§二十八** — `finalizeWithPairwise` + WaitingPage 状态机。**M3.8-M12B**（enabled display 规划）见 **§二十九**。**M3.8-M13**（read path + Final 页）见 **§三十**。

## 二十九、M3.8-M12B planning note（Enabled-mode 写入策略 / E2E）

**状态**：**仅规划** — **本轮不改代码**、**不写 `MatchResult`**、**不改 `MatchResult.finalScore`**、**不改 worker batch-match 主排序**、**不改** Full RRM / `ai_simulation_v1` / `evaluateRrmSimFromSimulationV2` / `extractDPre` / `rrm-sim-formula.ts` / `rrm-sim.constants.ts`、**不**进入正式 **M4**。

### 一、enabled mode 的目标（语义边界）

`PAIRWISE_FINAL_MATCH_MODE=enabled` **不等于**正式 **M4**（不做 RRM 排序融合、不改公式常量、不改 worker 主链写入语义）。

在本规划内，**enabled** 仅表示：

- 在 **Final Match 尚未冻结 / 尚未对用户展示最终对象** 之前；
- 若 pairwise **侧车 meta** 表明 **M7 proposal** 通过闸（等价 **`pairwise_winner_eligible`**，且满足 **MIN_CONFIDENCE / MIN_SCORE_GAP / strongRisk** 等，见 **§二十二**、下文 **§五**）；
- 则允许 **`selectedCandidateUserId`（侧车 JSON 语义）采用 pairwise winner**，且 **仅在 Top2 内二选一**；
- 否则 **`selectedCandidateUserId = staticTop1`**（与 `MatchResult.candidateUserId` 所代表的静态主路径一致）。

**必须同时成立的产品约束**

| 约束 | 说明 |
|------|------|
| 仅 Top2 内二选一 | 不得把 pairwise 扩展为 6 人池重排 |
| 不重排 6 人池 | 输入仍来自既定 shortlist Top2 |
| 不参与 worker `batch-match` 主排序 | worker 行为与既有 `MatchResult` 生成语义不变 |
| 不改 `finalScore` | **不改** `MatchResult.finalScore` 及 worker 写入的分数列 |
| 不覆盖已展示结果 | **late pairwise**、晚到 finalize **不得**静默替换用户已看到的对象 |

---

### 二、写入 / 持久化方案比较（A / B / C）

**方案 A：直接改 `MatchResult.candidateUserId`**

| | |
|--|--|
| **优点** | 读路径简单，与历史字段名一致 |
| **缺点** | 与 static 预写竞态、审计弱、回滚难；误写 / 晚到代价高 |
| **结论** | **不推荐第一版**（与 **§二十六**、**§二十七** 一致） |

**方案 B：`MatchResult` 不动，读路径优先 `PairwisePoolFinalizeMeta`（及 JSON `meta` 内 `selectedCandidateUserId` 等）**

| | |
|--|--|
| **优点** | **不改** `MatchResult` 物理行；与 **M11** 已有侧车表对齐；回滚 = 关 flag + API 回落 `MatchResult.candidateUserId` |
| **缺点** | `GET /matching/result` 须绑定 **哪条 `poolId`** 上的 meta；须防跨池误用 |
| **结论** | **推荐为最小安全 MVP** |

**方案 C：新增 `FinalMatchDecision` / `FinalMatchDisplaySource` 表**

| | |
|--|--|
| **优点** | 来源清晰；易挂 **`displayedAt`、审计、版本**；与 `batchId` 生命周期解耦 |
| **缺点** | 多表、迁移与 join；与 **B** 职责可能重叠 |
| **结论** | **可选演进**（合规 / 强审计 / 读路径过复杂时） |

**推荐（最小安全）**：**方案 B** 作第一版；**不**采用 **方案 A**；**方案 C** 按需引入。

### 三、FinalMatch read path 规划（方案 B）

**路由**：`GET /matching/result/:userId`（或等价 viewer-safe BFF）。

**响应可新增（规划名，实现时以 DTO 为准）**

| 字段 | 语义 |
|------|------|
| `finalMatchDecisionMeta` | **可选**、**裁剪后** viewer-safe 摘要（**禁止** raw 分 / dimensions / `strongRisk` / A/B）；可为 `null` |
| `displayCandidateUserId` | **C 端展示用**最终对象 id，由服务端 **派生** |
| `displaySourceType` | 粗粒度枚举（如 `static_match_result` \| `pairwise_finalize_sidecar`），**不**暴露 pairwise 推理细节 |

**必须保证**

### 四、冻结（frozen）规则

1. **`POST .../finalize-with-pairwise` 成功写入**后，`PairwisePoolFinalizeMeta.frozen=true`（**§二十七**）。  
2. **已 frozen** 时重复 finalize → **`already_frozen`**；**不得**用晚到 pairwise **覆盖**已存 display 相关语义。  
3. **`FinalMatchPage` 首次视为「已对用户展示」**时（**M13** 须收敛一种机制）：**要么**写 **`displayedAt`**（侧车扩展列或 **方案 C** 表）；**要么**定义 **隐式冻结**（仅 static、无 meta 亦锁定后续 display），须与产品一致。  
4. **同一 `(viewerUserId, poolId)`** 仅一行侧车（`@@unique`）。  
5. **enabled** 下亦 **禁止**在已展示后因 late success **静默切换** `displayCandidateUserId`。

### 五、enabled mode gate（`selectedCandidateUserId = pairwise winner` 须全部成立）

1. `PAIRWISE_FINAL_MATCH_ENABLED=1`

**否则**：**`selectedCandidateUserId = staticTop1`**。
