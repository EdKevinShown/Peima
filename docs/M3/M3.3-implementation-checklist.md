# M3.3 Implementation Checklist

> **定位**：把 [M3.3 Durable Queue MVP](./M3.3-durable-queue-mvp.md) 从方案压缩为 **最小代码实施清单**（规划文档，**非**可执行代码）。  
> **约束**：不改 `finalScore`、不改 worker `batch-match` 主排序、不改 `MatchResult.finalScore`、不改 RRM 公式、不进入 M4、不恢复 `shortlistScenariosV0`、不引入 Redis/BullMQ；优先 **DB-backed queue**；**尽量不做 migration**，除非确认 `updatedAt` 不足以做 stuck recovery。

## 2. 每个文件改什么

### `ai-simulation-v1.service.ts`

- **`requestRunJobAsync`**：移除 **`void executeRunJobBody`** 与 API 内 **`queued → running` claim**；改为 **只入队**（保证/维持 **`queued`**、校验 `viewerUserId`；对 **`running` / `completed`** 返回 `already_running` / `already_completed` 等 **与产品约定一致**的 reason）。**API 内不执行 LLM 循环**。
- **`runJob`**（若仍存在同步路径）：与 admin 行为对齐或标记 **仅测试/CLI**；避免生产 **双路径** 在 API 内仍 `await` 全长任务。
- **`executeRunJobBody` / `runOneItemWithRetries` 及私有依赖**：**迁入 shared runner**（或 worker 内临时副本，**不推荐**）；API **不再**启动该执行体。

### `admin.controller.ts`

- `POST .../jobs/:jobId/run` 仍调 service；**若语义集中在 service，本文件可不改**。

### `post-pool-deep-screen-orchestrator.service.ts`

- 对 **`requestRunJobAsync`** 的调用：期望从「API 内 claim + 后台跑」变为「**job 保持 `queued`**，由 **worker** 消费」；若有依赖 **`started` / `jobStatus: running`** 的日志或分支，**一并调整**。

### `apps/worker/src/main.ts`

- 保留现有 **daily-match `node-cron`**。
- **注册** AI simulation：**poll 定时器**（拉 `queued` → claim → 调 runner）；**注册** **stuck recovery** 定时器（可与 runner 同文件或拆分）。

### `ai-simulation-v1-runner.ts`（新建）

- **`pollOnce`**：`jobStatus === queued`，`orderBy updatedAt asc`，`take` 小（如 1～3）。
- **`claimJob(jobId)`**：`updateMany({ id, jobStatus: queued } → running)`，**仅 `count === 1`** 时调用 **`executeRunJobBody` 等价逻辑**。
- **`recoverStuckRunningOnce`**：见 **§6**。
- 初始化 **PrismaClient**、读 **与 API 一致的 simulation / LLM env**；结构化 **log**（`jobId`、`viewerUserId`、`event`）。

### `ai-simulation-v1.constants.ts`

- 增加 **poll 间隔**、**stuck 阈值** 等 **env 键名常量**（API/worker 共用字符串来源）。

### `.env.example`

- 注释 **`AI_SIMULATION_V1_WORKER_POLL_MS`**、**`AI_SIMULATION_V1_STUCK_TIMEOUT_MS`**（名称以实现为准）。

## 3. 是否需要抽 shared runner

**需要（推荐）。**

- **`executeRunJobBody`** 依赖 Prisma、LLM client、config、logger 及同目录多模块；worker **不应**依赖整个 Nest **`AiSimulationV1Service`**。
- **推荐**：新建 **`packages/ai-simulation-v1-runner`**（或 `packages/job-runners` 子包），导出 **`runAiSimulationV1JobExecution(deps, { jobId, viewerUserId })`**，由 **worker 直接调用**；API 侧 **删除**进程内执行，必要时 **薄封装**调用同一包（仅测试或编排）。
- **备选（仅 spike）**：先复制进 worker 再抽包 — **技术债高**，不作为默认清单项。

---

## 4. API `/run` 如何从 fire-and-forget 改成只入队

| 现状 | 目标 |
|------|------|
| API 内 **`updateMany(queued → running)`** | **不在 API claim**；`running` **仅由 worker** 写入 |
| **`void executeRunJobBody(...)`** | **删除**；API **永不**调 LLM item 循环 |
| 返回 **`running` + `started: true`** | 改为 **`queued` + `started: false`** + **`reason`**（如 `enqueued_for_worker`），或与前端约定 **兼容字段**（实现前定稿，**诊断页**以 **GET** 轮询为准） |

**边界**：`already_running` / `already_completed` **读 DB 原样短路**；orchestrator 创建 job 后仍为 **`queued`**。

---

## 5. Worker 如何 poll `queued` job

1. **周期**（如 5～15s，env）：`findMany({ where: { jobStatus: 'queued' }, orderBy: { updatedAt: 'asc' }, take: 1 })`（或 `take: 3` 再逐个 claim）。
2. 对每个候选 **`jobId`**：**`claimJob`**（条件 **`queued` → `running`**，`count === 1`**）。
3. **仅 claim 成功**时 **`await runAiSimulationV1JobExecution(...)`**（MVP **建议串行**，避免 worker 内无界并发）。
4. **`AI_SIMULATION_V1_ENABLED=0`**：与 API 对齐，**跳过**或仅 log。
5. **与 batch-match 共存**：两定时器独立；注意 **Prisma 连接池**（单 worker 进程 MVP 通常足够）。

---

## 6. Stuck recovery MVP

1. **定时**（如每 1～5 min）：扫描 **`jobStatus === 'running'`** 且 **`updatedAt < now() - STUCK_MS`**。
2. **`updateMany`**：**`running` → `queued`**（**不加 migration 的前提**：实现前 **确认** `executeRunJobBody` 执行期间 **是否频繁更新 `AiSimulationV1Job` 行**；若 **仅更新 item**，则 **`job.updatedAt` ≈ claim 时刻**，可用于 MVP）。
3. **若不可靠**：**停止**用 `updatedAt`；**再** migration 增加 **`runStartedAt DateTime?`**（claim 写入；recovery 用该字段）。
4. **阈值**：大于 **单 job 最坏 LLM 时长**（如 8×单 item 上限 + 余量）。
5. **item 级 `running`**：与现有 `runOneItemWithRetries` / 重入语义对齐，**列入实现 todo**（避免双写或半条 item 卡死）。

## 7. 单测清单

| 用例 | 目的 |
|------|------|
| **`requestRunJobAsync` 不调 LLM** | mock chat client / runner，断言 **0 次** completions |
| **API 不把 job 置 `running`**（claim 不在 API） | mock DB / spy `updateMany` |
| **并发双 claim** | 同一 `jobId` 两次 claim，**仅一次** `count === 1` |
| **`already_running` / `already_completed`** | 与约定一致 |
| **（可选）stuck recovery** | 测试 DB 插 `running` + 旧 `updatedAt`，期望 **`queued`** |
| **Orchestrator** | `post-pool-deep-screen-orchestrator.spec.ts`：spy **无** API 内 `executeRunJobBody` |

Worker 若无 Jest：**runner 包纯函数 + api 测试** 覆盖 claim 逻辑即可。

## 8. 手动验收步骤

1. 准备 **`queued`** job（orchestration MVP 或手工 DB）。
2. **`POST /admin/.../run`**：**快速返回**；DB **不因 API 进入 `running`**（仍为 **`queued`**，直至 worker claim）。
3. **启动 worker**：日志 **claim → running → items → completed**。
4. **只重启 API**（worker 不关）：job **仍能跑完**。
5. **（可选）双 worker 进程**：确认 **无双跑**。
6. **模拟 stuck**：DB 将 job 置 **`running`** + 旧 **`updatedAt`**，触发 recovery → **`queued`**，再被消费（**勿**在 **`completed`** 上误恢复）。
7. **`GET job`** 轮询与 **M3.3 MVP 文档 §10** 对齐；抽样确认 **MatchResult / finalScore** 无意外变更。

## 9. 明确哪些不做

- **不引入** Redis / BullMQ / SQS。
- **不做 M4**；**不让 RRM-Sim 参与主排序融合**。
- **不改** `finalScore`、**worker `batch-match.processor` 主排序**、**`MatchResult.finalScore`**、**RRM 公式**。
- **不恢复** `shortlistScenariosV0` 产品路径。
- **不写**假 transcript / **不**强行把 failed item 标成功。
- **默认不做 migration**；MVP **不做** heartbeat / `lockOwner` / 多队列优先级。
- **不**为验收 **重跑 LLM** 制造假数据。

---

## 10. 一句话汇总

**抽 shared runner → API `/run` 只保证 `queued` 并快速返回 → worker 定时 poll、条件 `queued→running` claim、`await` 执行原 `executeRunJobBody` 语义 → 定时 stuck 将异常 `running` 退回 `queued`（先信任 `job.updatedAt`，不可靠再加 `runStartedAt`）→ 单测锁 claim 与 API 不调 LLM → 手动验 API 重启与双 worker。**
