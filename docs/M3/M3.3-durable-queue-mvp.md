# M3.3 Durable Queue MVP

## 1. 一句话结论

M3.3 推荐采用 **DB-backed queue**：由 **`apps/worker`** 消费 **ai-simulation-v1** 的 **`queued`** job；**API** 只负责 **入队 / 快速返回**，**不在 API 进程内**执行长链路 LLM。**不引入 Redis / BullMQ**。**不改变** RRM 公式、**finalScore**、worker 主排序或 **`MatchResult.finalScore`**。

## 3. 当前仓库现状（与实现对照）

- **`apps/worker`**：在保留 **`node-cron`** batch-match / daily-match 的前提下，**注册** **`registerAiSimulationV1QueueWorker()`**（poll + recovery 双 interval，受 env 门控）。
- **`batch-match.processor.ts`**：仍与 **AI Simulation v1 无关**。
- **`docker-compose.yml`**：仍 **无 redis**；**未**为 AI 队列新增服务。
- **依赖**：仍 **无** bullmq / redis / ioredis **队列库**。
- **`AiSimulationV1Job` / `AiSimulationV1Item`**：字段与状态枚举 **未改 schema**；与 **§5 MVP 目标**一致。
- **API `requestRunJobAsync`**：**只入队**，返回 **`jobStatus: queued`** + **`enqueued_for_worker`**（`started` 恒 `false`）；**不**在 API 内 claim 或执行 runner。
- **执行体**：**`packages/ai-simulation-v1-runner`** 内 **`runAiSimulationV1JobExecution`**（原 `executeRunJobBody` 语义）；**worker** 与 **`runJob`**（测试/手动）共用。
- **Stuck recovery**：**已实现**（见 §2 M2）；**无** heartbeat / `lockOwner`。

### 3.1 本地 / Docker 运维（避免双 worker）

- 若 **`docker compose`（或同类栈）里 `peima-worker` 容器在跑**，它会与 **`pnpm -w run dev:worker`** 消费 **同一** `ai_simulation_v1_jobs` 队列 → 可能出现 **`POST /run` 返回 `already_running`**、或 **重复 claim / 并行跑同一 job**。  
- **本地 E2E / 严格验证「仅 API 入队」** 时：建议 **`docker stop peima-worker`**（**不** `docker rm`），测完再 **`docker start peima-worker`** 恢复。  
- **根目录 `pnpm -w run dev:worker`**：须调用 **`pnpm --filter @peima/worker run dev`**（**不要**写成裸 `… worker dev`，否则 pnpm 会把 `dev` 当成顶层子命令而失败）；并由 **`dotenv -e .env --override`** 加载根 **`.env`**（含 **`DATABASE_URL`**）。  
- **无 LLM 的验收脚本**（可选，**不**提交亦可删）：`tools/m33-e2e-queue-polish.cjs`（`POST /run` + Prisma 立刻读 DB + 还原行）、`tools/m33-e2e-stuck-polish.cjs`（构造 stale `running` + 调 `recoverStuckAiSimulationV1JobsOnce` + 还原）；均在仓库根 **`cd apps/api && node ../../tools/…`** 下执行。

## 4. 为什么需要 M3.3

M3.2 已解决 **用户同步等待**（管理员/编排路径可快速返回），但仍 **不能**解决：

- **API 重启 / 崩溃**导致进程内后台任务 **丢失**，DB 上可能长期 **`running`** 且无进展。
- **`running` job 卡住**（僵尸态），无自动恢复。
- **多实例部署**下，任务应由 **谁消费、如何抢占** 需在 **持久层 + 单写者语义** 上明确（仅依赖「偶发 API 单实例」不可靠）。
- **stuck job** 没有 **恢复机制**。
- **job 级 durable retry / 重新可见** 不清晰。
- **无 heartbeat / recovery**，运维与可观测性不足。

以上属于 **执行与部署可靠性**；**不改变** RRM-Sim 的数学语义或主站匹配分数字段。

## 5. M3.3 MVP 目标

只做：

- **durable enqueue**（队列状态以 DB 为准，请求结束后仍可被消费）。
- **worker / background consumer**（独立进程拉取并执行，与 M3.2 的 API 内 `void` 分离）。
- **`queued` → `running` claim**（原子条件更新，保证单 job 单执行者）。
- **`running` stuck recovery**（超时将异常 `running` 恢复为可再次消费的 `queued` 或等价策略）。
- **单 job 防重复执行**（依赖 DB 条件 `updateMany` / 条件 `update`，`count === 1` 才执行体）。
- **item 级失败不影响其它 item**（保持现有 per-item 写回语义）。
- **复用**现有 RRM / LLM / sidecar 写回语义（**搬迁调用栈**，不重写公式）。
- **不改变**最终业务上的 **主排序 / MatchResult / finalScore** 语义（本队列仅承载 AI 模拟侧车 job）。

## 6. 方案选择

### 方案 A：DB-backed queue

**优点**

- 复用现有 **`jobStatus` / item `status`**。
- **不引入 Redis**。
- **改动面相对小**，与已有 **独立 `worker` 进程** 匹配。
- 对当前 **每 job 少量 candidate（如 top 2–3～8）** 的 **低吞吐** 足够。

**缺点**

- **轮询**带来延迟与少量 DB 读。
- **吞吐一般**。
- **stuck recovery** 需自研规则与阈值。
- **多实例 worker** 下依赖 **DB 条件 update** 做分布式抢占。

### 方案 B：Redis / BullMQ

**优点**

- **retry / backoff / lock / visibility timeout** 等模式成熟。
- 更适合 **高吞吐生产队列**。

**缺点**

- **当前仓库无 Redis**；需 **新增依赖** 与 **docker-compose**（或外部托管）。
- **运维与故障面**更大。
- 对 **本阶段「最小耐久队列」** 目标 **过重**。

**结论**：推荐 **方案 A：DB-backed queue**。

## 7. 最小实现设计（已实现）

- **`POST /admin/ai-simulation/v1/jobs/:jobId/run`**：**只入队**，**不**在 API 内 **await** LLM；**不**执行与 **`executeRunJobBody`** 等价的长任务（具体落点：`AiSimulationV1Service` + `AdminController`）。
- 若 job **`queued`**：确保可被 worker 消费，响应体现 **`queued`**（或 `started: false` + 理由，与现有 JSON 形状对齐时再定）。
- 若 job **`running`**：返回 **already_running**（或等价 reason），**不**再起第二个 runner。
- 若 job **`completed`**：返回 **already_completed**，**不**重复执行全 job（除非产品另定「重跑」流程，**不在本 MVP 默认路径**）。
- **worker** 按间隔 **poll** **`jobStatus === queued`** 的 job（可 `ORDER BY`、`take` 限制并发）。
- **worker** 使用 **`updateMany`**（或等价）条件 **`jobStatus === 'queued'` → `'running'`** 抢占；**仅当 `count === 1`** 时进入 **`executeRunJobBody` 等价逻辑**。
- **执行体**：与现网相同的 item 循环、**item 级 `running` / `succeeded` / `failed`**、**job `finally` → `completed` + 侧车重算**。
- **失败路径**：不通过本功能 **修改 finalScore**；侧车与 item 状态与现有一致。

## 8. Stuck recovery 设计（已实现）

**MVP 可先**用 **`AiSimulationV1Job.updatedAt`** 辅助判断：

- **claim** 为 **`queued` → `running`** 时会 **更新 job 行**，通常 **`updatedAt` 会刷新**。
- 若在 **`running`** 期间 **很少或不更新 job 行**（仅更新 item），则 **`updatedAt` 可近似「进入 running 的时间」**，用于 **超时 → 恢复 `queued`**。
- **阈值**建议 **env**，例如 **`AI_SIMULATION_V1_STUCK_TIMEOUT_MS`**（或秒级变量名，实施时统一即可）。

**若** **`running` 期间 job 行会被频繁 `update`**（例如未来加进度、心跳写 job），则 **`updatedAt` 不可靠**，建议 **migration** 增加 **`runStartedAt DateTime?`**：claim 时写入，recovery 用 **`now - runStartedAt`**。

**Migration 判断**

- **首选**：**不加 migration**，在代码审查中 **确认 running 阶段对 job 的写频率**。
- **若 `updatedAt` 不可靠**：新增 **`runStartedAt`**（nullable），仅用于 **recovery / 观测**，不改变 RRM 语义。

**不要**在本 MVP 一开始就加 Redis。

## 12. 最终架构总结（已实现）

1. **Admin `POST .../jobs/:jobId/run`**（`requestRunJobAsync`）：**快速返回** **`jobStatus: queued`**、**`reason: enqueued_for_worker`**、**`started: false`**；**不在 API 内** claim 或执行 LLM。  
2. **Worker poll**：定时 **`findFirst(queued)`** → **`updateMany(queued→running)`**，**`count === 1`** 才执行。  
3. **Worker execute**：**`await runAiSimulationV1JobExecution`**（item 循环、LLM、**`finally`** 侧车重算、**`jobStatus: completed`**）。  
4. **Recovery**：定时 **`recoverStuckAiSimulationV1JobsOnce`** — **`running` + `updatedAt` 过旧** → **`queued`**；仅 **`running` item** → **`queued`**；**`succeeded` / `failed` / `queued` item** 不变。  
5. **主站匹配**：**`finalScore` / `MatchResult.finalScore` / worker batch-match 主排序** — **未改**。

## 13. 暂不进入 M4（与 M3 closure 对齐）

M3.3 解决的是 **任务耐久与运维可恢复性**，**不代表** RRM-Sim 已可参与 **主排序 / 融合**。

**当前仍不进入 M4**，理由与 [M3 RRM-Sim real chain closure](./M3-rrm-sim-real-chain-closure.md) 一致，摘要如下：

- **M3.1-real** 深度验证仍以 **单一真实 job** 为主，样本量不足支撑排序融合决策。  
- 历史上 **`scoreDistributionFlag`** 曾出现 **`too_narrow`** 等诊断信号，**不构成**「RRM 已给出强区分排序信号」。  
- **RRM-Sim** 定位仍为 **read-only sidecar / diagnostic layer**；**`finalScore` 与 worker 主排序保持原样**。  

可选后续：**M3.3-hardening**（多实例更严 **lease**、**`runStartedAt`**、heartbeat、观测面板）— **非** M4。
