# M1.3 Evaluator Calibration Planning

## 一句话结论

**M1.3 只做 evaluator calibration 规划与设计文档化；当前阶段不改生产 evaluator、不改 RRM 公式、不进入正式 M4。**

---

## 1. 背景

- **M4.1 shadow report** 链路已跑通，可对 completed 的 ai-simulation-v1 job 做多候选只读诊断与 M4.0 read-only ranking proposal。
- 当前观测：**usableJobCount = 4**，**fallbackCount = 0**（usable 子集内 RRM 非 fallback 行充足）。
- 但 **4 个 usable job 全部** `scoreDistributionFlag = too_narrow`，且 `recommendation` 全部为 **`insufficient_separation`**。
- **M4.1-too-narrow-diagnostic** 结论：主因 **B — evaluator / score mapping 压缩为主**；样本同质化 **A** 为辅；**spread &lt; 8** 诊断硬阈值 **D** 可作为次要讨论。
- 问题重心已从「能否生成 RRM-ready v2 完整模拟」转为：**在同一 job 多候选上，`simulatedRhythmScore` 的跨候选分布是否被评估管线压得过窄**，从而 shadow 层无法给出「足够分离」的只读信号。

---

## 2. 当前 evaluator 结构（只读梳理）

以下描述对应生产代码路径（本轮**不修改**这些文件）：`evaluateRrmSimFromSimulationV2`（`apps/api/src/modules/ai-simulation-v1/rrm-sim.evaluator.ts`）及其依赖 `rrm-sim-extractor.ts`、`rrm-sim-formula.ts`、`rrm-sim.constants.ts`。

### 2.1 输入

- **`transcriptLite`**：schema v2、七场景完整、RRM-ready 的 LLM 输出载荷。
- **`staticContext`**（可选）：成功项在 `AiSimulationV1Service.enrichResultsWithRrmSim` 中由 viewer/candidate 问卷与 `buildMatchReviewStaticSummary` / `buildAiSimulationStaticContext` 构造；失败项路径使用 `null`。

### 2.2 全局标量（对七场景共享）

| 字段 | 作用 |
|------|------|
| **C_pred** | `extractCPred`：无静态时偏 transcript/场景均分；有静态时融合 `reviewStaticScore`、`majorFits`/`majorRisks`、`axes` 和谐度与场景均分等，`[0,1]`。 |
| **F_sim** | `extractFGlobal`：跨场景一致性、方差、confidence、`crossScenarioConsistency` 等合成后 **`applyFsimCap`**，上限 **`RRM_SIM_F_SIM_CAP`（0.85）**，`[0,1]`。 |
| **D_pre** | `extractDPre`：模拟 `mainRisks` + 有静态时 `majorRisks`、relationship 提示等，`[0,1]`。 |
| **R_pre** | `extractRPre`：强迫/威胁类等尊重风险命中（含静态 `majorRisks`），`[0,1]`。 |

### 2.3 逐场景量与 RFI

- 对每个场景行：**A** = `scenarioApproachIntensity`（与场景键绑定）；**S / E / Q** 由 `extractSPerScenario` / `extractEPerScenario` / `extractQPerScenario` 从 `scenarioScore` 与信号文本等得到；**R_scenario** 由 transcript 等提取。
- **`computeRfiScenario`**：产品约定的分段公式（`A` 与 `C_pred` 比较两支），使用同一组全局 `C_pred, F_sim, D_pre, R_pre`。
- **`aggregateRfiSim`**：按 `RRM_SIM_SCENARIO_WEIGHTS` 对七场景 RFI **加权求和**，再 **clamp 到 [-1, 1]**。

### 2.4 RFI → simulatedRhythmScore

- **`rfiToSimulatedRhythmScore`**：`RFI_sim` 线性映射到 **0–100** 并 **round**，再 clamp 到 `[0, 100]`。

### 2.5 输出层闸门（尊重 / 静态分歧）

- **Respect gate**：`R_pre >= RRM_SIM_RESPECT_R_PRE_GATE`（0.7）时，`suggestedAction = stop_or_step_back`，`progressionWindow = closed`，且 **`simulatedRhythmScore = min(score, 25)`**。
- **D_pre gate**：`D_pre >= RRM_SIM_STATIC_D_PRE_GATE`（0.8）时，`suggestedAction = slow_down`，`progressionWindow` 依 `D_pre` 是否 ≥ 0.9 在 `closed` / `weak_open`（**不**在此分支再次改写 rhythm 数值，与 respect 分支不同）。
- **否则**：`progressionWindow` 仅由 `simulatedRhythmScore` 阈值分段（如 35 / 60 / 85）；`suggestedAction` 由 rhythm 分段后经 **meanQ** 软封顶（如限制 `soft_progress`）。

### 2.6 多候选诊断：`scoreDistributionFlag` 与 spread

- **`buildRrmSimMultiCandidateDiagnostic`**：在非 fallback 的 `simulatedRhythmScore` 上计算 `spread = max - min`；当 **`rrmAvailableCount >= 3` 且 `spread < 8`** 时标为 **`too_narrow`**。
- **`buildRrmRankingProposal`**：若 `scoreDistributionFlag === too_narrow`，则 **`recommendation = insufficient_separation`**（只读提案，不参与真实排序）。

## 3. 当前压缩点分析

| 压缩点 | 说明 |
|--------|------|
| **全局共享项** | `C_pred`、`F_sim`、`D_pre`、`R_pre` 在一次 completion 内对 **7 个场景相同**，跨候选差异主要来自各场景 S/E/Q 与 A、C 的相对关系；候选间模拟质量接近时，聚合后 rhythm 易挤在一起。 |
| **F_sim cap = 0.85** | `F*Q` 支路整体被上限压住，削弱「靠 F 拉高差异」的空间。 |
| **staticContext** | 同 viewer 与多候选配对时，`C_pred` / `D_pre` 易因相似静态画像与风险摘要而 **接近**，并可能 **同时触发 D_pre 输出分支**（行为层同质化）。 |
| **RFI_sim 窄带** | `D_pre` 作为减项进入每场景 RFI；聚合后再 **clamp [-1,1]**，易出现 **略负～小幅正** 的窄区间。 |
| **linear + round** | `rfiToSimulatedRhythmScore` 线性映射且四舍五入到整数，**小 RFI 差**对应 **小 rhythm 步长**，加剧并列与低 spread。 |
| **spread &lt; 8** | 诊断层 **硬阈值**；与「真实匹配排序是否还有效」解耦，但会导致 **usable 子集长期全 `too_narrow`** 的报表形态。 |
| **辅因：样本同质化** | usable job 数量有限、viewer/shortlist 重叠时，即使诊断阈值调整，也需用 **更多 viewer / 更分散 shortlist** 区分「映射压缩」与「数据重叠」。 |

## 4. Calibration 方案（仅规划）

### 方案 A：调整诊断阈值

| 维度 | 内容 |
|------|------|
| **作用范围** | `buildRrmSimMultiCandidateDiagnostic` / `buildRrmRankingProposal` 或等价 shadow 脚本中的 **spread 阈值与分档**（例如 `too_narrow` 从 `spread < 8` 改为 `< 5` 或按 item 数分档）。 |
| **优点** | 不动 RRM 数值管线；**风险最低**；报表语义可快速迭代。 |
| **风险** | **不增加**真实分数分离度，可能「绿灯」弱信号；M4.0 解读需同步更新文案与门槛。 |
| **是否改生产 evaluator** | **否**（仅诊断层）。 |
| **推荐优先级** | **高**（作为 M1.3-M0 对照组之一，或与 M0 结论联动后再定是否落代码）。 |

### 方案 B：调整 RFI → rhythmScore 映射

| 维度 | 内容 |
|------|------|
| **作用范围** | **`rfiToSimulatedRhythmScore` 及下游阈值一致性**（`progressionWindow` / `suggestedAction` 分段依赖 0–100 rhythm）。 |
| **优点** | **不改 `computeRfiScenario` 公式**即可在中间区放大差异或减少 round 并列（若未来获准实现）。 |
| **风险** | 中：需回归 **尊重/D_pre 分支** 与产品文案语义，避免「分数含义漂移」。 |
| **是否改生产 evaluator** | 若落地则 **是**（改映射层，仍属 evaluator 范畴）；**当前阶段不做**。 |
| **推荐优先级** | **中**（在 M1.3-M0 上验证后再决策）。 |

### 方案 C：调整 evaluator 聚合权重 / cap / 静态融合

| 维度 | 内容 |
|------|------|
| **作用范围** | `RRM_SIM_SCENARIO_WEIGHTS`、`RRM_SIM_F_SIM_CAP`、`extractFGlobal` / `extractCPred` / `extractDPre` 中静态与 transcript 的权重等。 |
| **优点** | 可直接针对 **全局共享量** 导致的压缩做结构性缓解。 |
| **风险** | **最高**：触及安全闸门（R_pre、D_pre 分支）与多候选公平性，需 **远多于 4 个 job** 的样本与人工 bad case 审查。 |
| **是否改生产 evaluator** | **是**（若落地）。**当前阶段不做**。 |
| **推荐优先级** | **低–中**（仅在有 M0 + 扩大样本证据链后进入独立里程碑）。 |

### 方案 D：继续数据扩展

| 维度 | 内容 |
|------|------|
| **作用范围** | 第二个 viewer、更多 completed job、更分散 shortlist；执行见 `docs/M4/M4.1-data-expansion-execution-plan.md`。 |
| **优点** | 不改公式即可检验 **辅因 A**；若新 viewer 上出现 `ok`，说明同质化占比大。 |
| **风险** | 时间与队列成本；若扩展后仍 **全局 too_narrow**，更支持 **B/C** 方向。 |
| **是否改生产 evaluator** | **否**。 |
| **推荐优先级** | **高**（与 M1.3-M0 **并行**推荐）。 |

---

## 5. 推荐路线

1. **不立刻改生产 evaluator**（不改 `rrm-sim.evaluator.ts` / `rrm-sim-formula.ts` / `rrm-sim.constants.ts`）。
2. **先实现 M1.3-M0 offline calibration simulator**（独立工具或测试夹具；**不写 DB**、**不重跑 LLM**；**不提交含真实用户数据的报表**）。
3. 使用 **当前 4 个 usable job + 后续新增 job**，对多份 **calibrationConfigs** 做 **what-if** 对比（基线须与 shadow 对齐：**成功项使用与线上一致的 staticContext 路径**）。
4. 仅在多 job 上 **分布与解释均合理** 后，再分里程碑决策：**是否改诊断阈值（A）** 或 **是否改生产映射/权重（B/C）**。
5. **绝不根据仅 4 个样本直接修改生产公式或上线 calibrated 分数。**

## 6. M1.3-M0 Offline Simulator 设计

### 6.1 目标

- 输入已有 **rrm-ready v2** job 的持久化数据，**不重跑 LLM**。
- **不修改**仓库内生产 evaluator 源文件；M0 内允许 **fork 的纯函数**（复制公式逻辑 + 可调参数）做离线对照。
- 输出 **JSON 报表**（shadow-only / 研发本地），默认不含可识别 PII；**不提交真实用户数据报表**。

### 6.2 输入

- **Job 标识**：如 `simulationJobId` 列表或导出文件路径。
- **每条 item**：`transcriptLite`（完整 v2）；以及下列之一：
  - **现算**：与 `enrichResultsWithRrmSim` 一致的 **staticContext**（问卷 + `buildMatchReviewStaticSummary` + `buildAiSimulationStaticContext`），或
  - **基线快照**：已持久化的 **`rrmSimResult`**（用作 **current** 对照，避免重复 IO）。

### 6.3 输出（JSON 建议结构）

- **`calibrationConfigs`**：本 run 启用的配置元数据列表。
- **`summary.perConfig`**（每个 config 一份）：
  - **`scoreFlagDistribution`**：`ok` / `too_narrow` / `too_many_fallbacks` 计数。
  - **`recommendationDistribution`**：`insufficient_separation` / `supports_existing_rank` / `review_manually` 等计数。
  - **`avgSpread`**、**`medianSpread`**：在约定 usable 子集（如 `rrmAvailableCount >= 3` 且 `fallbackCount == 0`）上统计。
  - **`changedTopRate`**：相对 **current** 的 `rrmTopCandidateUserId`（或等价 top）变化比例。
- **`perJobDiff`**：每 job 每 config 的 `spread`、`scoreDistributionFlag`、`recommendation`、可选 `topCandidateChanged` 等。

### 6.4 候选 calibrationConfigs（规划名）

| id | 含义（仅 M0 内 what-if） |
|----|-------------------------|
| **current** | 与生产一致的 evaluator 输出（或等价快照）。 |
| **threshold_spread_5** | 仅改诊断：**too_narrow** 判定改为例如 `spread < 5`（或分档），不改 rhythm。 |
| **rhythm_mapping_expanded** | 在 M0 fork 中替换 **RFI → rhythm** 映射曲线（不改 `computeRfiScenario` 源码）。 |
| **lower_d_pre_penalty** | 在 M0 fork 中对传入 **`D_pre` 乘系数**或缩放后再代入 RFI 副本。 |
| **lower_f_cap_effect** | 在 M0 fork 中提高 **`F` 上限常数**（例如高于 0.85 的试验值）再算全局 F 与 RFI 副本。 |

**实现注意**：`buildRrmSimMultiCandidateDiagnostic` 与 `buildRrmRankingProposal` 的阈值逻辑在 M0 中应 **参数化复制**或 **可注入**，避免在未达成共识前修改生产模块。

## 8. 下一步：M1.3-M0 implementation prompt（复制用）

在 **不修改** `apps/api/src/modules/ai-simulation-v1/rrm-sim.evaluator.ts`、`rrm-sim-formula.ts`、`rrm-sim.constants.ts`、worker、MatchResult、finalScore **源文件**的前提下，新增 **M1.3-M0 offline calibration simulator**：

1. **只读**从 Prisma（或团队认可的导出 JSON）加载指定 `simulationJobId` 列表的 **completed** job 及其 items 的 **`transcriptLite`**；可选读取已存 **`rrmSimResult`** 作为 **current** 基线。
2. 若需现算基线：对每个 **succeeded** item 复现 `AiSimulationV1Service.enrichResultsWithRrmSim` 的 **staticContext** 构建（`QuestionnaireService.getProfileForUser` + `buildMatchReviewStaticSummary` + `buildAiSimulationStaticContext`），再调用 **`evaluateRrmSimFromSimulationV2(transcriptLite, staticCtx)`**（允许 **import** 生产函数作为只读黑盒，**禁止**改其源码）。
3. 在同一进程内为下列 config 生成并列结果（**M0 专用 fork 纯函数**）：**current**；**threshold_spread_5**（仅改 spread 阈值常数后重算 diagnostic/proposal）；**rhythm_mapping_expanded**（替换 RFI→rhythm 映射副本）；**lower_d_pre_penalty**（对 D_pre 缩放后代入 `computeRfiScenario` / `aggregateRfiSim` **逻辑副本**）；**lower_f_cap_effect**（提高 F cap 常数副本）。每个 job 跑 **`buildRrmSimMultiCandidateDiagnostic` + `buildRrmRankingProposal` 的逻辑副本且阈值可注入**，或从 diagnostic 结构重组 proposal。
4. 汇总 **`scoreFlagDistribution`、`recommendationDistribution`、`avgSpread`、`medianSpread`、`changedTopRate`、`perJobDiff`**，输出 **单一 JSON**（stdout 或本地文件）；**默认不写 DB**；**不包含**可识别 PII。
5. 为固定 **fixture**（仓库内匿名化测试 payload）添加最小单元测试，断言各 config 下 **spread / flag** 的单调或预期关系；**不**提交真实 job 导出。

## 9. M1.3-M0 implementation note（已落地）

### 9.1 实现位置与依赖

- 脚本路径：**`tools/m13-m0-calibration-simulator.mjs`** → 通过 **`npx tsx`** 执行 **`tools/m13-m0-calibration-simulator.impl.ts`**（离线实验工具，非 DB migration）。
- What-if 重算（M1.3-M2）：**`apps/api/src/modules/ai-simulation-v1/rrm-sim-calibration-whatif.ts`**（仅 tools / Jest 引用；不挂 HTTP）。
- 纯函数库：**`tools/lib/m13-calibration-aggregate.mjs`**（诊断分类、proposal 推导、rhythm proxy、汇总；供模拟器与测试共用）。
- **Prisma**：通过 `createRequire(packages/database/package.json)` 加载 **`@prisma/client`**（根目录不直接依赖 Prisma 时亦可运行）。
- **基线**：**`inputMode: "api_readonly_baseline"`** — 与 `packages/database/scripts/m4-shadow-evaluation-report.mjs` 相同，对每条候选 job 调用 **`GET /admin/ai-simulation/v1/jobs/:id`**，使用响应中的 **`rrmSimMultiCandidateDiagnostic` / `rrmRankingProposal` / `results[].rrmSimResult`** 作为 **current** 生产等价基线（含静态上下文 enrich 后的分数）。**未**在 M0 内复刻 `QuestionnaireService` 重建 staticContext，以避免扩大改动面。
- **环境**：需要 **`DATABASE_URL`**、**`JWT_SECRET`**、**`PEIMA_ADMIN_USER_IDS`**（至少一个 admin sub）、可连通的 **`VITE_API_BASE_URL` / `API_PUBLIC_BASE_URL`**（默认 `http://localhost:3000`）。API 进程需已启动，否则 admin GET 失败，job 会进入 **`skipped`**。

### 9.2 已实现 configs

| id | 行为 |
|----|------|
| **current** | 直接使用 admin 响应中的 diagnostic + proposal。 |
| **threshold_spread_5** | 仅重算诊断：`too_narrow` 当且仅当 `rrmAvailableCount >= 3` 且 **`spread < 5`**；`review_manually` 分支仍要求 **`spread >= 8`**（与生产 `buildRrmRankingProposal` 一致）。 |
| **threshold_spread_3** | 同上，`too_narrow` 阈值改为 **`spread < 3`**（用于阈值敏感性对照；在本仓库当前 4 个 usable job 上与 `threshold_spread_5` 计数可能相同）。 |
| **rhythm_mapping_expanded** | **Proxy（非正式 RFI 映射）**：对每个非 fallback 的 `simulatedRhythmScore` 做 **`score' = round(clamp(50 + (score-50)*1.5, 0, 100))`**，再对整份 `results` 走 M0 内复制的 **`buildMultiCandidateDiagnostic`**（`too_narrow` 仍用生产 **&lt; 8**）。报表字段 **`itemScoresBeforeAfter`** 标明 before/after。 |

### 9.4 如何运行

在 monorepo 根目录（**默认 stdout**，不落盘则不含「提交报表」风险）：

```bash
node --env-file=.env tools/m13-m0-calibration-simulator.mjs --limit 20 --pretty
node --env-file=.env tools/m13-m0-calibration-simulator.mjs --limit 20 --pretty --includeDebug
```

可选参数：

- **`--jobId <id>`**：可重复或逗号分隔；指定时只拉这些 job（仍要求 completed + admin 可用 + usable 子集规则）。
- **`--out <path>`**：写入 JSON 文件（**勿将含真实 id 的文件提交仓库**）。
- **`--mode currentOnly`**：只输出 **current** config 的汇总（不做 what-if）。
- **`--includeDebug`**：启用 M1.3-M2 what-if configs、**`includeDebugProbe`**、**`debugSummary`**（默认关闭；不改变无 flag 时的 M0 行为语义）。

### 9.5 如何解读

- **`summary.perConfig`**：对比 **`tooNarrowCount` / `insufficientSeparationCount` / `avgSpread`** 是否在 **threshold** 或 **rhythm proxy** 下改善。
- **`threshold_*`**：只松绑**诊断标签**，**不改变**生产 `simulatedRhythmScore`。
- **`rhythm_mapping_expanded`**：可抬高 **`avgSpread`**，但若原始分数过于集中，**`too_narrow`（&lt;8）** 仍可能全部为 4 — 说明 **proxy 不足以单独打开 M4.0「足够分离」**。
- **`changedTopRate`**：相对 **current** 的 `rrmTopCandidateUserId` 是否变化；阈值-only 配置下通常为 0。

### 9.6 与正式 M4 的关系

- M0 **不参与**真实排序、**不写入** MatchResult、**不进入**正式 M4；仅用于研发侧 **what-if** 与文档化证据链。

### 9.9 M1.3-M2 — Debug 接入模拟器（`--includeDebug`，非生产）

**目标**：在**不**改 `evaluateRrmSimFromSimulationV2`、不改 `rrm-sim-formula.ts` / `rrm-sim.constants.ts`、不写 DB、不调 LLM、不把 debug 暴露给 admin/viewer API 的前提下，让离线校准脚本可对 **D_pre / F_sim / C_pred / 场景权重** 做 **tools-only** 的 what-if 试算。

**入口**：`tools/m13-m0-calibration-simulator.mjs` 通过 **`npx tsx`** 调用 `tools/m13-m0-calibration-simulator.impl.ts`（单一实现路径）。根目录已加 **`tsx`** 为 devDependency；亦可依赖 `npx --yes tsx` 临时拉取。

**`--includeDebug`**（默认关闭）：

- **What-if 标量代理**不依赖 debug 成功：基于 admin GET 返回的 **`rrmSimResult.scenarioScores` + `scores`**，在 `rrm-sim-calibration-whatif.ts` 内用与生产相同的 **`computeRfiScenario` / `aggregateRfiSim` / `rfiToSimulatedRhythmScore`** 与 **respect cap** 重算 rhythm（**非**改生产 evaluator）。

**启用的 configs**（仅当 `--includeDebug` 且非 `currentOnly`）：

| id | 含义（offline proxy） |
|----|------------------------|
| **lower_d_pre_penalty** | `D_pre' = clamp01(D_pre × 0.75)` 代入每场景 RFI 后重聚合。 |
| **lower_f_cap_effect** | `F' = min(0.95, clamp01(F_sim + 0.07))` 代入每场景 RFI。 |
| **c_pred_weighting_variant** | `C_pred' = clamp01(C_pred + 0.05)`。 |

| **d_pre_static_cap_proxy**（M1.3-M5） | `D_tx = extractDPre(transcriptLite, null)`；`D' = clamp01(D_tx + min(D_admin−D_tx, 0.25))`；缺 `D_tx` 的 job 对该 config **`notAvailable`**。 |
| **d_pre_major_risk_dedup_proxy**（M1.3-M5） | `D' = clamp01(D_tx + min(staticLift, 0.18))`；**proxyBasis** = 静态 lift 封顶，**非**精确 majorRisks dedup。 |

**报表**：`calibrationConfigs` 中 **M2 四项 + M5 三 active + M5 二 deferred** 在 **无** `--includeDebug` 时，M2/M5 active 项为 `not_available_in_m0`；有 flag 时 M2/M5 可跑项为 **`active`**。每个 **`perJobDiff[].perConfig[configId]`** 含 **`spread`**、**`itemScoresBeforeAfter`**、**`debugSummary`**（`avgDPre` / `avgFSim` / `avgCPred` / `avgRPre`；what-if 行对 D/F/C 使用**代理输入**的平均）。**`summary.perConfig`** 延续 M0 的 **`avgSpread` / `medianSpread` / `scoreFlagDistribution` / `recommendationDistribution` / `changedTopRate` / `okCount` / `tooNarrowCount` / `insufficientSeparationCount`**。

#### 9.10.3 哪个 config 改善最大

- **`lower_d_pre_penalty`**：**`avgSpread` 从 1.75 → 4.5**，且 **唯一**在 **`okCount`** 上取得 **1/4** job 的 **`scoreDistributionFlag === ok`**（其余 proxy 在本批未打开「ok」桶）。

#### 9.10.4 为什么不能直接把 `lower_d_pre_penalty`（或等价逻辑）上线

1. **仅为 offline proxy**：在工具内对 **已聚合的 admin `scores.D_pre`** 做 **`×0.75`** 后再代入 **存储的** `scenarioScores` 重算 RFI；**不是**生产 `extractDPre` 路径的等价替换，也未覆盖 enrich 时 **staticContext** 与问卷差异。  
2. **效果仍弱于产品决策门槛**：**仅 1/4** job 在诊断桶上变为 **`ok`**，其余仍 **`too_narrow`**；**不足以**支撑「跨候选已足够分离」的结论。  
3. **样本量过小**：**n = 4** 极易被单个 job 的 spread 形态主导；统计上**不应**据此改 **`evaluateRrmSimFromSimulationV2` / `rrm-sim-formula.ts` / `rrm-sim.constants.ts`**。  
4. **治理约束**：M1.3 阶段明确 **不让 RRM-Sim 参与真实排序**、**不写 MatchResult**、**不进入正式 M4**；**`lower_d_pre_penalty` 不得作为已批准生产变更上线**（与项目阶段门禁一致）。

#### 9.10.5 当前判断（结论条）

1. **`lower_d_pre_penalty`** 是当前 **最有效** 的 what-if **proxy**（相对 F / C / 场景权重变体）。  
2. 它**仍是 offline proxy**，不是已验证的生产配方。  
3. 本批 **仅 1/4** job 在 **`ok`** 桶上改善，**3/4** 仍 **`too_narrow`**。  
4. **`usableJobCount = 4`**，**不足以**做稳健外推。  
5. **不足以**据此修改 **production evaluator**。  
6. **不足以**进入 **正式 M4**（只读诊断与 shadow 证据链仍应保持「观测」定位）。  
7. **后续**应并行考虑：**数据扩充（更多 viewer / job）** 与 **D_pre 中间量只读审阅**（见下节）。

#### 9.10.6 下一步建议分支（候选）

**A. 继续 data expansion**

- 补 **第二个 viewer** 或多条 **分散 shortlist** 的 completed job，使 **`usableJobCount >= 5`**（越高越好）。  
- 用**同一命令**再跑 **`--includeDebug`**，观察 **`lower_d_pre_penalty`** 是否**仍为**最有效的 spread / `okCount` 改善项。  
- 风险：若 **`D_pre` 来源文本高度同质**，仅扩样本可能仍长期 **`too_narrow`**，**烧 token / 跑数成本**偏高。

**B. D_pre intermediate audit（只读）**

- 对每个 **usable job**（或扩大后的子集）**抽样**：admin 或 DB 只读拉取 **`D_pre`**、**`majorRisks` / `mainRisks`**、与 **risk 相关文本**（不涉及改公式、不写回）。  
- 判断 **`D_pre` 高**是 **合理风险对齐** 还是 **提取层过度惩罚 / 文本同质化** 导致的 **跨候选拉不开**。  
- **不改** `rrm-sim-formula.ts` / **constants**；目标仅为 **假设验证** 与是否值得开 **受控 M1.3 后续** 的输入。

**推荐优先级：先 B，再小规模 A。**

**原因简述**：若 **B** 发现 **`D_pre` 主要由同质风险叙述驱动**，则单纯 **A** 扩样本可能重复得到 **`too_narrow`**；先理解 **D_pre 信号来源** 更省成本，再决定扩样本规模与是否值得进入 **更重的 evaluator 讨论**（仍非本轮范围）。

#### 9.10.7 D_pre 工作假设（hypothesis note，非结论）

- **假设**：当前观测到的 **跨候选 rhythm 偏窄**，在 proxy 空间中 **`lower_d_pre_penalty` 缓解最明显**，提示 **「全局 `D_pre` 作为 RFI 减项」** 可能是 **主要可解释压缩杠杆之一**（与 **F cap**、**共享 C_pred**、**线性映射** 等并存）。  
- **非结论**：尚未证明生产 **`extractDPre`** 或 **静态融合** 「错误」；仅证明 **在固定 scenario 行上缩放 `D_pre` 输入** 能 **部分** 拉开 spread。  
- **与 M4 的边界**：即使假设成立，**上线 D 调整** 仍属 **产品 / 安全 / 校准** 决策，**不属于** M1.3-M2  closure 的交付范围。
