# M1.3-M1 Intermediate Signal Extraction Planning

## 一句话结论

**M1.3-M1 只做「中间量可观测 / 可重算」的方案设计**：在**不改 RRM 公式、不改现有 `evaluateRrmSimFromSimulationV2` 返回契约**的前提下，为离线 M0 模拟器提供 **what-if** 所需的全量或增量信号；**本轮不实现、不写库、不调 LLM、不进入正式 M4**。

---

## 1. 当前 evaluator 中间量现状（只读结论）

### 1.1 管线与函数位置

| 环节 | 位置 | 说明 |
|------|------|------|
| 入口 | `evaluateRrmSimFromSimulationV2`（`rrm-sim.evaluator.ts`） | `transcriptLite` + 可选 `staticContext` |
| 全局量 | `extractCPred` / `extractFGlobal` / `extractDPre` / `extractRPre`（`rrm-sim-extractor.ts`） | 对七场景 **共享** |
| 逐场景 | `extractSPerScenario` / `extractEPerScenario` / `extractQPerScenario` / `extractRScenario` | 每场景一行 |
| RFI | `computeRfiScenario`、`aggregateRfiSim`、`rfiToSimulatedRhythmScore`（`rrm-sim-formula.ts`） | 聚合后 clamp，`rhythm` 再经 **respect / D_pre / meanQ** 等输出层 |
| 常量 | `rrm-sim.constants.ts` | cap、gate、权重等 |

### 1.2 `RrmSimResult` 已暴露的字段（类型见 `rrm-sim.types.ts`）

- **`scores`**：`C_pred`、`F_sim`、`D_pre`、`R_pre`、`RFI_sim`、`simulatedRhythmScore`（其中 **`simulatedRhythmScore` 为输出层闸门后的最终对外节奏分**）。
- **`scenarioScores`**：长度与 `RRM_SCENARIO_KEYS_ORDERED` 一致时为 **7**；每行含 **`scenario`、`A_scenario`、`S_sim`、`E_sim`、`Q_sim`、`R_scenario`、`RFI_scenario`**（及 LLM 侧 `suggestedAction` 解析结果）。
- **`evidence`**：人类可读 snippet 数组（**非**原始数值中间量的权威来源）。
- **未在类型中单列的**：`respect` / `D_pre` 分支作用后的 **「闸门前的 rhythm」** 与 **「闸门后 rhythm」** 的显式双轨——当前实现中 **最终 rhythm 只体现在 `scores.simulatedRhythmScore`**；若 respect 分支触发，**`RFI_sim` 仍为聚合 clamp 后的值**，与最终 rhythm 可能不一致（需 debug 结构显式记录 **preGateRhythm** / **gateApplied**）。

### 1.3 持久化与 admin GET

- Prisma **`AiSimulationV1Item`** 当前 **不持久化** `rrmSimResult`（见 `RrmSimResult` 类型注释：read-time enrich）。
- **Admin GET**（`getJobById` → `enrichResultsWithRrmSim`）在响应 **`results[].rrmSimResult`** 中返回 **完整** `RrmSimResult`，因此 **已包含** `scores` 中的 **C_pred / F_sim / D_pre / R_pre / RFI_sim** 及 **`scenarioScores` 每行 RFI_scenario**。
- **Per-scenario**：有 **逐场景 `RFI_scenario`**；**无**单独字段列出「每场景权重乘子后的加权和」——权重来自 `RRM_SIM_SCENARIO_WEIGHTS`，可在 debug 或 M0 侧 **只读拼接**。

### 1.4 与 M0 缺口的关系

- M0 若仅依赖 admin JSON，**已能读取**全局标量与 **7 条** `scenarioScores`，足以做 **权重 what-if、D_pre/F 缩放后重算 RFI**（需 **import 现有 `computeRfiScenario` / `aggregateRfiSim` / `rfiToSimulatedRhythmScore`**，**不改公式源码**）。
- M0 当前未实现 **`lower_*`** 的原因主要是 **工程策略**（避免在纯 `.mjs` 中重复 import 路径 / 未接 tsx），**不是**「中间量在数学上不存在」。

## 2. M1.3-M1 目标（相对 M0）

| 目标 | 说明 |
|------|------|
| **可观测** | 离线报表中稳定输出 **与生产一致的** 全局量 + 逐场景量 +（可选）**闸门前后 rhythm** |
| **可重算** | 在 **同一 `transcriptLite` + `staticContext`** 下，对 **D_pre / F / C_pred 权重 / 场景权重** 做 **what-if**，重算 `RFI_sim` → `simulatedRhythmScore`（输出层规则可配置为「与生产完全一致」或「仅诊断分支」） |
| **非目标** | **不改**生产 `evaluateRrmSimFromSimulationV2` 的默认返回值；**不向用户**暴露 debug；**不写库** |

## 3. 方案 A / B / C 比较

| 维度 | **A：Fork 到 `tools/lib`** | **B：生产 evaluator 增加 `includeDebug`** | **C：独立 debug wrapper（同模块或邻文件）** |
|------|---------------------------|---------------------------------------------|-----------------------------------------------|
| **是否改生产 `evaluateRrmSimFromSimulationV2` 签名/默认返回** | 否 | 是（可选参数或分支） | 否（新符号） |
| **是否改 `rrm-sim.evaluator.ts` 文件** | 否（若 fork 全在 tools） | 是 | **可不改**（新文件 `rrm-sim.evaluator-debug.ts` 仅 import 现有 extract/formula） |
| **漂移风险** | **高**（控制流复制在 tools） | 低 | **低–中**（控制流在新函数中与生产对齐，公式仍单源） |
| **测试成本** | 需大量对齐测试防 drift | 中等（防默认路径回归） | **中**（wrapper vs production **最终 rhythm 一致** 的黄金对照） |
| **维护成本** | 高 | 中 | **中偏低**（公式与 extractor 仍一处） |
| **是否适合当前阶段** | 可短期凑合，**不推荐**作长期主路径 | 触碰「生产文件语义」，**与「本轮不改 evaluator」的保守策略冲突** | **适合**：与倾向 **C** 一致 |

### 3.1 对「方案 C」的独立判断

**结论：倾向方案 C 合理。**

- **理由**：M1.3-M1 的核心是 **复用** `extract*`、`computeRfiScenario`、`aggregateRfiSim`、`rfiToSimulatedRhythmScore` 与 **同一套闸门常量**，仅在 **新导出的 debug 管线**中暴露 **pre/post gate** 与 **逐场景权重展开**；**默认 API / 用户路径**继续只调用 **`evaluateRrmSimFromSimulationV2`**，契约不变。
- **注意**：若严格坚持 **「`rrm-sim.evaluator.ts` 永不增行」**，可把 wrapper 放在 **`rrm-sim.evaluator-debug.ts`**（或 `testing/` 下），由 **tools（tsx）或 api 测试**引用；**避免**在 `evaluateRrmSimFromSimulationV2` 上叠加 `includeDebug`（即 **不选 B**），以减少生产路径回归面。

若 **C** 也不新增任何 TS 文件、仅 tools fork，则退化为 **A**，漂移风险上升——**不推荐作为 M1.3-M1 终态**。

## 4. 推荐方案（落地形态）

1. **阶段 0（无新生产代码）**：M0 扩展 **从 admin `results[].rrmSimResult` 解析** 已有 `scores` + `scenarioScores`，写入报表 **`rrmDebugIntermediateLite`**（与下文结构子集等价），先支撑 **文档化 / 对照**。
2. **阶段 1（推荐 C）**：新增 **`evaluateRrmSimDebugFromSimulationV2(transcriptLite, staticContext)`**（独立文件），返回 **`RrmSimResult` + `rrmDebugIntermediate`**；实现上 **复制 evaluator 主循环的控制流** 或抽取 **内部 `runRrmCore(...)`**（实现阶段再定），保证与生产 **最终 `scores.simulatedRhythmScore`** 一致（黄金测试）。
3. **阶段 2**：M0 通过 **tsx** 或 **api 内 dev-only 脚本** 调用 debug wrapper，启用 **`lower_d_pre_penalty` / `lower_f_cap_effect` / 权重 variant**。

## 5. `rrmDebugIntermediate` 输出结构设计（建议）

```typescript
type RrmDebugIntermediate = {
  scores: {
    C_pred: number;
    F_sim: number;
    D_pre: number;
    R_pre: number;
    RFI_sim: number;
    /** 与 RrmSimResult.scores.simulatedRhythmScore 对齐：闸门后的最终节奏分 */
    simulatedRhythmScore: number;
  };
  scenarioDebug: Array<{
    scenarioKey: string; // RrmScenarioKeyV1
    A: number;
    S: number;
    E: number;
    Q: number;
    R_scenario: number;
    RFI_scenario: number;
    weight: number; // RRM_SIM_SCENARIO_WEIGHTS[scenarioKey]
    /** 可选：该场景对加权和的分摊贡献 RFI_scenario * weight */
    weightedContribution?: number;
  }>;
  gates: {
    respectGateApplied: boolean;
    dPreGateApplied: boolean;
    meanQCapApplied: boolean;
  };
  mapping: {
    /** aggregate + clamp 后、输出层前的 RFI（与 scores.RFI_sim 一致） */
    rawRfiSim: number;
    /** rfiToSimulatedRhythmScore + clamp(0,100)，闸门 respect 前 */
    mappedRhythmBeforeRespect: number;
    /** respect 分支 cap 后的 rhythm（若未触发 respect 则与上一字段相同） */
    rhythmAfterRespectCap?: number;
    /** D_pre / meanQ 分支后的最终对外 rhythm（与 scores.simulatedRhythmScore 一致） */
    finalRhythmScore: number;
  };
  /** 可选：what-if 基线指纹，便于报表 diff */
  sourceFingerprint?: {
    evaluatorVersion: string;
    staticContextPresent: boolean;
  };
};
```

**说明**：`scenarioDebug.length === 7` 与生产七场景一致；**`lower_*` what-if** 在 M0 内对 **`D_pre` / `F_sim`（或 cap 前 F_raw 若未来暴露）** 做 **缩放副本** 后重跑 **`computeRfiScenario` 链**，**不修改** `rrm-sim-formula.ts` 内公式实现，仅 **调用**。

## 6. Simulator 接入方式（M1.3-M1 之后）

| Config | 数据依赖 | 接入方式 |
|--------|----------|----------|
| **lower_d_pre_penalty** | `D_pre` + 七场景 RFI 重算 | `D_eff = clamp01(D_pre * k)` 后代入 `computeRfiScenario` |
| **lower_f_cap_effect** | `F_sim` 或 cap 前 raw（若 debug 增补 `F_raw`） | 缩放或替换 cap 常数 **仅在 M0 fork 调用路径**（不改编译进生产的 constants 文件，可用 **局部常量覆盖**） |
| **c_pred_weighting_variant** | `C_pred` | `C_eff = clamp01(lerp(0.5, C_pred, w))` 等试验曲线，再入 `computeRfiScenario` |
| **per_scenario_weight_variant** | 每场景 `RFI_scenario` + 权重 | 替换 `aggregateRfiSim` 的权重数组（M0 内副本函数） |

**约束**：仅 **offline JSON**；**不写 DB**；**默认** `--out` 仍受 `.gitignore` 保护。

## 8. 明确不做什么

- 不改 **finalScore**。
- 不改 **worker 主排序**。
- 不改 **`MatchResult.finalScore`**。
- **不写** `MatchResult`。
- **不让 RRM-Sim 参与真实排序**。
- **不进入正式 M4**。
- **不向用户展示** C/A/S/E/F/Q/D/R **原始中间量**（含 debug JSON 面向终端用户的路径）。
- **不把** debug 或 calibrated 分数 **直接上线**为匹配结论。
- **不写假数据**、**不提交**含真实用户标识的离线报表。

## 9. 下一步 implementation prompt（复制用）

在遵守 **§8 非目标** 的前提下：

1. **只读验证**：在本地 admin GET 样本上确认 `results[].rrmSimResult.scores` 与 `scenarioScores` 已含 M1.3-M1 所需字段；记录 respect 分支下 **RFI_sim 与 final rhythm** 的差异案例。
2. **实现方案 C**：新增 **`evaluateRrmSimDebugFromSimulationV2`**（路径 `rrm-sim.evaluator-debug.ts`），复用 **`extract*` / `computeRfiScenario` / `aggregateRfiSim` / `rfiToSimulatedRhythmScore`** 与与生产对齐的闸门片段；返回 **`RrmSimDebugResult`**（`production` + 可选 `debug`）；**不得修改** `evaluateRrmSimFromSimulationV2` 的默认返回形状。
3. **黄金测试**：fixture 下 **`production`** 与单独调用 **`evaluateRrmSimFromSimulationV2`** 一致；**`debug.mapping.finalRhythmScore`** 与 **`production.scores.simulatedRhythmScore`** 一致；全局标量与 **`RFI_sim`** 在容差内对齐。
4. **扩展 M0**：在 **tsx 或 api 脚本** 中调用 debug wrapper（或从 admin 读 lite 中间量），实现 **`lower_d_pre_penalty` / `lower_f_cap_effect`** 的 **what-if** 分支；输出仍仅 JSON。
5. **API 边界**：默认 **admin GET 不附加** `rrmDebugIntermediate`；若需联调，仅允许 **显式 env / 内部路由**，且 **FinalMatchPage 不引用**。
