# M6.0-A2 — Scoring v2 Product Logic Plan

> **范围**：**产品设计 / 工程边界 / 迁移路径** 文档。承接 **M6.0-A / M6.0-A1** 对 `finalScore` v1 的诊断结论，定义 **relationshipProfileScore**、**finalScore v2** 的产品语义与落地阶段。  
> **不含**真实 `userId`、`token`、`DATABASE_URL`。  
> **本文不修改** worker、API、前端、Prisma、RRM resolver；**v1 与 `MatchResult.candidateUserId` 保持现状** 直至后续里程碑显式切换。

---

## 1. 一句话结论

**finalScore v1**（`apps/worker/src/jobs/matching-score.ts`）在工程上是 **池内加权排序分**：`previewPoolScore` 来自固定槽位 `baseScore`（`preview-pool.service.ts` 的 `LAYER_SPECS`），`preferenceScore` 与 **预览池硬筛**（`preference-hard-gate.ts`）维度对齐，导致 **池内候选人偏好命中常为 1**；`styleScore` 在测试数据下易拉满；**`profileScore` 仅占 20%**，问卷变化对 **0～1 总分** 影响被压缩。因此 **v1 不适合单独作为商业化「匹配指数」** 对外承诺。

**M6.0** 需要引入以 **20 维 G1-R 关系画像** 为核心的 **`relationshipProfileScore`**（及可选 **`finalScore v2`**），并把 **硬筛、池位、偏好软分、画像分、RRM 展示** 的职责拆开：**硬筛只决定入池**；**池位只影响展示顺序或 tie-breaker**，不应主导用户看到的「基础适配指数」；**已通过硬筛的偏好维度不应再重复高权重加分**；**用户可见的基础适配 / 关系画像适配度应主要来自 20 维**；**RRM Top2 只影响 `displayCandidateUserId` / `displaySourceType`，不改 `finalScore`、不改 `candidateUserId`**（与 `docs/M5/M5.6-closure-rrm-top2-controlled-production-path.md` 不变量一致）。

## 2. 当前 v1 的问题

| 现象 | 原因（代码层） |
|------|----------------|
| **previewPoolScore 占 35%** 且常为 **0.8** | `W_PREVIEW = 0.35`；池项 `baseScore` 由 **rankInPool** 写死（如 rank 1 → **0.8**）。胜者记录里常见 **0.8**，与 **排序平局偏向低 rank** 叠加，易固定为槽位 1。 |
| **preferenceScore 占 30%** 且常为 **1** | `W_PREF = 0.3`；`computePreferenceScore` 为 **hits/denom**。预览池构建时 **`passesPreferenceHardGate`** 与 **denom 维度一致**，池内用户已在各维 **全部命中** → **soft 分失去区分度**。 |
| **styleScore 占 15%** 且易为 **1** | `computeStyleScore` = 交集 / `len(viewerTags)`；测试数据或标签设计下易满分。 |
| **profileScore 仅占 20%** | `W_PROF = 0.2`；`computeProfileScore` 为 20 轴 **`mean(1−|a−b|)`**（双方非 null 维）；问卷变化主要只动这一项。 |
| **总分锁在 0.88～0.89+** | 三项高分平台 + 低权画像小幅波动 → **窄带饱和**。 |

## 3. 新职责分工

| 模块 | 新职责 | 是否参与最终展示分（目标态） | 说明 |
|------|--------|-------------------------------|------|
| **硬筛条件**（与 `preference-hard-gate` 对齐的维度） | **仅**决定能否进入候选池 / 预览池 | **否**（或仅审计侧记录） | 与 v1 soft `preferenceScore` **语义去重**：入池已通过则 **不再** 作为高权重「加分项」。 |
| **Preview pool / `baseScore`** | **展示顺序**、池内 **tie-breaker**、运营分层（visual / preference / backup） | **否** 作为「基础适配指数」主项；可保留 **内部排序** 或 **开发者对照** | 与 **用户理解的「关系适配」** 解耦。 |
| **preferenceScore（v1 语义）** | 若继续计算：仅 **影子 / 分解说明**；**不**再作为用户主指数的高权重项 | **默认否**（硬筛已覆盖同维度） | 若未来存在「硬筛未覆盖的软偏好」，可单独建模，**避免**与硬筛维度重复计分。 |
| **styleScore** | **辅助**：图像风格标签与 viewer 偏好标签重合度 | **可**，建议 **≤10～15%** 权重（若进入任何 v2 混合公式） | 不参与硬筛；不应压过画像。 |
| **20 维 G1-R `profileScore`**（与 `questionnaire.scorer` → `UserProfile` 一致） | **用户可见「基础适配指数 / 关系画像适配度」的核心** | **是** | 定义 **`relationshipProfileScore`** 的主来源（见 §4）。 |
| **RRM Top2** | **`displayCandidateUserId` / `displaySourceType`** 解析与受控写入 | **否**（不改 `MatchResult.finalScore` / `candidateUserId`） | 与 M5.6 closure：**不变量** 不变。 |
| **interaction-simulation-lite**（若存在侧车） | **解释 / hint / 侧车证据** | **否**（默认不参与主指数） | 与现有产品注释一致：不参与 worker `finalScore` 重算。 |

## 4. v2 分数定义

### 4.1 `relationshipProfileScore`（用户主语义：基础适配指数）

**第一版定义（推荐从简）：**

- **`relationshipProfileScore = profileScore`**  
  其中 **`profileScore`** 与 v1 中 **`computeProfileScore(viewerProfile, candidateProfile)`** 的数学定义一致（20 维、`1−|a−b|` 在双非 null 维上平均；无重叠维时当前实现为中性 **0.5** —— v2 落地时可再区分「缺失」与「低适配」）。

**可选增强（第二版，需工程评估）：**

- **`relationshipProfileScore = 0.9 × profileScore + 0.1 × confidenceAdjustedSignal`**  
  `confidenceAdjustedSignal` 来自问卷侧 **`user_profiles.confidence`** 或未来 **低质量答卷检测** 输出；**若 confidence 暂不接入**，则退化为 **纯 `profileScore`**。

**产品表述：**

- 给用户看的 **「基础适配指数」** = **基于双方 20 维关系画像的适配度**，**不是** 池槽位分，**不是** 已通过硬筛的重复偏好分。

### 4.2 `finalScoreV2`（可选总包名）

- **`finalScoreV2`** 用于指代 **面向展示的总分方案**（可能 **等于** `relationshipProfileScore`，或为 **画像主导混合**，见 §5）。  
- **`finalScore`（v1）** 保留在 **`MatchResult.finalScore`**，用于 **审计、回滚、与历史数据对齐**。

## 5. v2 公式候选

### 方案 A：纯画像分

**`finalScoreV2 = profileScore`**（即 **`finalScoreV2 ≡ relationshipProfileScore`**）

| 优点 | 缺点 |
|------|------|
| 语义最直观；问卷改动对展示分 **敏感** | 不包含 style；需文案解释 **硬筛已在入池前完成** |
| 彻底避免 **硬筛 + soft pref** 重复计分 | 运营侧若希望「风格」微调排序，需 **另轨**（非主指数） |

### 方案 B：画像主导 + 少量辅助

**`finalScoreV2 = 0.80 × profileScore + 0.10 × styleScore + 0.10 × previewTieBreakerScore`**

- **`preferenceScore` 不参与**（已通过硬筛的维度不再进入展示分）。  
- **`previewTieBreakerScore`**：建议 **归一化后的槽位分或 rank 反函数**，仅作 **小幅** 扰动，**上限建议明显低于 v1 的 0.35 权重效果**。

| 优点 | 缺点 |
|------|------|
| 保留风格与池序的 **微弱** 信号 | 需定义 `previewTieBreakerScore`，避免再次「锁高分段」 |
| 仍突出画像 | 参数需回归标定 |

### 方案 C：画像 + RRM 只做展示

- **`finalScoreV2 = profileScore`**（同方案 A）。  
- **`displayCandidateUserId`** 由 **RRM resolver** 决定；前端分区展示：  
  - **基础适配指数** → `profileScore` / `relationshipProfileScore`  
  - **关系节奏推荐 / 展示对象** → RRM 的 `displaySourceType` 等  

### 推荐（M6.0 shadow 阶段）

- **先用方案 A 做 shadow**：最易与 v1 对比、最易做 **全 A / 全 B / 正常** 回归、最易向用户解释。  
- B / C 在 **M6.0-E 回归** 后再选型或组合。

## 6. 低质量答卷处理

**共识**：全 A / 全 B / 全同档 **不是** 高置信、可比的「真实关系画像」输入。

**建议检测信号（后续工程实现）：**

| 信号 | 含义 |
|------|------|
| **straightLineRate** | 单一选项占比过高 |
| **answerEntropy** | 选项分布过窄 |
| **longestSameAnswerRun** | 最长连续同答 |
| **lowEffortFlag** | 综合上述规则打标 |

**M6.0 策略（先弱后强）：**

- **仅提示 / shadow**：`lowEffortFlag = true` 时在 **开发者区** 或 **内部报表** 提示。  
- **后续**：可降低 `confidence`、对 **`relationshipProfileScore` / `finalScoreV2` 设上限**、或 **要求重新填写**。  
- **M6.0 不默认拦截** 入池或匹配队列，避免误伤线上。

## 9. 回归测试要求

至少覆盖：

1. **正常答卷 viewer × 正常答卷 candidate**。  
2. **viewer 全 A**、**viewer 全 B**。  
3. **candidate 全 A**、**candidate 全 B**。  
4. **多候选** 下 **`profileScore` / `relationshipProfileScore` 差** 在前端或 shadow API **可见**。  
5. **RRM 生效**（`displayCandidateUserId` ≠ `candidateUserId`）时：**`finalScore`（v1）不变**；**`relationshipProfileScore`（v2 核心）不因 RRM 重写**（仍基于同一对 **viewer–被评估画像** 的业务定义需在产品层写死：通常 **viewer vs 当前展示候选人画像** 或 **viewer vs worker 胜者** —— **须在 M6.0-D 前锁死一种**，避免双口径）。  
6. **硬筛不符合** 的用户 **不出现在** 该 viewer 的 active preview pool。
