# M6.7-C2 — Observation API / Admin Debug Surface Plan

## 1. 本轮目标

- C1 已提供只读 snapshot script（`m6-r7-rrm-observation-snapshot.mjs`）。
- C1b 已在本地 DB 可达后产出匿名 snapshot run。
- C2 目标是规划 admin / debug observation surface 的后续实现路径。
- C2 仅做方案文档，不写代码，不接 true bounded decision flag。

## 2. 当前观测基线

摘录 C1b 关键匿名结果（`limit=50`）：

- sampleSize = 50
- withScoreShadowV2 = 25
- withRrmV2Top2Selector = 16
- withRrmDecisionShadow = 14
- withRrmBoundedDecision = 1
- decisionShadow.same_as_baseline = 14
- boundedDecision.would_use_baseline = 1
- malformedCount = 0
- parseErrorCount = 0
- unexpectedExceptionCount = 0

说明：

- 样本窗口仍偏小。
- `boundedDecision` 仅 1 条，仍处于早期观测阶段。
- 当前数据不能作为 true bounded decision 上线依据。

## 3. Observation surface 目标

Admin / debug surface 应能够稳定观察以下匿名信号：

- `rrmDecisionShadow` 是否存在。
- `rrmBoundedDecision`（dry-run）是否存在。
- `decisionShadow` 分布。
- `boundedDecision` 分布。
- `fallbackReasonDistribution` 分布。
- `malformedCount` / `parseErrorCount` / `unexpectedExceptionCount`。
- `scoreShadowV2` 覆盖情况。
- `rrmV2Top2Selector` 覆盖情况。
- `selectedTop2` 覆盖情况（来自 `inputPresence`）。
- legacy `scoreShadow` 存在情况（仅用于历史分层观察）。
- `resolved projection` 不在 DB 中持久化的边界说明。
- handoff mismatch / owner warning 属于 runtime UI 信号的边界说明。

## 4. 候选实现方案

### A. 继续使用 database script

优点：

- 风险最低。
- 不暴露 admin API。
- 不改 runtime。
- 适合本地与运维观测。

缺点：

- admin 前端不可直接消费。
- 不利于产品化、可视化与统一入口。

### B. 新增只读 API endpoint

示例：

- `GET /admin/rrm-observation/summary`

优点：

- 可被 admin 页面直接消费。
- 可纳入统一鉴权 / RBAC。
- 支持自动化调用与可观测平台接入。

缺点：

- 需要新增 API controller / service。
- 需要严格处理鉴权与输出脱敏。
- 需要防止输出 raw ID / raw payload。

### C. Admin 页面 debug card

优点：

- 可视化、管理员可读性强。
- 降低脚本依赖，便于日常诊断。

缺点：

- 依赖 API 支撑。
- 需要 admin 页面改动，范围更大。

推荐：

- M6.7-C3 优先做方案 B（只读 API summary）或短期继续强化 A（script）。
- M6.7-C4 再评估 C（admin UI card）。
- C2 本轮不做实现。

## 5. Recommended C3 scope

建议 M6.7-C3 二选一：

- Option 1：只读 API endpoint  
  `GET /admin/rrm-observation/summary?limit=50`
- Option 2：继续增强 script（例如 `--output-file` / `--window`）。

推荐优先 Option 1，但必须满足：

- admin / debug only。
- 不输出真实 ID。
- 默认 `limit` 且有上限。
- 全程只读。
- 对 malformed rows 容错。
- 鉴权 / admin guard 与现有 admin 体系一致。

## 6. API contract 草案

若 C3 采用 API，可参考以下匿名返回形状：

```json
{
  "sampleSize": 50,
  "coverage": {
    "withScoreShadowV2": 25,
    "withRrmV2Top2Selector": 16,
    "withRrmDecisionShadow": 14,
    "withRrmBoundedDecision": 1
  },
  "decisionShadow": {
    "same_as_baseline": 14,
    "switch_to_top2_candidate": 0,
    "no_shadow_decision": 0,
    "blocked": 0,
    "unexpected_exception": 0
  },
  "boundedDecision": {
    "would_use_baseline": 1,
    "would_switch_to_rrm": 0,
    "fallback_baseline": 0,
    "fallbackReasonDistribution": {}
  },
  "quality": {
    "malformedCount": 0,
    "parseErrorCount": 0,
    "unexpectedExceptionCount": 0
  },
  "notes": []
}
```

不得包含：

- `matchResultId`
- `userId`
- `candidateUserId`
- `conversationId`
- raw `matchInsights`
- raw `selectedTop2` IDs

## 7. Security / privacy requirements

- admin/debug only。
- no raw IDs。
- no raw `matchInsights`。
- no candidate identity leakage。
- M6.7-C3 不做 user-level drilldown。
- `limit` 必须可控且有上限。
- 错误响应不应向客户端泄露 DB 内部细节。

## 8. Product / engineering interpretation

- `same_as_baseline` 高：当前窗口内 RRM 与 baseline 一致，不代表“效果一定更好”，仅代表未观察到切换。
- `switch_to_top2_candidate = 0`：说明当前样本未覆盖切换事件，不代表系统没有切换能力。
- `boundedDecision` 样本少：dry-run 观测仍不足。
- `malformed/parseError/unexpectedException = 0`：当前窗口结构稳定。
- v1 legacy 字段存在：仅说明历史数据仍有 legacy 痕迹，不代表新链路依赖 v1。
- `sampleSize` 小：不可直接用于上线结论。
