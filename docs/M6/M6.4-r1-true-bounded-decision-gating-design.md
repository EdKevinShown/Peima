## 3. True bounded decision 定义

**True bounded decision** **指**：在 **feature flag** 开启、**evaluation gate** 满足、**guardrails** 全部通过时，系统**允许**在 **`selectedTop2`**、**`rrmBoundedDecision`**、**`rrmDecisionShadow`** 所构成的**闭包**内，将**正式匹配结果**从 **baseline candidate** **切换**为 **bounded target candidate**（**仍限于 Top2**，**非**全池重算）。

**必须同时满足的边界：**

- **仍然不能**扩大候选池或从全池重选；
- **仍然不能**调用**额外** **RRM resolver** 改写全局 **ranking**；
- **仍然不能**绕过 **guardrails**；
- **只能**在 **Top2** 范围内做**有限**切换；
- **任何**契约破坏、输入缺失、观测或解释未就绪 → **fallback baseline**（优先级高于「激进采用 switch」）。

## 4. True decision 与 dry-run 的关系

### Dry-run（**当前已实现**）

- 写入 **`matchInsights.rrmBoundedDecision`**；
- **`mode=dry_run`**；
- **`wouldSwitch`** **仅观测**，**不**改变 **`MatchResult.candidateUserId`** **或** **`finalScore`**；
- 与 **M6.1 shadow** 类似：**审计 / 评估**侧车。

### True bounded decision（**未来实现，受门控**）

- 在**更严格**的 **gates** 之后才允许**影响正式结果**（展示、resolver 或持久化字段，见 **§7**）；
- **可能**影响正式结果路径 → **必须**有完整的 **decision meta**、**fallback**、**rollback**、**解释统一**；
- **`wouldSwitch`（dry-run）** **≠** **`actualSwitch`（true）**；**仅**在 **true** 路径下 **`actualSwitch`** 可为 **`true`**。

## 6. Gating requirements

在 **true bounded decision implementation** 之前，建议分为四层门控；**任一层未满足则不允许生效**。

### 6.1 Evaluation gate

- 至少完成 **`N ≥ 10`** 本地 **batch**（与 **M6.2** 量级思路对齐）；更理想 **`N ≥ 50`** **pre-pilot** 评估窗口；
- **`unexpectedExceptionRate = 0`**（**bounded** 路径与 **summarize** 工具一致口径）；
- **`malformedCount` / `parseErrorCount`** 为 **0**；
- **`invalidSelectorRate` / `missingInputRate`** 在**书面阈值**内且**可解释**；
- **`blockedRate`** **可解释**（非静默失败）；
- **`v1LegacyPresenceRate`**：**不作为**质量门槛，但系统须**保持**对 v1 **非依赖**；
- **必须**有真实 **`would_switch_to_rrm` / `guardrail_blocked` / `fallback_baseline`** 等**多样**样本，或**书面说明**当前数据缺口与**采样计划**（**M6.2** 已示警同质样本风险）。

### 6.2 System gate

- **Fallback baseline** 路径**可用**且**单测 / 集成**覆盖；
- **Feature flag** 默认 **off**；**one-click disable** 可行（运维 / 配置）；
- **Decision meta** **可审计**（**`sourceVersion` / `generatedAt` / `fallbackReason`** 等）；
- **No schema surprise**：若未来需新列，须**单独** **ADR + migration** 评审（**r1** **不**引入 migration）；
- **No hidden RRM resolver mutation**：**resolver** 行为变更须**显式** flag 与文档（与 **M6.0** 只读 display 精神一致）。

### 6.3 Product / explanation gate

- **`MatchResult.candidateUserId`**、**`displayCandidateUserId`**、**`displaySourceType`**、**`decisionSourceType`（若引入）**、**`finalScore`**、**`relationshipProfileScore`**、**`primaryConclusion`**、**`matchExplanation`**、**`matchReview`**、**`reasonSummary`** 的**用户可见解释**须**统一**（见 **§11**）；
- **`FinalMatchPage`** 文案**不**与后端 **display slice**（**`matching-result-display.ts`**）矛盾；
- **Chat / timeline** 入口使用的「匹配对象」须**有单一权威定义**或**显式**「正式 vs 展示」双轨说明。

### 6.4 Observation gate

- 至少具备 **debug report** 或 **admin observation** 计划（**M6.4-r4**）；
- 能查询（**不含**生产环境随意导出真实 ID 到日志外系统；**设计层**指**字段存在**）：**`decisionSource`**、**`fallbackReason`**、**`wouldSwitch` / `actualSwitch`**、**`guardrails`**、**`blockReasons`**、**`sourceVersion`**。

## 7. True decision write strategy candidates

与 **M6.3-r2** 方案族对齐，比较三种**正式生效**路径（**r1** **不选定**最终实现，**只**比较风险）。

### Strategy A：Still display-only

- **`PEIMA_M6_RRM_BOUNDED_DECISION_ENABLED`** 仍**只**驱动 **API display resolver**（如扩展 **`displayCandidateUserId` / `displaySourceType`** 枚举语义）；
- **不改** **`MatchResult.candidateUserId`**；
- **最安全**；**回滚**简单（关 flag 即回 **`match_result_original`** 类语义）；
- **缺点**：**不是**「持久化正式决策」；**审计**依赖 **meta + 日志**，弱于 **B/C**。

### Strategy B：Decision meta + resolver override（**推荐作为 M6.4 首选演进方向**）

- **继续**写 **`matchInsights.rrmBoundedDecision`**（或 **v2 schema** 的 **`mode=enabled`** 变体，见 **§9**）；
- **保留** **`MatchResult.candidateUserId`** = **baseline**（或与 **display** 显式双轨）；
- **后端** **`matching-result-display`**（及下游只读 API）在 **true flag on** 且 **gate ok** 时读取 **meta** 决定**展示与下游只读行为**；
- **风险可控**、与 **M6.0** **readonly** 路径一致；
- **缺点**：**`candidateUserId`** 与 **`displayCandidateUserId`** **可能长期分离** → **§8** 必须定义 **chat / timeline** 跟哪一条。

### Strategy C：Write **`MatchResult.candidateUserId`**

- **Bounded** 结论**直接**成为 **`candidateUserId`**；
- **真正**进入「主结果链」；
- **风险最高**：须 **full explanation unification / audit / rollback**（**§8 / §11 / §12**）；
- **建议**：**M6.4-r2** **不**直接落地 **Strategy C**；若要做 **C**，须**单独** **M6.5+** 里程碑与 **ADR**。

**本轮建议：**

- **M6.4-r2** **不**直接做 **Strategy C**；
- **优先**细化 **Strategy B** 的 **gated resolver override**，或延续 **dry-run** 扩大样本至 **M6.4-r5 readiness report**；
- **Implementation** **不应早于** **M6.4-r5** 之后（见 **§13**）。

## 8. Candidate / display / score consistency

### 8.1 若 **`candidateUserId` 不变** 但 **`displayCandidateUserId` 变**

- **必须**在 UX 与文档中标明为 **display override**，**不是** **true persisted decision**（除非后续显式升级策略）；
- **Chat / timeline** 跟 **display** 还是跟 **persisted candidate**：**必须**二选一并**全链路一致**（避免「消息发给 A、详情页是 B」）。

### 8.2 若 **`candidateUserId` 改变**（**Strategy C**）

- **`finalScore`** **必须**对应**新** candidate（**禁止**把 baseline 分数**直接套**到 **switched target**）；
- **`primaryConclusion` / `matchExplanation` / `matchReview` / `relationshipProfileScore` / `reasonSummary`** 均须对应**新** candidate；
- **`fallbackReason`** **必须**可查；**baseline candidate** **必须**在 **meta** 中可审计（**`baselineRef` redacted**）；
- **任一**字段无法一致更新 → **fallback baseline**，**不**写半状态。

## 9. Required true decision meta（**草案，r1 不落库**）

以下 JSON **为设计草案**；**字段名 / 枚举**可在 **M6.4-r2** 合同化；**不写**真实 ID。  
**`mode`** 取其一：**`enabled`** | **`dry_run`** | **`fallback`**。**`decision`** 取其一：**`use_baseline`** | **`use_rrm_bounded`** | **`fallback_baseline`**。**`decisionSource`** 取其一：**`baseline`** | **`rrm_bounded`** | **`fallback`**。

```json
{
  "schemaVersion": 1,
  "sourceType": "rrm_true_bounded_decision",
  "sourceVersion": "m6.4-rrm-true-bounded-decision-v1",
  "mode": "enabled",
  "decision": "use_rrm_bounded",
  "baselineRef": { "redacted": true },
  "selectedRef": { "redacted": true },
  "decisionSource": "rrm_bounded",
  "actualSwitch": false,
  "fallbackUsed": false,
  "fallbackReason": null,
  "guardrails": {},
  "evaluationGate": {},
  "sourceVersions": {},
  "generatedAt": "ISO_TIMESTAMP"
}
```

**说明：**

- **`baselineRef` / `selectedRef`**：**不**在日志或文档中写入真实 **`userId`**；
- **`actualSwitch`**：**仅**在 **true decision** 路径且**已**切换时可为 **`true`**；
- **Dry-run** 的 **`wouldSwitch`** **不等于** **`actualSwitch`**。

## 10. Must fallback conditions

以下**任一**成立时，**必须** **fallback baseline**（**不**执行正式 switch，或**回退**展示到 baseline）：

- **True decision flag** **off**；
- **仅** dry-run 模式（**无** true flag 或 **gate** 未满足）；
- **缺失** **`rrmBoundedDecision`** 或 **malformed** / **`sourceVersion` mismatch**；
- **`mode`** 非支持集合；
- **`decision`** 非 **`would_switch_to_rrm`（dry）** / **`use_rrm_bounded`（true 草案）** 等允许值；
- **`scoreShadowV2`**、**`rrmDecisionShadow`**、**`selectedTop2`** **缺失**；
- **`target_not_in_top2`**、**target user / profile missing**；
- **`guardrails.blocked === true`** 或 **`blockReasons`** 非空；
- **Context flags** 高风险（与 **M6.1** 语义对齐）；
- **Evaluation gate** 未满足；
- **Explanation unification** 未就绪（**§11**）；
- **Admin observation** 未就绪（**§6.4**）；
- **Unexpected exception**（须 **meta** 记录 **`unexpected_exception`**，**不**抛毁主流程）。

## 12. Rollback / kill switch

**设计要求：**

- **`PEIMA_M6_RRM_BOUNDED_DECISION_ENABLED`** **off** → **完全**回到 **baseline**（展示与持久化策略按所选 **Strategy** 定义，但**不得**残留「半开关」状态）；
- **不需要** **DB migration 回滚**即可恢复页面安全态；
- **不需要** **手修历史 `MatchResult`** 才能恢复 **FinalMatchPage**（历史行可保留 **meta** 供审计，**读路径** **flag off** 时**忽略** true 语义）；
- **Fallback path** **永远**可用；
- **True decision meta** **必须**保留 **`baselineRef`**（**redacted**）以便审计与对账；
- 若 **bounded** 路径 **异常率 `> 0`**（与 **evaluation gate** 阈值冲突），应**关闭 true decision flag** 并走 **incident / r5 类 readiness** 复盘。
