# M6.6-r1 — Resolved Owner / Explanation / Navigation Unification Plan

## 1. 本轮目标

- **M6.5** 已完成：**`GET /matching/result/:userId`** 的 **resolved projection**、**`FinalMatchPage`** 对 resolved / targets 的消费、**chat / timeline / feedback** 的 **`resolveTargetId`** fallback 链、**`finalMatchPeerUserId`** handoff query、以及 **C4** 回归记录。
- **M6.6** 目标：在不变更 **true bounded** 写入、**`MatchResult.candidateUserId`**、**`finalScore`**、worker / resolver 主决策的前提下，将 **页面展示、聊天、时间线、反馈、解释、分数语义 owner** 的**目标对象**在端到端路径上**对齐到同一合同**（resolved + owner + warnings）。
- **M6.6-r1（本文）** 只做**范围调查、风险罗列、分阶段建议与 API/前端需求清单**；**不写代码**、**不改业务逻辑**、**不接** **`PEIMA_M6_RRM_BOUNDED_DECISION_ENABLED`**。

## 3. M6.6 要解决的问题（风险）

| 风险 | 表现 |
|------|------|
| **展示 vs 会话成员分裂** | **FinalMatch** 主卡片围绕 **resolved B**，但 **`ChatPage`** 展示的 **`conversation.candidateUserId`** 或侧车仍让用户感觉是 **baseline A**（若后端与会话创建路径任一侧漂移）。 |
| **时间线语义分裂** | 用户从 **Final Match** 进入 **时间线**，以为在看 **B** 的关系进展，但时间线项 **`meta.actorUserId`** 或会话上下文仍与 **A** 混淆（仅 UI 层，无 DB 变更也可能造成误解）。 |
| **反馈归因错误** | 用户对 **B** 的主观反馈进入 **`structuredPayload.targetUserId`** 时若仍默认 **conversation.candidateUserId`** 为 **A**，学习管道与复盘会错位。 |
| **分数语义错位** | **`scoreOwnerCandidateUserId` ≠ `resolvedCandidateUserId`** 时，主卡片仍把 **`finalScore`** 读成「当前展示对象」的分数，违反 **M6.5-r3 / r4** 的 score contract。 |
| **解释语义错位** | **`explanationOwnerCandidateUserId` ≠ `resolvedCandidateUserId`** 时，解释/复审段落仍像在为 **resolved** 对象生成，而无 **warning / fallback** 分区。 |
| **跨页 warnings 丢失** | **`consistencyWarnings`** 仅在 **Final Match** 展示；**Chat / Timeline** 不继承 handoff 提示，用户忽略 **owner mismatch** 继续操作。 |
| **Handoff query 未消费** | **`finalMatchPeerUserId`** 已写出但下游**不读**，无法在客户端做 **expected vs actual** 校验或调试 surfaced。 |

## 6. M6.6 分阶段实施建议

### M6.6-C1：ChatPage consume `finalMatchPeerUserId` / resolved handoff

- **目标：** **`ChatPage`** 读取 **`finalMatchPeerUserId`**；与 **`conversation.candidateUserId`** 比较，做 **debug / warning / 折叠说明**；**不**强行改会话成员，除非 **`POST /chat/conversations`** 合同扩展且后端支持。
- **约束：** 不改 **chat** 主流程默认行为的首个里程碑可仅为**只读校验**。

### M6.6-C2：Timeline target alignment

- **目标：** **`RelationshipTimelinePage`**（及从 **Chat** 链到的时间线入口）读取 **`finalMatchPeerUserId`** 或从 **`GET`** 缓存的 **`timelineTargetUserId`**（实现策略二选一在 C2 设计稿中定稿）；**先**做 **read / display / debug** 对齐，**不**改 **Prisma**。

### M6.6-C3：Feedback target alignment

- **目标：** **FinalMatch / Chat** 提交 **P6.12** 时 **`targetUserId`** 与 **`feedbackTargetUserId`** 一致；若仅 handoff、无 **GET** 重拉，则在会话建立后从 **`matchResultId`** 再取一次 **GET** 或由后端返回 **`feedbackTargetUserId`**（需求在 **§7** 跟踪）。
- **约束：** **不**污染 baseline 归因；**不**改 **`MatchResult.candidateUserId`**。

### M6.6-C4：Explanation / score owner alignment

- **目标：** **`scoreOwnerCandidateUserId` ≠ `resolvedCandidateUserId`** 时，主路径**不得**把 **baseline `finalScore`** 文案化成 **resolved** 对象的分数；**`explanationOwner` ≠ resolved** 时 **warning / fallback** 与 **MatchReview / Explanation AI** 入口一致。
- **依赖：** **match-explanation-ai**、**match-review-ai** 服务端是否已用 **matchResultId** 自洽解析（**needs** **M6.6-C4** 代码审）。

### M6.6-C5：Final regression / push prep

- **目标：** API / Web /（若触及）Worker 测试与 **`tsc`**、**`build`**；确认 **§10** 不变性；**准备** **`git push`**（由维护者执行）。
