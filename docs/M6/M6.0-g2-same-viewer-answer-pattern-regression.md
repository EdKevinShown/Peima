# M6.0-G2 — Same Viewer Answer Pattern Regression

> **范围**：**同一 viewer** 依次 **Normal → All-A → All-B** 的 **严格 E2E** 回归记录，用于在 **控制 `candidateUserId` 可比性** 的前提下，观察 **legacy `finalScore` v1**、**`reasonSummary` 四分量**、**`matchInsights.scoreShadow`** 与 **`relationshipProfileScore`**（与 **GET `/matching/result`** 解析一致）。  
> **本文不写** 真实 **`userId` / `candidateUserId` / `matchResultId` / token / `DATABASE_URL`**。  
> **与 M6.0-G 的差异**：M6.0-G 为 **跨用户匿名抽样**；**G2 要求同 viewer 顺序三态**，否则 **不得** 单独作为 **主分数切换（M6.0-H）** 依据。

---

## 1. 一句话结论

**同 viewer、同一 `candidateUserId`** 下依次 **Normal → All-A → All-B** 的实测表明：**legacy `finalScore` v1** 仍被 **`previewPoolScore` / `preferenceScore` / `styleScore`** 压在 **~0.88–0.89** 窄带；**`relationshipProfileScore`（与 `profileScore`）** 对问卷三态的 **区分度明显更强**。**All-A / All-B** 在分数上仍可「好看」，**不能** 当作高质量问卷，**仍需 low-effort questionnaire detection（M6.0-I）**；在此基础上 **可进入 M6.0-H** 前端主分数切换 **方案评审**。

## 3. 回归方法

### 3.1 前置

- **固定一个本地 viewer**（有 **`user_profile`**、**active 预览池**、可选 **styleTags / 偏好** 与 **候选人带图**；与 **M6.0-F** 相同库前提）。  
- **API** 与 **DB** 使用 **同一 `DATABASE_URL`**；**`dev:api`** 已启动时可走 **JWT** 调 **`POST /questionnaire/submit`**（见 **`SubmitQuestionnaireDto`**：30 条 **`questionKey` + `answerValue`**）。

### 3.2 每一态（Normal / All-A / All-B）重复

1. **`POST /questionnaire/submit`**：写入 **Normal** 或 **q01–q30 全 A** 或 **全 B**（合法 **`answerValue`**）。  
2. **只读校验**：`questionnaire_answers` **30 行**；**`A`/`B` 计数**；**`user_profiles.updatedAt`** 是否推进。  
3. **`POST /matching/enqueue`**（viewer **本人** JWT，`body.userId` 与 token 一致）。  
4. **`batch-match`**（与 **M6.0-F** 相同：`node apps/worker/dist/main.js --batch-match` 或本机已验证命令）。  
5. **读最新 `match_results`**（该 **viewer** `ORDER BY createdAt DESC LIMIT 1`）。  
6. **GET `/matching/result/:viewerUserId`**：记录 **`relationshipProfileScore`**（**`source`**）、**`scoreBreakdown`**；**`displaySourceType` / `displayCandidateUserId`**（**不在 `match_results` 行上**，见 **§3.3**）。

### 3.3 `displaySourceType` 说明

- **`match_results`** 表 **无** **`displaySourceType`** 列；该字段由 **`GET /matching/result`** 经 **`resolveMatchResultDisplay`** 等 **读路径聚合** 返回。  
- **对比解释**：若 **`candidateUserId` 在某一态发生变化**，**`profileScore` / `relationshipProfileScore` 的对比对象已变**，**不得** 再当作「仅问卷自变量」解释；须在 **§5「candidate 是否变化」** 列 **显式标注**。

### 3.4 SQL 模板（占位符）

**问卷聚合**（将 `<LOCAL_VIEWER_USER_ID>` 替换为维护者本地值，**勿写入 git**）：

```sql
SELECT COUNT(*) AS total,
       COUNT(*) FILTER (WHERE "answerValue" = 'A') AS a_count,
       COUNT(*) FILTER (WHERE "answerValue" = 'B') AS b_count,
       MAX("updatedAt") AS max_updated_at
FROM questionnaire_answers
WHERE "userId" = '<LOCAL_VIEWER_USER_ID>';
```

**最新匹配行**（**仅** `match_results` 列）：

```sql
SELECT "candidateUserId",
       "finalScore",
       "reasonSummary",
       "matchInsights"->'scoreShadow' AS score_shadow,
       "createdAt"
FROM match_results
WHERE "userId" = '<LOCAL_VIEWER_USER_ID>'
ORDER BY "createdAt" DESC
LIMIT 1;
```

**`displaySourceType`**：在 **GET `/matching/result`** 响应 JSON 中查看（**非**上表）。

## 6. 观察结论

### 6.1 本轮实测前提（结论性）

1. **同一 viewer、同一 `candidateUserId`（三态均未变化）** → 属于 **有效对比**：**问卷** 为自变量，**候选人 20 维画像** 为固定对照，**不存在**「换 candidate 导致 profile 不可比」的混淆。

### 6.2 定量摘要（便于与 M6.0-A2 对照）

- **`finalScore` v1** 三态极差约 **0.013**（0.881 → 0.894）。  
- **`relationshipProfileScore` / `profileScore`** 三态极差约 **0.065**（0.756 → 0.821）。  
- **`previewPoolScore` / `preferenceScore` / `styleScore`** 三态 **完全相同**（0.800 / 1.000 / 1.000）→ **`finalScore` 的波动主要由加权合成中的其它项主导**，视觉上仍 **锁在高分段**。

### 6.3 产品结论（对应原 §E 判定）

1. **同一 viewer 下，legacy `finalScore` 是否仍易被锁在高分段？**  
   **是**。三态 **`preview` / `preference` / `style` 不变**，**`finalScore` v1** 仍落在 **~0.88–0.89**，与 **M6.0-A2** 一致。

2. **同一 viewer 下，`relationshipProfileScore` 是否比 `finalScore` 更能体现问卷变化？**  
   **是**。**RPS / profile** 极差 **明显大于** **`finalScore` 极差**。

3. **若 `relationshipProfileScore` 变化也不明显？**  
   **本轮不适用**：三态 **RPS 已有可解释分层**；若未来其它 viewer 上出现 **RPS 仍平**，再单独讨论 **20 维映射 / 平均算法** 灵敏度。

4. **All-A / All-B 是否应进入 low-effort questionnaire detection？**  
   **是**。尽管 **All-A / All-B** 在本轮 **profile / RPS** 上可高于 **Normal**，其 **答卷形态仍为低信息量直线卷**，**不应** 视为高质量问卷；**须** **M6.0-I** 至少 **flag / 降权**。

5. **Normal 的 `finalScore` / RPS 低于 All-A、All-B 是否说明 Normal「错了」？**  
   **否**。仅说明 **该组 Normal 答案** 与 **该 candidate 的 20 维画像** 的 **相似度** 低于 **全 A / 全 B 映射后的画像**；**产品解读** 应 **脱开「高分即认真」** 的直觉。

6. **是否可进入 M6.0-H（前端主分数切换）？**  
   **可以进入方案评审**：**G2 同 viewer、同 candidate 门槛已满足**；**实施** 仍建议与 **M6.0-I**（low-effort）**并行规划**，避免 **直线卷** 在 UI 上被误读为「更匹配」。

7. **是否应优先 M6.0-I？**  
   **与 H 并行推进 I** 更稳妥：**G2 已证明** 极端答法在 **RPS 上仍可「好看」**，**I** 负责 **可信度与防误读**，**H** 负责 **主视觉与叙事**。
