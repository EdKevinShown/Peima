## 3. 回归方法

### 3.1 前置

- **固定一个本地 viewer**（有 **`user_profile`**、**active 预览池**、可选 **styleTags / 偏好** 与 **候选人带图**；与 **M6.0-F** 相同库前提）。  
- **API** 与 **DB** 使用 **同一 `DATABASE_URL`**；**`dev:api`** 已启动时可走 **JWT** 调 **`POST /questionnaire/submit`**（见 **`SubmitQuestionnaireDto`**：30 条 **`questionKey` + `answerValue`**）。

### 3.2 每一态（Normal / All-A / All-B）重复

1. **`POST /questionnaire/submit`**：写入 **Normal** 或 **q01–q30 全 A** 或 **全 B**（合法 **`answerValue`**）。  
2. **只读校验**：`questionnaire_answers` **30 行**；**`A`/`B` 计数**；**`user_profiles.updatedAt`** 是否推进。  
3. **`POST /matching/enqueue`**（viewer **本人** JWT，`body.userId` 与 token 一致）。  
4. **`batch-match`**（与 **M6.0-F** 相同：`node apps/worker/dist/main.js --batch-match` 或本机已验证命令）。  
5. **读最新 `match_results`**（该 **viewer** `ORDER BY createdAt DESC LIMIT 1`）。  
6. **GET `/matching/result/:viewerUserId`**：记录 **`relationshipProfileScore`**（**`source`**）、**`scoreBreakdown`**；**`displaySourceType` / `displayCandidateUserId`**（**不在 `match_results` 行上**，见 **§3.3**）。

### 3.3 `displaySourceType` 说明

- **`match_results`** 表 **无** **`displaySourceType`** 列；该字段由 **`GET /matching/result`** 经 **`resolveMatchResultDisplay`** 等 **读路径聚合** 返回。  
- **对比解释**：若 **`candidateUserId` 在某一态发生变化**，**`profileScore` / `relationshipProfileScore` 的对比对象已变**，**不得** 再当作「仅问卷自变量」解释；须在 **§5「candidate 是否变化」** 列 **显式标注**。

### 3.4 SQL 模板（占位符）

**问卷聚合**（将 `<LOCAL_VIEWER_USER_ID>` 替换为维护者本地值，**勿写入 git**）：

```sql
SELECT COUNT(*) AS total,
       COUNT(*) FILTER (WHERE "answerValue" = 'A') AS a_count,
       COUNT(*) FILTER (WHERE "answerValue" = 'B') AS b_count,
       MAX("updatedAt") AS max_updated_at
FROM questionnaire_answers
WHERE "userId" = '<LOCAL_VIEWER_USER_ID>';
```

**最新匹配行**（**仅** `match_results` 列）：

```sql
SELECT "candidateUserId",
       "finalScore",
       "reasonSummary",
       "matchInsights"->'scoreShadow' AS score_shadow,
       "createdAt"
FROM match_results
WHERE "userId" = '<LOCAL_VIEWER_USER_ID>'
ORDER BY "createdAt" DESC
LIMIT 1;
```

**`displaySourceType`**：在 **GET `/matching/result`** 响应 JSON 中查看（**非**上表）。

## 6. 观察结论（**在 §4/§5 有数据后逐条勾选**；以下为 **判定口径**）

1. **同一 viewer 下，legacy `finalScore` 是否仍易被锁在高分段？**  
   - 若三态 **`preview`/`preference`/`style` 均接近拉满** 且 **`finalScore` 仍集中在 ~0.88–0.90** → **是**（与 **M6.0-A2** 一致）。  
   - 若 **`preference`/`style` 可下探** → **可能否**，但仍需看 **`previewPoolScore`（槽位）** 是否主导。

2. **同一 viewer 下，`relationshipProfileScore` 是否比 `finalScore` 更能体现问卷变化？**  
   - 若 **`profileScore` 三态极差** 明显 **大于** **`finalScore` 极差** → **是**。  
   - 若 **`profileScore` 仍接近**（全 A / 全 B 映射后 20 维仍温和）→ **否或弱**，进入 **§6.3**。

3. **若 `relationshipProfileScore` 变化也不明显？**  
   - **可能**：**20 维 tag 聚合 / `mean(1−|Δ|)`** 本身对极端同档答卷 **不敏感**；需 **算法侧** 或 **low-effort 降权**（**M6.0-I**）再评估。

4. **All-A / All-B 是否应进入 low-effort detection？**  
   - **建议纳入**（与 **M6.0-A2**）：至少 **flag**，避免将 **直线卷** 当作高置信适配。

5. **是否可进入 M6.0-H（前端主分数切换）？**  
   - **须先完成 G2 数值表**；若 **G2 未跑完**，**不建议** 仅以 **M6.0-G** 定案 **H**。

6. **是否应优先 M6.0-I？**  
   - 可与 **H 并行设计**；若 **G2 显示直线卷画像仍「好看」** → **优先 I** 更紧迫。
