## 3. 回归方法

### 3.1 前置

- **代码版本**：含 **`3167dae`**（**M6.0-Q2**）或其后 **`main`**。  
- **固定同一本地 viewer**（**`user_profile`**、**active 预览池**、**styleTags / 偏好**、**候选人带图** 等前提与 **M6.0-F / G2** 一致）。  
- **API** 与 **DB** 共用 **`DATABASE_URL`**；**`POST /questionnaire/submit`** 须 **30** 条 **`questionKey` + `answerValue`**；合法值为每题 **`questions.ts`** 中该题的 **`options[].value`**（当前题池为 **A/B/C/D 四档**，**无** 独立 **`E`** 选项值；**`tags` 内 `5E` 等** 为轴档记号，**≠** 提交字母 **`E`**）。  
- **顺序**：建议固定为 **All-A → All-B → All-C → All-D → Normal**，以便与下表一致；**每态** 均 **enqueue → `batch-match` → 读最新 `match_results` + GET `/matching/result`**。

### 3.2 每一态重复

1. **`POST /questionnaire/submit`**：**All-A / All-B / All-C / All-D**（各 30 条同字母）或 **Normal**（混合合法答案）。  
2. **只读校验**：`questionnaire_answers` **30 行**；**A/B/C/D（及若存在的 E）计数**；**`user_profiles.updatedAt`**。  
3. **`POST /matching/enqueue`**（viewer **本人** JWT）。  
4. **`batch-match`**（与既有本地流程一致）。  
5. **`match_results`**：最新一行 **`finalScore` / `reasonSummary` / `matchInsights.scoreShadow` / `candidateUserId`**。  
6. **GET `/matching/result/:viewerUserId`**：**`scoreBreakdown`**（**previewPoolScore**、**preferenceScore**、**styleScore**、**profileScore**）、**`relationshipProfileScore`**（**`source`**）、**`displaySourceType`**（**仅 GET**，见 **§3.3**）。

### 3.3 `displaySourceType`

- **`match_results`** **无** **`displaySourceType`** 列；从 **GET `/matching/result`** 读取。

### 3.4 与 G2 历史基线的对比方式

- **不可** 用 **G2 v1.1** 表与 **G3** 表做「升格前后严格数值差」结论，除非 **同一 viewer、同一 candidate、同一池版本** 且明确 **仅闸门变更**；默认将 **G2** 作 **定性参照**、**G3** 作 **Q2 后主证据**。

### 3.5 SQL 模板（占位符；**勿**将真实 id 写入 git）

**问卷聚合**：

```sql
SELECT COUNT(*) AS total,
       COUNT(*) FILTER (WHERE "answerValue" = 'A') AS a_count,
       COUNT(*) FILTER (WHERE "answerValue" = 'B') AS b_count,
       COUNT(*) FILTER (WHERE "answerValue" = 'C') AS c_count,
       COUNT(*) FILTER (WHERE "answerValue" = 'D') AS d_count,
       COUNT(*) FILTER (WHERE "answerValue" = 'E') AS e_count,
       MAX("updatedAt") AS max_updated_at
FROM questionnaire_answers
WHERE "userId" = '<LOCAL_VIEWER_USER_ID>';
```

**最新匹配行**（**仅** `match_results` 列）：

```sql
SELECT "candidateUserId",
       "finalScore",
       "reasonSummary",
       "matchInsights"->'scoreShadow' AS score_shadow,
       "createdAt"
FROM match_results
WHERE "userId" = '<LOCAL_VIEWER_USER_ID>'
ORDER BY "createdAt" DESC
LIMIT 1;
```

## 6. 观察结论（**§4/§5 有数据后逐条勾选**；以下为 **判定口径**）

1. **`q01`–`q30` 全 `canonical` 后，`finalScore` v1 是否仍易被锁在高分段？**  
   - 若五态 **`preview` / `preference` / `style` 仍拉满或近拉满**，且 **`finalScore` 极差 ≪ `relationshipProfileScore` 极差** → **仍易锁带**（与 **M6.0-A2 / G2** 叙事一致，但 **须以 G3 数为准**）。

2. **`relationshipProfileScore` 是否比 `finalScore` v1 更能体现问卷变化？**  
   - 若 **RPS / `profileScore` 五态极差** 明显 **大于** **`finalScore` 极差** → **是**。

3. **All-A / B / C / D 的 `profileScore` 差异是否足够明显？**  
   - 若四直线卷 **极差仍小** → **不够**，倾向加强 **M6.0-J（v2 映射/聚合）** 或 **low-effort 降权** 讨论；若 **极差足够** → **够**，仍 **不** 等于「高质量问卷」，见 **§6.5**。

4. **`q29`/`q30` canonical 后是否须立刻更新 profileScore v2 设计？**  
   - **视 G3 结果**：若 **仅入两题** 已使 **五态分层显著变化**，先在文档中记录 **「v1 映射层已更敏感」**；**v2** 仍可在 **J** 统一做 **权重/稀疏轴/极端答法** 级设计，**非** 仅由两题单独驱动。

5. **是否仍需要 low-effort detection？**  
   - **产品侧仍建议需要**（直线卷可高分）；**本轮不实现**（与 **M6.0-Q2** 边界一致）。

6. **是否可进入 M6.0-H（前端主分数切换）？**  
   - **须 G3 表填毕**；若 **RPS 区分度** 仍明显优于 **v1**，可 **并行** **H** 方案稿。

7. **是否应先进入 M6.0-J（profileScore v2）？**  
   - 若 **§6.3** 为「不够明显」或 **v1 仍主导用户感知** → **倾向先 J 或与 H 并行**；若 **§6.3** 已足够且更紧迫的是 **叙事/UI** → **H 优先**。
