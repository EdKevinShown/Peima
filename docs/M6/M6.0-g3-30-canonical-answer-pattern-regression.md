# M6.0-G3 — 30-Canonical Answer Pattern Regression Record

> **范围**：在 **M6.0-Q2**（**`q01`–`q30` 全 `canonical`**、**`confidence` 分母 = 30**）之后，**同一本地 viewer** 依次 **All-A → All-B → All-C → All-D → Normal**（或维护者约定的固定顺序），记录 **legacy `finalScore` v1**、**`reasonSummary` 四分量**、**`matchInsights.scoreShadow`** 与 **`relationshipProfileScore`**（与 **GET `/matching/result`** 一致）。  
> **本文不写** 真实 **`userId` / `candidateUserId` / `matchResultId` / token / `DATABASE_URL`**。  
> **与 M6.0-G2 的关系**：**G2 v1.1 数值表**在 **Q2 前**（仅 **28** 题参与 v2 计分闸门）测得，见 **G2 v1.2 修订**；**不得** 当作 **30-canonical** 下的当前真值。**G3** 为 **Q2 后的正式重跑槽位**。

---

## 1. 一句话结论

**同一 viewer、同一 `candidateUserId`** 下 **30 canonical** 五态实测：**`finalScore` v1** 仍落在 **~0.88–0.90** 窄带（**`previewPoolScore` / `preferenceScore` / `styleScore` 三态不变**）；**`relationshipProfileScore`（≈ `profileScore`）** 五态约 **0.754–0.842**，**极差明显大于 v1**，**All-C** 显著低于其余直线卷与 **Normal**。**Normal 的 RPS 最高** 仅说明 **该组混合答案与当前 candidate 的 20 维更接近**，**非**「正常答卷应永远最高」。结论 **支持进入 M6.0-H** 主分数切换 **方案**；**All-A / All-B / All-D 的 RPS 仍不低**，后续仍需 **M6.0-J（`profileScore` v2）** 与/或 **low-effort detection**（实现仍后置时可接受，但产品缺口仍在）。

## 3. 回归方法

### 3.1 前置

- **代码版本**：含 **`3167dae`**（**M6.0-Q2**）或其后 **`main`**。  
- **固定同一本地 viewer**（**`user_profile`**、**active 预览池**、**styleTags / 偏好**、**候选人带图** 等前提与 **M6.0-F / G2** 一致）。  
- **API** 与 **DB** 共用 **`DATABASE_URL`**；**`POST /questionnaire/submit`** 须 **30** 条 **`questionKey` + `answerValue`**；合法值为每题 **`questions.ts`** 中该题的 **`options[].value`**（当前题池为 **A/B/C/D 四档**，**无** 独立 **`E`** 选项值；**`tags` 内 `5E` 等** 为轴档记号，**≠** 提交字母 **`E`**）。  
- **顺序**：建议固定为 **All-A → All-B → All-C → All-D → Normal**，以便与下表一致；**每态** 均 **enqueue → `batch-match` → 读最新 `match_results` + GET `/matching/result`**。

### 3.2 每一态重复

1. **`POST /questionnaire/submit`**：**All-A / All-B / All-C / All-D**（各 30 条同字母）或 **Normal**（混合合法答案）。  
2. **只读校验**：`questionnaire_answers` **30 行**；**A/B/C/D（及若存在的 E）计数**；**`user_profiles.updatedAt`**。  
3. **`POST /matching/enqueue`**（viewer **本人** JWT）。  
4. **`batch-match`**（与既有本地流程一致）。  
5. **`match_results`**：最新一行 **`finalScore` / `reasonSummary` / `matchInsights.scoreShadow` / `candidateUserId`**。  
6. **GET `/matching/result/:viewerUserId`**：**`scoreBreakdown`**（**previewPoolScore**、**preferenceScore**、**styleScore**、**profileScore**）、**`relationshipProfileScore`**（**`source`**）、**`displaySourceType`**（**仅 GET**，见 **§3.3**）。

### 3.3 `displaySourceType`

- **`match_results`** **无** **`displaySourceType`** 列；从 **GET `/matching/result`** 读取。

### 3.4 与 G2 历史基线的对比方式

- **不可** 用 **G2 v1.1** 表与 **G3** 表做「升格前后严格数值差」结论，除非 **同一 viewer、同一 candidate、同一池版本** 且明确 **仅闸门变更**；默认将 **G2** 作 **定性参照**、**G3** 作 **Q2 后主证据**。

### 3.5 SQL 模板（占位符；**勿**将真实 id 写入 git）

**问卷聚合**：

```sql
SELECT COUNT(*) AS total,
       COUNT(*) FILTER (WHERE "answerValue" = 'A') AS a_count,
       COUNT(*) FILTER (WHERE "answerValue" = 'B') AS b_count,
       COUNT(*) FILTER (WHERE "answerValue" = 'C') AS c_count,
       COUNT(*) FILTER (WHERE "answerValue" = 'D') AS d_count,
       COUNT(*) FILTER (WHERE "answerValue" = 'E') AS e_count,
       MAX("updatedAt") AS max_updated_at
FROM questionnaire_answers
WHERE "userId" = '<LOCAL_VIEWER_USER_ID>';
```

**最新匹配行**（**仅** `match_results` 列）：

```sql
SELECT "candidateUserId",
       "finalScore",
       "reasonSummary",
       "matchInsights"->'scoreShadow' AS score_shadow,
       "createdAt"
FROM match_results
WHERE "userId" = '<LOCAL_VIEWER_USER_ID>'
ORDER BY "createdAt" DESC
LIMIT 1;
```

## 6. 观察结论

### 6.1 定量摘要（**v1.1**）

- **`finalScore` v1**：约 **0.881–0.898**，极差约 **0.017**。  
- **`relationshipProfileScore` / `profileScore`**：约 **0.754–0.842**，极差约 **0.088**。  
- **`previewPoolScore` / `preferenceScore` / `styleScore`**：五态 **完全相同**（0.800 / 1.000 / 1.000）。

### 6.2 实测前提

1. **五态均为同一 viewer、同一 `candidateUserId`（均未变化）** → **对比有效**。

### 6.3 对原判定问题（**E.1–E.7**）的直接回答

1. **`q01`–`q30` 全 `canonical` 后，`finalScore` v1 是否仍易被锁在高分段？**  
   **是**。五态 **`preview` / `preference` / `style` 不变**，**`finalScore` v1** 仍约 **0.88–0.90**。

2. **`relationshipProfileScore` 是否比 `finalScore` v1 更能体现问卷变化？**  
   **是**。**RPS**（与 **`profileScore`**）五态极差明显大于 **`finalScore` v1** 五态极差。

3. **All-A / All-B / All-C / All-D 的 `profileScore` 差异是否足够明显？**  
   **部分明显**：**All-C** 相对 **All-A / B / D** 拉开 **显著低谷**；**A / B / D** 之间 **仍较接近**，**不能** 单靠当前 **v1 profile 分差** 完全区分「哪条直线更不认真」。

4. **`q29`/`q30` canonical 后是否需要更新 `profileScore` v2 设计？**  
   **仍建议推进 M6.0-J**：G3 证明 **30 维入口** 后 **profile 层已能表达 C 档极端**；**v2** 仍可统一处理 **权重、low-effort、轴拥挤** 等，**与是否仅两题升格无矛盾**。

5. **是否仍需要 low-effort detection？**  
   **是**（产品侧）。**All-A / All-B / All-D** 的 **RPS 仍可达 ~0.82 档**，**不能** 当高质量问卷背书；**实现可继续后置**。

6. **是否可以进入 M6.0-H（前端主分数切换方案）？**  
   **可以**。**G3** 已提供 **Q2 后** 主证据，**RPS 叙事** 成立。

7. **是否应先进入 M6.0-J（`profileScore` v2）？**  
   **与 H 并行规划 J**：**H** 解决 **主视觉与默认叙事**；**J + low-effort** 解决 **直线卷仍「好看」** 的可信度问题。

### 6.4 产品解读（与 **M6.0-G2** 对齐）

- **Normal 的 `finalScore` / RPS 高于 All-A / All-B / All-D** **不** 推出「正常答卷应系统性地更高」，仅说明 **本组 Normal** 与 **该 candidate 的 20 维画像** **更接近**。
