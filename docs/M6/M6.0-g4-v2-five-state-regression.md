# M6.0-G4 — V2 five-state regression record

> **范围**：在 **M6.0-J4**（**GET `/matching/result`** 已返回 **`relationshipProfileScoreV2`**，**`FinalMatchPage`** 技术区可读 **V2 shadow**）之后，**同一本地 viewer** 依次 **All-A → All-B → All-C → All-D → Normal**（与 **M6.0-G3** 顺序对齐），每态 **提交问卷 → 校验 30 题 → enqueue → `batch-match` → 读最新 `match_results`**，并 **可选** 调 **GET `/matching/result`** 确认 **`relationshipProfileScoreV2.source === match_insights_score_shadow_v2`**。  
> **目的**：验证 **`scoreShadowV2.displayScore100`** 相对 **`scoreShadow.relationshipProfileScore`（RPS v1）** 是否 **更能拉开分数**，以及 **V2 `band` / penalty / cap** 是否符合直觉。  
> **本文不写** 真实 **`userId` / `candidateUserId` / `matchResultId` / token / `DATABASE_URL`**。  
> **与 G3 的关系**：**G3** 侧重 **30-canonical** 下 **v1 `finalScore` + RPS v1**；**G4** 在 **同协议** 上 **叠加 V2 shadow 列** 与 **API V2 读数**。

## 3. 回归方法

### 3.1 前置

- **代码版本**：含 **J3 / J3B / J4** 之后的 **`main`**（J4 commit：**`987a5a3`** 或其后）。  
- **固定同一本地 viewer**；**`user_profile`**、**active 预览池**、**候选人 `UserProfile` 齐全** 等与 **G3 / J3B** 一致。  
- **每态**：`POST /questionnaire/submit`（All-A / All-B / All-C / All-D 各 30 条同字母；Normal 为混合合法答案）→ **§C.1 SQL** 校验 **30 行 + A/B/C/D/E 计数 + `max_updated_at`** → **`POST /matching/enqueue`** → **`batch-match`** → **§C.2 SQL** 读 **`scoreShadow` + `scoreShadowV2`** → **可选** `GET /matching/result` 看 **`relationshipProfileScoreV2`**。

### 3.2 与 J4 的衔接

- **DB**：以 **`matchInsights.scoreShadowV2`** 为金源。  
- **API**：**`relationshipProfileScoreV2`** 经 **`resolveRelationshipProfileScoreV2Shadow`**；若 **`source`** 非 **`match_insights_score_shadow_v2`**，应先排查 **JSON 合法性**（见 **`matching-relationship-profile-score-v2.ts`**），再记表。

### 3.3 `candidate` 列（§5）

- 仅填 **否 / 是 / 待确认**；**不写 id**。五态若 **刻意固定池与候选**，应为 **否**。

## 6. 观察结论（§E 答题；v1.0 为待数据版）

以下 **带「待 §5」** 的条目须在 **填完 §4–§5** 后改为 **是/否 + 数值**。

1. **V2 `displayScore100` 是否比 RPS v1 更能拉开差距？**  
   **待 §5**：比较五态 **`displayScore100` 极差** vs **`relationshipProfileScore×100` 极差**（或同尺度散点）。设计意图见 **J1B 分段映射**；**以表为准**。

2. **五态中 `displayScore100` 最高与最低相差多少？**  
   **待 §5**。

3. **All-C / All-A / All-B / All-D 是否被 V2 更清楚地区分？**  
   **待 §5**（建议对比 **V2 `band` + `displayScore100`** 与 **RPS v1** 排序是否一致、差异是否放大）。

4. **`penalty` / `cap` 是否触发？**  
   **待 §5**。若 **极少触发**：通常说明 **viewer–candidate 核心轴 diff 未越过阈值**（与 **J3B** 单样本「温和对齐」可并存），**不等于**公式失效。

5. **若 penalty/cap 很少触发，是否说明样本与 candidate 没有强核心冲突？**  
   **在 §5 为低冲突时**：**倾向是**（仅描述 **该固定候选** 关系；换候选可能不同）。

6. **`V2 band` 是否符合直觉？**  
   **待 §5**（对照 **G3** 对 All-C / Normal 的定性预期）。

7. **是否可以进入 M6.0-H（前端主分数切换方案）？**  
   **待 §5**：若 **V2 跨态区分力 ≥ 产品阈值** 且 **不变量**（§7）全满足，可 **启动 H 方案评审**；否则先 **J5 调参** 或 **补样本**。

8. **是否还需要 M6.0-J5（V2 权重 / mapping 调参）？**  
   **待 §5**：若 **区分力不足** 或 **`band` 与业务直觉系统性偏离**，**需要 J5**。

9. **是否仍后置 low-effort detection？**  
   **是（产品层默认）**：与 **G3** 一致 — **低努力检测** 不改变本档 **V1/V2 shadow 读数** 协议；**实现仍可后置**，但 **缺口是否阻断 H** 需产品单独拍板。

## 附录 C — SQL 模板（占位符）

**问卷聚合**：

```sql
SELECT COUNT(*) AS total,
       COUNT(*) FILTER (WHERE "answerValue" = 'A') AS a_count,
       COUNT(*) FILTER (WHERE "answerValue" = 'B') AS b_count,
       COUNT(*) FILTER (WHERE "answerValue" = 'C') AS c_count,
       COUNT(*) FILTER (WHERE "answerValue" = 'D') AS d_count,
       COUNT(*) FILTER (WHERE "answerValue" = 'E') AS e_count,
       MAX("updatedAt") AS max_updated_at
FROM questionnaire_answers
WHERE "userId" = '<LOCAL_VIEWER_USER_ID>';
```

**最新 `MatchResult`（含 V2）**：

```sql
SELECT "candidateUserId",
       "finalScore",
       "reasonSummary",
       "matchInsights"->'scoreShadow' AS score_shadow_v1,
       "matchInsights"->'scoreShadowV2' AS score_shadow_v2,
       "createdAt"
FROM match_results
WHERE "userId" = '<LOCAL_VIEWER_USER_ID>'
ORDER BY "createdAt" DESC
LIMIT 1;
```
