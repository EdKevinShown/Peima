# M6.0-R1 — RRM × Scoring V2 integration scan and plan

> **范围**：**只读扫描** 当前 **RRM / RRM Top2 / `GET /matching/result` display resolver** 与 **worker `batch-match` / V2 shadow** 的耦合情况；**输出方案**（**V2 Top2 → RRM 子集**）与 **分阶段实现建议**。**本轮只写文档**；**不改** worker / API / Web / resolver / schema / migration；**不做** low-effort detection；**本文不写** 真实 **`userId` / `token` / `DATABASE_URL`**。  
> **依据**：**`apps/api/src/modules/matching/matching-result-display.ts`**、**`rrm-top2-display-eligibility.ts`**、**`matching.service.ts`**；**`apps/worker/src/jobs/batch-match.processor.ts`**、**`batch-match-match-insights.ts`**；**`docs/M5/`**、**`M6.0-j1c-matching-pipeline-v2-responsibility-alignment.md`**、**`M6.0-k1-scoring-v2-rollout-and-closure-plan.md`**、**`M6.0-index.md`**、**`README.md`**。

---

## 1. 一句话结论

**当前 RRM（M5.3 `rrm_top2_bounded_selector`）尚未接入 Scoring V2**：**`resolveMatchResultDisplay`** 在启用 RRM 分支时 **只读** **`matchResultRrmTop2DisplayMeta`**（冻结 JSON）与 **`matchInsights` 内的 `rrmSimReadonlySummary`** 做 **eligibility**；**不**读取 **`matchInsights.scoreShadowV2`**，**不**使用 **`relationshipProfileScoreV2.displayScore100`** 决定 Top2。**worker 胜者** 仍由 **`computeFinalScoreV1`** 等 **legacy** 路径决定；**V2** 仅写入 **shadow** 供 **GET** 展示与 **FinalMatch** 主视觉 flag。**下一步**：先以 **纯函数 `selectV2Top2Candidates`**（**R2**）固定 **「谁有资格进 RRM 子集」**；再以 **shadow / feature flag** 渐进接入 **RRM 输入** 与 **`displaySourceType` 新枚举**（**R3–R5**），保证 **不把低 V2 分系统性顶到主展示**（见 **§4–§8**）。

## 2. 当前 RRM 实现状态

| **当前 RRM 是否已经影响 `displayCandidateUserId`？** | **是（条件满足时）**：`PEIMA_M5_RRM_TOP2_*` 启用、meta **frozen** 且 **eligibility `ok`** 时，返回 **`displayCandidateUserId = meta.newDisplayCandidateUserId`**，**`displaySourceType = "rrm_top2_bounded_selector"`**。 |
| **当前 RRM 是否读取 `scoreShadowV2`？** | **否**。resolver 路径 **无** `scoreShadowV2` / `relationshipProfileScoreV2` 读取。 |
| **当前 RRM 是否知道 `relationshipProfileScoreV2.displayScore100`？** | **否**（**GET 聚合层**解析的 V2 字段 **不参与** RRM 闸门）。 |

| **当前 RRM 是否仍基于 legacy `finalScore` / pairwise / static fallback？** | **worker 真源**：**`batch-match.processor.ts`** 仍用 **`computeFinalScoreV1`** 选胜者 → **`MatchResult.candidateUserId`**。**GET 展示**：在 RRM **未**命中时，走 **pairwise finalize meta** 或 **`match_result_original`**；与 **V2 shadow** **并行存在、无绑定**。 |

## 3. 当前 FinalMatch display resolver 状态

| 问题 | 结论 |
|------|------|
| **FinalMatchPage 最终展示对象来自哪个字段？** | 前端优先 **`displayCandidateUserId`**（API 已解析），无则 **`candidateUserId`**（与 **README / FinalMatchPage** 一致）。 |
| **`candidateUserId` 与 `displayCandidateUserId` 的关系？** | **`candidateUserId`**：**`MatchResult` 行真源**（worker 写入）。**`displayCandidateUserId`**：**读模型**；RRM 或 pairwise finalize **可**将展示切到 Top2 内另一人，**不**改库行 **`candidateUserId`**。 |
| **`displaySourceType` 当前有哪些可能值？** | **`match_result_original`**、**`static_final`**、**`pairwise_final`**、**`static_fallback`**、**`rrm_top2_bounded_selector`**（见 **`matching-result-display.ts`** 类型）。 |
| **RRM 成功时 `displaySourceType` 是什么？** | **`rrm_top2_bounded_selector`**；且 **`finalMatchDecisionMeta` 刻意为 `null`**（**M5.3-C2.1**，避免与 pairwise 形状混用）。 |
| **fallback 时走什么？** | RRM 分支失败 → 尝试 **pairwise frozen meta**（env **enabled** 且 **staticTop1** 与 **`candidateUserId`** 对齐等）；再失败 → **`match_result_original`**（**`displayCandidateUserId = candidateUserId`**，`meta` **null**）。 |

**补充扫描**：**`match-readout-fusion`**、**`match-review-ai`** 模块内 **未发现** **`relationshipProfileScoreV2` / `scoreShadowV2`** 引用（**R1** 扫描时 **grep 无命中**）；与 **V2** 主分展示 **解耦**。

## 4. RRM-V2 正确产品规则（目标态）

- **V2**：双方 **20 维 G1-R** 的 **基础关系画像适配分**（**`displayScore100` / `band` / cap / conflict 计数** 等），**shadow** 先行。  
- **RRM**：在 **V2 Top2 / 高潜** 子集上做 **关系节奏 / 风险** 二次判断；**输出只读展示决策**，**不**重定义 V2 数值语义。  
- **RRM 不能把 V2 很低的人强行顶到主展示**：须 **硬门槛**（**band / display 下限 / guardrails**）与 **「分差过大不介入」** 类规则（见 **§5**）。  
- **RRM 只影响** **`displayCandidateUserId` / `displaySourceType`**（及未来 **readonly meta**），**不**改 **`MatchResult.finalScore`**、**不**改 **`candidateUserId`**、**不**回写 **`relationshipProfileScoreV2`** / **`scoreShadowV2`**。  
- **与 J1C 对齐**：硬筛 → 池 → **V2** → **Top2 子集** → **RRM** → **Final**；**本轮不落地**，仅冻结规则叙述供 **R2+** 对照。

---

## 5. V2 Top2 候选选择规则建议（第一版 · 仅方案）

1. **输入**：active **6 人池** 内各候选的 **`matchInsights.scoreShadowV2`**（或等价 viewer/candidate profile 现场计算）→ **`displayScore100`**。  
2. **排序**：按 **`displayScore100` 降序**；缺失 / invalid 的条目 **剔除或降权**（与 **G5 missing/invalid** 策略一致）。  
3. **取 Top2**：取前 **2** 名。  
4. **最低门槛**：两人 **`displayScore100` ≥ T**（建议 **T = 60 或 65**，产品可调）。**低于 T** 的第二名 **不进入** RRM 子集（**仅展示 Top1** 或走 **legacy 展示策略**）。  
5. **分差闸门**：若 **`top1 − top2 > Δ`**（建议 **Δ = 10 或 12**），**RRM 不介入**，**`displayCandidateUserId`** 固定为 **Top1**（减少「节奏」推翻「明显更高 V2」的观感）。  
6. **仅在** **`top2` 满足门槛且分差 ≤ Δ` 时** 将 **{Top1, Top2}** 交给 **RRM** 在二者内择 **`displayCandidateUserId`**。

## 6. RRM 输入建议（隐私与契约）

**不应**向模型或侧车直接投喂 **原始问卷逐题答案**、**token**、或可逆 **明文 userId**（与 **P6 / M5** 只读摘要风格一致）。建议输入（示意）：

- **viewer**：**profile summary / 轴聚合**（已有 **questionnaire profile v3** 或 **FinalMatch 侧** 可裁剪摘要）。  
- **candidateA / B**：**V2 `displayScore100`**、**`band`**、**conflict 计数**（**core / strong / redFlag**）、**安全 opening topics / 解释片段**（来自 **`matchInsights`** 既有字段，**非** raw Q/A）。  
- **若已有**：**`rrmSimReadonlySummary`** 同类 **viewer-safe** 摘要。  
- **明确禁止**：raw questionnaire rows；任意 **secret**；可枚举 **真实 id** 进 **prompt**（若需 trace，用 **hash / fingerprint**）。

---

## 7. RRM 输出建议（契约草案 · 本轮不实现）

建议未来 **readonly meta**（或 **扩展 `MatchResultRrmTop2DisplayMeta`**）可携带：

```json
{
  "selectedDisplayCandidateUserId": "<uuid>",
  "displaySourceType": "rrm_top2_v2_bounded_selector",
  "reasonCodes": [],
  "rhythmSummary": "",
  "guardrails": {},
  "fallbackUsed": false
}
```

**要求**：**不**写 **`MatchResult.finalScore`**；**不**改 **`candidateUserId`**；**只**写 **展示用 meta / 只读侧车**；**`fallbackUsed: true`** 时 **保留** 当前 **`resolveMatchResultDisplay`** 回退顺序（**RRM-v2 失败 → 既有 RRM / pairwise / original**）。**`displaySourceType` 新枚举** 须 **feature flag** 与 **API 类型** 同步评审（**不在 R1 改代码**）。

## 9. 风险

| 风险 | 说明 |
|------|------|
| **旧 `MatchResult` 无 `scoreShadowV2`** | **V2 Top2** 无法构造 → **必须 fallback** 至 **legacy-only** 或 **仅 Top1**。 |
| **worker winner 仍是 legacy v1** | **主视觉 V2** 可能与 **`candidateUserId`** 指向的「排序真源」**短期不一致**；须在 UI/文档中 **显式区分** 直至 **阶段 C**（见 **K1**）。 |
| **RRM 不受 V2 门槛约束** | 可能把 **低 `displayScore100`** 候选 **推到主展示** → **须 guardrails + 分差闸门**（**§5**）。 |
| **需要 feature flag 与 fallback** | 避免 **production** 半套切换；与 **M5.6** **controlled** 传统一致。 |
| **文案风险** | 避免将 RRM 表述为 **「重算匹配分 / 改写 finalScore」**；坚持 **「展示对象 / 节奏建议」** 口径。 |
