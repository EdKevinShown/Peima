# M6.10-r1 — Candidate-level Score Snapshot Audit

## 1. 本轮目标

说明：

- RRM read-layer 已可决定 `resolvedCandidateUserId`。
- 下一步需要保证 resolved candidate 拥有自己的可投影分数。
- r1 仅审计当前是否已有 candidate-level score snapshot（docs-only）。

## 2. 当前问题

- 当前持久化 `MatchResult.candidateUserId` / `MatchResult.finalScore` 仍对应 baseline winner。
- 在 M6.8 behind-flag 场景下，`resolvedCandidateUserId` 可能切换到 bounded target。
- 若缺少 target 对应分数快照，会出现“展示对象与分数 owner 不一致”。

## 3. Worker 计算链路审计

基于 `apps/worker/src/jobs/batch-match.processor.ts` 与相关 helper：

- 候选池中的候选人（通常来自 preview pool）会逐个进入 `computeFinalScoreV1` 计算，形成内存态 `scored[]`。
- `scored[]` 内每一项包含：
  - candidate 引用
  - `components`（含 `previewPoolScore` / `preferenceScore` / `styleScore` / `profileScore` / `finalScore`）
- worker 对 `scored[]` 按 `components.finalScore` 排序后只取 `best = scored[0]`。
- 持久化 `MatchResult` 时仅写：
  - `candidateUserId = best candidate`
  - `finalScore = best.components.finalScore`
  - `reasonSummary`（来自 best）
  - `matchInsights`（以 best 为中心构建）
- 非 winner 候选人的 `finalScore/components` 在当前链路不持久化到 `MatchResult`。

审计结论：

- **计算阶段：全池有分数。**
- **持久化阶段：仅 winner finalScore 稳定落库。**

## 4. scoreShadowV2 结构审计

基于 `apps/worker/src/jobs/batch-match-match-insights.ts`、`apps/worker/test/batch-match-match-insights.spec.ts`、`packages/shared/types/match-p1.ts`：

当前 `matchInsights.scoreShadowV2` 为单对象（winner 视角），字段包含：

- `scoringVersion`
- `rawCompatibilityScore`
- `weightedBaseScore`
- `penaltyTotal`
- `cappedRawScore`
- `displayScore100`
- `band`
- `capApplied`
- `coreConflictCount`
- `strongConflictCount`
- `redFlagConflictCount`
- `validAxisCount`
- `skippedAxisCount`
- `source`

未发现以下候选人级容器字段：

- `candidates`
- `poolCandidateScores`
- `top2Scores`
- `candidateUserId -> score` 映射
- 候选人级 `rank` 列表
- 候选人级 `components` 列表

结论：

- `scoreShadowV2` 当前不是 candidate-level snapshot；它是当前 winner 的单行 v2 shadow。

## 5. rrmV2Top2Selector 结构审计

基于 `apps/worker/src/jobs/rrm-v2-top2-selector.ts`、`apps/worker/src/jobs/batch-match-match-insights.ts`、`packages/shared/types/match-p1.ts`：

`rrmV2Top2Selector.selectedTop2` 当前每行包含：

- `candidateUserId`
- `displayScore100`
- `band`

同层还包含：

- `top1CandidateUserId`
- `top2CandidateUserId`
- `top2Gap`
- `contextFlags`
- `thresholds`
- `reason`

未包含：

- `finalScore`（worker finalScore v1）
- 完整 `components`
- 显式 `rank` 字段（rank 主要由 selectedTop2 顺序隐含）

结论：

- `selectedTop2` 是轻量 Top2 meta，并非完整候选人分数快照。

## 6. API 可用性判断

基于 `apps/api/src/modules/matching/matching.service.ts` 与 `apps/api/src/modules/matching/matching-result-display.ts`：

- 当前 API 在 M6.8 能把 `resolvedCandidateUserId` 切到 bounded target。
- 但 API 返回中的 `finalScore` 仍来自 `MatchResult.finalScore`（baseline winner 持久化值）。
- `scoreOwnerCandidateUserId` 在 projection 中仍默认 baseline。
- 当前没有 `resolvedFinalScore` 字段，也没有稳定的 candidate-level finalScore 来源可直接按 `resolvedCandidateUserId` 索引。

因此当前 API **不能**直接保证：

- `resolvedCandidateUserId = B` 时返回 `resolvedFinalScore = B 的 finalScore`（严格语义）。

## 7. 结论分类

本次审计结论为：**B（部分可做到）**。

原因：

- 可用部分：Top2 轻量分数（`displayScore100`）与 band 存在，可支持“Top2 相对强弱”层面的有限投影。
- 缺失部分：candidate-level `finalScore/components/rank` 未持久化，无法严格满足“展示谁就显示谁自己的 finalScore（与 components owner 一致）”。

## 8. 推荐下一步

推荐路线（对应 B）：

- M6.10-C1：Top2 Score Snapshot Normalization  
  目标：先把可用于 resolved score 的 Top2 分数字段标准化（明确 owner、来源、字段语义）。
- M6.10-C2：Resolved Final Score Projection  
  目标：在 API read-layer 引入 `resolvedFinalScore`（第一版可限制在有可靠 Top2 snapshot 的场景）。

补充建议：

- 若产品要求“任意 resolved candidate 都有严格 finalScore/components”，则应升级到 candidate-level score snapshot 持久化（将路线从 B 向 C 扩展）。
