# M6.0-H1 — Final Match 主分数切换方案评审

> **范围**：在 **M6.0-G4** 收口（**V2** 已 **helper + worker shadow + API + 技术区**；五态回归见 **`M6.0-g4-v2-five-state-regression.md`**）之后，评审 **FinalMatchPage** 是否、如何把 **主视觉分数** 从 **legacy `finalScore` v1** 切换为 **`relationshipProfileScoreV2.displayScore100`**。  
> **本轮**：**只写方案**；**不改** `FinalMatchPage`、**不改 API**、**不改 worker**、**不改** 既有 **scoring / ranking**、**不改 RRM**。  
> **本文不写** 真实 **`userId` / `candidateUserId` / `matchResultId` / token / `DATABASE_URL`**。

---

## 1. 一句话结论

**建议**：**FinalMatchPage** 主视觉应从 **legacy `finalScore` v1** 切换为 **`relationshipProfileScoreV2.displayScore100`**（语义：**基础关系画像适配指数**）。

**第一步应采用 feature flag + fallback**：

- **有合法 V2**（`relationshipProfileScoreV2.source === "match_insights_score_shadow_v2"` 且 `displayScore100` 可用）：主视觉显示 **V2 `displayScore100` / 100**。  
- **无 V2 / `invalid`**：**fallback** 到当前 **legacy `finalScore` v1**（百分展示规则与现网一致）。  
- **legacy `finalScore` v1** 仍保留在 **技术折叠区**，用于审计、回归与排障。

---

## 2. 为什么要切主分数

结合 **M6.0-G4**：

- **legacy `finalScore` v1`** 受 **`previewPoolScore` / `preferenceScore` / `styleScore`** 与权重归一影响，五态下仍易 **挤在高分窄带**（约 **0.881–0.898**，极差约 **1.7** 分量级观感）。  
- **RPS v1**（`scoreShadow.relationshipProfileScore`）较 legacy **更能区分问卷画像**，但仍是 **0–1 线性影子**，五态极差约 **8.8** 分（×100 后）。  
- **V2 `displayScore100`** 五态极差约 **23** 分，**更能体现 20 维画像差异**（含 **penalty / cap / 分段映射**，见 **J1B**）。  
- **产品定位**：主视觉更贴近 **「基础关系画像适配指数」**（与 **J1C** 链路中 **V2 在 RRM 之前**、**RRM 不改 V2** 的职责划分一致）。

---

## 3. 不切会有什么问题

- 用户长期看到 **约 88–90** 的 **legacy** 主分，易 **误以为所有候选都高度匹配**。  
- **预览池 / 偏好 / 风格** 与 **画像** 的 **信息重复** 堆在「一个总分」上，**主视觉无法突出问卷画像贡献**。  
- **V2** 与 **20 维** 价值若只放在技术区，**主路径感知弱**，与 **G4** 结论（V2 更适合主视觉基础适配）不一致。  
- **RRM** 仅决定 **展示对象** 时，若主分仍是 legacy，**「为什么换展示人」与「画像有多适配」** 叙事 **不够对齐**（见 **§7**）。

---

## 4. 新主视觉展示方案

**主标题（建议）**：**关系画像适配度**

**主分**：**`relationshipProfileScoreV2.displayScore100` / 100**

**副文案按 `band`**（与 API / worker 枚举对齐）：

| `band` | 副文案（示例） |
|--------|----------------|
| `high` | 高度适配 |
| `good` | 较好适配 |
| `medium` | 中等适配 |
| `low` | 低适配，建议谨慎了解 |
| `strong_conflict` | 存在明显关系冲突 |

**说明文案（建议固定一句）**：  
「该分数基于双方 **20 维关系画像**、**核心轴差异** 与 **冲突惩罚** 计算。」

**注意**：**`band === "missing"`** 仅出现在 **API 解析层** 的 fallback 路径，不应作为「成功主视觉」展示；见 **§5**。

---

## 5. fallback 方案

**定义**（与 **`matching-relationship-profile-score-v2.ts`** / **`MatchingResultResponse`** 一致）：

1. **`relationshipProfileScoreV2.source === "match_insights_score_shadow_v2"`** 且 **`displayScore100`** 为 **0–100 有限数**：  
   - **主分** = **V2 `displayScore100`**。

2. **`source === "missing"`**（无 **`scoreShadowV2`** 或旧结果）：  
   - **主分** = **legacy `finalScore` v1`**（现有格式化逻辑）；  
   - **轻提示**（非恐吓）：「该结果生成较早，**暂无 V2 关系画像分**。」

3. **`source === "invalid"`**（JSON 非法或校验失败）：  
   - **主分** = **legacy `finalScore` v1`**；  
   - **技术区**可提示：「**V2 shadow 数据异常**，已使用 **旧版匹配指数**。」

**原则**：**fallback 不改变** `MatchResult.finalScore` **读数本身**；仅 **UI 主视觉数据源** 在 **flag 开启时** 优先 **V2**。

---

## 6. 技术折叠区保留项

**建议保留**（与现网能力对齐，仅增不减）：

- **legacy `finalScore` v1**  
- **`scoreBreakdown`**（`previewPoolScore` / `preferenceScore` / `styleScore` / `profileScore`）  
- **RPS v1**（`relationshipProfileScore` shadow）  
- **V2** 明细：`rawCompatibilityScore`、`penalty`、`cap`、`core` / `strong` / `redFlag` 计数等（与 **J4** 技术区一致或合并）  
- **`displaySourceType`** / **RRM** 相关只读说明（不改变 resolver 行为）

**明确**：**legacy `finalScore` v1 不删除**，用于 **审计、回归、排障** 与 **旧客户端理解**。

---

## 7. RRM 展示关系

- **主分数（方案下）**：**V2 `displayScore100`**（**RRM 不修改**该字段）。  
- **展示对象**：仍由 **`displayCandidateUserId`** + **`displaySourceType`**（**RRM / pairwise** 等 resolver）决定。  
- **不变量**：**RRM 不改变** **`candidateUserId`**、**不改变** **`MatchResult.finalScore`**、**不改变** **`relationshipProfileScoreV2`** 的 **worker 写入**（与 **J1C / J3 / J4** 一致）。

**页面文案需区分**：

- **「基础适配度」**：对 **`displayScore100`**（viewer–**当前展示对象** 的画像关系，若展示对象与静态候选一致则与 worker 写入时一致）。  
- **「当前展示推荐来源」**：对 **`displaySourceType` / RRM** 解释 **为何展示该人**，**避免**用户把 **换展示人** 误读为 **「画像分变差」**。

---

## 8. feature flag 建议

**建议新增**前端构建期开关（**本轮不实现**），例如：

- **`VITE_FINAL_MATCH_USE_V2_PRIMARY_SCORE=1`**：开启 **主视觉 V2**；未设置或非 `1` 时保持 **legacy 主分**。

**默认值建议**（实现阶段再定）：

- **开发环境**：可 **默认开**，便于联调。  
- **生产环境**：先 **关** 或 **灰度**（按渠道 / 用户段），待 **G5** 验收与舆情观察后再切默认。

**注意**：**H1 仅方案**；**H2** 再落地 flag 与 UI。

---

## 9. 风险与回滚

**风险**

- **旧 `MatchResult`** 无 **`scoreShadowV2`** → **大量 fallback**（体验与现网接近，但文案需温和）。  
- **主分数字**从 legacy 窄带切到 **V2** 后，**绝对值可能下降**，需避免 **「分低 = 匹配变差」** 的 **误读**（应强调 **度量口径变更**）。  
- **G4** 尚未覆盖 **强冲突** 下 **`cap` / `redFlagConflict`** 的 UI 心智；**极端 band** 文案需产品再润色。  
- **多语言 / 无障碍** 若后续要做，主副文案需统一走文案表。

**回滚**

- **关闭 feature flag** → 主视觉回到 **legacy `finalScore` v1**。  
- **技术区仍展示 V2**（若 API 仍有数据），便于 **对比与排障**。

- 不改 **RRM**。  
- 不做 **low-effort detection**。  
- 不做 **cap / redFlag** **调参**（属 **J5** 与专项回归）。
