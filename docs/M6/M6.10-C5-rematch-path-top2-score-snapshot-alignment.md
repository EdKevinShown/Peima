# M6.10-C5 — Rematch Path Top2 Score Snapshot Alignment

## 1. 本轮目标

对齐「手动触发 batch-match」与「通过 API 子进程触发 batch-match」的行为：避免出现一侧写入 `matchInsights.top2ScoreSnapshot`、另一侧因陈旧编译产物未写入的情况。

## 2. 现象（匿名）

- 手动 worker batch-match：观测到 `hasTop2ScoreSnapshot=true`，`top2ScoreItems=2`，分项分数类型为 number。
- 部分「排队后经 API / 测试按钮等方式触发的 batch-match」生成的新行：`hasTop2ScoreSnapshot=false`。

不在文档中记录真实 ID、`userId`、库表主键或原始 JSON。

## 3. 根因

`POST /admin/batch-match/run-once` 与 `POST /test/matching/run-batch-once` 共用 `AdminService.runBatchMatchSubprocess`。历史上该函数在检测到 `apps/worker/dist/main.js` 存在时，**优先**执行 `node dist/main.js --batch-match`。

若本地曾构建过 worker，但 **dist 未随源码更新**，则子进程运行的是**旧 bundle**，其中不包含 M6.10-C1 的 `top2ScoreSnapshot` 写入逻辑；而开发者手动执行 `pnpm --filter @peima/worker run batch-match`（tsx + `src/`）则始终使用最新源码，因而出现路径不一致。

补充说明（运维层面，非本提交代码变更）：长时间未重启的 `dev:worker` 进程内存中的旧代码，也可能与单次 CLI 运行的版本不一致；修复依赖重启 worker。

## 4. 修改文件

- `apps/api/src/modules/admin/admin.service.ts`
- `apps/api/test/admin-batch-match-subprocess.spec.ts`
- `docs/M6/M6.10-C5-rematch-path-top2-score-snapshot-alignment.md`

## 5. 修复方式

- **默认**：API 子进程始终执行 `pnpm --filter @peima/worker run batch-match`（与 worker `package.json` 脚本一致，走 tsx + `src`），避免陈旧 `dist/main.js`。
- **可选**：设置环境变量 `PEIMA_BATCH_MATCH_SUBPROCESS_USE_DIST=1`（或 `true` / `yes`）且 `apps/worker/dist/main.js` 存在时，仍可使用 `node dist/main.js --batch-match`（适用于已构建且希望避免 tsx 的路径）。
- 抽出纯函数 `resolveBatchMatchSubprocessPlan`，便于单测覆盖分支。

前端「重新匹配」仍仅调用 `POST /matching/enqueue`；队列实际消费仍依赖 worker cron 或上述 API 触发的 batch-match。本修复消除 **API 触发路径** 与 **tsx 手动路径** 的默认分歧。

## 8. 重新验证方式

在完成一次重新匹配或队列处理后，用临时只读脚本查询该 viewer 最新 `MatchResult` 的 `matchInsights`（勿打印原始全文到公开文档），核对：

- `hasTop2ScoreSnapshot === true`
- `top2ScoreSnapshot.items.length === 2`
- 两项 `finalScore` 类型为 `number`
- `rank` 为 `1` 与 `2`

若仍缺失：确认 `dev:worker` 已重启拉取最新代码；确认未强制 `PEIMA_BATCH_MATCH_SUBPROCESS_USE_DIST=1` 却未重建 worker dist。
