## 1. 一句话结论

在 **当前本地库** 中，以 **`questionnaire_answers` 聚合（30 题全 A / 非全 A·非全 B 记为 Normal）** 各取 **一条「该 viewer 最新 `match_results`」** 做匿名对照：**All-A 样本**上 **legacy `finalScore` 仍处高分段（≈0.89）**，**`relationshipProfileScore`（= `profileScore`）≈0.82**；**Normal 样本**因 **`reasonSummary` 中 `preferenceScore`/`styleScore` 为 0**，**`finalScore` 明显下探（≈0.53）**，而 **`profileScore` 仍约 0.84** —— 说明 **v1 总分仍强依赖池位 + 偏好/风格分量**，**画像分单独看变化小于「全问卷极端模式」直觉**。**`scoreShadow` 仅在 M6.0-E 之后新写入的行上出现**；旧行 **无 `scoreShadow`** 时 **`relationshipProfileScore` 仍可由 `reasonSummary` fallback**。本库 **未命中**「30 题全 B + 存在 `match_results`」的样本行，**All-B 数值表留空**，由维护者按 **§3** 补跑同一 viewer 三态更佳。

## 3. 回归方法

### 3.1 理想方法（同一 viewer，三态顺序）

1. **Normal**：问卷正常填写 → **`questionnaire_answers` / `user_profile`** 更新 → **`POST /matching/enqueue`** → **`batch-match`** → 读 **`match_results`**。  
2. **All-A**：同一 viewer **q01–q30 全 A** → 同上。  
3. **All-B**：同一 viewer **全 B** → 同上。

### 3.2 本轮实际方法（本地库匿名抽样）

- 在 **`questionnaire_answers`** 上按 **`userId` 聚合**：**`n = 30` 且 `na = 30` → All-A**；**否则且非 `nb = 30` → Normal**（混合/正常卷）。  
- 对每个 **`scenario`**，取该 **`userId` 在 `match_results` 上 `ORDER BY createdAt DESC LIMIT 1`** 的一行（**`DISTINCT ON (scenario)`** 保证 **每场景最多一行**）。  
- **限制**：**不是**「同一账号顺序三次改写问卷」的严格 E2E；且本库 **无** 满足 **「30 题全 B」且存在 `match_results`** 的抽样行 → **All-B 表内记为 —**。

## 6. 观察结论（对应任务 §E）

1. **legacy `finalScore` v1 是否仍然区分度弱（就「仅问卷极端模式」而言）？**  
   **部分成立**：在 **preview/pref/style 均高** 的 **All-A** 样本上，**v1 仍贴高分段**；但在 **pref/style 为 0** 的 **Normal** 样本上，**v1 可大幅下探** —— 区分度弱主要体现在 **「问卷驱动的画像变化」对 v1 总分的杠杆仍小于池位 + 偏好 + 风格**（与 **M6.0-A2** 一致）。

2. **`relationshipProfileScore` 是否更适合作为「基础适配指数」？**  
   **倾向是**：其与 **20 维 `profileScore`** 同源，**不混入池位分**；但本轮显示 **仅换极端答卷（All-A vs 本 Normal 样本）时 `profileScore` 本身差距不大**，**仍建议** 配合 **M6.0-I low-effort** 与 **更宽样本** 再判读。

3. **是否可进入 M6.0-H（前端主分数切换方案）？**  
   **可以进入方案评审**：**shadow 已稳定落库 + API 优先读取**；切换主视觉时需 **并列 legacy v1** 与 **文案**（硬筛已完成等）。

4. **是否仍需要 low-effort questionnaire detection？**  
   **需要**：**全 A** 仍可得 **~0.82** 档画像分，**与「正常卷」画像分未必拉开**，需防 **直线作答** 误判为高适配。

5. **是否继续保留 legacy `finalScore` v1 作开发者 / 审计指标？**  
   **是**：与 **worker 排序 / 历史 `reasonSummary`** 对齐，**保留** 利于回放与争议排查。
