# M6.0-D — finalScore v2 Shadow Plan

> **范围**：**设计文档 only**。规划 **worker** 内并行计算 **`finalScore` v1** 与 **v2 / `relationshipProfileScore`** 的路径，以及 **shadow 回归** 与 **API / 前端** 的演进顺序。  
> **不含**真实 `userId`、`token`、`DATABASE_URL`。  
> **本文不修改** 代码、Prisma、迁移、RRM、**`MatchResult.finalScore` / `candidateUserId`**。

---

## 1. 一句话结论

**M6.0-D 不直接替换 `finalScore`。** 下一步应在 **`apps/worker/src/jobs`**（与 **`batch-match.processor.ts`** 写库路径）引入 **结构化 v2 shadow**：以 **`computeProfileScore`**（与现 v1 同源的 **20 维 G1-R**）得到 **`relationshipProfileScore` / `finalScoreV2` 候选**，与 **`computeFinalScoreV1`** 并行落盘或写入 **JSON 侧车**，以便与 v1 **对比、回归、审计**。**v1** 继续写入 **`MatchResult.finalScore`**，保留 **回滚与历史对齐** 能力。

---

## 2. 当前 M6.0-B / C 已完成什么

| 能力 | 状态 |
|------|------|
| **`scoreBreakdown`** | **GET `/matching/result`** 从 **`reasonSummary`** 只读解析 v1 四分量（**M6.0-B**）。 |
| **`relationshipProfileScore`（API 字段）** | **第一版** = 解析得到的 **`scoreBreakdown.profileScore`**（**M6.0-C**）；**FinalMatchPage** 展示「关系画像适配度」。 |
| **worker 内正式 v2** | **尚未**：未在 **`matching-score.ts`** 增加并行导出；未在 **batch-match** 持久化结构化 v2。 |
| **持久化 v2 独立列** | **尚未**（本计划默认 **不** 为 v2 开新列，除非后续里程碑另立 **schema / migration**）。 |
| **主分数切换为 v2** | **尚未**；主视觉仍为 **legacy `finalScore`**。 |

## 3. 为什么需要 worker shadow

| 原因 | 说明 |
|------|------|
| **M6.0-C 的数据源是「复述」而非「真源」** | **`relationshipProfileScore`** 当前来自 **`reasonSummary`** 字符串；该串为 **人类可读摘要**，**不适合**作为长期机器真源或 feedback 主键字段。 |
| **字符串脆弱** | 文案微调、历史格式、非 v1 摘要会导致 **解析失败**（`parse_failed` / `missing`）。 |
| **真源在 worker** | **v1 `finalScore`** 与 **`computeProfileScore`** 已在 **`matching-score.ts`** 与 **`batch-match.processor.ts`** 同一次计算中具备 **结构化分量**；v2 应在 **同一执行边界** 计算，保证 **与写库 `MatchResult` 同一事务语义**（时间戳、候选集合一致）。 |
| **测试与 M6.1** | **结构化 shadow** 才能稳定做 **单测 / 集成回归**，并在 **Feedback `decisionContext`** 中记录 **v1 vs v2** 与 **展示层** 上下文。 |

---

## 4. finalScoreV2 候选定义

### 4.1 推荐第一版（与 M6.0-A2 一致）

- **`finalScoreV2 = profileScore`**（等价命名：**`relationshipProfileScore = profileScore`**）。  
- **语义**：**20 维 G1-R 画像适配度**（与 **`computeProfileScore(viewerProfile, candidateProfile)`** 一致）。  
- **不包含**：**`previewPoolScore`**、**`preferenceScore`**、**`styleScore`**。  
- **不受 RRM 改写**：RRM 只影响 **`displayCandidateUserId` / `displaySourceType`**（M5.6 不变量）。

### 4.2 可选第二版（延后）

- **`finalScoreV2 = 0.9 × profileScore + 0.1 × styleScore`**（示例）。  
- **建议**：在第一版 **纯 `profileScore`** 验证 **问卷敏感度、回归基线** 后再引入，避免再次引入 **「易拉满」** 分量稀释 v2 信号。

## 5. v1 / v2 并存策略

| 项 | 策略 |
|----|------|
| **v1** | **继续**写入 **`MatchResult.finalScore`**；**继续**写入现有 **`reasonSummary`**（`formatReasonSummaryV1`）与 **`matchInsights`**（占位解读）—— **不破现有消费者**。 |
| **v2** | **不**替换 **`finalScore`** 列；**不**改 **`candidateUserId`**。 |
| **v2 落盘（无 schema 变更的优先选项）** | 在 **`matchInsights`** JSON 内增加 **`scoreShadow`**（或并列 **`scoringShadow`**）对象，与现有 **`explanation` / `openingTopics`** 等键 **并存**；**需注意** 前端 **`isValidMatchInsights`** 若 **严格校验键集合**，应 **显式允许** 新键或改为 **「核心键必填 + 忽略未知键」**。 |
| **若必须强类型 / 索引** | 再单独立项 **Prisma 字段 + migration**（**不在 M6.0-D 承诺范围内**）。 |

**推荐 payload 形状（M6.0-E 实现时参考）：**

```json
{
  "scoreShadow": {
    "finalScoreV1": 0.894,
    "relationshipProfileScore": 0.821217,
    "scoringVersion": "m6.0-profile-score-shadow-v1"
  }
}
```

- **`finalScoreV1`**：与 **`MatchResult.finalScore`** 应 **数值一致**（冗余用于审计切片）。  
- **`relationshipProfileScore`**：worker 内 **`computeProfileScore`** 输出。  
- **`scoringVersion`**：便于 **多版本 shadow** 共存与回放。

## 6. 回归测试设计

### 6.1 数据与场景（至少）

- **viewer**：正常答卷、全 A、全 B。  
- **candidate**：正常、全 A、全 B。  
- **多候选**：**`profileScore`** 高低差 **明显**；**`preferenceScore`** 多为 **1**、**`styleScore`** 多为 **1** 的池内环境（贴近现网饱和态）。  
- **RRM**：**`displaySourceType === "rrm_top2_bounded_selector"`** 时，确认 **v2 不随 RRM 重写**（仍对 **同一对** viewer–**worker 胜者画像** 或产品已锁定的 **viewer–展示候选人画像** 口径计算 —— **须在实现前二选一并文档化**）。

### 6.2 验证点

| 验证 | 期望 |
|------|------|
| **问卷敏感度** | **v2** 随 **全 A / 全 B / 正常** 变化幅度 **大于** **v1 `finalScore`** 的窄幅波动。 |
| **v1 不变** | **`MatchResult.finalScore`**、**`candidateUserId`**、**`reasonSummary` v1 句式** 保持既有行为。 |
| **RRM** | **不改 v2**、**不改 `candidateUserId`**；**`displayCandidateUserId`** 仍由 **resolver** 决定。 |

| 阶段 | UI 建议 |

## 8. 与 Feedback `decisionContext` 的关系（M6.1）

建议在 **M6.1** 的 **`decisionContext`**（或等价 payload）中 **结构化记录**（具体字段名以实现为准）：

- **`finalScoreV1`**（或 **`matchResult.finalScore`**）  
- **`relationshipProfileScore`**（v2 核心 / worker shadow）  
- **`scoreBreakdown`**（v1 四分量，可与 worker 写入的 shadow **交叉校验**）  
- **`displaySourceType`**  
- **`candidateUserId`**（MatchResult 静态胜者）  
- **`displayCandidateUserId`**（展示对象）  
- **RRM active / env 门闸**（只读标记，便于分层分析）  
- **feedback 目标**（喜欢 / 不喜欢 / 跳过 等）

**目的**：评估 **v2 是否比 v1 更能对齐用户主观反馈**，并支持 **争议工单回放**。

## 10. 下一步实现建议

### M6.0-E（worker + 持久化 JSON + API 读取优先级）

1. 在 **`matching-score.ts`** 旁新增 **`computeScoreShadowM60`**（命名示例）：输入与 **`computeFinalScoreV1`** 相同上下文，输出 **`{ finalScoreV1, relationshipProfileScore, scoringVersion }`**（**`relationshipProfileScore`** = **`computeProfileScore`** 结果）。  
2. 在 **`batch-match.processor.ts`** 写 **`MatchResult`** 时，将 **`scoreShadow`** 合并进 **`matchInsights`**（**浅合并** / **不可破坏** 现有 `buildMatchInsightsPlaceholder` 结构 —— 实现时定 **深度合并策略**）。  
3. **API**：**`GET /matching/result`** 的 **`relationshipProfileScore`** 优先从 **`matchInsights.scoreShadow`** 读取；**缺失时 fallback** 到 **`buildRelationshipProfileScoreShadow(scoreBreakdown)`**（M6.0-C）。  
4. **前端**：**FinalMatchPage** 继续展示「关系画像适配度」；**数据来源切换** 以 API 为准（**可不改 UI 文案**，仅换数据源）。

### M6.0-F（run records / 回归）

- 固化 **种子用户 + 池配置** 的 **run record**（文档或 CI artifact）。  
- 跑通 **全 A / 全 B / 正常** 与 **RRM on/off**；确认 **v2 区分度** 与 **v1 不变量**。
