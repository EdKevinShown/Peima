## 3. 本地匹配执行摘要

维护者按顺序执行（占位符仅作说明，勿将真实 ID 写入版本库文档）：

1. **Viewer**：确认目标 viewer 问卷 / `user_profile` 完整。
2. **池与候选**：确认存在 active preview pool，且候选具备可用 profile。
3. **入队**：通过 API 或 DB 插入一条处于 waiting 的 `batch_match_queue`（或项目约定等价路径）。
4. **Worker**：在 `apps/worker` 下使用已构建产物与本地 `.env` 执行，例如：  
   `node --env-file=..\..\..env dist\main.js --batch-match`  
   （路径随仓库根目录 `.env` 位置调整。）
5. **批次**：确认对应 `match_batch` 的 `successCount` 等符合预期（例如 `successCount = 1`）。
6. **MatchResult**：对最新一条 `match_results` 做第 4 节 SQL 核对。

**本记录登记环境说明**：在自动化登记 Build 时，曾尝试 `node dist/main.js --batch-match`；若遇 `ERR_MODULE_NOT_FOUND`（例如 shared `types` 扩展名解析），以维护者本机实际可运行的启动方式为准（必要时用 `tsx` / monorepo 约定入口），**不改变 R3 业务结论**：R3 代码路径以 **worker 测试 + 本机构建** 为基线，DB 冒烟为增量确认。

## 5. `rrmV2Top2Selector` 字段检查

对 `matchInsights->'rrmV2Top2Selector'` 的 JSON 逐项核对（维护者本地记录，**不**写入本文）：

| 字段 / 组 | 预期 |
|-----------|------|
| 存在性 | 键存在且为 object |
| `version` | `m6.0-rrm-v2-top2-selector-shadow-v1` |
| `eligible` | `true` 或 `false`（至少两人合法 V2 时为 `true`） |
| `reason` | `ok` \| `not_enough_valid_v2_candidates` \| `invalid_score_shadow_v2`（**无**旧 R2 的 `top2_below_min_score` / `top2_gap_too_large`） |
| `selectedTop2` | 数组长度 **≤ 2**；`eligible === true` 时长度 **恰好 2** |
| `top1CandidateUserId` / `top2CandidateUserId` | 与 `selectedTop2[0]` / `[1]` 的 `candidateUserId` 一致 |
| `top2Gap` | 为 `number` 或 `null`（不足两人时 `null`） |
| `contextFlags` | 含 `top2GapLarge`、`hasLowBand`、`hasStrongConflictBand`、`anyBelowSuggestedFloor` |
| `thresholds` | 含 `suggestedFloorDisplayScore100`、`largeGapThreshold` |

**与 R3 设计一致的不变量**：

- `low` / `strong_conflict` / 分差大 / 低于建议分 **只**体现在 `contextFlags`，**不**单独作为 `reason` 阻断。
- 未调用 RRM；`displayCandidateUserId` 不由本 worker 路径改写（若列为 `NULL` 属既有 schema/业务状态，非 R3 写入）。
