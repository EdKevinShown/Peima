# P5：治理与历史化（Analytics / 建议中心 / 运营工具）— 规划

> Status: Historical / Archived
> **状态说明**：**历史规划/背景文档**。本文成文时用于规划 P5；当前仓库中 P5 关键能力（RBAC、建议中心、审计日志、通知中心、分析仪表板）已落地，当前实现状态以 `README.md` 与 `docs/P5/*COMPLETION*` / `docs/P5/*DELIVERY*` 文档为准。  
> **前置**：P0～P3 已完成；P4（若执行）以 **用户端体验收口** 为主，P5 转向 **数据可追溯、权限与运营效率**。

---

## 1. 标题

**P5 — 治理与历史化**：围绕 **摘要 / Copilot / 建议 / 信号** 等已落库或可落库数据，建立 **版本与审计可读性**，补强 **Analytics**，并引入 **轻量后台或运营工具**（可与 `apps/admin` 或独立路由共存），**仍不** 承诺生产级多租户 SaaS。

---

## 2. 本阶段定位

P2 已写入 `conversation_summaries`、`profile_update_suggestions` 等；业务上很快会出现 **「哪一版摘要曾展示给用户」**、**「建议从哪次会话产生」** 等问题。P4 不解决 **跨时间维度** 的治理；P5 专门承接 **历史、审计、统计口径、内部可见工具**，与 P4 的「同一屏体验」、P6 的「模型生产」划界。

---

## 3. 与前一阶段的关系

| 阶段 | 关系 |
|------|------|
| **P4** | P4 收 **端上体验**；P5 在 **服务端与后台** 增加 **查询维度**（时间范围、版本、操作人），**可依赖** P4 稳定后的前端入口链接到「我的历史」（若产品需要）。 |
| **P3** | 时间线 **只读聚合** 保持；P5 若增加 **服务端历史 API**，应 **不破坏** P3 已有 `GET .../timeline` 契约，可 **新增** 独立路径或查询参数（需评审）。 |

---

## 4. 本阶段核心目标

1. **可追溯**：关键用户可见文案（摘要快照、建议状态变更）在库表或日志层面 **可回答「何时、何版本」**。  
2. **可运营**：内部角色能以 **受控方式** 查看聚合指标、异常会话、建议积压（不等同于完整 BI）。  
3. **权限清晰**：延续 P2.5 **白名单** 思路，扩展为 **可文档化的 RBAC 或等价机制**（不必一次到位到企业 IAM）。  

---

## 5. 建议纳入范围（做什么）

- **摘要 / Copilot 相关历史（若产品要）**：只读列表或时间轴 API；**不** 默认改变当前「最新一条」的读取逻辑，除非显式迁移策略。  
- **建议中心（产品形态）**：独立页或 admin 子模块，**列表 + 筛选 + 状态**；与现有 accept/dismiss **共用** 后端契约或薄封装。  
- **Analytics**：在现有 `p2-overview` 基础上 **增加维度或缓存策略**（需防刷与隐私边界）；全局大盘 **RBAC** 从 env 白名单 **演进** 为可配置数据源（设计待定）。  
- **审计日志（轻量）**：对敏感操作（全局 overview、建议批量操作）记 **append-only** 或等价轨迹。  
- **文档**：数据保留策略、统计口径说明（可放 `docs/P5`）。  

---

## 6. 明确不纳入范围（不做什么）

- **不** 在本阶段 **用模型重写** 摘要或 Copilot 生成逻辑（归 **P6**）。  
- **不** 承诺 **完整数据仓库 / 实时数仓**、**多区域合规认证**。  
- **不** 替代 P4 的 **聊天内体验优化**；若仅为改文案，应 **回退到 P4** 或 hotfix。  
- **不** 改变 P0 **核心聊天** 的 **最小可用契约**（发消息、会话列表）除非单独重大版本说明。  

---

## 7. 预期产出物

- Prisma **迁移**（若新增历史表或审计表）+ API + **可选 admin/web** 页面。  
- `docs/P5/` 下 **口径说明**、**权限矩阵草稿**、**验收 checklist**。  
- README 状态更新（由实施 PR 完成）。  

---

## 8. 验收口径 / 完成标准

- **权限**：非授权用户 **无法** 访问全局/敏感接口（自动化或手动用例）。  
- **历史**：至少一条 **端到端** 场景：生成摘要 → 列表中可见多条记录或版本标识（以最终设计为准）。  
- **回归**：P2.5 个人 overview、P3 时间线、P4（若已交付）核心路径 **仍通过**。  

---

## 9. 主要风险与依赖

| 风险 / 依赖 | 说明 |
|-------------|------|
| **隐私与合规** | 历史与审计 **放大** 数据暴露面；需 **最小必要** 字段与保留期。 |
| **存储成本** | 摘要/信号追加频繁时，需 **归档或 TTL** 策略（可与运维协同）。 |
| **admin 定位** | `apps/admin` 若长期占位，需决定 **合并到 P5** 还是 **独立部署**，避免双轨。 |

---

## 10. 推荐实施顺序

1. **数据模型评审**：哪些实体要版本化、哪些仅审计日志即可。  
2. **权限模型**：从白名单扩展到 **角色或 scope** 的最小实现。  
3. **只读历史 API + 最小 UI**。  
4. **Analytics 增量 + 文档**。
