## 1. 当前现状

> **P6.12 已落地**后的能力与验收见文首 **「实现状态与接口验收」**；下表为 **P2 / P4 期**基线描述，用于对照演进。

仓库内已存在 **P2 结构化反馈主链**：

| 能力 | 说明 |
|------|------|
| `POST /feedback` | 鉴权后写入 `UserFeedback`；`userId` 必须与 JWT 用户一致。 |
| `GET /feedback/mine` | 当前用户最近 **200 条**反馈，按 `recordedAt` 降序。 |
| `UserFeedback` 表 | P6.12 起含可选 **`structuredPayload`（Json）**；并含 `subjectKind` / `subjectId` / `sourceType` / `sourceVersion` / `rating` / `tags` / `comment` / 时间戳等。 |
| **P6.12 前**无结构化列时 | 聊天侧**仅**能通过 `rating`（1–5）、`tags[]`、`comment` 表达。 |
| `ChatPage` | P6.12 起默认带 **P6.12 量表** + `p6.12-chat-feedback-structured-v0`；旧 P4 路径仍可不带 `structuredPayload`。 |
| 只读消费 | **Copilot**（同会话的 `rating` 聚合）、**关系时间线**（反馈事件）、**Analytics**（计数等）读 `userFeedback`；**不**进入匹配主链。 |

**历史缺口（已由 P6.12 列与契约缓解）**：具名、可版本化的多维度量表，现落库于 `structuredPayload` v0。

## 2. 本轮目标（P6.12 v0）

1. 在**不改变**主匹配公式与排序**语义**的前提下，为「聊天后反馈」增加 **v0 结构化 payload** 的**数据与产品契约**（以 JSON 子文档形式存于表内）。  
2. 聊天场景统一 **`subjectKind = conversation`**、**`subjectId = conversationId`**。  
3. 通过 **固定 `sourceVersion`** 识别 P6.12 结构化记录，与旧版（如 P4 post-chat action hub）可区分、可混跑分析。  
4. 为后续 `ChatPage` 最小 UI、DTO 校验、Copilot/时间线/报表扩展提供**单一真源**说明。

**说明**：本 spec 批准后的**实现**可包含：Prisma 字段、`CreateFeedbackDto` 可选字段、前端表单；**但上述实现不在本「仅写文档」变更范围内**。

## 4. 数据契约（v0）

### 4.1 表与字段（规划）

- **`UserFeedback.structuredPayload`**：类型 **`Json?`**，**可空**；有值时须满足本文 **§5、§6** 的 v0 形状与版本。  
- **实现侧注意**：`NULL` 表示「无结构块」= 与旧 P4/仅星级+文本记录兼容。

### 4.2 主体与引用

| 字段 | 值（聊天闭环 v0） |
|------|-------------------|
| `subjectKind` | 固定 **`conversation`** |
| `subjectId` | **`conversationId`**（与 `Conversation` 主键一致） |
| `sourceVersion` | 固定 **`p6.12-chat-feedback-structured-v0`**（本条 spec 的识别锚点；若子版本仅扩展可选键，可后续 bump 为 `…-v0.1` 等，由实现约定） |
| `sourceType` | 见 **§4.3** |

### 4.3 `sourceType` 取值推荐：`hybrid` 与 `rule_based` 二选一

`P2SourceType` 现网枚举为：`rule_based` | `template_based` | `placeholder` | `hybrid`。

| 取值 | 推荐场景 |
|------|----------|
| **`rule_based`** | 表单项、取值范围**完全**由产品 + 前后端**固定规则**校验、无中间 LLM 参与生成。P6.12 **默认推荐**：采集路径明确、可测试、可审计。 |
| **`hybrid`** | 若未来在**同一次提交**中混入**模板 + 非生成式逻辑以外的辅助**（例如预填文案仍由规则产生，但来源标记为混合管线），**或**与「模板化问卷页」强绑定且希望与纯规则区分。 |

**P6.12 v0 建议**：在**无 LLM 参与采集**的落地实现中，**优先 `rule_based` + `sourceVersion: p6.12-chat-feedback-structured-v0`** 即可；若产品坚持将「多维度量表」视为与纯星级不同的 `hybrid` 产品语义，**允许**用 `hybrid`，但须在分析侧按 `sourceVersion` 为主键，避免仅依赖 `sourceType` 区分 P6.12 与别模块。

**不推荐**：为结构化反馈单独引入未在 `P2SourceType` 中的新值（需改 shared 常量，超出本 spec 的「只写文档、不改代码」的当前变更范围；若需要，在实现阶段另开任务）。

### 4.4 与 `match` 的关系

- `subjectId` **仍**为 `conversationId`（v0 **不**改为 `match` 作为主 subject）。  
- 可选与某次 `matchResult` 的关联**放在 `structuredPayload` 内**（`matchResultId` 可选，见下节）。

## 5. `structuredPayload` v0 示例

下列为**逻辑示例**；实际存储为 JSON 对象，键名与类型以 §6 为准。

```json
{
  "schemaVersion": 1,
  "kind": "p6.12_conversation_v0",
  "conversationId": "cxxxxxxxxxxxxxxxx",
  "matchResultId": "mxxxxxxxxxxxxxxxx",
  "targetUserId": "uxxxxxxxxxxxxxxxx",
  "overallRating": 4,
  "continueIntent": 3,
  "comfortLevel": 4,
  "replyQuality": 3,
  "safetyFeeling": 4,
  "awkwardness": 2
```

**无终局/无对端信息**时的最小可提交示例（仅填必填 + 不 optional）：

```json
{
  "schemaVersion": 1,
  "kind": "p6.12_conversation_v0",
  "conversationId": "cxxxxxxxxxxxxxxxx",
  "overallRating": 4,
  "continueIntent": 3,
  "comfortLevel": 4,
  "replyQuality": 3,
  "safetyFeeling": 4,
  "awkwardness": 2
```

## 6. 字段说明、取值范围、是否必填

### 6.1 元数据

| 键 | 类型 | 必填 | 取值 / 说明 |
|----|------|------|-------------|
| `schemaVersion` | 整数 | **是** | 与 JSON 结构演进同步；v0 固定为 **`1`**。 |
| `kind` | 字符串 | **是** | 固定 **`p6.12_conversation_v0`**，用于解析器分支。 |
| `conversationId` | 字符串 | **是** | 须与**表级** `subjectKind`+`subjectId` 中针对本次会话的 `conversationId` **一致**；实现层应在写入前校验，避免错绑。 |
| `matchResultId` | 字符串 / null | **否** | 当用户自「终局匹配页」等入口进入且已知 `matchResultId` 时填写；**不得**与 conversation 的参与者关系冲突（实现侧可做弱校验或仅信前端）。未进入终局链路的聊天可为 `null` 或省略。 |
| `targetUserId` | 字符串 / null | **否** | 被评价/感受对象（通常为**对方**用户 id）；不展示给对方，**仅**用于内部分析与防串会话。无则 `null` 或省略。 |

### 6.2 量表维（v0 统一 1–5 整数标度）

**约定**：数值越大表示该维度**越正面 / 越舒适 / 越安全**，**`awkwardness` 相反——数值越大表示越尴尬/越不自然**（与「舒适度」可独立采集）。若产品后续改为 1=更尴尬，须 bump `schemaVersion` 或 `kind`。

| 键 | 必填 | 范围 | 含义（用户向） |
|----|------|------|----------------|
| `overallRating` | **是** | 1–5 | 本次聊天**总体**感受（与现有表字段 `UserFeedback.rating` 应对齐：见 **§7**）。 |
| `continueIntent` | **是** | 1–5 | **继续聊下去**的意愿；**整数量表**，非 yes/maybe/no 枚举。 |
| `comfortLevel` | **是** | 1–5 | **与 TA 交流时的整体舒适度**。 |
| `replyQuality` | **是** | 1–5 | **对对方回复质量**的主观感受。 |
| `safetyFeeling` | **是** | 1–5 | **安全感/心理安全**（非技术「内容安全」标签）。 |
| `awkwardness` | **是** | 1–5 | **尴尬/不自然**程度；分越高越尴尬。 |

**校验**：各键必须是 **整数** 且在 **1–5** 闭区间内；`structuredPayload` 存在时，上述键**全必填**（与「最小闭环」一致；若未来允许「跳过一题」再 bump 版本）。

## 7. 与现有 `rating` / `tags` / `comment` 的关系

| 列 | 与 `structuredPayload` 的约定（v0） |
|----|--------------------------------------|
| **`rating`** | 与 `structuredPayload.overallRating` **必须一致**（避免排名/列表展示与细项矛盾）。**实现**应在服务端若收到两者则校验相等，或**仅**写 `structuredPayload` 后由服务层**同步** `rating = overallRating`。只写其一且另一默认的做法需在实现 PR 中写清。 |
| **`tags`** | 可继续用于入口标记。建议：P6.12 提交时增加可识别 tag，如 **`p6.12_structured_v0`** 或继续沿用 `post_chat_action_hub` 并**完全**依赖 `sourceVersion` 区分；推荐**至少**用 **`sourceVersion`** 作为分析主键。 |
| **`comment`** | 仍为**选填**自由文本；**不**用于解析结构化维度。`structuredPayload` **不**替代 `comment`；二者可同时存在。 |

**Copilot / 时间线 / Analytics**  
当前多处以 **`rating` + `subjectKind` + `subjectId`** 为主；v0 落地后，只读服务可逐步「优先读 `structuredPayload` 中的维度**用于展示或聚合**」，**或**在过渡期仍用 `rating` 保持兼容。本 spec 要求**不得**因新增 JSON 而破坏只读 SQL 的既有行为：未迁移的旧行仍只有 `rating`/`comment`。

## 8. 前端 `ChatPage` 最小 UI 方案（v0）

**目标**：一屏内可完成、单提交，与 P4 星级+备注**不冲突**（见 §10）。

- **主区**：5 个 **1–5 量表**（可用分段按钮/滑条/radio 行）对应 `continueIntent`、`comfortLevel`、`replyQuality`、`safetyFeeling`、`awkwardness`；**总体**可单独一题或从「与 overallRating 同一控件」二选一。  
- **总评**：`overallRating` 单独控件，或与现「评分」区合并，但须与行内存 state 和提交 JSON 一致。  
- **可选文字**：保留「备注」= `comment`（选填）。  
- **上下文**：若路由或父组件传入 `matchResultId` / 对方 `userId`，写入 optional 字段；**无**则省略。  
- **提交**：`POST /feedback` 与现相同路径；在实现阶段请求体带 **`structuredPayload`**（见 §9），`sourceVersion = p6.12-chat-feedback-structured-v0`，`sourceType` 按 **§4.3** 选定。  
- **隐私提示**：轻量文案如「**仅用于改进体验，对方不会看到**」（与 **§3** 非目标一致）。

不强制在本期做设计系统大改；以现有内联/朴素控件为主即可。

## 10. 兼容旧 P4 feedback 的策略

| 类型 | 特征 | 读侧行为 |
|------|------|----------|
| **旧** | `sourceVersion` 为 `p4-post-chat-action-hub-v1` 等，**`structuredPayload` 为空** | 与现网完全一致；展示「星级 + 备注」；**无** 6 维量表。 |
| **新** | `sourceVersion = p6.12-chat-feedback-structured-v0`，**`structuredPayload` 有值** | 展示/分析以 JSON 为主；`rating` 与 `overallRating` 应一致。 |
| **混库** | `GET /feedback/mine` 同时返回新旧行 | 前端可按 `sourceVersion` 或 `structuredPayload == null` 决定渲染**简化卡**与**量表卡**。 |

**不迁移旧数据**（除非运营单独提需求）：旧记录保持不动。

**重复提交**（同用户、同 conversation 多次 feedback）：现网**未**在 spec 层禁止；产品可约定「仅一条最新」或「允许多条」时间序列；若需幂等/更新，在实现或后续 spec 中定义，**v0 本文件不强制**。
