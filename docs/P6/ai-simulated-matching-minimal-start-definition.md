# AI 模拟匹配 — 最小起步定义草案

> **前置依据**（视为已落盘、可引用）：  
> - 《P6.8 / P6.10 最小系统回归 — 执行记录（2026-04-21）》所验证的 **M0–M5 主链事实**；  
> - 《进入 AI 模拟匹配前 — 边界说明草案》所钉定的 **主链边界与语义风险**（含：正式结果写入口 / 对照输出分流、`sourceType`/`sourceVersion` 误读风险、空队列语义等）。  
>  
> **本文性质**：**下一阶段「最小起步」的范围与验收定义**；**不**展开实现细节（无代码、无算法、无数据表字段级设计）。

---

## 1. 下一阶段最小目标是什么

在**不破坏**已验证的 **Final match 主链**（`preview-pool` → `enqueue` → `worker batch-match` → **`GET /matching/result/:userId`** → **Final Match 页**）前提下，引入 **「AI 模拟匹配」的最小可见增量**，使得团队能在真实联调环境中回答一个问题：

> **在同一 viewer、同一套正式结果仍存在的前提下，AI 模拟输出以何种「只读对照」形态出现，且不会被默认理解为正式匹配结论？**

换言之：**先做到「能看见、能对照、能关断、不误认」**；不在本最小目标内追求 **替换规则引擎、改写正式落库语义、或完成全量 AI 匹配产品化**。

---

## 2. 明确不做什么（本最小起步之外）

下列事项**明确不在**本最小起步范围内（避免范围蔓延与回归口径漂移）：

- **不**把 AI 模拟输出默认写入与 **正式 `match_result` / 正式匹配结论** 同一语义层（除非另行通过边界说明升级决策并完成独立回归）。  
- **不**以本最小起步为由，改写 **预览池生成规则、enqueue 队列状态机、worker `batch-match` 既有成功路径** 的「已验证行为」；**不**将 **M5 空队列（`totalQueues=0`）** 重新定义为失败。  
- **不**在本最小起步内补齐 **P6.8 `dismiss` 全路径**、**429 事前拦截** 等本轮未覆盖项（可作为后续独立增量，但不阻塞本起步的「可见对照」）。  
- **不**在本最小起步内展开 **AI 模拟匹配的完整技术方案**（模型选型、训练、打分公式、全量观测体系等）。  
- **不**把「最小起步交付」等同于「AI 匹配已上线」：对外与验收口径必须仍能以 **规则/占位主链** 为 **正式真值来源**。

---

## 3. 建议先落在哪个接入点（只选一个）

**唯一接入点（第一步）**：**`GET /matching/result/:userId` → Final Match 页的「读取与展示链」**。

解释口径（仍不写实现细节）：

- 以 **读取链** 作为第一步承载 AI 模拟对照信息（例如：与正式结果 **并置**、**默认折叠/默认关闭**、**显式标注为模拟/对照** 等——具体形态由实现阶段决定，但**语义归属**必须先落在「读取侧的可选增量」上）。

---

## 4. 为什么这个接入点最适合作为第一步

1. **与已验证主链天然对齐**：M1 已证明 **`GET /matching/result/:userId` → Final Match** 是稳定、可复述、可对照用户感知的闭环；在此链路上增加「**可选**」增量，**最不依赖**新一轮队列造数即可被看见与验收。  
2. **最贴合边界说明的核心风险**：边界说明强调必须避免 **「模拟结果与正式结果混淆」**；把第一步放在 **读取/展示链**，最容易做到 **「正式真值不变、模拟信息可分离」** 的产品语义。  
3. **对写入路径的侵入最小**：最小起步优先避免在 **worker 写库路径** 或 **enqueue 状态机** 上「第一步就改语义」，从而降低对 **M1/M5 队列语义** 的误伤概率。  
4. **验收成本低、证据链清晰**：验收可以直接复用本轮已固定的 **API 基址、端口、VITE 指向、viewer** 与 **Final Match 可读** 事实；新增部分以 **「是否误读为正式」** 为红线做肉眼与字段级核对即可。

---

## 5. 最小验收标准是什么

> 下列标准为 **「最小起步完成」** 的必要条件；**不**声称覆盖 AI 模拟匹配全主题。

### 5.1 主链不被破坏（回归底线）

- 在 **AI 模拟对照能力关闭**（或默认不展示）时，`POST /preview-pool/generate`、`POST /matching/enqueue`、**worker `batch-match`**、`GET /matching/result/:userId`、Final Match 页的 **既有通过口径** 仍可复现为 **通过**（允许数据不同，但不允许「正式读取语义」无理由改变）。  
- **空队列复验语义**仍遵循边界说明：**`totalQueues=0` 且正常结束** 不得被重新解释为失败。

### 5.2 对照可见且不混淆（产品语义底线）

- 在 **开启对照展示** 的验收场景中，用户能在 **Final Match（及/或同链路的 API 响应）** 同时看到：  
  - **正式匹配结论**（仍以本轮已验证的 `matching/result` 与页面口径为准）；  
  - **AI 模拟对照信息**（必须带可区分的 **来源/版本语义**，与 P6.8 已强调的 `sourceType`/`sourceVersion` 思路一致：**不得**让人默认把模拟块当作正式结果）。  
- **验收红线**：在对照信息存在时，**不得出现**「页面或字段层级上把模拟输出展示为唯一/默认的最终匹配结论」的歧义（以产品可读性与字段标注为准，具体 UI 细节由实现阶段落实）。

### 5.3 可关断与可排障（工程底线）

- 对照能力必须具备 **明确开关/环境闸**（名称与默认值由实现阶段定义），使得联调失败时能快速判断：问题来自 **AI 侧配置** 还是 **正式主链**（延续边界说明中「避免误判」的目标）。

### 5.4 可关闭后回到纯正式口径

- 当 AI 模拟对照能力关闭时，Final Match 页与 `GET /matching/result/:userId` 的表现应回到本轮已验证的规则/占位口径，**不残留模拟信息，不改变正式结果读取语义**。
