## 1. 必测项（Must）

> 下列每一项 **未通过** 则本阶段 **整体不通过**。证据列写 **可复现步骤 + 观测点**（不必贴密钥）。

### 1.1 后端权威 — R1（无新消息不得再生成）

| # | 验收点 | 最小操作 | 通过判据 | 证据记录 |
|---|--------|----------|----------|----------|
| B1 | 无新消息连续生成 | 固定 `conversationId`，在无新聊天消息的前提下，连续触发「生成画像建议」**至少 2 次** | **第 2 次起**请求被 **稳定拒绝**（非未定义 500）；响应或全局错误处理中有 **可区分「无新消息」** 的说明（措辞实现自定，须可读） | 第 1/第 2 次 status + 错误摘要 |
| B2 | 与既有 pending 409 的关系 | 先制造 **pending 未决**，再触发生成 | 仍符合草案 §F-6：**已有 pending** 时不可再生成（与本轮既有行为一致或可更强，但 **不得** 静默成功出第二条 `pending`） | pending 条数 / status |

### 1.2 后端权威 — R2（同一增量不重复多条 pending）

| # | 验收点 | 最小操作 | 通过判据 | 证据记录 |
|---|--------|----------|----------|----------|
| B3 | 连点 / 双开竞态 | 在一次「新消息批次」后，**快速连续**或 **两标签页同时** 触发生成 | **至多一条** `pending` 可被用户视为该增量轮次结果；**不得**出现两条并存的等价 `pending`（以 DB 或 `mine` 列表为准） | `mine` 中 `pending` 条数；必要时 DB 截图说明 |
| B4 | 与 R1 一致 | 无新消息时重复触达 | 与 B1 同结论，且不绕过 R1 | 引用 B1 记录即可 |

### 1.3 后端权威 — R3（状态与消息增量可追溯）

| # | 验收点 | 最小操作 | 通过判据 | 证据记录 |
|---|--------|----------|----------|----------|
| B5 | 每条建议可回答「相对哪条消息快照」 | 对 **新建** 与 **已决** 各抽 1 条（若仅有 pending 则两条均测 pending 生命周期前后） | 数据层可查 **cursor 或等价字段**（草案 §C 推荐语义）；`GET .../mine` 或详情响应中 **至少一处** 对客户端可证（实现可选是否暴露给 UI） | 字段名 + 示例值（可打码 id） |

### 1.4 后端权威 + 前端 — R4 / R5（可读摘要与 accept 前可理解）

| # | 验收点 | 最小操作 | 通过判据 | 证据记录 |
|---|--------|----------|----------|----------|
| B6 | 默认展示非 patch | 打开 Chat 待处理建议区（**不展开**任何「高级/调试」区） | **不得**仅以裸 `proposedPatch` JSON / 内部 code 结构作为 **唯一** 信息；须见 **≥2 条** 要点级可读说明（草案 §F-4） | 截图或文案摘录 |
| B7 | 与 patch 同源 | 对比 **摘要载荷** 与 **`proposedPatch`（调试区或 API）** | 二者 **无矛盾**（同源派生，草案 §E-2、§D） | 同一屏或同响应内对照说明 |
| B8 | accept 前两问可答 | accept 前默认同屏 | 可见 **将影响的维度/分支** + **接受后的高层取向**（草案 §F-5）；不要求长文 | 截图或要点列表 |
| B9 | accept 后一致 | 执行 accept | 实际画像变更与 accept 前说明 **不矛盾**（草案 §F-5） | accept 前后各一行说明 |

### 1.5 回归 — 不破坏既有 P6.10 / pending 409

| # | 验收点 | 最小操作 | 通过判据 | 证据记录 |
|---|--------|----------|----------|----------|
| B10 | P6.10 禁用态 | 存在 `pending` 时看生成按钮与说明行 | 仍：**不可重复点击** + **单行说明**（与既有产品一致，草案 §F-6） | 截图或原文 |
| B11 | 既有 pending 冲突 | 同会话同 `sourceVersion` 已存在 pending 时再生成 | **不得** 静默成功第二条；行为与既有 **409 语义** 一致或可文档化升级，但不得弱化为 200 双 pending | status + body 摘要 |

## 3. 后端权威规则（实现必须遵守）

> 与草案 §D **底线**一致：**凡「允许/禁止再生成」「是否写入画像」一律后端权威。**

| 编号 | 规则陈述 | 验收映射 |
|------|------------|----------|
| BR1 | **无新消息**（相对已持久化的消息 cursor）→ **禁止**再次成功生成 P6.8 建议 | B1 |
| BR2 | **同一对话增量窗口**内 → **不得**多条实质等价 `pending` | B3 |
| BR3 | 每条建议须 **可查询** 其生成所基于的 **消息快照 / cursor**（语义见草案 §C） | B5 |
| BR4 | 响应须含 **审阅用摘要载荷**，与 `proposedPatch` **同源派生** | B6、B7 |
| BR5 | **accept 前** 摘要须与 **实际 apply** 一致（核心字段后端给出） | B8、B9 |
| BR6 | **不削弱** 既有「同会话 pending 409」与 P6.10 体验 | B2、B10、B11 |
