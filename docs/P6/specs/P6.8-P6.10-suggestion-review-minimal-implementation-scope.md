# P6.8 / P6.10 建议生成与审阅规则收口 — 最小实现范围说明

> **依据**（仅以下两份已落盘文档，不引入其它范围）：  
> - `docs/P6/P6.8-suggestion-generation-review-minimal-rules-draft.md`（下称「规则草案」）  
> - `docs/P6/P6.8-P6.10-suggestion-review-minimal-acceptance-checklist.md`（下称「验收清单」）  
>  
> **主线**：**唯一**阶段 —「P6.8 建议：消息增量绑定 + 审阅可读摘要（最小规则收口）」。**不**并行展开 AI 模拟匹配或其它主题。

## 1. 这一小阶段最小要改哪些点

对齐规则草案 §C（R1–R5）与 §E（Must），实现侧 **最少** 需覆盖：

| 序号 | 改动点（能力级） | 对齐规则 |
|------|------------------|----------|
| P1 | **生成门禁**：在「无相对上次生成而言的新消息 / 新对话进展」时，**拒绝**再次成功生成 P6.8 会话画像建议 | R1 |
| P2 | **增量内单 pending**：在同一「消息增量窗口」内，不因连点、重试、多标签竞态产生 **多条**用户感知为同轮的 `pending` | R2 |
| P3 | **可追溯绑定**：每条 P6.8 建议与「生成时所依据的消息快照」之间关系 **可查询**（cursor 或等价物，语义见规则草案 §C） | R3 |
| P4 | **审阅摘要载荷**：生成（及/或查询）响应中提供 **与 `proposedPatch` 同源派生** 的可读摘要，满足默认审阅需要 | R4、R5 |
| P5 | **Chat 默认 UI**：默认区展示摘要；**patch/JSON** 降级为非默认路径（规则草案 §E-3、验收清单 FR1–FR2） | R4、§E |
| P6 | **回归保持**：不削弱「已有 `pending` 不可再生成」与 P6.10 禁用体验（规则草案 §F-6、验收清单 B2/B10/B11） | 回归 |

---

## 2. 哪些必须后端改

与规则草案 §D **底线**、验收清单 §3 **BR*** 一致，下列 **必须由后端实现并作为唯一权威**：

| 项 | 说明 |
|----|------|
| **生成允许/拒绝** | P1、P2：无新消息拒绝、同增量不产多条 `pending`；**不得**依赖仅前端拦截 |
| **cursor / 快照语义持久化** | P3：写入可查询存储（规则草案 §C 推荐语义；具体表/列名由实现定） |
| **409 / pending 冲突语义** | 保持或强化「同会话同版本已存在 `pending`」时的拒绝行为；**不得**弱化为 200 + 双 `pending`（验收清单 B11） |
| **摘要载荷生成与返回** | P4：摘要字段与 `proposedPatch` **同源派生**（规则草案 §E-2、§D）；保证与 **accept 实际 apply** 一致（验收清单 BR5、B9） |
| **错误语义** | 拒绝时返回 **可读、可区分** 的原因（验收清单 B1：非泛化 500） |

## 3. 哪些前端只做展示 / 禁用即可

对齐规则草案 §D「可仅前端」与验收清单 §4 **FR***：

| 项 | 允许范围 | 禁止 |
|----|------------|------|
| **摘要排版** | 列表、折叠、强调样式、与 accept/dismiss 同屏布局（FR4） | 把「是否允许生成」的唯一真相放在前端 |
| **patch 降级展示** | 「高级 / 调试」折叠；默认路径不依赖 JSON 可读（FR1–FR2） | 默认区仅 patch |
| **生成按钮辅助态** | 与后端错误/状态联动的禁用、提示文案（FR3）；P6.10 既有禁用 + 单行说明（B10） | 仅靠前端隐藏按钮绕过 POST |

## 4. 预计会动到哪些模块 / 文件类型

> 以下为 **按文档推导的改动面类型**，不指定具体文件名，避免超出「仅依据两份文档」的边界；实现时以仓库实际结构为准。

| 区域 | 文件 / 模块类型（预期） |
|------|-------------------------|
| **API — 会话画像生成入口** | 与规则草案 §E-1 所述 **`POST .../profile-completion-suggestion`** 同路径的 **Controller / Service** 一类文件；在其内或下游编排 **门禁 → LLM/映射 → 持久化** |
| **API — 建议域** | **Profile suggestion** 相关 **Service / Repository**：创建建议、重复校验、与 cursor 一并写入 |
| **API — 会话与消息读** | 用于判定「是否有新消息」「增量窗口」的 **只读查询**（依赖现有会话消息模型） |
| **数据持久化** | **Prisma schema + migration**（若新增 cursor 或关联字段）；**禁止**仅靠内存态满足 R3 |
| **Web — Chat** | **Chat 页**及与 **画像建议 / 生成按钮** 绑定的 **组件/样式**；默认展示摘要、调试区折叠 |
| **Web — API 客户端** | 与 profile-completion、`mine` 响应解析相关的 **TS/JS API 封装**（若响应结构扩展） |
| **文档** | 本阶段范围内 **已实现行为与验收清单 B# 的映射备注**（可选记在本文「修订记录」或 PR 描述；规则草案 §E-4 所指「一页」已由验收清单承担时可只交叉引用） |

## 5. 哪些明确不动

对齐规则草案 §B「不做」、§E「不在范围内」及验收清单 §2 **N1–N6**：

| 类别 | 明确不动 |
|------|-----------|
| **产品主题** | **AI 模拟匹配** 任一步实现（验收清单 N1） |
| **匹配主链** | **Final match / preview-pool / enqueue / worker batch-match** 行为与契约改造（N2） |
| **问卷 / 模型** | 全问卷重构、新模型选型、训练、通用打分公式改造（N3） |
| **本阶段非必测** | 将 **`dismiss` 全路径**、**429 事前拦截**、`mine` 空集等作为 **本阶段通过门槛**（N4、N5） |
| **体验范围** | **长文自然语言**「完整改写简历」式生成（N6） |

## 6. 实现完成后如何按《验收清单》验收

按 `docs/P6/P6.8-P6.10-suggestion-review-minimal-acceptance-checklist.md` **顺序执行**：

1. **必测闭环（§1）**  
   - 依次执行 **B1 → B11**（B4 可引用 B1 证据，须在记录中注明）。  
   - 每条记录 **最小操作、通过判据、证据**（清单表格列）；**任一条失败** → 整阶段 **未通过**（清单 §5）。

2. **不测项守门（§2）**  
   - 确认 **N1–N6** 未被误并入本阶段「必须通过」集合（清单 §5 条件 2）。

3. **规则符合性核对（§3–§4）**  
   - 将实现与 **BR1–BR6**、**FR1–FR4** 对照；若有字段/文案差异，在验收记录 **备注** 写 **一行等价映射**（清单 §5 条件 3）。

4. **整轮结论**  
   - 仅当清单 §5 三个条件同时满足时，在验收记录表填：**整轮结论 = 通过**；否则填 **未通过** 并指向 **失败 B#**。
