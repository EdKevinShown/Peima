# P6.x — AI Match Review MVP

## 目标

在**不修改问卷打分算法**、**不落库**的前提下，为「当前登录用户 × 其最新 `MatchResult` 候选人」提供基于**双方问卷画像（`GET /questionnaire/profile` 同源数据）**的 **AI 匹配复审**：静态摘要 + 可选大模型结构化 JSON，失败时规则回退。

> **Worker 侧说明**：不改变 `computeFinalScoreV1` 等打分公式；仅增加**准入过滤**——预览池只选「有图 + 已有问卷派生 `user_profiles`」的用户，batch-match 跳过池中无画像的槽位，避免产生「最终匹配指向无画像候选人」而与复审接口冲突。

## 接口

- **方法 / 路径**：`POST /match-review-ai/review`
- **鉴权**：`Authorization: Bearer <JWT>`（与现有 matching 一致）
- **请求体**（仅此字段）：

```json
{ "candidateUserId": "<必须与当前用户最新 MatchResult.candidateUserId 完全一致>" }
```

- **成功**：HTTP **200**，body 见 `MatchReviewResponseDto`（实现于 `apps/api/src/modules/match-review-ai/match-review-ai.types.ts`）。
- **错误**：
  - 无 JWT：**401**
  - `candidateUserId` 与最新匹配结果不一致：**403**
  - 无 `MatchResult`：**404**（`MatchingService.getLatestResultForUser`）
  - 任一侧无问卷画像行：**404**（错误文案已区分 *viewer* / *matched candidate*，便于定位）

## 环境变量（独立前缀）

与 `MATCH_EXPLANATION_AI_*` 并列，见仓库根 `.env.example`：

- `MATCH_REVIEW_AI_ENABLED`
- `MATCH_REVIEW_AI_PROVIDER`
- `MATCH_REVIEW_AI_BASE_URL`
- `MATCH_REVIEW_AI_MODEL`
- `MATCH_REVIEW_AI_API_KEY`
- `MATCH_REVIEW_AI_TIMEOUT_MS`

关闭或未配 Key 时走**规则层**，`debug.fallbackUsed === false`（未尝试模型）；模型失败或 JSON 无效时 **`debug.fallbackUsed === true`**，`debug.sourceType` 为 `match_review_fallback_rule_based`。

## 前端

- **`FinalMatchPage`**：区块「AI 匹配复审（MVP）」；主展示 `aiReview` 的复审分、recommendation、strengths/risks、explanation、conversationPotential、longTermPotential。
- **调试信息**：折叠 `<details>` 内展示 `reviewStaticScore`、`matchResult.finalScore`、`sourceType`、`sourceVersion`、`fallbackUsed`、`meta.reason`。

## 上游准入：预览池 + batch-match（修复后事实）

复审依赖 **`QuestionnaireService.getProfileForUser`**，要求 **viewer 与 `MatchResult.candidateUserId` 双方在库中均有 `user_profiles`（问卷提交产物）**。下列上游已与之一致：

| 环节 | 行为 |
|------|------|
| **预览池生成**（`PreviewPoolService.pickSixCandidatesWithImages`） | 除「他人 + 至少一张图」外，还要求 **`relationProfile` 存在**（即有问卷画像行）。 |
| **batch-match**（`batch-match.processor.ts`） | **viewer** 无画像则该队列失败（`VIEWER_PROFILE_MISSING`）；**池内某一槽候选人**无画像则跳过该槽（`CANDIDATE_PROFILE_MISSING`），不参与排序与写库。 |

因此：**新产生的** active 池与**新跑批**写下的 `MatchResult`，其候选人应始终具备画像；历史脏数据（旧池/旧结果指向无画像用户）需按下文「主链验收」重新生成池并入队跑批。

## 本地主链验收操作清单（按顺序、可打勾）

以下为当前本地（Postgres + `pnpm dev:api` + `pnpm dev:web` + 可跑 worker）**推荐顺序**；数字为最少人数约束。

### 1. 测试数据准备

| 角色 | 最少人数 | 必须满足 |
|------|----------|----------|
| **Viewer（用户 A）** | **1** | 已注册、可登录（JWT）；**已完整提交问卷**，库中存在 **`user_profiles`**（与 `questionnaire_answers` 一致）；用于打开 FinalMatch 的 URL **`?userId=` 必须与 JWT 用户 id 一致**（否则 matching 接口 401）。 |
| **候选池用户（他人）** | **至少 6 人** | 每个为**不同于 A** 的用户；每人 **至少一条 `user_images`**；每人 **已提交问卷** 且存在 **`user_profiles`**。不足 6 人时「生成预览池」接口会 **400**（错误信息中含 `others_with_image_and_profile` 等计数）。 |

### 2. 推荐操作顺序（不要颠倒「池 → 队 → 批」）

1. **先补问卷与图**（若尚未满足上表）：优先保证 **6 个他人** 与 **A** 均有画像；缺图则先生成/上传图再生成池。  
2. **重新生成 preview pool**（对 A 调用现有「生成预览池」能力，使 active 池 6 槽均为「有图 + 有画像」用户）。  
3. **Enqueue matching**（A 入队 `batch_match_queue`，状态 `waiting`）。  
4. **跑 batch-match**（worker 或 admin 触发的一次性批处理，与当前环境一致）。  
5. **打开** `/final-match?userId=<A 的 id>`（已登录为 A），再点 **获取相处参考**（`POST /match-review-ai/review`）。

### 3. 每步成功时的现象

| 步骤 | 成功现象 |
|------|----------|
| 补数据 | DB：`users` + `user_profiles` +（池内用户）`user_images`；A 与 6 他人 id 可列出来。 |
| 生成预览池 | API **200**；返回的 pool items 共 **6** 条，每条 `candidateUserId` 指向的用户在 DB 中均有 `user_profiles`。 |
| Enqueue | **200**；`GET /matching/status/:A` 可为 `waiting` 或随后 `processing`/`ready`（依是否已跑批）。 |
| batch-match | worker 日志无整批致命错误；对应队列 **`matched`**；`match_results` **新增一行** `userId=A`。 |
| FinalMatch 页 | **200** 拉到 `GET /matching/result/A`；页面展示匹配指数等；**无**「暂无结果」类错误。 |
| 点击复审 | **200**，body 含 `aiReview`、`reviewStaticScore`、`staticSummary`、`debug`；若关 AI 则为规则层 `meta.reason` 等（见上文 checklist）。 |

### 4. 失败时优先怀疑哪一步

| 现象 | 最可能未满足的条件 |
|------|---------------------|
| 生成预览池 **400** / not enough candidates | **不足 6 个**「他人 + 图 + **画像**」；或只修了图未提交问卷。 |
| Enqueue **400** questionnaire | **A 未提交问卷** / 无 `user_profiles`。 |
| batch-match 后队列 **failed** / 无新 `MatchResult` | active 池为空；池内 6 人**全无画像**（应已被 worker 跳过导致无可选）；或 viewer 无画像（`VIEWER_PROFILE_MISSING`）。 |
| FinalMatch 拉结果 **404** | A **尚无**任何 `match_results`（未跑批或失败）。 |
| 复审 **404** `…viewer…` | **当前 JWT 用户**无画像或用户被删（与 URL userId 不一致时先 401，一般不会走到此条）。 |
| 复审 **404** `…matched candidate…` | **仍在使用旧 `MatchResult`**：候选人无 `user_profiles`；需 **重新生成池 + enqueue + batch-match** 得到新结果。 |
| 复审 **403** | body 里 `candidateUserId` **≠** `GET /matching/result/A` 返回的最新 `candidateUserId`。 |

### 5. 如何确认读到的是「新」`MatchResult` 而非旧脏数据

1. **看 DB（最准）**：`SELECT id, "candidateUserId", "createdAt" FROM match_results WHERE "userId" = '<A>' ORDER BY "createdAt" DESC LIMIT 1`；跑批前后对比 **`id` / `candidateUserId` / `createdAt`**，应出现**新行**或至少 **`createdAt` 更新为最近**。  
2. **看接口**：同一登录下 `GET /matching/result/<A>` 始终返回 **`findFirst` + `orderBy: createdAt desc`** 的一条；把响应当中的 **`id`、`candidateUserId`、`createdAt`** 与跑批前保存的对比。  
3. **看页面技术折叠**（若已实现）：`matchResultId` / `candidateUserId` 与上述接口一致；若候选人已换且无画像问题，复审应能通过。

## 本地验证建议

1. 准备 DB、迁移、登录用户 A，完成问卷；存在最终匹配结果且 `candidateUserId` 为 B；B 也有画像。
2. `MATCH_REVIEW_AI_ENABLED=0`：点击复审 → 应 200，规则文案，`fallbackUsed: false`，`meta.reason: disabled`。
3. 配置有效 Key 并 `ENABLED=1`：应可能 `model_ok`，`fallbackUsed: false`。
4. 故意填错 baseUrl：应 200 + fallback，`fallbackUsed: true`。
5. 传错误 `candidateUserId`：应 **403**。

## 手工验收 Checklist（真实环境逐项打勾）

**前置**：本地 Postgres 已迁移；`pnpm dev:api` + `pnpm dev:web`；浏览器已登录（JWT 写入与 `FinalMatchPage` 使用的 `userId` 一致）；用户 A 已完成问卷并有 `UserProfile`；存在**最新** `MatchResult(A→B)`；用户 B 也有问卷画像（否则无法测「成功路径」）。

### 正常成功路径

- [ ] 打开 `/final-match?userId=<A 的 id>`，页面能加载 `candidateUserId`、`finalScore` 等，无报错。
- [ ] 点击「生成 AI 匹配复审」，请求 `POST /match-review-ai/review`，body 为 `{ "candidateUserId": "<与页面一致的 B>" }`。
- [ ] HTTP **200**；响应含 `aiReview`（`finalScore`、`recommendation`、`strengths`、`risks`、`explanation`、`conversationPotential`、`longTermPotential`、`confidence`）。
- [ ] 主区域可读：复审分、中文档位、亮点/留意列表、说明正文段落舒适；**不依赖**展开「调试信息」也能理解大意。
- [ ] `strengths` / `risks` / `explanation` 读起来像**产品说明**（允许少量「问卷/维度」用语，但不应像 stack trace 或 JSON 键名列表）。

### disabled 路径（未开 AI）

- [ ] 设置 `MATCH_REVIEW_AI_ENABLED=0`（或 unset），**可保留** `MATCH_REVIEW_AI_API_KEY` 任意值；重启 API。
- [ ] 再次点击「生成 AI 匹配复审」→ **200**。
- [ ] 展开调试：`debug.fallbackUsed === false`，`debug.sourceType === "match_review_rule_based"`，`debug.meta.reason === "disabled"`（或与实现一致之 rule-only 原因）。
- [ ] 主展示仍为完整 `aiReview`（规则生成），页面不白屏、不报 500。

### missing key / 错 baseUrl 等 fallback 路径

- [ ] `MATCH_REVIEW_AI_ENABLED=1`，**删除或置空** `MATCH_REVIEW_AI_API_KEY`，重启 API → **200**，`debug.fallbackUsed === false`，`meta.reason === "missing_config"`（规则直出，未调模型）。
- [ ] 填有效 Key，`MATCH_REVIEW_AI_BASE_URL` 指向**明显错误**主机（如 `https://invalid.example.test`）→ **200**，`debug.fallbackUsed === true`，`debug.sourceType` 含 `fallback`；主展示仍为可读复审结论。
- [ ] （可选）超时：极短 `MATCH_REVIEW_AI_TIMEOUT_MS=1` → 应走 timeout fallback，**200** + `fallbackUsed: true`。

### candidateUserId 错误 → 403

- [ ] 在 DevTools 或临时改前端，对 `POST /match-review-ai/review` 传入与当前 `GET /matching/result/:userId` **不一致**的 `candidateUserId`。
- [ ] 期望 HTTP **403**，body 为 Nest 默认错误结构；**非** 500。

### 无 MatchResult → 404

- [ ] 使用**尚无** `match_results` 行的用户登录（或新注册用户仅问卷、未入队/未跑批）。
- [ ] 打开 Final Match 若本身会 404，则本项不适用；若页面能进，对复审接口：用有 JWT 但该用户无 `MatchResult` 时调用复审（可通过 curl + token）→ **404**。

### 一方无画像 → 404

- [ ] 构造：A 有匹配结果指向 B，但 **B 无** `user_profiles` 行（或删 B 的 profile 后测）；A 有画像。
- [ ] A 点击复审 → **404**，文案含 **`matched candidate`** / **regenerate preview pool**（或 viewer 侧缺画像时的 **`viewer`** / **logged-in user**）；**非** 500。

### FinalMatchPage 展示与层级

- [ ] **「匹配复审」主模块在「补充解读」之前**；主按钮、错误提示、主内容、**折叠的调试信息**层级清晰；调试区默认收起。
- [ ] 主展示以**中文**为主（匹配建议、潜力、可信度）；英文枚举若出现，仅为**小字对照**，不作为唯一标题。
- [ ] 「相处亮点」「需要留意」有简短引导语；「综合说明」为独立滚动区域，行高舒适、长文不撑爆整页。

### 回归（不破坏既有能力）

- [ ] `/questionnaire/profile/:userId` 与问卷画像页行为与改前一致。
- [ ] `GET /matching/result`、`match-explanation-ai` 行为未因本迭代改变；**Worker 批处理**仅增加无画像槽位跳过与预览池画像准入，不改变核心打分公式。

## MVP 收口总结

**P6.x — AI Match Review（MVP）** 已收口：在**不改变 worker 匹配打分公式、复审结果不落库**的前提下，为「当前登录用户 × 其最新 `MatchResult` 候选人」提供基于**双方问卷画像**（与 `GET /questionnaire/profile` 同源）的匹配复审——**静态摘要（`reviewStaticScore` 等）+ 可选大模型结构化 `aiReview`**；配置缺失、超时或模型返回无效 JSON 时**规则回退为预期路径**（`debug` 可区分来源与 fallback）。前端 **`FinalMatchPage`** 承载入口与展示分层。

**能力范围**：`POST /match-review-ai/review`（JWT；`candidateUserId` 须与最新 `MatchResult` 一致）；独立 `MATCH_REVIEW_AI_*` 配置；与 **预览池 / batch-match** 对齐的候选人准入（须具备问卷画像；池内需有图 + 画像）。**已验证主链**：preview pool → enqueue → batch-match → 最新 `MatchResult` → 最终匹配页 → 复审接口成功（`POST /match-review-ai/review` 在 Nest 下为 **201**，见下文「自动化测试」；含规则-only 与 fallback）。**已知限制**：复审不落库；`reviewStaticScore` 与 worker `finalScore` 语义不同；大模型依赖环境与 Key；本地种子与克隆脚本仅用于开发验收。
