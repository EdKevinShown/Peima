# P6.8 / P6.10 — 建议生成与审阅「最小规则收口」阶段草案

> **定位**：在 **不进入「AI 模拟匹配」实现**、**不做全量重构** 的前提下，针对当前已暴露的 **重复生成、消息增量语义不清、审阅可读性不足** 等问题，定义 **唯一** 一个最小收口阶段。  
> **仓库事实锚点**：后端已对「同会话仍存在 P6.8 `pending`」做过 **409** 级重复防护；**`pending` 清空后** 仍可再次生成，故「无新消息仍反复生成」需由本阶段单独钉规则。

---

## A. 是否应优先于「AI 模拟匹配」第一步

**结论：应优先。**

**理由（仅基于已收口主链与当前问题性质）**：

1. **信任与合规风险在前**：`accept` 已会改画像；若用户 **看不清会改什么**、又可在 **无对话进展** 下 **反复生成**，产品风险集中在 **误操作与不可解释变更**，与是否引入「AI 模拟匹配」无依赖关系。  
2. **与已落盘边界一致**：《进入 AI 模拟匹配前 — 边界说明草案》强调 **`sourceType` / `sourceVersion` 与读取口径**；本问题正是 **同一产品面上的语义与可追溯** 缺口，应先补齐，否则下一阶段会在 **「正式 / 对照」** 之外再叠加一层 **「建议侧噪声」**。  
3. **不改变最小起步方向**：AI 模拟匹配第一步落在 **`GET /matching/result` → Final Match**；本阶段落在 **P6.8 建议生成与审阅**，二者 **不抢同一接入点**，但 **P6.8 若不收口**，主产品体验会持续劣化。

---

## B. 唯一最小收口阶段（只选一个）

**阶段名称（建议）**：**「P6.8 建议：消息增量绑定 + 审阅可读摘要（最小规则收口）」**

**阶段目标（一句话）**：  
让用户在 **accept 前** 能 **稳定理解「会改什么」**，且系统保证 **无新对话进展则不可再刷建议、同一批新消息不可重复产出多条等价建议**。

**本阶段明确不做**：不改匹配主链、不上 AI 模拟匹配、不扩展问卷全链路重构、不把「画像建议」改成完整自然语言生成产品（仅 **最小可读说明 + 约束**）。

---

## C. 本阶段至少要解决的规则（按优先级）

| # | 规则（陈述句） | 对应现状缺口 |
|---|----------------|--------------|
| R1 | **自上次「可计数的对话进展」以来若无新消息，则不得再次生成** P6.8 会话画像建议（含：`pending` 已清空后仍连点）。 | 反复点击、无新消息仍生成 |
| R2 | **同一对话增量窗口内**（见下文定义），**至多存在一条**可被用户视为「同一轮产出」的 P6.8 建议；**不得**因连点或重试产生多条实质等价的 `pending`。 | 同一批消息下重复产出 |
| R3 | **`pending` / `accepted` / `dismissed` 与「消息增量」关系必须可叙述**：每条建议必须能回答「**相对哪条消息快照** 生成」。 | 状态与对话关系不清 |
| R4 | **待处理建议的默认展示**必须是 **用户可读的变更说明**（短文案 + 结构化要点），**禁止**仅展示 **patch / JSON / 内部 code 结构** 作为唯一信息。 | patch 展示 |
| R5 | **accept 前** 用户必须能回答两件事：**会改哪些维度/字段**、**改后的取向是什么（高层）**；不要求长篇生成，但必须 **可扫读、可对照**。 | accept 影响不清 |

**「对话进展 / 消息增量窗口」最小定义（本阶段钉死其一即可）**：

- **推荐最小定义**：以 **会话消息有序列表** 为基准，持久化 **`lastSuggestionMessageCursor`**（例如：**最后一条纳入建议生成的消息的 `id` 或 `(createdAt, id)`**）。  
  - **R1**：若当前最新消息 **不晚于** 该 cursor → **拒绝生成**（理由：无新消息）。  
  - **R2**：若自 cursor 之后 **尚未出现「新的 viewer/candidate 消息」**（或团队选定的一种最小「进展」定义）→ **不得**再产 **第二条** 针对「同一增量」的建议。

（具体字段名实现阶段再定；本草案只固定 **语义**。）

## D. 哪些规则必须落在后端；哪些可以只做前端

| 规则 | **必须后端（权威）** | **可仅前端（展示）** |
|------|------------------------|------------------------|
| R1 无新消息禁止再生成 | **是**：否则绕过 API/脚本仍可刷写。 | 否（前端可辅助禁用，但不能唯一依赖） |
| R2 同一增量不重复产出多条 | **是**：竞态、连点、双开 Tab 只有后端能串行裁决。 | 前端防抖仅作体验 |
| R3 状态与消息增量关系 | **是**：必须在 DB 层 **可查询**（cursor 或等价物写在建议行或会话扩展表）。 | 前端可用文案解释，但 **不能** 是唯一真相来源 |
| R4 可读变更说明 | **推荐后端**：返回 **稳定字段**（如 `summaryLines[]` / `changeBullets[]`），由 **规则或模板** 从 `proposedPatch` **派生**，避免各端各写一套。 | 若短期仅映射「维度编码 → 中文名」且无业务争议，可 **临时** 前端映射；**accept 红线文案** 仍建议后端给 **同一套** 字符串 |
| R5 accept 前「会改什么」 | **核心字段应由后端给出**（与 R4 同源），保证与 **实际 apply 路径** 一致。 | 排版、折叠、图标可前端 |

**底线**：凡涉及 **「允许或禁止再生成」**、**「是否写入画像」** 的，**一律后端权威**。

## E. 最小可交付范围（MoSCoW：只做 Must）

1. **后端**：在 `POST .../profile-completion-suggestion`（或等价服务层）实现 **R1 + R2 + R3** 的 **硬拒绝**（HTTP 状态与错误码由实现阶段按现有风格对齐；本草案不规定码表）。  
2. **后端**：为每条（或每次）建议响应增加 **审阅用摘要载荷**（满足 **R4 + R5**），与现有 `proposedPatch` **同源派生**，避免两套真相。  
3. **前端**：Chat 待处理区 **默认展示** 上述摘要载荷；**patch 结构降级** 为「高级 / 调试」折叠或开发环境可见（产品默认不可见）。  
4. **文档**：在 `docs/P6` 增补 **一页**「本阶段规则与验收清单」（可与本草案合并或拆分，**不**另开多线文档树）。

**不在范围内**：新模型、全问卷重写、与 Final match / worker 的耦合改造。

---

## F. 最小验收标准（可打勾）

1. **无新消息**：在同一 `conversationId`、无新聊天消息的前提下，连续请求生成 → **第二次起稳定失败**，且用户看到 **明确原因**（非泛化 500）。  
2. **有消息但同一增量**：在一次「新消息批次」内，**不可**出现两条 **均为 `pending`、且用户感知为同一轮** 的 P6.8 建议（以 **DB 查询 + 产品判定** 为准）。  
3. **可追溯**：任意一条 P6.8 建议（`pending` 或已决）在数据上能回答：**基于不晚于哪条消息快照生成**（cursor 可查）。  
4. **可读**：默认 UI **不出现** 裸 `proposedPatch` JSON 作为唯一内容；用户 **不展开** 即可读到 **≥2 条** 要点级变更说明。  
5. **accept 可理解**：在 accept 前，同一屏可见 **「将影响的维度/分支」** 与 **「接受后的取向」**（允许简短模板句）；accept 后行为与说明 **不矛盾**。  
6. **回归不破坏**：既有 **「存在 `pending` 时不可再生成」**（409 语义）与 **P6.10 禁用按钮** 仍成立；本阶段 **不** 削弱该体验。
