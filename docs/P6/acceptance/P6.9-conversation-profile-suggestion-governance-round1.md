# P6.9 Conversation Profile Suggestion Governance — 首轮收口（Round 1）

## 1. 标题

见页首 H1。

## 2. 一句话结论

**P6.9 首轮已落地并收口**：在 **不改动** P6.8 主链路、**不改** schema 与 accept/dismiss 的前提下，于唯一生成入口 `POST /chat/conversations/:conversationId/profile-completion-suggestion` 上增加三道治理（消息条数、pending 门禁、时间冷却），统一 **400 / 409 / 429** 口径，减少重复建议、短时刷请求与弱会话误触发。

## 3. 本轮目标

- 为 **P6.8 聊天驱动画像补全**增加**最小**治理能力，**不**新辟产品线、**不**引入 worker / 多 Agent / simulation。
- **仅**在 P6.8 的 POST 生成路径上拦截；**不**扩展到 CopilotPage、admin、时间线、suggestion center。
- 与既有 **P6.8 白名单**（四键：`initiativeLevel`、`socialEnergy`、`emotionalExpression`、`relationshipPace`）并存，**不**扩画像字段体系。

## 4. 实现范围

| 层级 | 内容 |
|------|------|
| 入口 | 仍仅为 `POST /chat/conversations/:conversationId/profile-completion-suggestion`；治理逻辑在调用 LLM **之前**执行，被拦截请求**不**消耗模型调用。 |
| 常量 | `PROFILE_COMPLETION_GOVERNANCE_MIN_MESSAGES`（首轮 **6**）、`PROFILE_COMPLETION_GOVERNANCE_COOLDOWN_MS`（首轮 **1 小时**）；与 `PROFILE_COMPLETION_SOURCE_VERSION`（`p6.8-profile-completion-ai-v1`）联动查询。 |
| 数据 | 只读 `profile_update_suggestions`：`userId` + `sourceVersion` + `status` / `createdAt`；**无** migration、**无**新表新列。 |
| 服务 | `ProfileSuggestionService` 新增只读：`countPendingByUserIdAndSourceVersion`、`findLatestCreatedAtByUserIdAndSourceVersion`；**不**改 `create` / `accept` / `dismiss` 语义。 |
| 模块 | `ConversationProfileCompletionService` 内串联三道检查；日志事件仍为 `profile_completion_ai`，`outcome: blocked`，`reason` 区分 `governance_insufficient_messages` / `governance_pending_exists` / `governance_cooldown`。 |

**本轮未改**：matching、Prisma schema、其它 profile suggestion 创建入口、前端（错误由 HTTP 状态与 message 透出即可）。

## 5. 三项治理规则

| 规则 | 判定 | 说明 |
|------|------|------|
| **最小消息条数** | 参与本次拼 prompt 的 **消息切片**（与既有 `messageLimit` 截断后的 `slice`）条数 **≥ 6** | 弱会话不上模型；**未**引入 self 条数、总字数等附加规则。 |
| **pending 门禁** | 当前用户已存在 **`status = pending`** 且 **`sourceVersion = p6.8-profile-completion-ai-v1`** 的建议 | 需先 **accept** 或 **dismiss** 后再生成；其它 `sourceVersion` 的 pending **不**阻塞 P6.8。 |
| **冷却** | 同一用户、同一 `sourceVersion` 下，**任意状态**的最近一条建议的 `createdAt` 距现在 **&lt; 1 小时** | 降频刷接口；满 1 小时后可再次生成（仍须通过 pending 与消息条数检查）。 |

## 6. 状态码口径（400 / 409 / 429）

| HTTP | 场景 |
|------|------|
| **400 Bad Request** | 切片内消息条数 **&lt; 6**（与「会话尚无消息」等既有 400 区分：本轮为带 `minMessages` 语义的文案）。 |
| **409 Conflict** | 已存在 **pending** 的 P6.8 建议（`sourceVersion` 如上）。 |
| **429 Too Many Requests** | 处于 **冷却窗**内（距上次同 `sourceVersion` 建议创建不足 1 小时）。 |

其它 P6.8 行为保持不变（如 AI 未开 **503**、无有效 patch **422** 等）。

## 7. 验收记录（本轮已完成、已验证）

以下项已在实现侧与人工/联调路径上**核对通过**，作为 Round 1 收口依据。

| 项 | 预期 | 结果 |
|----|------|------|
| 消息 &lt; 6 | **400**，不调用 LLM，不新增 suggestion | **通过** |
| pending P6.8 已存在 | **409**，不调用 LLM | **通过** |
| 冷却窗内再次生成 | **429**，不调用 LLM | **通过** |
| 三项均通过 | 与收紧前一致可 **200** 创建 pending，accept/dismiss 仍可用 | **通过** |
| 非 P6.8 pending | **不**因其它 `sourceVersion` 的 pending 触发 409（仅匹配 P6.8 `sourceVersion`） | **通过** |

**构建旁证**：`apps/api` `nest build` 已通过（不替代业务验收）。

## 8. 最终结论

**P6.9 首轮（Round 1）已完成、已验证、已收口**：P6.8 唯一 POST 在模型前增加消息门槛、pending 门禁与冷却，状态码 **400 / 409 / 429** 与文档一致；无 schema 变更、无 worker、无扩展页面，accept/dismiss 与其它建议来源保持原状。

## 9. 明确未做项

- 无 **env** 开关治理参数（首轮为代码常量）。
- 无 **按会话维度**持久绑定（未增加 `conversationId` 等字段）。
- 无 **self 消息数 / 字数**等第二道门槛。
- 无 **Retry-After** 响应头等扩展。
- 无 **Copilot / admin / timeline / suggestion center** 接入。
- 本文档**不**承担 P6.10+ 或 worker/simulation 规划。
