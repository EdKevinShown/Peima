## 2. 《观察期问题收集清单》

观察期内 **只做轻量记录**，不展开为完整运维或监控体系建设。建议仅关注下列条目（有则记一条，无则不必填表）：

1. **成功路径**：在约定配置下，Copilot 模型路径是否持续可用；`sourceType` / `sourceVersion` 是否与预期一致。  
2. **Fallback**：在密钥缺失、超时、供应商错误等场景下，是否仍为 **HTTP 200 + 规则层**，用户侧是否可接受；是否出现 **非预期** 的空白、报错页或主聊天链路受影响。  
3. **前端**：`/chat` 与 `/copilot` 是否出现异常展示、重复请求、明显卡顿或与洞察数据不一致（仅记现象与复现条件）。  
4. **日志**：`copilot_ai` 中是否出现 **高频、集中** 的同一类 `reason`（如持续 `timeout`、`http`、`invalid_model_payload` 等）；是否便于与配置或供应商侧对应。  
5. **配置与理解**：是否反复出现 **同一类误配** 或文档/环境变量 **理解歧义**（例如 `AI_PROVIDER` 与 host 推断、`openai_compatible` 含义、密钥未加载等），并简述根因是否为文档、示例或运行环境。

**不要求** 在本阶段补齐大盘、自动告警、成本分析、重试策略或限流方案；上述项仅服务于 **是否结束冻结、是否单独立项** 的决策。

## 3. 《P6.5 开启条件》

**满足以下任一情况，方可启动对「P6.5」或同等命名下一阶段的讨论与立项；否则默认维持 P6 第一轮冻结，不进入 P6.5。**

1. **明确缺陷**：线上或联调中出现 **可复现** 的问题，且经判断需在 P6 已交付范围内 **修复**（含安全、正确性、与已发布契约不一致的行为）。  
2. **稳定性或配置收口**：观察期内出现 **高频 fallback**、或 **高频、同因** 的误配/歧义，需在 **不扩大功能边界** 的前提下做针对性收口（例如日志字段、文档、极小修复或配置校验说明）。  
3. **产品扩能力**：产品方 **明确** 要落地 **下一条** AI 能力（如摘要、匹配、说明、异步、多 Agent 等），且 **已单独立项**（含范围、验收标准、资源与时间），**不得** 以「顺手加在 Copilot 里」替代立项。  
4. **可观测性/告警**：业务或运维 **明确要求** 更正式的观测或告警，且 **单独划定范围与交付物**（例如对接哪类日志平台、哪些字段、哪些阈值）；**不** 将「顺便做监控」并入日常开发默认排期。

**原则**：  
- **不默认** 进入 P6.5；冻结期结束须由 **显式决策**（问题单、立项或书面范围）触发。  
- **不因**「代码还能改」「还能再优化」**或**「人力有空」**而继续推进**；下一阶段必须以 **问题或已批准需求** 为入口。
