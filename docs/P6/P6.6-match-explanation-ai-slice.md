## P6.6 定义：Match Explanation AI（独立切片）

### 1. 做什么

- 在**已有最终匹配结果**（例如 Final Match / 结果页已确定的 candidate、score、规则标签等**只读上下文**）之上，**按需**生成 **AI 解释**：向用户说明「**为什么系统给出这一匹配/这一排序结果**」。
- 产出形态可以是：**一段可读解释文本**，或 **结构化字段**（如「依据维度：…」「不确定性说明：…」），具体 JSON 契约在立项实现时定死；**不改变**任何数值型 score 或排序位次。
- 实现上为**独立模块**：独立配置、独立 HTTP 入口、独立 prompt/映射、独立日志与 `sourceType`/`sourceVersion`，**不**挂在 Copilot insights、不挂在 Summary AI、不挂在 matching 批处理或 Worker。

### 2. 不做什么

- **不让 AI 决定匹配结果**：不参与打分、不重算 rank、不替换或覆盖现有 matching 输出。
- **不改** matching 核心链路：`enqueue`、batch、worker、cron、score 计算、候选生成与筛选等**主逻辑零侵入**（仅只读拉取已落盘或已 API 暴露的最终结果快照）。
- **不改**最终配对/进入聊天的业务流程；用户**不请求解释**则行为与现网一致。
- **本轮默认不做 explanation 落库**；若未来要审计或缓存，须**单独立项**（表结构、失效策略、合规）。

### 3. 为什么适合作为「下一条」独立切片

- **边界清晰**：输入是「已定案」的 match 视图，输出是「说明层」，与 **P6.5 Summary（会话内）**、**Copilot（沟通侧）** 场景不同，不易混在一条接口里。
- **用户价值单一**：回答「为什么是我/为什么 TA」，比继续扩 matching 模型或 Copilot 能力**更容易写验收**（成功 = 有解释且可追溯来源；失败 = 规则占位，不影响结果页）。
- **技术风险可控**：只读 + 可选调用 + 强 fallback，符合你们已验证的 **单切片** 打法（与 P6.5 同一套「独立入口、独立日志、独立回退」）。
- **与「matching 核心 AI 化」正交**：先练「解释层」不触动核心排序，避免一条 PR 同时动算法与产品叙事。

### 4. 独立入口怎么定

**后端（建议）**

- 独立路径命名空间，例如：  
  **`GET /match-explanation-ai/match-results/:matchResultId`**  
  或 **`GET /match-explanation-ai/conversations/...`**（若解释锚点以会话为准，仍以**独立 controller** 实现，**禁止**复用 `/copilot/...`、`/summary-ai/...`）。
- 鉴权与「谁有权看该条匹配结果」**与现有 final-match / match 详情接口对齐**（同一用户只能看自己的结果），**不**新增业务语义上的越权面。

**前端（建议）**

- 在 **Final Match / 匹配结果页**（或结果卡片区域）增加**单独触发**：如「生成匹配说明（试点）」按钮，或展开区「查看系统说明」；**默认不自动请求**（与 P6.5 ChatPage 一致）。
- **不**在列表页、matching-waiting、Copilot、Summary 流程中顺带拉 explanation，除非产品单独立项。

### 5. fallback 怎么做

- **开关关闭 / 无 key / 超时 / 非 2xx / 空 content / JSON 或 schema 校验失败**：一律 **HTTP 200**（与 P6/P6.5 试点口径一致），返回 **规则层或固定占位说明**（例如「暂无法生成详细说明，以下为规则摘要…」），并带 **`match_explanation_rule_based` 类 `sourceType`**（见下节）。
- **禁止**：因解释失败导致结果页白屏、阻断「发起聊天」「查看资料」等**主 CTA**；解释区域可隐藏或显示简短提示。
- **主流程**：final-match 页**渲染与数据加载不依赖**本接口成功；解释请求失败时**不重试自动风暴**（是否单次点击重试由前端显式控制即可）。

### 6. `sourceType` / `sourceVersion` 设计

**原则**：与 Copilot、Summary **完全区分命名空间**，日志与前端一眼可分辨「匹配解释」链路。

**建议取值（实现时固化常量）**

| 场景 | `sourceType`（示例） | `sourceVersion`（示例） |
|------|----------------------|-------------------------|
| 规则/占位/失败回退 | `match_explanation_rule_based` | `p6.6-match-explanation-rule-v1` |
| 模型成功 | `match_explanation_model_<slug>` | `<slug>\|<model>\|<prompt 版本>`，如 `deepseek\|deepseek-chat\|p6.6-match-explanation-prompt-v1` |

**禁止**：使用 `summary_*`、`rule_based`（裸）、`model_<slug>`（裸）作为本切片唯一来源标识，避免与 Summary/Copilot 混读。

### 7. 日志怎么独立

- **独立 `event`**：例如 **`match_explanation_ai`**（单行 JSON，便于检索）。
- **字段口径**（与 P6.5 对齐风格）：至少 **`matchResultId`**（或等价锚点 id）、**`outcome`**（`model_ok` / `fallback`）、**`reason`**（与客户端/服务内枚举一致）、**`durationMs`**、**`providerSlug`**（非敏感）；可选 **`status`/`detail`**（截断，无 key、无完整用户画像全文）。
- **独立 reason 枚举**：在实现阶段维护 **「P6.6 原因码表」** 小节（文档或 runbook），与 `summary_ai`、`copilot_ai` **不共用同一套语义表**（可形似，但 **event 与文档分册**）。

### 8. 最小验收怎么做

1. **成功路径**：开启 `MATCH_EXPLANATION_AI_*`（或最终定名的前缀）、配置正确 → `GET` 独立接口 → **200**，`sourceType` 为 **`match_explanation_model_<slug>`**，正文可读且与**当前页展示的 match 结果一致**（不编造未展示字段）。  
2. **fallback 路径**：关开关 / 错 key / 超时等 → 仍 **200**，`sourceType` **`match_explanation_rule_based`**，主结果区数据与无 AI 时一致。  
3. **页面**：结果页点击触发后出现解释区；未点击**无**对 `/match-explanation-ai/...` 的请求；loading **不锁死整页**。  
4. **主链路**：同会话下进入聊天、刷新结果、Copilot/Summary **行为与改造前一致**（抽样 HTTP 或 E2E 任选其一写进验收表）。

---

**目标重申**：P6.6 仅 **Match Explanation** 一条切片 — **独立接口、独立配置前缀、独立 `sourceType`/`sourceVersion`、独立日志 event、独立 fallback、独立验收**；**不**动 matching 核心与库表（除非 explanation 落库另立项）。
