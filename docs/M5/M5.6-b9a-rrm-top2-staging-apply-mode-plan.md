# M5.6-B9-A — Staging Apply Mode Plan（RRM Top2 Hook Job）

> **范围**：**设计文档 only（B9-A）**。规划如何将 **B8** independent dry-run poller 能力演进为 **staging apply mode**。**本轮不实现** staging apply、**不**接 production 自动轮询、**不**改 Prisma schema / migration。文档不含真实业务 id、token、`DATABASE_URL`。

---

## 1. 一句话结论

**B9-A** 只设计 **staging apply mode**：在 **staging / 本地受控** 环境中小批量将 pending hook jobs 经 **apply** 路径落库。**Staging apply 必须复用** M5.6-B7-B **shared apply service**（`processRrmTop2HookJobsApplyBatch` / `applySingleRrmTop2HookJob`），**禁止**复制 B5-B 状态迁移与 writer 编排逻辑。**默认**仍不进入 production 自动写入；任何 **production 常驻自动 apply** 均 **不在** 本计划范围内。

---

## 2. 当前基础

| 项 | 说明 |
|----|------|
| **B5 controlled apply runner** | 已实现：`findPending` → `markProcessing` → writer（`dryRun: false`）→ `processed` / `skipped` / `failed`；含 CLI gate（`--apply` + `--confirmControlledApply=I_UNDERSTAND`）、limit 钳制、no-op 映射与错误 sanitize。 |
| **B6** | **env-on + frozen meta** 下 **`existing_meta_frozen` → `skipped`** 等路径已有 run record（如 `M5.6-b6b`）。 |
| **B7 shared apply service** | `rrm-top2-hook-job-apply.service.ts`：**dry-run aggregate** 与 **apply batch** 单一路径；B5 runner 已委托该 service。 |
| **B8 dry-run poller** | Independent **dry-run** CLI 已落地；`M5.6-b8c` 记录 **`totalJobsRead=0`** 等 aggregate-safe 输出；**无**写库。 |
| **Staging apply mode（独立命名）** | **尚未**作为与 B8 poller 同形态的「staging-only apply」产品化开关；staging 上可控小批量 apply 目前主要通过 **B5 CLI** 达成。 |

---

## 3. Staging apply 的目标

| 目标 | 说明 |
|------|------|
| **环境** | **Staging 或本地**；显式 env + CLI，**非** production 默认行为。 |
| **批量** | **小批量** apply pending hook jobs（上限严格，见 §5）。 |
| **复用** | 调用 **`processRrmTop2HookJobsApplyBatch`**（及 service 内单条 apply），与 B5 **同一**语义。 |
| **验证** | `processed` / `skipped` / `failed` 状态迁移；writer **env gates**（meta / summary）与 no-op 分布可观测。 |
| **生产** | **不**默认在生产开启；production 下 **拒绝** 或 **仅 dry-run**（与 B5/B8 精神一致）。 |

---

## 4. 强 gate 设计（建议，B9-B 实现时对齐）

Staging apply **必须同时满足**（**全部**为真才允许进入 apply 路径；任一失败 → **`refused` 或退化为 dry-run only**，**不** `mark*`、**不**写 meta）：

| Gate | 条件（建议值） |
|------|----------------|
| **Node** | `NODE_ENV !== "production"` |
| **Poller 总开关** | `PEIMA_M5_RRM_TOP2_HOOK_POLLER_ENABLED=1` |
| **模式** | `PEIMA_M5_RRM_TOP2_HOOK_POLLER_MODE=apply` |
| **显式确认** | `PEIMA_M5_RRM_TOP2_HOOK_POLLER_APPLY_CONFIRM=I_UNDERSTAND`（与 B5 文案一致，防误触） |
| **Meta 写** | `PEIMA_M5_RRM_TOP2_META_WRITE_ENABLED=1` |

若涉及 **summary** 写入（由现有 writer / env 定义）：

| Gate | 条件 |
|------|------|
| **Summary 写** | `PEIMA_M5_RRM_SIM_READONLY_SUMMARY_WRITE_ENABLED=1`（名称以代码与 `M5.6-b6` 文档为准；实现时 **核对** 实际 env key） |

**不满足任一 gate**：返回 **refused** 或 **仅 dry-run** JSON；**不写** HookJob 状态；**不写** `MatchResultRrmTop2DisplayMeta`；**不写** `matchInsights` summary。

---

## 5. Limit 规则

| 规则 | 建议 |
|------|------|
| **默认 limit** | **1**（与 B5 默认接近，staging 更保守） |
| **最大 limit** | **5** 或 **10**（二选一在 B9-B 固定；**不得** unlimited） |
| **输出** | 每轮 **aggregate JSON**（与 B5 apply 形态对齐：`processedCount` / `skippedCount` / `failedCount` / `noOpReasonCounts` / `items[]` 等，**不**含真实业务 id） |

## 6. Staging apply CLI / poller 形态（方案比较）

### 方案 A — 新增 `m56-b9-*` staging apply poller（dev-cli）

| | |
|--|--|
| **形态** | 例如 `m56-b9-rrm-top2-staging-apply-poller.ts` + `*-cli.ts`：**默认 dry-run**；仅当 **`--apply-staging`**（名称可微调）且 **§4 env gates** 全满足时调用 `processRrmTop2HookJobsApplyBatch`。 |
| **优点** | 与 B8 **命名对称**（poller 家族）；可把 **poller 专用 env** 与 B5 **CLI flag** 区分开。 |
| **缺点** | 多一套 **入口与单测**；若编排仅薄包装 shared service，需严格避免复制 B5 gate 逻辑（应 **委托** service + 集中 gate 函数）。 |

### 方案 B — **复用 B5 apply runner**（`m56-b5-*`）+ 文档约定 staging 流程

| | |
|--|--|
| **形态** | 不改代码或仅补 env 文档：在 staging 上设置 writer / meta env，使用 **`--apply` + `--confirmControlledApply=I_UNDERSTAND`** 调用现有 CLI；底层已走 **shared service**。 |
| **优点** | **零重复** apply 编排；B5 单测与 B6 run record 已覆盖主路径；**B9-B 可零代码**先做 **B9-C staging apply run record**。 |
| **缺点** | CLI 名仍为「b5」；与 B8「poller」产品线叙事略不统一（可用文档章节 **「B9 staging 使用 B5 runner」** 解释）。 |

### 推荐（B9-B 短期）

- **优先方案 B**：**B9-B 先用 B5 controlled apply runner** 完成 **staging apply run record**（B9-C），**不新增第二套** apply CLI。  
- **若未来**需要与 B8 dry-run poller **同一操作界面**（统一脚本名、统一 env 前缀）：再实施方案 A 的 **薄 dev-cli**，内部 **仅** 调 `processRrmTop2HookJobsApplyBatch` + 共享 gate 校验，**不接** `apps/worker/src/main.ts`，**不** production 默认开启。

## 7. 推荐方案（摘要）

| 阶段 | 建议 |
|------|------|
| **短期 B9-B** | **复用 B5 apply runner** + 强 env 文档与运维 checklist；**不新增** `m56-b9` apply CLI，除非产品明确要求 poller 命名统一。 |
| **可选后续** | **仅** dev-cli **staging apply poller**，**薄封装** shared service + §4 gates；**永不**默认注册 worker 自动 apply。 |

## 8. 状态迁移预期（staging apply 应能验证）

| 场景 | 预期 |
|------|------|
| **existing_meta_frozen** | → **`skipped`** |
| **writer_disabled** | → **`skipped`** |
| **rrm_summary_missing**（预检 / writer no-op） | → **`skipped`** |
| **eligible + meta env on** | → **`processed`**（`wroteMeta` 等以 writer 为准） |
| **Writer 异常** | → **`failed`**（`apply_exception` + sanitize） |

**eligible + processed** 若 staging 数据暂不可构造，可在 B9-C run record 中标注为 **follow-up**，不阻塞「skipped / frozen」类证据收集。

---

## 9. Run Record 计划（B9-C）

**B9-C** 宜记录：

- **Env gates** 设置摘要（**不**贴 secret / `DATABASE_URL`）。  
- **Pending 条数**（仅计数或区间，**不**贴真实 id）。  
- **Apply 输出**：`processedCount` / `skippedCount` / `failedCount`、`noOpReasonCounts`。  
- **`candidateUserId` / `finalScore` 不变**（与 B5/B8 记录方式一致）。  
- **GET**：不写库、不接 GET 驱动 apply。  
- **可选**：是否产生 **rrm_top2_bounded_selector**（或当前产品名之 display meta 侧车）等 **字段级** 摘要，**无** raw prompt / transcript。

---

## 10. 安全边界

以下 **永远不因** staging apply **而直接篡改**（与既有 M5 不变量一致）：

- **`MatchResult.candidateUserId`**  
- **`MatchResult.finalScore`**  
- **worker ranking**  
- **`PairwisePoolFinalizeMeta`**  
- **user profile**  
- **chat messages**  

**GET** 保持 **只读**。

Staging apply **允许**（在 writer + env 允许时）经 **shared apply service** 写入：

- **HookJob** 状态与审计字段；  
- **`MatchResultRrmTop2DisplayMeta`**；  
- **`matchInsights` 内只读 summary**（若单独 env 允许且 writer 设计如此）。
