# M5.5-M6-A — RRM Top2 Automatic Hook Scan Record

> **范围**：代码扫描结论固化；**不写代码**、**不改 schema**、**不新增 migration**。本文不出现真实业务 ID、token、`DATABASE_URL`。

---

## 1. 一句话结论

**当前还不建议直接实现「真正」的 automatic hook（全自动、零歧义绑定）。**

根本原因是缺少 **稳定、可审计的 durable 关联**：**`matchResultId` ↔ RRM 相关 job ↔ Static Top2 ↔ `top2Fingerprint`**。若在 **零 schema** 前提下强行自动写侧车，只能退化为 **半自动 consumer** 或 **启发式关联**（例如按 `viewerUserId` + `latest MatchResult` + `poolId` 推断），在 **多批次、重跑、重新匹配** 等场景存在 **错绑 MatchResult** 的风险；一旦写错对象，即使不覆盖 `candidateUserId`/`finalScore`，也会造成 **展示侧车与错误行绑定** 的产品与合规问题。

**下一步更应进入** **schema / outbox（hook job 表）设计**（见 §7、§9），而非跳过设计直接落地 M5.5-M6-B 全链路实现。

## 2. 当前可复用机制

| 类别 | 结论 |
|------|------|
| **通用队列（如 Bull）** | 仓库内 **未发现** Nest/Bull 式应用内通用任务队列；匹配与 AI 侧多为 **Prisma 表 + 状态字段**。 |
| **Prisma poller 范式** | **`packages/ai-simulation-v1-runner`**：`registerAiSimulationV1QueueWorker` + 轮询 `AiSimulationV1Job`。**`packages/ai-pairwise-decision-runner`**：对 `AiPairwiseDecisionJob` 的类似轮询。二者均可作为 **「独立 worker 轮询消费」** 的工程参考。 |
| **Writer foundation** | **M5.5-M2**：`writeRrmTop2DisplayMetaForMatchResult`、env 闸门、`validateRrmTop2DisplayEligibility` 对齐路径；可选 `rrmSimReadonlySummary` 合并与 `writeRrmSimReadonlySummaryToMatchResult`。 |
| **Controlled runner** | **M5.5-M4**：`m55-m4` 受控 production hook runner（默认 dry-run，`--apply` 写库）；与 GET / worker 主流程 **未接线**。 |

## 3. 为什么零 schema 自动 hook 风险高

- **`AiSimulationV1Job` 无 `matchResultId`**：completed job 只能落到 `viewerUserId`、`poolId` 等维度，**无法**与某条 `MatchResult` 行做 **数据库级唯一约束**。
- **`MatchResult` 无 `poolId`**：从 job 反查「当时匹配所用的池」依赖 **业务推断**，与 schema 真值分离。
- **「按 viewer 取 latest `MatchResult`」**：在 **重跑 batch、多条历史结果、rematch** 时 **极易错绑**；幂等也不能仅靠「侧车已存在」区分「从未处理」与「条件不满足应重试」。
- **`existing_meta_frozen` 等 writer no-op**：可防止 **覆盖已冻结 meta**，但 **不能**表达 **从未尝试**、**可重试**、**永久跳过（硬 no-op）**、**失败待人工** 等 **工作流状态**。
- **无 `processedAt` / `noOpReasonCode` / `retryCount` 等列**：运维与审计无法对自动链路做 **可观测、可回放** 的闭环。

## 4. Static Top2 来源现状

| 来源 | 说明 |
|------|------|
| **`AiPairwiseDecisionJob.shortlistSnapshot`** | 经校验的 **RelationshipShortlistTop2** 快照，**相对稳定**；键域为 viewer + pool + fingerprint 等，**不直接等于 `matchResultId`**，需编排层绑定。 |
| **`PairwisePoolFinalizeMeta`（`frozen`）** | 可用于 **冻结 finalize** 语境；**不是** `matchResultId` 上一键 JOIN，需 **viewerUserId + poolId** 等与 `MatchResult` 对齐策略。 |
| **`PreviewPoolItem` + `rankInPool`** | 可还原 **某一时刻** 池内排序，属 **弱快照**；池子生命周期与「绑定到某条 `MatchResult`」无硬 FK，**不宜**当作唯一 frozen Top2 真源。 |
| **`AiSimulationV1Job.shortlistBinding`** | 含 previewPool / shortlist 指纹等 **绑定信息**；**不一定**等同于最终用于 writer 的 **两名 distinct Top2**，常需与 finalize / pairwise 快照等 **组合**解读。 |

**结论（与 M5.5-M5 / M5.5-M3 一致）**：

- **禁止**在 writer 或 hook 内 **重算 shortlist** 冒充 frozen Top2。
- 若编排层 **无法**得到与 **`MatchResult.candidateUserId`** 一致的 **稳定 frozen Top2**，则 **必须 no-op**（可审计）。

---

## 5. RRM summary 来源现状

- **`matchInsights.rrmSimReadonlySummary`**：GET 读路径可通过 **`tryParseRrmSimReadonlySummaryPayloadV1FromMatchInsights`** 消费（只读）。
- **新写入的 `MatchResult`**：worker 侧默认 **`buildMatchInsightsPlaceholder`**，**不含** `rrmSimReadonlySummary`；即 **多数新行默认无 summary**。
- **Builder / writer 已存在**：如 **`buildRrmSimReadonlySummaryFromRrmSimResult` / `buildRrmSimReadonlySummaryFromRrmProposal`**（纯函数）与 **`writeRrmSimReadonlySummaryToMatchResult`**（受控写 `matchInsights` 单键）；**生产自动路径尚未接入**。
- **自动 hook 含义**：若要在自动链路中满足 writer 的 summary 前提，需从 **simulation job 侧车、proposal、diagnostic 等** **构造** viewer-safe payload，再经 **既有 writer** 写入 **`matchInsights`**（仍受 env 与 frozen 规则约束）。

---

## 6. Guardrails explicit pass 来源现状

- **Writer 硬要求**：`writeRrmTop2DisplayMetaForMatchResult` 需要 **`RrmTop2DisplayMetaGuardrailsV1`**，且 **explicit pass**（`status === "pass"` 且 `blockReasons` / `cautionReasons` 均为空）才会进入可写路径（见 M5.5-M2 实现）。
- **当前无自动流水线** 生成该 **explicit** 结构；**dev-cli / 受控 runner** 通过参数或默认值注入。
- **`buildGuardrailsReadonly`**：从 **`matchInsights` 的 cautions/riskFlags** 与 **finalize `fallbackReason`** 等推导 **多源只读 guardrails**，**语义与形状与 writer 的 explicit guardrails 输入不完全等价**，**不能**不经规则映射即当作 explicit pass。
- **若无明确 pass**：自动 hook **必须 no-op**（并建议在未来 outbox 中记录 **`noOpReasonCode`**）。

## 7. 推荐路线

### 短期

- **不落地**「真正」的 **零 schema full automatic hook**。
- **继续**使用 **M5.5-M4 controlled runner** / **dry-run** 做验证与人工闸门下的写库。
- **优先**完成 **durable outbox / hook job 表** 的 **schema 与状态机设计**（见下一里程碑命名建议 §9）。

### 中期（建议新增）

新增 **RRM Top2 hook job / outbox** 表（名称可微调），至少绑定：

- `matchResultId`
- `viewerUserId`
- `poolId`
- `aiSimulationJobId` / `pairwiseJobId`（**可选**，便于审计与重放）
- `staticTop2Snapshot`（JSON，或等价规范化列）
- `top2Fingerprint`
- `status`：`pending` / `processed` / `skipped` / `failed`（枚举可细化）
- `noOpReasonCode`（可空）
- `processedAt`（可空）
- `sourceVersion`（契约世代）

### 长期

- **独立 post-match aggregation worker** 轮询该表（或等价队列），在 **inputs 齐备** 时调用 **`writeRrmTop2DisplayMetaForMatchResult`**；GET 仍只读；worker batch-match **仅 enqueue** 或 **由 API 在「MatchResult 已提交」事件写入 outbox 行**（实现阶段再定，须避免阻塞主事务）。

---

## 8. 不推荐路线

明确 **不推荐**：

- 在 **`GET /matching/result`**（或任意用户读路径）**写库**或触发 writer。
- 在 **worker `batch-match` 同步尾部** 直接写 RRM Top2 meta / summary（阻塞与顺序风险）。
- **仅从 `latest MatchResult` 猜测** 与某 completed job 的关联。
- **从当前 `PreviewPool` rank 重新计算 Top2** 当作 frozen 真源。
- **没有 explicit guardrails pass** 却 **当作 pass** 调用 writer。
- **自动覆盖** 已 **frozen** 的 `MatchResultRrmTop2DisplayMeta`（writer 已有 no-op 保护，产品层仍应避免设计依赖误触发）。

---

## 9. 下一步建议

**下一步应是：**

**M5.6-A — RRM Top2 Hook Outbox Schema Plan**（或同义里程碑）：定义 **表结构、状态迁移、幂等键、与 `MatchResult` / job 的 FK、索引、与 M6-B 实现的边界**。

**而不是**在缺少 durable 关联的前提下 **直接**进入 **M5.5-M6-B full implementation**。

若业务方 **坚持零 schema**：仅可交付 **semi-auto consumer**（例如 CLI / admin 触发 + 显式传入 `matchResultId`），且 **必须在文档与运行手册中标注错绑与不可审计风险**；**不建议**作为商业化默认路径。

---

## 10. 红线

再次固定（与 M5.5-M1/M3/M5 一致）：

- **不改** `MatchResult.candidateUserId`。
- **不改** `MatchResult.finalScore`。
- **不在 GET** `/matching/result` **写库**。
- **不阻塞** worker 主匹配事务路径。
- **不自动发送** chat。
- **不暴露** raw score / 原始 prompt / 全量 transcript / 内部 formula（遵守现有 viewer-safe 与侧车契约）。
- **不改** `PairwisePoolFinalizeMeta` **主语义**写入路径（RRM Top2 仅侧车 `MatchResultRrmTop2DisplayMeta` + 可选 `matchInsights` 键）。
