# M5.3-A — RRM Top2 Enabled Display Plan

## 1. 一句话结论

M5.3 **不**重新造一套最终展示系统，而是**复用 M3.8-M13 已落地的** `displayCandidateUserId` / `displaySourceType` / `finalMatchDecisionMeta`（及 `resolveMatchResultDisplay` 读路径）。M5.3 的目标是在**严格开关与 eligible rules** 下，让 **20 维 / Static 先产出 Top2**，再让 **RRM-Sim 仅在 Top2 内做 bounded 二选一**，经 **Guardrails** 校验后，**才把 RRM winner 写进展示层**（即与 today 相同的 display 字段语义）；**始终不覆盖** `MatchResult.candidateUserId`、**不修改** `finalScore`。

## 2. 为什么改成 RRM Top2 bounded selector

全量候选 + Pairwise + RRM + Guardrails 的多源主链在工程与 AI 成本上偏重。为压缩 MVP / 商业化早期成本，产品路线收敛为：

- **20 维 / Static**：低成本筛出 **Top2**（与既有 preview pool + shortlist 能力对齐，见 M3.8-M1 与 `relationshipShortlistTop2` 相关实现）。
- **RRM**：**只在 Top2 内二选一**（bounded selector），避免 RRM 在全池自由排序。
- **Pairwise**：从「每次必跑主链」降级为 **optional**（audit / fallback / premium 档位），主展示不依赖 Pairwise 必成功。
- **GET `/matching/result`**：**不**在现场重跑 RRM evaluator（与 M5.1/M5.2 红线一致）；展示依赖**已持久化或可复算的 viewer-safe 摘要**（如 `rrmSimReadonlySummary` 写入路径，见 M5.2 文档与 writer）。
- **FinalMatchPage**：继续只读 API 返回的 `displayCandidateUserId`（与 M3.8-M13 一致）。

### 3.2 M3.8 已经实现的 display 机制（代码还原）

1. **`GET /matching/result/:userId`**（`MatchingController.getResult` → `MatchingService.getLatestResultForUser`）在返回 `MatchResult` 行之外，**合并** `resolveMatchResultDisplay` 产出的 **`displayCandidateUserId` / `displaySourceType` / `finalMatchDecisionMeta`**，并附加 M5.x 的 **`multiSourceFinalDecision`** 只读侧车（不改变 display 解析结果）。
2. **`resolveMatchResultDisplay(prisma, matchRow)`**（`matching-result-display.ts`）：
   - 若 **`readPairwiseFinalizeEnv()`** 为 `enabledFlag !== true` 或 **`mode !== "enabled"`**：直接返回 **`displayCandidateUserId = matchRow.candidateUserId`**，`displaySourceType = "match_result_original"`，`finalMatchDecisionMeta = null`**。
   - 否则：按 `viewerUserId` + `frozen: true` 查询最多 12 条 **`pairwise_pool_finalize_meta`**，解析 `meta` 为 **`FinalMatchDecisionMetaV1`**（`parseFinalizeMetaV1Loose`），且要求 **`meta.staticTop1CandidateUserId === matchRow.candidateUserId`**（与 batch 静态 Top1 绑定）；校验 **`selectedCandidateUserId`** 存在于 `User` 表，且属于 `{staticTop1, pairwiseWinner}` 允许集合；通过后返回 **`displayCandidateUserId = selected`**，并由 **`mapDisplaySourceTypeFromMeta`** 决定 **`displaySourceType`**，附带 **viewer-safe** 的 **`finalMatchDecisionMeta`**。
3. **`MatchingFinalizePairwiseService`** 将冻结元数据写入 **`PairwisePoolFinalizeMeta`**，**不**写 `MatchResult`（与 M3.8-M11 注释一致）。

### 3.3 `displayCandidateUserId` 在哪里生成 / 解析 / 返回

- **生成（展示语义）**：在 **`resolveMatchResultDisplay`** 内计算；**非** SQL 生成列，而是 API 读路径组合 `MatchResult` + `pairwise_pool_finalize_meta` + env gate。
- **返回**：`MatchingService.getLatestResultForUser` 将 `display` 字段 spread 进响应（`MatchResultViewerPayload`）。

### 3.4 `displaySourceType` 当前可能取值

类型定义见 **`MatchResultDisplaySourceType`**（`matching-result-display.ts`）：

- `match_result_original`
- `static_final`
- `pairwise_final`
- `static_fallback`

映射规则见 **`mapDisplaySourceTypeFromMeta`**：若 `selected !== originalCandidateUserId` → `pairwise_final`；否则依 `meta.sourceType` 区分 `static_fallback` / `pairwise_final` / `static_final`。

### 3.5 `finalMatchDecisionMeta` 当前 viewer-safe 字段

**API 对外**使用 **`ViewerSafeFinalMatchDecisionMeta`**（`toViewerSafeFinalMatchDecisionMeta` 投影自 **`FinalMatchDecisionMetaV1`**），字段包括：

`sourceType`, `mode`, `pairwiseProposalRecommendation`, `selectedCandidateUserId`, `staticTop1CandidateUserId`, `pairwiseWinnerCandidateUserId`, `wouldChangeStaticResult`, `fallbackReason`, `frozen`, `frozenAt`, **`appliedToFinalScore`**, **`appliedToWorkerRanking`**

（不含 raw pairwise 分数、六维、`strongRisk` 等；与 M3.8-M11 设计一致。）

### 3.6 Pairwise finalize 是否已能影响 `displayCandidateUserId`

**能**——在 **`PAIRWISE_FINAL_MATCH_ENABLED=1` 且 `PAIRWISE_FINAL_MATCH_MODE=enabled`** 且存在**绑定成功**的冻结 `pairwise_pool_finalize_meta` 时，`resolveMatchResultDisplay` 可将 **`displayCandidateUserId`** 设为 **`meta.selectedCandidateUserId`**（可能等于 static Top1 或 pairwise winner，取决于 `buildFinalMatchDecisionMetaV1` 的门禁逻辑）。

### 3.7 `appliedToFinalScore` / `appliedToWorkerRanking`

- **`FinalMatchDecisionMetaV1`** 中两字段类型为字面量 **`false`**（`final-match-decision-meta.builder.ts`）。
- **`parseFinalizeMetaV1Loose`** 拒绝 **`appliedToFinalScore !== false` 或 `appliedToWorkerRanking !== false`** 的持久化 JSON。
- **Viewer-safe** 响应中照抄为 **boolean**，当前产品路径下恒为 **`false`**。

### 3.8 是否已做到「不改 `MatchResult.candidateUserId`、不改 `finalScore`，只改 display」

**是（在现有 finalize 与 GET 路径下）**：`MatchingFinalizePairwiseService` 文档化承诺**不**更新 `MatchResult` 行；`getLatestResultForUser` **不**写库；展示通过 **额外字段** `displayCandidateUserId` / `displaySourceType` 表达。`finalScore` 仍为行上原始分数。

### 3.9 M5.3 可复用的 M3.8 能力

- **`resolveMatchResultDisplay`** 的 **env gate + DB 绑定 + viewer-safe meta** 模式。
- **`displayCandidateUserId` / `displaySourceType` / `finalMatchDecisionMeta`** 作为**唯一**用户可见「当前匹配对象」来源（前端已用 `displayCandidateUserId || candidateUserId`，`FinalMatchPage.jsx`）。
- **`pairwise_pool_finalize_meta`** 作为「展示决策侧车」落库范式（M5.3 可考虑**同类侧车**或**扩展 meta schemaVersion**，本计划**不写代码**）。
- **`MatchResultViewerPayload` + `MatchingResultResponse`** 的扩展习惯（已含 `multiSourceFinalDecision`）。

### 3.10 M5.3 不能复用或需补齐的能力

| 能力 | 状态 |
|------|------|
| **RRM Top2 bounded 二选一的展示门禁** | **未实现** — 今日 resolver 只理解 **pairwise finalize meta**；RRM winner 进入 display 需 **新 eligible 规则 + 新 meta 或 schemaVersion 扩展**，属 **M5.3-B+ 代码里程碑**。 |
| **产品级 Guardrails 引擎（非 M5.1 侧车 cautions）** | **未与 display 写路径挂钩** — M5.1 `sources.guardrails` 为只读侧车；**需 M5.3-B** 定义硬拦截与 `viewer_safe_no_caution_signal` 的边界。 |
| **`displaySourceType` 新枚举** | **类型上未存在** — 若引入 `rrm_top2_bounded_selector` / `multi_source_rrm_top2`，需同步 **`MatchResultDisplaySourceType`**（API + `apps/web/src/api/matching.ts` + 前端分支），本计划仅命名预案。 |
| **Top2 来源与 RRM 输入对齐** | **需设计对齐** — Static Top2 shortlist 与 RRM 输入 job 的关联键（poolId / jobId / fingerprint）须在 M5.3-B 冻结，避免「RRM 看到的 Top2」与「Static Top2」漂移。 |

若某项在后续实现中发现与上表冲突，以代码为准并回写本计划「修订记录」。

## 4. M5.3 与 M3.8 的关系

**M3.8 已解决：**

- **`MatchResult.candidateUserId`** 保留为 **batch / worker 语义下的 baseline（静态 Top1）**。
- **`finalScore`** 保留为行上原始分数。
- **实际展示**由 **`displayCandidateUserId` / `displaySourceType` / `finalMatchDecisionMeta`** 组合表达；前端**不必**等于 `candidateUserId`。
- **Pairwise** 通过 **finalize 侧车表** 影响展示，且不写回 `MatchResult` 主列。

**M5.3 不推翻 M3.8**，只在 **同一 display 层**增加一种（或多种）**受控来源**：

- 建议新增 `displaySourceType` 取值（**命名预案**，实现属 M5.3-B）：例如 **`rrm_top2_bounded_selector`** 或 **`multi_source_rrm_top2`**，与现有 `pairwise_final` / `static_final` 等并列，由 **`resolveMatchResultDisplay`（或与其等价的单一 resolver）** 在开关打开时择优返回。
- **`multiSourceFinalDecision`**（M5.1/M5.2）继续作为 **只读审计 / shadow**；是否进入 **enabled** 的 **决策 trace** 应写入 **meta 或侧车 JSON**（与 M5.2-M4 audit 口径衔接），具体字段 **M5.3-B** 冻结。

## 5. M5.3 Enabled Display 的目标

### 5.1 M5.3 要做

- 在 **feature flag + eligible rules** 下允许 **RRM Top2 bounded selector** 影响 **`displayCandidateUserId`** 与 **`displaySourceType`**。
- **扩展 / 版本化** `finalMatchDecisionMeta`（或平行结构）以记录 **来源、规则版本、shadow/consensus 引用、回滚指针**（不写 raw RRM 向量）。
- **支持回滚**：关闭开关或 guardrail fail → 回退到 **`match_result_original` 或 static/pairwise 既有路径**（优先级在 M5.3-B 写死）。
- **Admin audit**：延续 M5.2-M4 CLI / 聚合思路，对 **enabled** 决策单独出 run record（**不**在本计划写实现）。
- **为 M6.1 `decisionContext` 预留**：在 meta 中预留 **稳定、可审计、无敏感比较** 的字段位（具体 schema **M5.3-B**）。

### 5.2 M5.3 不做（红线）

- **不**改 `MatchResult.candidateUserId`、**不**改 `finalScore`、**不**改 20 维画像算法本体、**不**改 RRM evaluator 公式实现。
- **不**改 Pairwise **生成**逻辑（可将调用频次降为 optional，而非改 prompt/schema）。
- **不**在 **`GET /matching/result` read path** 现场跑 RRM；**不**让 RRM 脱离 Top2；**不**让 RRM 绕过 Guardrails。
- **不做** M7 Assistant / M8 Timeline / M9 evaluation dashboard（与本里程碑无关）。

## 6. 推荐流程（产品 / 工程顺序）

```text
Step 1：Hard filters / preference filters（既有池与门禁）
Step 2：20 维画像 + Static scoring 生成 Top2（复用 shortlist / pool 现有能力）
Step 3：RRM-Sim 仅对 Top2 做二选一（离线或异步 job；结果进入 viewer-safe 摘要 / meta）
Step 4：生成并校验 viewer-safe rrmSimReadonlySummary（与 M5.2 契约一致）
Step 5：Guardrails 检查 RRM winner（产品规则 + 与 M5.1 侧车信号的关系在 M5.3-B 定义）
Step 6：若 enabled 开关打开且满足 eligible rules，则：
        displayCandidateUserId = RRM Top2 winner
        displaySourceType = rrm_top2_bounded_selector（或计划最终命名）
Step 7：保留 MatchResult.candidateUserId / finalScore 不变
Step 8：记录 decisionContext，为 M6.1 feedback 做准备
```

## 7. 风险与红线

- **Shadow ≠ Enabled**：M5.2 shadow proposal **不改变**用户所见；M5.3 enabled 一旦误配，**直接影响** `displayCandidateUserId`，需 **默认 off + 灰度 + 回滚**。
- **`viewer_safe_no_caution_signal` 误读**：M5.1/M5.2 侧车中的 pass **不等于**完整安全系统通过（见 M5.2-M4 audit 注释）；M5.3 **必须**单独定义 **eligible guardrails**。
- **Top2 漂移**：若 RRM 输入与 static shortlist 不一致，可能出现 **合规 / 解释**风险；需 **单一事实来源**（fingerprint / job 绑定）。
- **Resolver 复杂度**：`resolveMatchResultDisplay` 已含 pairwise 分支；追加 RRM 需 **明确优先级与互斥**，避免多源竞态。

## 8. 与 M5.1 / M5.2 的衔接

- **M5.1** `multiSourceFinalDecision`：**只读**侧车；可作为 **enabled** 前的 **观测与 shadow 共识**输入（已实现 M5.2-M3 shadow proposal 纯计算）。
- **M5.2** `rrmSimReadonlySummary` **writer**：enabled 后应保证 **GET** 仍 **不**重跑 evaluator；展示依赖 **已写入** 或 **可推导** 的 viewer-safe 摘要。
- **M5.2-M4B CLI**：可作为 **Admin** 侧回归工具；**不**替代产品 telemetry。
