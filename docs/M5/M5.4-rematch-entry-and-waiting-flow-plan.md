# M5.4 — Rematch Entry and Waiting Flow Plan

## 1. 一句话结论

当前用户在**已存在 ready 的 `MatchResult`** 时进入 **`/matching-waiting`**，会被 **`GET /matching/status` 的 `ready`** 触发 **`MatchingWaitingPage` 的「ready → 编排 / AI job → 跳转 `FinalMatchPage`」逻辑**，从而在**未完成新一轮入队与 batch-match** 的情况下回到**旧**最终结果（含旧 `finalScore`）。修复应走 **最小增量**：在 **`FinalMatchPage` 提供显式「重新匹配」**（调用既有 **`POST /matching/enqueue`**），在 **`MatchingWaitingPage` 增加 rematch 模式**（在确认 **`GET /matching/result` 已换为新行** 之前**禁止**沿用旧 `ready` 的自动跳转）。**无需删除旧 `MatchResult`**；新 run 由 worker **`matchResult.create`** 产生新行，**`batchId` / `id` / `createdAt`** 均可区分新旧（见下文）。

## 2. 用户路径与复现

1. 用户曾完成匹配 → DB 中存在 `match_results` 行，`batch_match_queue` 最新行为 `matched`（或历史上曾匹配）。
2. 用户重新填写问卷 → `QuestionnairePage` 提交后仅展示成功文案，**不调用** `enqueueMatching`；用户点击 **「下一步：前往匹配等待页」** → 导航至 `/matching-waiting?userId=…`（见 `apps/web/src/pages/QuestionnairePage.jsx`）。
3. `MatchingWaitingPage` 挂载后 `getMatchingStatus` → **`ready`**。
4. `status === "ready"` 的 `useEffect`（编排 / `getLatestPreviewPool` / `ssLastJob` / `navigateFinalWithJob`）执行 → **直接 `replace` 到 `/final-match?...`**，用户看不到「入队」入口或新一轮等待。

## 3. 根因分析（对应排查结论）

### 3.1 等待页为什么会自动跳 `FinalMatchPage`？

`MatchingWaitingPage` 在 **`statusPayload?.status === "ready"`** 时进入大块 `useEffect`：拉取最新 preview pool、复用或触发 orchestration、并根据 AI simulation job 状态调用 **`navigateFinalWithJob`** → `/final-match?userId=…&aiSimJobId=…`（见 `apps/web/src/pages/MatchingWaitingPage.jsx` 约 218～403 行）。该逻辑假设 **「ready」即本轮结果已可消费并应去最终页**。

### 3.2 是否因为 `GET /matching/status` 返回 `ready`？

**是。** 后端 `MatchingService.getStatusForUser` 在以下情况返回 **`{ status: "ready" }`**（见 `apps/api/src/modules/matching/matching.service.ts`）：

- 不存在任何 `batch_match_queue` 行时：若存在任意 `matchResult`，则 **`ready`**（第 77～78 行）；
- 最新队列行 **`status === "matched"`** 时：**`ready`**（第 87～88 行）；
- 其他非 `waiting` / `processing` 的队列状态且存在 `latestResult` 时，亦可能落到 **`ready`**（第 91～93 行）。

因此**只要历史上已有匹配结果 / 上一轮队列已 `matched`**，用户再次进入等待页就会拿到 **`ready`**，与「是否刚发起新一轮匹配」无关。

### 3.3 是否因为 `GET /matching/result` 已存在？

**间接是**：`status` 的 **`ready`** 由 **「最新队列 + 是否存在 `MatchResult`」** 推导，**不**单独查询「是否有**新** batch 的结果」。最终页展示的仍是 **`getLatestResultForUser`** 按 **`createdAt desc`** 取到的**最新一行**；若用户未跑新 batch，则一直是**旧行**（旧 `finalScore`）。

### 3.4 重新提交问卷后是否会自动 `enqueue matching`？

**否。** `QuestionnairePage` 在 `submitQuestionnaire` 成功后仅 `setSubmitOk(true)`，并提供按钮跳转 **`/matching-waiting`**，**没有**调用 `enqueueMatching`（`apps/web/src/pages/QuestionnairePage.jsx`）。

### 3.5 当前是否已有「重新生成 preview pool / enqueue matching」的 API？

| 能力 | 路径 / 方法 | 说明 |
|------|-------------|------|
| 入队 | `POST /matching/enqueue` + `EnqueueMatchDto` | 已有；需问卷画像存在；若已有一条 `waiting` 队列则返回该条（`matching.service.ts` `enqueue`）。 |
| 状态 | `GET /matching/status/:userId` | 已有；payload 当前**仅** `{ status }`，**无** `latestMatchResultId` / `batchId`。 |
| 结果 | `GET /matching/result/:userId` | 已有；返回**最新** `MatchResult` + display 等。 |
| Preview pool | `GET .../preview-pool/user/:userId/latest`、`POST /preview-pool/generate` | 已有（`apps/web/src/api/previewPool.ts`）。**重新匹配是否必须先 regenerate** 取决于 worker 是否要求 **active** preview pool 及池内候选人是否随问卷更新；属产品/运维策略，本计划不强制与「仅 enqueue」绑定，但若 batch 失败原因为 **无 active pool**，前端可在计划外增加「去预览池」引导。 |

### 3.6 当前是否已有 `batchId` / `runId` 可区分新旧匹配？

**有，无需新 schema 即可区分「哪一次匹配结果」**：

- **`MatchResult`**：`id`（cuid）、`batchId`（外键 `MatchBatch`）、`createdAt`（`schema.prisma` `match_results`）。
- Worker 每轮成功匹配对队列项执行 **`matchResult.create`**（**新行**），再 **`batchMatchQueue.update` → `matched`**（`batch-match.processor.ts`）。

因此「新 run 完成」的判据可以是：**`GET /matching/result` 返回的 `id`（或 `batchId` / `createdAt`）与 rematch 开始前记录的 baseline 不同**。

**队列侧**：`batch_match_queue.id` 每 enqueue 一条新 `waiting` 行；**`orderBy: { createdAt: "desc" }`** 下「最新队列」与「最新 `MatchResult`」在时间上应对齐同一轮 batch，但**以前端为准**时建议以 **`MatchResult.id` 变化** 作为「新结果已落地」的硬条件，避免仅依赖 `status === "ready"` 的竞态。

## 4. 目标行为（产品规格）

### 4.A `FinalMatchPage` — 最小「重新匹配」入口

- 增加次要按钮文案示例：**「重新匹配」**（样式保持与现有页面一致即可，避免大改 UI）。
- 点击后顺序建议：
  1. **可选**：`GET /matching/result/:userId` 读取当前展示的 **`id`** 与 **`createdAt`**（作 baseline），写入 **`sessionStorage`**（例如键 `peima:rematchBaselineMatchResultId`、`peima:rematchBaselineMatchResultCreatedAt`），**避免把真实 ID 写进 URL**（防泄露与误分享）。
  2. **`POST /matching/enqueue`**；失败则 toast / 页面内错误文案，**不导航**。
  3. 成功则 **`navigate('/matching-waiting?userId=…&rematch=1', { replace: true })`**（或 `replace: false` 按产品偏好；建议 `replace` 减少「后退又回到旧 final」）。
- **若 enqueue 因业务原因不可行**（例如缺画像）：沿用现有 API 错误信息，**不写假成功**。

### 4.B `MatchingWaitingPage` — `rematch=1` 模式

当 **`searchParams.get('rematch') === '1'`**（可与 `forceNewRun=1` 同义，择一即可）：

1. **禁止**在「旧 `ready` + 旧 `MatchResult`」上与当前实现一样**立刻**执行 `navigateFinalWithJob`。
2. 典型时序：入队后应先出现 **`waiting` → `processing` → `ready`**。在 **`waiting` / `processing`** 阶段，保持现有轮询 **`getMatchingStatus`** 即可。
3. 当再次变为 **`ready`** 时：
   - 调用 **`getMatchingResult(userId)`**（或已有 load 链中附带结果比较）；
   - 若 **`result.id`（或 `batchId`）仍等于 baseline** → 视为**新一轮结果尚未写入**（或极端竞态），**继续定时 `load()`**，并展示简短说明（避免无限静默）；
   - 若 **已不等于 baseline** → **清除**与 orchestration / `ssLastJob` / pairwise 相关的 **sessionStorage** 中**该 user+pool** 键（避免沿用**上一轮**的 `aiSimJobId` 跳 final），再**允许**执行现有「ready → 编排 → final」逻辑，或 **`navigate('/final-match?userId=…')`** 让最终页自行拉最新 result。
4. **入队失败**（未进入 rematch 成功路径）：不设置 `rematch=1`，或设置错误状态并 **不**自动跳转。

### 4.C 后端最小方案（可选增强）

**默认可不改后端**：仅靠 **`MatchResult.id` / `createdAt`** + `rematch` + `sessionStorage` 即可闭环。

**可选**（减少前端轮询歧义）：扩展 **`MatchStatusPayload`**，例如增加：

- `latestMatchResultId?: string | null`
- `latestMatchResultCreatedAt?: string | null`（ISO）
- `latestQueueStatus?: string | null`
- `latestQueueId?: string | null`

在 **`getStatusForUser`** 内与现有查询合并返回（**不改** `MatchResult` 表）。前端 rematch 模式可优先用 **`status === 'ready' && latestMatchResultId !== baseline`** 判定，**仍建议**最终以 **`GET /matching/result`** 为准做一次确认。

**不推荐**为「rematch token」单独加表，除非合规审计强制要求；当前 **`batchId` + `MatchResult.id`** 已足够追溯。

### 4.D 不删除旧结果

与 worker 行为一致：**每次成功匹配 `create` 新行**；旧行保留，满足审计 / M9 / 对比需求。**禁止**在前端或 API 通用路径 **`delete` 旧 `MatchResult`**。

### 4.E 不改写旧行上的 `candidateUserId` / `finalScore`

重新匹配仅依赖 **新 insert**；**不**对旧行做 `update`。

### 4.F 与 M5.3 RRM / Pairwise 的关系

- **不改** `resolveMatchResultDisplay`、RRM evaluator、Pairwise **生成**逻辑。
- Rematch 仅改变 **「哪一条 `MatchResult` 为 latest」**；新行仍走同一套 display / RRM meta 读路径。
- **可选**：进入 rematch 成功后清理 **与旧 pool / 旧 job 绑定的 sessionStorage**，避免 M3.8 编排层误用旧 `aiSimJobId`（见 §4.B）。

## 5. 测试与验收建议

| # | 场景 | 期望 |
|---|------|------|
| 1 | 已有 `ready` 的 `MatchResult`，普通打开 `/final-match` | 仍展示**当前最新**结果（可为旧行）。 |
| 2 | 点击「重新匹配」并入队成功 | **不**立刻回到 final（应先落在 `matching-waiting?rematch=1` 且状态为 `waiting`/`processing`）。 |
| 3 | `rematch=1` 且旧 `ready` | **不**触发自动跳转 final，直至 **`getMatchingResult` 的 `id` ≠ baseline**。 |
| 4 | 新 batch 完成 | `status` → `ready` 且新 `MatchResult` 出现后，再允许跳转 final；**新** `finalScore` / `batchId` 来自新行。 |
| 5 | DB | 旧 `MatchResult` 仍存在；行数随 rematch 次数增加（成功时）。 |
| 6 | `PEIMA_M5_RRM_TOP2_ENABLED` | rematch 流程**不依赖**该开关；resolver 行为不变。 |

自动化：可为 `getStatusForUser` 增加极小的单元测试（多队列 + 多 result 排序）；前端以 **RTL / e2e** 或 **mock fetch** 验证 rematch gate（若项目已有同类测试基础设施）。

## 6. 实现顺序建议（最小 PR 切分）

1. **文档评审**（本文）→ 锁定 `rematch` 参数名与 `sessionStorage` 键名。  
2. **`MatchingWaitingPage`**：抽「是否允许 ready 自动跳 final」的谓词；接入 `rematch` + baseline 比较；必要时在「新 result 已确认」后清理 session 键。  
3. **`FinalMatchPage`**：增加按钮 + `enqueueMatching` + 写 baseline + 导航。  
4. **（可选）** `MatchingService.getStatusForUser` 扩展 payload + `matching.ts` 类型 + 单测。  
5. **问卷页（可选）**：提交成功后除「去等待页」外增加一句「若已匹配过，请到最终结果页使用重新匹配」——避免用户仍以为「去等待页 = 新匹配」；属 UX 文案，非必须。
