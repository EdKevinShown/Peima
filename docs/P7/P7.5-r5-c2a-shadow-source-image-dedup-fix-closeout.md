## 1. 问题现象

[P7.5-r5-c2](./P7.5-r5-c2-apply-writer-signoff-runner-closeout.md) signoff runner 五案中 **Case D FAIL**：

- 期望：`sourceVersion=onboarding-photo-preview-v2-vision`，`applyResult.applied=true`，`reason=ok`

结论：runner 与 writer guard **行为正确**；阻塞在 **shadow hypothetical 槽位** 未满足 6 个互异 `sourceImageKey`。

---

## 2. 根因

1. **Shadow builder 未对齐 r4-o2 去重**：`buildVisualRankingShadowV1` 在 3+2+1 选位时只排除 `candidateUserId`，未在每一档 pick 时维护 `usedSourceImageKeys`（`displaySourceKey`）。
2. **`pickTopByScore` 单次批量 slice**：同一 tier 内一次 `slice(0, take)` 可在 **未更新** `excludeSourceKeys` 的情况下选中多名共享同一 `r4h:<slug>` 的候选（例如 demo 中 a、b 同图），导致 shadow 6 槽出现重复 source key，writer 按 r5-c1 拒绝写 v2。

门控池若本身有足够互异 r4h slug，baseline v1 可过 active audit，但 shadow 仍可能因上述逻辑重复 key。

## 4. Shadow `sourceImageKey` 去重规则（对齐 r4-o2）

- 每个 shadow 候选在构建时计算 `displaySourceKey` = `previewPoolRowDisplaySourceKey({ id, firstImageUrl })`：
  - r4h / r4h-import URL → `r4h:<slug>` / `r4h-import:<slug>`
  - 解析失败 → 完整 URL 或 `candidate:<id>` fallback
- 3+2+1 每一档 pick（含 reflow）排除：
  - 已选 `candidateUserId`
  - 已选 `displaySourceKey`
- `pickTopByScore` 每取 1 人即更新本地 exclude，再取下一名（避免同 tier 内重复 slug）
- 可用 **互异** source image **不足 6**：shadow 可少于 6 槽（readonly 对照仍可用）；writer 继续 `insufficient_unique_source_images`，**不**用重复图凑 v2
- 仍保持：无 viewer self、异性 gate、无 blocked review（由门控池 + writer guard 保证）
