# P7.4-r1 — Onboarding 照片检测能力设计方案（仅方案，无代码）

## 设计前提与边界

- **不做** AI 美化、**不生成** AI 头像。  
- **不改** worker、`finalScore`、`MatchResult`、旧 `PreviewPool`、**onboarding 3+2+1 池生成规则**（P7.1 / P7.2 主链保持）。  
- P7.3 已完成：**格式 / 大小 / 可解码** 的前端 MVP；P7.4 在「是否适合作为本人照进入预览流程」上增量决策。

---

## 重点设计问题（1–10）

### 1. 是否需要人脸检测

**建议：需要，但分阶段、弱依赖「高精度识别」。**

| 阶段 | 做法 | 说明 |
|------|------|------|
| **r1（最小）** | 可选 **人脸存在性**（是否检测到 ≥1 张人脸），阈值保守 | 降低「无脸 / 风景 / 物体图」进入预览的概率 |
| **r2+** | 人脸框质量、姿态、是否多人脸辅助 | 与单人照、遮挡策略联动 |

**不推荐 r1 上「强身份认证级」人脸比对**（与「不做复杂人脸识别」一致）：不做「是否本人」与公安库比对，仅做「像一张含有人脸的人像照」的弱门槛。

### 2. 是否需要单人照检测

**建议：需要，r1 用「弱规则」即可。**

- **r1**：人脸数 **= 1** 为通过；**= 0** 拒绝；**> 1** 提示「请上传单人照片」或进入「需人工/二次确认」分支（见误伤）。  
- **原因**：多人照会污染审美预览与后续运营观感；与 P7 onboarding 产品叙事一致。

### 3. 是否需要清晰度检测

**建议：需要，以「可解释的简单指标」为主。**

- **前端**：可继续做 **分辨率下限**（P7.3 曾可扩展）、**文件熵/压缩后尺寸** 等轻量启发（易误伤，慎用）。  
- **后端 / 异步**：更适合 **拉普拉斯方差、Tenengrad、边缘密度** 等经典无参考清晰度指标（无深度学习也可实现），设 **双阈值**：硬拒绝仅极端模糊，中间带 **警告 + 允许继续**（见误伤）。

### 4. 是否需要遮挡 / 过暗 / 过糊判断

**建议：r1 做「粗粒度、可降级」。**

| 维度 | r1 建议 | 说明 |
|------|---------|------|
| **过暗** | 亮度均值/直方图分位数 | 实现简单，误伤可控（阈值偏松） |
| **过糊** | 与清晰度指标合并 | 避免重复弹窗 |
| **遮挡** | **r1 可不单独建模** | 口罩/手挡脸等易与合规、文化场景冲突；可放到 r2 或运营策略 |

若 r1 必须上遮挡：建议仅 **极端情况**（如人脸框内有效像素占比过低）且默认 **警告不拦**。

### 5. 检测放在前端、后端，还是异步审核任务

**推荐组合（分层）：**

| 层级 | 职责 | 说明 |
|------|------|------|
| **前端** | 已有 P7.3：格式、大小、可解码；可选 **分辨率下限**、**上传前压缩提示** | 即时反馈、省带宽 |
| **后端（同步）** | **上传完成后**对落盘文件跑检测流水线（人脸数、清晰度、亮度等），**在响应或紧随其后的 status 中返回** | 可信、不依赖用户篡改 MIME |
| **异步（可选）** | **抽检 / 复审 / 风控升级**、模型迭代 | 不阻塞首屏；与 worker 禁令解耦可用 **独立队列或 cron**，但**默认不占用现有 matching worker** |

**结论**：**P7.4-r1 推荐「前端轻量 + 后端同步检测」**；异步审核作为 **P7.6 运营后台** 的延伸，不在 r1 强依赖。

### 6. 是否新增 `UserImage.status` / `reviewStatus` / `rejectionReason` / `reviewedAt`

**建议：新增（或等价枚举字段），利于审计、重试与误伤申诉。**

**最小集合（推荐）：**

- **`detectionStatus`**（或 `status`）：`pending` | `passed` | `failed` | `skipped`（历史数据兼容）  
- **`detectionReasonCodes`**：`string[]` 或 JSON（机器可读，便于 i18n 映射）  
- **`detectionDetail`**：可选 JSON（阈值、分数、版本号，排障用）  
- **`detectedAt`**：`DateTime?`  

**人工/运营复审（可与 P7.6 合并）：**

- **`reviewStatus`**：`none` | `pending_review` | `approved` | `rejected`  
- **`rejectionReason`**：文本或 code（运营填写 / 模板）  
- **`reviewedAt`**  

**r1 可只上 `detectionStatus` + `detectionReasonCodes` + `detectedAt`**，`review*` 留到 P7.6，避免一次 migration 过大。

### 7. 不合格照片是否阻止进入 `/onboarding/photo-preference`

**建议：阻止「明确不合格」；对「灰区」采用「警告 + 允许」。**

- **硬拦**：格式/大小/不可读（P7.3 已拦）；**人脸数 = 0**、**人脸数 > 1（若启用）**、**极端模糊/全黑**（低于硬阈值）。  
- **软提示**：略暗、略糊、略小分辨率 → **Toast/横幅 + 仍允许上传**，或在 `UserImage` 上标记 `warning` 但不改 `detectionStatus=failed`。  

进入 **`/onboarding/photo-preference`** 的前置条件建议与 **「是否存在至少一张 `detectionStatus=passed` 的 UserImage」** 对齐（或「最新一张为 passed」——产品二选一）。

### 8. 如何避免误伤用户

1. **双阈值**：硬拒绝 vs 仅警告。  
2. **版本化检测**：`detectionModelVersion` / `rulesVersion`，便于回滚与 A/B。  
3. **重试与替换**：同一用户允许多张图；**仅最新一张参与门禁**或 **任一 passed 即可**，避免一次失败卡死。  
4. **申诉入口（P7.6）**：`reviewStatus` 管道预留。  
5. **文案**：说明「系统仅做基础质量判断，非身份认证」，降低「被冤枉」感受。  
6. **降级开关**：环境变量或远程配置 **关闭人脸检测**（例如活动期、低端机型服务端失败时 fallback）。

### 9. 失败提示文案（建议）

| 场景 | 文案（示例） |
|------|----------------|
| 未检测到人脸 | 未检测到清晰的人脸，请上传一张正脸、光线充足的本人照片。 |
| 多人入镜 | 请上传单人照片，避免多人合影。 |
| 画面过暗 | 照片偏暗，建议到光线更亮的环境重新拍摄。 |
| 画面模糊 | 照片不够清晰，请对焦后重新拍摄或换一张更清晰的照片。 |
| 检测服务暂不可用 | 暂时无法完成照片检测，请稍后重试；您仍可尝试继续（若开启降级）。 |

（具体以产品定稿与 i18n 表为准；**错误码 + 文案映射** 优于写死长句。）

### 10. 与 P7.1 / P7.2 / P7.3 的关系

| 阶段 | 职责 |
|------|------|
| **P7.1** | 登录分流、onboarding 路由与问卷门禁 |
| **P7.2** | 独立 onboarding 预览池 3+2+1、`acknowledge`、与旧 PreviewPool 隔离 |
| **P7.3** | 前端 **格式 / 5MB / 可解码**，不上模型 |
| **P7.4** | 在 **上传成功之后** 增加 **「适不适合做人像预览」** 的检测与状态；**不改变** 池内排序与生成公式，仅在 **准入** 上收紧或提示 |

即：P7.4 是 **UserImage 准入层**；P7.2 的池生成逻辑仍只吃「已通过检测」的图片集合（由查询或状态过滤实现）。

---

## A. 推荐方案（摘要）

- **人脸**：r1 做 **≥1 脸** 的弱检测；**单人** 用 **脸数 = 1**（>1 拦或警告按配置）。  
- **清晰度 + 过暗 + 过糊**：合并为 **少量无参考指标 + 双阈值**；遮挡 r1 不强制。  
- **位置**：**前端保持 P7.3**；**同步检测放后端**（上传接口内或紧接的 webhook 式内部调用），结果写入 **UserImage 检测字段**；异步复审留给 P7.6。  
- **门禁**：**无 passed 图则不进** `photo-preference`（与现有「有图」逻辑对齐并加强）；灰区 **警告可继续**（可配置）。

---

## B. 数据结构建议

**Migration（建议单独一条，命名示例）：`YYYYMMDDHHMMSS_user_image_detection_p7_4`**

在 `UserImage` 上（命名可微调）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `detectionStatus` | enum / string | `pending` / `passed` / `failed` / `skipped` |
| `detectionReasonCodes` | `String[]` 或 Json | 如 `NO_FACE`、`MULTI_FACE`、`TOO_DARK`、`TOO_BLUR` |
| `detectionScoreJson` | Json? | 各子项分数，可选 |
| `detectionRulesVersion` | string | 规则/模型版本 |
| `detectedAt` | DateTime? | 完成检测时间 |

**P7.6 预留（可同表延后加）：** `reviewStatus`、`rejectionReason`、`reviewedAt`。

**索引**：`(userId, detectionStatus, createdAt)` 便于取「用户最新一张 passed 图」。

---

## C. 前端流程

1. **P7.3 不变**：选文件 → 本地校验 → 上传。  
2. **上传返回**扩展：返回 `detectionStatus` / `reasonCodes`（或轮询 `/images/:id` 直到非 `pending`——若检测异步则才需要轮询；**r1 推荐同步返回**）。  
3. **结果分支**：  
   - `passed` → 允许跳转 **`/onboarding/photo-preference`**（或自动跳转，与现产品一致）。  
   - `failed` → 留在上传页，展示 **§9** 映射文案 +「重新选择照片」。  
   - `pending`（若存在）→ Loading + 超时提示 + 重试。  
4. **`GET /onboarding/photo/status`**：可将「是否有 **passed** 的图」纳入 `nextStep` 或单独字段 `hasPassingPhoto`，与问卷门禁文档对齐（需产品确认是否升级 API）。

---

## D. 后端流程

1. **`POST /images/upload`**（或专用 onboarding 上传路由）：落盘 → **检测流水线**（顺序：解码校验 → 亮度 → 清晰度 → 人脸数）。  
2. **写库**：更新对应 `UserImage` 的 `detectionStatus` 等；失败时 **不删文件** 或按策略删除（建议保留便于审计，标记 failed）。  
3. **与 onboarding**：`getPhotoStatus` / 前端门禁以 **`UserImage` 状态** 为准，而非仅 `count > 0`。  
4. **依赖**：可选引入轻量库（如 OpenCV 绑定、face-api 级 WASM **仅服务端**）——实现阶段再选型；**禁止** 在上传路径引入大模型推理 unless 独立异步服务。

---

## E. 是否需要 migration

**需要**（若采用 §B 字段）。  
- **r1 最小**：仅 `detectionStatus` + `detectionReasonCodes` + `detectedAt` + `detectionRulesVersion` 即可。  
- **历史数据**：现有 `UserImage` 可 **`skipped` + 一次批处理 backfill** 为 `passed`（需产品同意「旧图默认信任」）或 **`pending`** 触发重检队列（工作量大，不推荐 r1）。

---

## G. 风险与误伤控制

- **环境光、肤色、妆容、口罩** → 误报；用 **双阈值 + 警告路径 + 配置降级**。  
- **服务端 CPU** → 限制最大边 resize 后再算子；超时则 `skipped` + 日志，产品决定「是否仍允许通过」。  
- **隐私** → 检测在自有服务器完成，日志不落原图；合规声明更新用户协议（非代码）。  
- **与 P7.2 池生成**：仅 **过滤候选数据源** 或 **仅允许 passed 图作为 viewer 主图**；**不改** 3+2+1 打分与 slot 逻辑。

3. **Prisma migration** + `UserImage` 字段 + 旧数据 backfill 策略文档一行。  
4. **ImagesService**：上传后检测函数（纯函数 + 可单测）→ 更新 row。  
5. **OnboardingService.getPhotoStatus**：`hasPhoto` 语义升级为 **hasPassingPhoto**（或新字段，避免破坏兼容则并行加字段）。  
6. **前端**：上传结果 UI + preference 入口守卫 + 文案表。  
7. **测试**：`images` 单测 + `onboarding` 单测 + 手测清单。  
8. **文档**：P7.4 closeout + 与 P7.6 边界说明。
