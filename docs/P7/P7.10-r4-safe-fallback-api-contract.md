## 2. Why this API contract is needed

[P7.10-r3](./P7.10-r3-p76-canonical-writer-design.md) defines a future **P7.6 canonical writer** that will formally write `MatchResult` / `matchInsights` / score / provenance. Before that writer (or before disabling the legacy PreviewPool worker), **GET `/matching/result/:userId` must express outcomes in a single, explicit vocabulary** so clients, ops, and monitoring do not misread HTTP 404 as “product broken.”

**Today (code-evidenced gaps):**

- `getLatestResultForUser` returns a full payload when a `MatchResult` row exists; otherwise throws `NotFoundException` (`No match result for user …`) — see `apps/api/src/modules/matching/matching.service.ts`.
- Queue state (`waiting` / `processing` / `not_queued` / `ready`) lives on **`GET /matching/status/:userId`** only (`getStatusForUser`).
- `FinalMatchPage` calls `getMatchingResult` only; a 404 surfaces as a generic error string — no `matching_pending` or `no_result` branch.
- P7.6 read overlay (`p76ReadPathMeta`, `fallbackUsed`, `fallbackReason`) is attached when a row exists, but there is **no top-level `resultState`** tying together canonical / sidecar / baseline / pending / empty.

If the legacy worker is turned off without this contract, viewers with no new `MatchResult` row will see unexplained **404** on Final Match while status may still say `waiting` or `not_queued` on another endpoint — unacceptable for safe deprecation.

**Terminology (from P7.10-r2):**

- **safe_fallback** = P7.6 preferred path unavailable, display safely uses **stable baseline** (`match_result_original`, `static_fallback`, or resolver baseline projection) — **not** “legacy photo matching fallback.”
- **`PEIMA_P76_READ_PATH_FALLBACK_LEGACY`** = fallback to **baseline display** when read-path overlay cannot apply (`p76-read-path-env.ts`).

**This round:** design only — **no API implementation.**

| Aspect | Current behavior |
|--------|------------------|
| Route | `getStatus` → `getStatusForUser` (`matching.controller.ts` L47–56) |

## 4. Target state vocabulary

Primary field: **`resultState`**

```text
"ready" | "safe_fallback" | "matching_pending" | "no_result"
```

Optional: treat internal resolver exception with baseline display as **`safe_fallback`** with `safeFallback.reason = "exception"` (no separate `error_safe_fallback` enum required).

### 4.1 State definitions

| resultState | Meaning | HTTP strategy (recommended) | Has MatchResult? | UI destination |
|-------------|---------|:--:|:---:|----------------|
| **ready** | Displayable match outcome; canonical or stable baseline row; P7.6 overlay may change `displayCandidateUserId` without changing row | **200** | Yes (typical) | `FinalMatchPage` |
| **safe_fallback** | P7.6 canonical/sidecar path unavailable; **safe** use of baseline display / stable `MatchResult` / approved sidecar read-only per policy | **200** | Yes (typical) | `FinalMatchPage` (+ optional technical hint) |
| **matching_pending** | User in `waiting` or `processing` queue (or rematch awaiting new row) without a displayable new result | **200** (recommended) | Optional (stale row may exist) | `MatchingWaitingPage` |
| **no_result** | No displayable result; no active pending queue (or queue failed terminal with no row) | **200** (recommended) | No | Empty / CTA / onboarding |

**Notes:**

- **safe_fallback is not an error** and **not** legacy photo matching.
- **matching_pending** / **no_result** are **GET-level contracts**; they are **not** written into `MatchResult` by any writer ([P7.10-r3](./P7.10-r3-p76-canonical-writer-design.md) §6).

### 4.2 Mapping from today’s signals (design reference)

| Today signal | Future `resultState` | `displaySourceCategory` (additive) |
|--------------|----------------------|-------------------------------------|
| Row exists + overlay applied `p76_allowlist_sidecar_readonly` | `ready` (or `safe_fallback` if baseline display kept intentionally) | `p76_sidecar` |
| Row exists + `p76ReadPathMeta.fallbackUsed=true` | `safe_fallback` | `safe_baseline` |
| Row exists + `displaySourceType=match_result_original` / `static_fallback` (no P7.6 overlay) | `ready` or `safe_fallback` (if P7.6 was expected for allowlisted viewer) | `safe_baseline` / `finalize` |
| Row exists + future `matchInsights.p76CanonicalWriter.appliedToMatchResult` | `ready` | `p76_canonical` |
| Status `waiting` \| `processing`, no new row for rematch | `matching_pending` | `pending` |
| No row + status `not_queued` | `no_result` | `no_result` |
| No row + status `waiting`/`processing` | `matching_pending` | `pending` |
| 404 today (`No match result`) | `no_result` or `matching_pending` (must disambiguate via queue) | — |

## 5. Recommended response shape

**Additive / backward-compatible.** Do **not** remove or rename: `candidateUserId`, `finalScore`, `displayCandidateUserId`, `displaySourceType`, `static_fallback`, `match_result_original`.

### 5.1 Core type (design)

```typescript
type MatchResultResponseV1 = {
  resultState: "ready" | "safe_fallback" | "matching_pending" | "no_result";

  // Existing fields preserved when a displayable result exists
  id?: string;
  userId?: string;
  candidateUserId?: string;
  finalScore?: number | null;
  reasonSummary?: string | null;
  matchInsights?: unknown;
  status?: string;
  createdAt?: string;
  updatedAt?: string;
  displayCandidateUserId?: string | null;
  displaySourceType?: string | null; // enum values unchanged

  // Existing projection / sidecars — preserved when present
  resolvedCandidateUserId?: string | null;
  resolvedSourceType?: string | null;
  baselineCandidateUserId?: string | null;
  fallbackUsed?: boolean;
  fallbackReason?: string | null;
  p76ReadPathMeta?: {
    enabled: boolean;
    fallbackUsed: boolean;
    fallbackReason: string | null;
    sidecarId: string | null;
    sourceVersion: string | null;
    rolledBack: boolean | null;
    violationStatus: string | null;
    pmSignoffStatus: string | null;
    opsSignoffStatus: string | null;
  };
  scoreBreakdown?: unknown;
  relationshipProfileScore?: unknown;
  relationshipProfileScoreV2?: unknown;
  multiSourceFinalDecision?: unknown;
  finalMatchDecisionMeta?: unknown;

  // Additive classification (new strings — not replacements for displaySourceType)
  displaySourceCategory?:
    | "p76_canonical"
    | "p76_sidecar"
    | "safe_baseline"
    | "finalize"
    | "pending"
    | "no_result";

  safeFallback?: {
    active: boolean;
    policyVersion: "safe_fallback_v1";
    reason?:
      | "canonical_missing"
      | "sidecar_missing"
      | "not_allowlisted"
      | "stale_sidecar"
      | "rolled_back"
      | "violation_row"
      | "candidate_missing"
      | "env_disabled"
      | "exception"
      | "baseline_only";
    from?: "p76_canonical" | "p76_sidecar" | "p76_read_path";
    to?: "baseline_display" | "stable_result" | "matching_pending" | "no_result";
  };

  queue?: {
    status?: "not_queued" | "waiting" | "processing" | "ready";
    queueId?: string;
    updatedAt?: string;
  };

  noResult?: {
    reason?:
      | "no_match_result"
      | "not_queued"
      | "candidate_pool_empty"
      | "onboarding_incomplete"
      | "legacy_writer_disabled"
      | "unknown";
    recoverable: boolean;
    nextAction?: "wait" | "start_matching" | "complete_onboarding" | "contact_support";
  };

  contractVersion: "p7.10-r4-safe-fallback-api-contract-v1";
};
```

### 5.2 Field presence by `resultState`

| resultState | Required top-level | Typical omitted |
|-------------|-------------------|-----------------|
| `ready` | `id`, `candidateUserId`, `displayCandidateUserId`, `finalScore`, `displaySourceType`, `contractVersion` | `noResult` |
| `safe_fallback` | same as ready + `safeFallback.active=true` | — |
| `matching_pending` | `resultState`, `queue`, `contractVersion` | `candidateUserId` (optional stale row fields) |
| `no_result` | `resultState`, `noResult`, `contractVersion` | match row fields |

### 5.3 Client compatibility

- **Old clients:** ignore unknown `resultState`; continue to use 200 body as today when row fields present.
- **Old clients on 404:** unchanged until implementation; migration window may dual-emit 404 + `resultState` on 200 (not recommended long-term).
- **Web `MatchingResultResponse`** (`apps/web/src/api/matching.ts`): future widen union for `displaySourceType` to include `p76_allowlist_sidecar_readonly` — **implementation deferred**.

## 6. HTTP strategy comparison

### 6.1 `matching_pending` and `no_result`

| Strategy | Pros | Cons | **Recommendation** |
|----------|------|------|-------------------|
| **A — Typed 200** with `resultState` + sparse body | No breaking change for clients that only check status code; Final page can branch on JSON; aligns with status endpoint fusion | Clients that only handle 404 must be updated to read `resultState` | **Preferred** |
| **B — 404 + structured body** | Familiar “not found” for caches | Nest default 404 may strip body consistency; conflates user-not-found vs no-result; breaks Final page today | Reject for primary path |
| **C — 202 Accepted** for pending | Semantically “in progress” | Unfamiliar for GET; caching/CDN odd | Optional alias only |

**User-not-found** remains **404** (`User … not found`) — distinct from `no_result`.

### 6.2 Implementation sketch (future, not r4)

Pseudo-flow for `getLatestResultForUser` successor:

```text
ensureUserExists
load latestQueue, latestMatchResult
if !latestMatchResult && queue in (waiting|processing) → 200 matching_pending + queue
if !latestMatchResult && !activeQueue → 200 no_result + noResult
if latestMatchResult → resolve display → classify ready | safe_fallback → 200 full body
```
