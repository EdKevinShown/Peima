# P7.5-r4-o2 — Active preview pool audit & image source dedupe (closeout)

## 1. 问题现象

- **男性浏览者**在 `/onboarding/photo-preview` 中，「符合你审美的人」**首张**仍出现**明显男性**肖像（与异性门控预期不符）。
- **「符合你审美的人」**与**「和你风格相近的人」**中出现**同一张物理图源**的重复展示（不同 `candidateUserId`，但视觉相同）。
- 示例 viewer：`/onboarding/photo-preview?userId=cmp70ft7a001e6znksjb2jo03`；funnel 显示 `after_opposite_gender_gate_final` 足够，但 UI 仍异常。

## 2. Active pool audit 结果（设计输出）

本机需在 **rebuild API** 后运行（脚本见下）。审计 JSON **不输出** phone / email / reviewNote / 完整 detection JSON；**userId 仅 masked**；`imageUrl` 不原文输出，使用 `image_url_redacted: true` 与 `source_image_key`。

CLI：

```bash
pnpm --filter @peima/api run p75:r4-o2-preview-pool-active-audit -- --viewerUserId=cmp70ft7a001e6znksjb2jo03
```

可选：`--mappingPath=.../dev-assets/test-user-images/mapping.json`（默认即该路径）。

每条 item 含：`pool_id_masked`、`viewer_gender_*`、`rank_in_pool`、`tier`、`candidate_user_id_masked`、`candidate_gender_raw`、`image_url_present`、`source_image_key`、`is_viewer_self`、`violates_opposite_gender_gate`、`duplicate_candidate_user_id`、`duplicate_image_source_key`、`mapping_file` / `mapping_gender`（若能从 r4h slug 反查 `mapping.json` 的 basename）。

**用于区分根因：**

| 类型 | 含义 |
|------|------|
| **A** | `violates_opposite_gender_gate: true`（DB 中候选性别与门控相反） |
| **B** | 门控为 false，但 `mapping_gender` 与人工素材不一致（标注/导入问题） |
| **C** | 页面缓存或旧池：对比 `pool_id_masked` 与重新生成后的审计 |
| **D** | `is_viewer_self` 或 `source_image_key` 与候选不一致（挂图错误） |

（本轮在生成链增加 **DB 性别二次校验** 与 **同源去重**，减少 A/D；B 依赖 **mapping + 重新 import** 更新 `User.gender`。）

## 3. 第一张「男生图」根因

典型组合：

1. **`User.gender` 仍为 female**，但首图实为男性素材（历史误导入 / 未复跑 import 合并性别）；异性门控只看 **DB gender**，故仍会进入池。
2. **NAM01915** 等男性图曾错误标为 female；mapping 修正后若 **未复跑** `p75:r4-import-candidate-images`，DB 性别未更新。

本轮在 **`mapping.json`** 增加 **`_devNote_r4o2`**，强调 **改 mapping 后必须复跑 import** 以执行 `mergeDemoCandidateUserFields`。

## 4. 第二 / 第四张重复图源根因

- **不同 `candidateUserId`** 复用 **同一 dev 源文件**：`imageUrl` 中 r4h **slug 段相同**（per-user 路径不同），仅做 **candidateUserId 去重** 无法排除。
- 审美 tier 与风格 tier 各自按分数选人，**未排除已选过的 `sourceImageKey`**，导致同一 slug 进入两个 tier。

## 6. Candidate 去重规则

- **`candidateUserId`**：六个 slot 互不相同（沿用 r4-o1：`buildSixNonSelfPreviewSlots` + `create` 前校验）。
- **`dedupeGatedCandidateRowsByUserId`**：Prisma 重复行仍保留。

## 7. Image source 去重规则

- 从首图 **`imageUrl`** 解析 **`extractDisplayImageSourceKeyFromImageUrl`**：优先 per-user marker `-r4h-u…--<slug>--`，其次 legacy `-r4h-import-<slug>`，否则 **整串 URL**（非 r4h 时退化为 URL 级唯一）。
- 选人维护 **`usedCandidateUserIds`** 与 **`usedImageSourceKeys`**（基于 `previewPoolRowDisplaySourceKey`）；**无 URL** 时使用 `candidate:<id>`，避免空 URL 误合并。
- **若无法凑满 6 个互异 source key**（在可选池约束下）：抛出与「候选不足」一致的 **`BadRequestException`**（中文长文案或「预览池生成出现异常」类守卫），**不重复凑图**。
- **`generate`**：对 slot 内 id 用 **`gAll` 再算一遍** 6 个 `source_image_key`，与 **Prisma `User.gender` 二次校验** 一并执行。
