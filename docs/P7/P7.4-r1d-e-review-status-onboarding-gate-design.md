# P7.4-r1d-e — reviewStatus 接入 Onboarding 门禁（设计方案，仅方案）

> 状态：**设计确认稿**；本轮 **不改代码、不写 migration、不生成 diff**。  
> 前置：P7.4-r1d-b（`reviewStatus` 字段 + 自动写入）、r1d-c2–c4（Admin API + 页面 + audit）、当前 `hasPassingPhoto` 仅看 `detectionStatus in (passed, skipped)`。

---

## 1. 一句话结论

**推荐采用方案 2：`hasPassingPhoto` 由「机器检测 + 人工审核」共同决定；`rejected` / `needs_reupload` 立即不算 passing 并可将 `nextStep` 拉回 `photo_upload`；`approved` 可覆盖机器 failed/skipped 视为 passing；`pending_review` MVP 不阻断但返回 `hasPhotoUnderReview`；`not_required` 仍按 detection 判断；不新增 DB 字段，只改 `onboarding.service.ts` 状态计算与前端提示。**

---

## 2. 推荐 hasPassingPhoto 规则

### 2.1 方案比较（A）

| 维度 | 方案 1：仅 detectionStatus | 方案 2：detection + reviewStatus（**推荐**） |
|------|---------------------------|---------------------------------------------|
| 与 Admin 一致性 | Admin reject 后用户仍可进问卷 | 审核结论对用户可见、可执行 |
| 实现复杂度 | 低 | 中（纯服务层规则） |
| 误伤 | 低 | 需定义 pending_review 不卡死 |
| 产品风险 | 违规/劣质图进入匹配叙事 | 审核滞后时 pending 仍可继续（可接受） |

**用户倾向评估（合理）**：

- `rejected` / `needs_reupload` → 不算 passing：**合理**，与运营动作一致。
- `approved` → 算 passing（即使 detection 为 skipped/failed）：**合理**，表达「人工放行」且不污染 `detectionStatus`。
- `pending_review` → MVP 允许继续：**合理**，避免 BlazeFace 超时导致全员卡死；用 `hasPhotoUnderReview` + 文案提示即可。
- `not_required` → 仍按 detection：**合理**，与 r1d-b 自动规则一致。

**补充硬规则**：

- 任意单张图：**先按 reviewStatus 判定，再回退 detection**（见下表）。
- **用户维度**：`hasPassingPhoto = ∃ 至少一张 UserImage 满足 per-image passing`（与现网「有一张 passed 即可继续」一致）。

### 2.2 单张 UserImage：`isPassingPhoto(row)` 规则表

| detectionStatus | reviewStatus | passing? | 说明 |
|-----------------|--------------|----------|------|
| * | **approved** | **true** | 人工终审通过，覆盖机器结论 |
| * | **rejected** | **false** | 人工拒绝 |
| * | **needs_reupload** | **false** | 要求换图 |
| passed / skipped | **pending_review** | **true** | MVP 不阻断；配合 `hasPhotoUnderReview` |
| failed / pending | **pending_review** | **false** | 机器未过且仍在审，不算 passing |
| passed / skipped | **not_required** | **true** | 与现网一致 |
| failed / pending | **not_required** | **false** | 与现网一致 |
| * | **appeal_approved** | **true** | 未来申诉通过（e 阶段可预留常量） |
| * | **appeal_rejected** | **false** | 未来申诉驳回 |
| * | **appealed** | **false**（建议） | 申诉中不算 passing，避免未决图进入匹配；可配文案「申诉处理中」 |

**逻辑伪代码（推荐实现）**：

```text
function isPassingPhoto(image):
  switch image.reviewStatus:
    case approved, appeal_approved: return true
    case rejected, needs_reupload, appeal_rejected, appealed: return false
    case pending_review:
      return image.detectionStatus in (passed, skipped)
    case not_required:
      return image.detectionStatus in (passed, skipped)
    default: return image.detectionStatus in (passed, skipped)  // 未知值保守按 detection
```

**`hasPassingPhoto(user)`** = `EXISTS image WHERE isPassingPhoto(image)`.

### 2.3 与用户倾向的差异说明

- **failed + approved → passing true**：采纳（人工覆盖）。
- **skipped + needs_reupload → false**：采纳。
- **passed + rejected → false**：采纳（该张不算，但若另有 approved 张则用户仍可 passing）。

## 3. reviewStatus 与 nextStep 关系（C）

### 3.1 nextStep 计算（不变骨架）

```text
if !hasPassingPhoto → photo_upload
else if !onboardingPhotoAestheticCompletedAt → photo_preference
else if !onboardingPhotoPreviewCompletedAt → photo_preview
else → questionnaire
```

**唯一变化**：`hasPassingPhoto` 改用 §2 规则（含 review）。

### 3.2 场景决策

| 场景 | hasPassingPhoto | nextStep | 说明 |
|------|-----------------|----------|------|
| 仅 rejected / needs_reupload 图 | false | **photo_upload** | 采纳用户倾向 §C.1 |
| 一张 rejected + 一张 approved | true | 按审美/preview 进度 | 采纳 §C.2：至少一张 passing 即可 |
| pending_review + skipped（无其他 passing） | true | 按进度；`hasPhotoUnderReview=true` | 采纳 §C.3 |
| 唯一 passing 图被 Admin 改为 needs_reupload | false | **photo_upload** | 采纳 §C.4：下次 `GET /onboarding/photo/status` 或进入问卷前 guard 拉回 |
| 全部 failed，一张 approved | true | 继续 | approved 覆盖 |
| 无照片 | false | photo_upload | 不变 |

### 3.3 问卷门禁

- **QuestionnairePage / 首页 CTA**：继续依赖 `getOnboardingPhotoStatus().nextStep`（已有模式）。
- Admin 改状态后：**无需 WebSocket**；用户下一次 status 请求即更新。
- **已填问卷用户**：若之后唯一 passing 图变为 needs_reupload，**不删问卷答案**；仅 `nextStep=photo_upload` 阻止「继续匹配流程」进入后续环节（与现网 gate 一致）。

## 4. API 返回字段建议（E）

### 4.1 保留字段

| 字段 | 含义（e 之后） |
|------|----------------|
| `hasPhoto` | 是否存在任意 UserImage |
| `hasPassingPhoto` | §2 规则 |
| `hasPhotoPreference` | 审美题完成标记 |
| `nextStep` | §3 |
| `hasPhotoUnderReview` | `∃ reviewStatus=pending_review`（可保留现实现） |
| `photoReviewStatusSummary` | 建议扩展枚举，见下 |

### 4.2 建议新增（不暴露 reviewNote）

| 字段 | 类型 | 用途 |
|------|------|------|
| **`blockingPhotoReviewStatus`** | `"rejected" \| "needs_reupload" \| "appealed" \| null` | 当 `!hasPassingPhoto` 且存在阻断性 review 时，取**最新一张**阻断图的 status（优先级 needs_reupload > rejected > appealed） |
| **`photoGateMessageKey`** | string | 前端 i18n key，如 `onboarding.photo.gate.needs_reupload` |
| **`photoGateReasonCodes`** | string[] | 用户可见 reason 子集（来自 `reviewReasonCodes` 白名单映射，**不含** reviewNote） |
| **`passingPhotoCount`** | number | 可选，调试/文案「已有 N 张可用照片」 |
| `hasBlockedPhoto` | boolean | 可选冗余：`blockingPhotoReviewStatus != null` |

**不建议**：`passingPhotoId` / `blockedPhotoId`（MVP 非必须；若要做「继续用哪张」再 e+）。

**`photoReviewStatusSummary` 扩展建议**：

```typescript
"none" | "pending_review" | "blocked_rejected" | "blocked_needs_reupload"
```

- 当 `hasPassingPhoto && hasPhotoUnderReview` → `pending_review`
- 当 `!hasPassingPhoto && blocking` → 对应 blocked_* 
- 否则 `none`

### 4.3 reasonCodes 对用户可见映射（示例）

| reviewReasonCodes（运营） | 用户文案方向 |
|---------------------------|--------------|
| NEEDS_REUPLOAD, FACE_NOT_CLEAR, LOW_QUALITY | 请上传更清晰本人照 |
| MANUAL_REJECTED, INAPPROPRIATE_CONTENT, SUSPECTED_NON_PERSON | 该照片暂不可用于匹配 |
| DETECTION_SKIPPED_REVIEW | 不单独展示（pending 用审核中文案） |

**禁止返回**：`reviewNote`、`reviewedByUserId`（可选返回 null 或不输出）。

## 5. 前端用户提示设计（D）

### 5.1 文案与阻断

| reviewStatus（阻断级） | 中文提示（建议） | 是否阻断 |
|------------------------|------------------|----------|
| pending_review | 照片正在审核中，你可以先继续完成资料。 | **否** |
| rejected | 这张照片暂时无法用于匹配，请上传一张更清晰的本人照片。 | **是** → photo_upload |
| needs_reupload | 请重新上传一张清晰的本人照片，以继续完成匹配流程。 | **是** → photo_upload |
| approved | 无额外提示 | 否 |
| appealed | 照片申诉处理中，请稍后再试或重新上传。 | **是**（建议） |

### 5.2 展示位置

| 场景 | 位置 |
|------|------|
| 阻断（rejected / needs_reupload / appealed） | **`/onboarding/photo-upload`** 顶部 banner（主）；从 questionnaire / home CTA 被 redirect 时 **带 query `?gate=needs_reupload`** 或读 status 字段展示同文案 |
| 非阻断 pending_review | **`/onboarding/photo-upload`** 与 **`/onboarding/photo-preference`** 可选轻提示；questionnaire 入口不弹窗 |
| questionnaire guard | 仅当 `nextStep !== questionnaire` 时 **Navigate** 到对应 step，在 **landing 页** 展示 `photoGateMessageKey` 对应中文 |

**不推荐**：在普通 `/images` 或匹配结果页展示 review 状态。

### 5.3 数据来源

- 首选：`GET /onboarding/photo/status` → `blockingPhotoReviewStatus` + `photoGateMessageKey` + `photoGateReasonCodes`
- 上传页：`useEffect` 拉 status；提交新照片成功后 **重新拉 status**（新图默认 not_required / pending_review 按规则重算）

**不需要。**

- 索引已有 `[userId, reviewStatus]`、`[userId, detectionStatus, createdAt]`，MVP 够用。

## 7. Admin 审核与用户流程关系（G）

| 问题 | 结论 |
|------|------|
| Admin **approve** 后 | **立即** 该图 `isPassingPhoto=true`；若用户此前无 passing 图，下一次 status → 可进入 preference/preview |
| Admin **reject / needs_reupload** 后 | **立即** 该图不算 passing；若为用户**唯一** passing 来源，下一次 status → `photo_upload` |
| 用户重新上传 | **新 UserImage 行**；旧 rejected 保留历史，**不参与** passing（除非被 approve） |
| 多图策略 | **只要存在 ≥1 张 passing 即可**；旧 rejected **自动忽略**（不参与 OR 存在判断） |
| 旧图清理 | **不自动删除** rejected 行；列表/UI 可灰显「不可用」（e3 前端可选） |

**与 detection 关系**：Admin **不修改** `detectionStatus`；gate 只读 detection + review。
