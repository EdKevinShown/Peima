# P7.4-r1d — 照片审核状态与运营复核（设计方案，仅方案）

> 状态：**设计确认稿**；本轮 **不改代码、不写 migration**。  
> 前置：P7.3 前端校验 → P7.4-r1a 画质 → P7.4-r1b 人脸存在性 → r1b-f1 冷启动 → r1c-a 多人脸 warning → r1c-b `primaryFace`。

---

## 1. 一句话结论

**推荐将 `detectionStatus`（机器检测）与 `reviewStatus`（人工/运营审核）分离；P7.4-r1d 阶段仅设计，MVP 实施时先在 `UserImage` 增加 `reviewStatus` 等最小字段，短期不改变现有 `hasPassingPhoto` / `nextStep`；技术类 failed 引导重传不进人工，skipped 与可选抽检进后台观察，违规与身份认证不在本阶段实现。**

---

## 2. 为什么需要 reviewStatus

### 自动检测解决不了的问题

| 问题 | 说明 |
|------|------|
| 语义与意图 | 机器只知「有几张脸 / 是否过暗」，不知是否违规、是否误导、是否非本人意愿展示 |
| 误检与漏检 | BlazeFace 误检背景脸、漏检侧脸；画质阈值误伤夜景自拍 |
| 产品例外 | 运营活动、客服工单、误判申诉需人工纠正 |
| 可解释性 | 用户质疑「为何不能用」时，需人工备注与审计轨迹 |
| 策略演进 | 未来收紧多人脸、主脸过小等规则，需人工兜底过渡期 |

### 为什么不能只靠 detectionStatus

- `detectionStatus` 表达的是**单次同步流水线结果**（passed / failed / skipped），不是「最终是否允许用于产品」的终审。
- 把人工 **approve** 写回 `detectionStatus=passed` 会**污染机器检测语义**，无法区分「模型通过」与「运营覆盖」。
- `skipped` 与 `failed` 混用历史兼容逻辑后，运营若改 status 会破坏 r1a/r1b 指标统计与 `detectionRulesVersion` 对齐。

### 哪些需要人工复核

- **skipped**（模型超时/加载失败）且用户反复上传仍 skipped  
- **运营抽检**：`MULTIPLE_FACES` warning、低 `primaryFace.areaRatio`（未来规则）  
- **用户申诉**：「我有脸但被拒」类工单  
- **举报/风控升级**（未来，非 r1d MVP）

### 哪些不需要人工介入

- **UNREADABLE_IMAGE / TOO_DARK / TOO_BLUR**：明确技术失败 → 用户重传即可  
- **FACE_NOT_FOUND**（默认）：先重传；仅申诉或抽检进人工  
- **passed + 无 warning**：默认不 review  
- **MULTIPLE_FACES**（当前策略）：warning only，不自动进队列  

### 与身份认证 / 真人认证的区别

| 维度 | P7.4 照片审核（r1d） | KYC / 真人认证 |
|------|----------------------|----------------|
| 目标 | 照片是否**可用于** onboarding / 预览叙事 | 是否**本人**、是否活体、是否证件一致 |
| 输出 | reviewStatus、运营备注 | 实名、证件号、生物特征比对 |
| 用户感知 | 「照片不合适，请换一张」 | 「完成真人认证」 |
| 合规 | 内容准入 + 运营质检 | 强实名、留存与授权要求高 |
| 数据 | 不做人脸 1:1 比对 | 人脸模板、证件 OCR |

**文案禁止**将人工审核称为「身份认证」「真人认证」。

## 3. detectionStatus vs reviewStatus

| 字段 | 含义 | 写入方 | 典型值 |
|------|------|--------|--------|
| **detectionStatus** | 机器检测流水线结果 | API 上传后同步检测 | pending / passed / failed / skipped |
| **detectionReasonCodes** | 机器失败原因 | 同上 | TOO_DARK, FACE_NOT_FOUND, … |
| **detectionScoreJson** | 机器解释数据 | 同上 | quality, face, primaryFace, warnings |
| **detectionRulesVersion** | 机器规则版本 | 同上 | p7.4-r1c-v1, … |
| **reviewStatus** | 人工/运营审核结论 | Admin / 申诉流程 | not_required, pending_review, approved, … |
| **reviewReasonCodes** | 人工分类原因 | 运营 | MULTIPLE_FACES_REVIEW, … |
| **reviewedAt / reviewedByUserId / reviewNote** | 审计与备注 | 运营 | — |

**原则**：机器结果**只读**（除重传产生新 `UserImage` 行）；人工结论**只写 review 字段**。

## 4. 推荐数据结构

### 方案比较

| 维度 | 方案 1：复用 detectionStatus | 方案 2：分离 reviewStatus（**推荐**） |
|------|------------------------------|--------------------------------------|
| 数据清晰度 | 差：机器/人工混写 | 好 |
| 运营后台 | 难过滤「待人工」 | `reviewStatus=pending_review` 清晰 |
| 申诉 | 无法保留机器原始结论 | 保留 detection + 覆盖 review |
| 老数据兼容 | 改动语义风险大 | 默认 `not_required` 即可 |
| migration | 看似无，实则语义破坏 | 一次加列，风险可控 |
| MVP 成本 | 低但债高 | 中，可分期 |

**推荐（与用户倾向一致）**：

**P7.4-r1d-b（MVP）**：在 `UserImage` 上增加字段（Prisma 草案，**本轮不落地**）：

```prisma
model UserImage {
  // ... existing P7.4 detection fields ...

  /// P7.4-r1d: not_required | pending_review | approved | rejected | needs_reupload | appealed | appeal_approved | appeal_rejected
  reviewStatus        String    @default("not_required")
  reviewReasonCodes   String[]  @default([])
  reviewedAt          DateTime?
  reviewedByUserId    String?   // admin user id
  reviewNote          String?   // internal; not full raw JSON

  @@index([reviewStatus, createdAt])
  @@index([userId, reviewStatus])
}
```

**P7.4-r1d-d+（扩展）**：若需分配队列、申诉历史、多次审核，再引入：

```prisma
model PhotoReviewTask {
  id               String   @id @default(cuid())
  userImageId      String
  userId           String
  status           String   // mirrors review lifecycle per task
  reasonCodes      String[] @default([])
  assignedToUserId String?
  reviewedByUserId String?
  reviewedAt       DateTime?
  note             String?
  createdAt        DateTime @default(now())
  updatedAt        DateTime @updatedAt

  userImage UserImage @relation(...)
  @@index([status, createdAt])
}
```

MVP **不必**上独立表；`UserImage.reviewStatus` 足够支撑列表与 approve/reject。

### reviewStatus 枚举（推荐）

| 值 | 含义 |
|----|------|
| **not_required** | 默认；机器结果无需人工（passed 无抽检、或技术 failed 仅重传） |
| **pending_review** | 已进入人工队列，尚未处理 |
| **approved** | 运营批准：可作为「有效照片」（即使 detection failed/skipped，若产品允许覆盖） |
| **rejected** | 运营拒绝：不可用于 onboarding passing |
| **needs_reupload** | 运营要求用户换图（软拒绝，引导回 upload） |
| **appealed** | 用户发起申诉，待处理 |
| **appeal_approved** | 申诉通过 → 等同 approved |
| **appeal_rejected** | 申诉驳回 → 等同 rejected |

**简化 MVP 可选子集**：`not_required | pending_review | approved | rejected | needs_reupload`（申诉后补）。

### reviewReasonCodes（运营分类，示例）

| Code | 用途 |
|------|------|
| MULTIPLE_FACES_REVIEW | 多人脸抽检 |
| FACE_NOT_CLEAR | 人脸不清晰（人工判定） |
| SUSPECTED_NON_PERSON | 非人物主体 |
| INAPPROPRIATE_CONTENT | 不当内容（未来合规链） |
| LOW_QUALITY | 质量不可用（人工） |
| DETECTION_SKIPPED_REVIEW | 机器 skipped 待确认 |
| USER_APPEAL | 用户申诉 |
| MANUAL_OVERRIDE | 无细分时的手工覆盖 |

## 5. 哪些照片进入复核

### 推荐策略（对齐产品倾向）

| 机器结果 | 是否自动 pending_review | 说明 |
|----------|-------------------------|------|
| failed + UNREADABLE_IMAGE | **否** | 引导重传 |
| failed + TOO_DARK / TOO_BLUR | **否** | 引导重传 |
| failed + FACE_NOT_FOUND | **否**（默认） | 引导重传；**申诉**或抽检 → pending_review |
| skipped | **可选是**（后台观察） | 不阻断用户；写入 `pending_review` 供运营扫，或仅 metrics 告警 |
| passed + MULTIPLE_FACES | **否**（默认） | warning only；**运营抽检**可手动标 pending |
| passed + 无 warning | **否** | 不 review |
| passed / 任意 | **举报**（未来） | 用户举报后 pending_review |

**口径评估**：合理。避免人工队列被技术失败淹没；skipped 与抽检分离「用户可继续」与「运营可追溯」。

### 触发规则（未来 r1d-b 配置化）

```text
autoPendingReview =
  detectionStatus === 'skipped'
  OR (feature flag && detectionReasonCodes includes 'FACE_NOT_FOUND' && appealFlag)
  OR adminManualFlag
  OR sampleRate(passed with MULTIPLE_FACES)  // 抽检，非默认
```

## 6. onboarding nextStep 影响

### 当前实现（保持不变至 r1d-b 之前）

- `hasPassingPhoto` = 存在 `detectionStatus in ('passed','skipped')` 的 `UserImage`。
- **不看** reviewStatus。

### 未来推荐（r1d-c 之后可切换，feature flag）

```text
isPassingPhoto(row) =
  (detectionStatus in ('passed','skipped') AND reviewStatus in ('not_required','pending_review','approved','appeal_approved'))
  OR reviewStatus in ('approved','appeal_approved')   // 运营覆盖机器 failed
  AND reviewStatus NOT IN ('rejected','needs_reupload','appeal_rejected')
```

| reviewStatus | 建议是否算 passing（未来） | nextStep 影响 |
|--------------|---------------------------|---------------|
| not_required | 沿用 detection | 不变 |
| pending_review | **是**（MVP 倾向：允许继续，后台观察） | 可进 preference |
| approved | **是** | 可覆盖 failed |
| rejected | **否** | 回 photo_upload |
| needs_reupload | **否** | 回 photo_upload |
| appealed | **是**（暂）或冻结（产品选） | 待定 |
| appeal_approved | **是** | 同 approved |
| appeal_rejected | **否** | 同 rejected |

**P7.4-r1d 设计阶段**：**不改变**现有 `nextStep` / `hasPassingPhoto`（与用户倾向一致）。

**3+2+1 预览池**：生成规则不改；若未来 rejected 不算 passing，则不会用该图作 onboarding 主图（生成仍基于「当前有效 user image」查询，非 worker 改分）。

## 7. Admin Photo Review 设计（本轮不实现）

### 页面

- 路由：`/admin/photo-review`
- Guard：现有 admin RBAC（如 `UserRole` / `AuditLog` 体系）

### 列表列

| 列 | 来源 |
|----|------|
| userId | UserImage.userId |
| thumbnail | imageUrl（签名 URL，短期有效） |
| detectionStatus | 机器 |
| detectionReasonCodes | 机器 |
| warnings | detectionScoreJson.warnings |
| detectionRulesVersion | 机器 |
| detectedAt | 机器 |
| reviewStatus | 人工 |
| reviewReasonCodes | 人工 |
| createdAt | UserImage |
| primaryFace summary | index, areaRatio, primaryScore |
| actions | approve / reject / needs-reupload / note |

### 筛选

- `reviewStatus=pending_review`
- `detectionStatus=failed|skipped|passed`
- `warnings` 含 MULTIPLE_FACES
- `detectionReasonCodes`
- 时间范围

### API（草案）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/admin/photo-review/items` | 分页列表 + filter |
| GET | `/admin/photo-review/items/:imageId` | 详情 + detectionScoreJson |
| POST | `/admin/photo-review/:imageId/approve` | body: reasonCodes?, note? |
| POST | `/admin/photo-review/:imageId/reject` | body: reasonCodes, note? |
| POST | `/admin/photo-review/:imageId/needs-reupload` | body: note? |

**响应**：不返回其他用户 PII；`detectionScoreJson` 仅 admin 可读。

**Audit**：每次操作写 `AuditLog`（action, adminUserId, userImageId, before/after reviewStatus）。

## 8. 用户侧文案

| 场景 | 是否展示 | 文案建议 |
|------|----------|----------|
| detection failed（现有） | 是 | 保持 r1a/r1b 中文（TOO_DARK、FACE_NOT_FOUND 等） |
| pending_review | 可选 | 「照片正在审核中，你可以先继续完成资料。」 |
| rejected | 是 | 「这张照片暂时无法用于匹配，请上传一张更清晰的本人照片。」 |
| needs_reupload | 是 | 同上 + 强调重传 |
| MULTIPLE_FACES warning | 是（upload 页） | 「建议上传单人照片…」（r1c-a 已定） |
| approved | 无感 | 不提示 |
| 申诉提交 | 未来 | 「我们已收到你的反馈，将在 1–3 个工作日内处理。」 |

**禁止**：「完成真人认证」「身份验证通过」等 KYC 表述。

**preview / questionnaire**：pending_review **不重复**打扰（与 r1c-a 一致）；rejected 在 **photo-upload** 拦截即可。

## 9. 风险与合规

| 风险 | 缓解 |
|------|------|
| 运营查看用户照片 | RBAC最小权限；培训；仅工作账号 |
| 日志泄露 URL | 日志打 imageId，不打完整 imageUrl；Audit 记 id |
| 无审计 | AuditLog：who/when/from→to |
| 用户不知情 | 隐私政策补充「照片可能人工审核以保障社区质量」 |
| 留存过久 | 与账号删除策略一致；拒绝图可定期清理（未来） |
| 被误认为 KYC | 产品文案与审核界面统一用「照片审核」 |
