# P7.5-r4-m：Onboarding Photo Preview Pool 候选漏斗调试 / Signoff（closeout）

## 目标

在**不改变** `OnboardingPhotoPreviewPoolService.generate` / `collectGatedCandidates` 行为的前提下，为「当前约 0 位候选」提供 **dev / test 可复现的漏斗审计**（计数 + 各步过滤原因），并核对 `dev-assets/test-user-images/mapping.json` 的性别覆盖是否足以支撑 **6 人池**（异性 + 门闸后）。

## 实现摘要

### 漏斗步骤（报告字段）

| 概念 | JSON 字段 / 含义 |
|------|------------------|
| 总用户数 | `counters.total_users_in_db` |
| 去掉 viewer 自己 | `counters.non_viewer_users` |
| 去掉自己后至少有 1 张图 | `counters.non_viewer_with_at_least_one_image` |
| **与 Collector `baseWhere` 一致**：非本人 + ≥1 Image + **`relationProfile` 存在** | `counters.base_where_eligible`（在扫描窗口内折叠得出） |
| 首张照片（按 `createdAt` 升序）是否 onboarding 口径可用（passed/skipped + review 规则） | `base_where_first_image_onboarding_usable` / `not_*`（**仅诊断**：当前 Collector **不因**首张不可用而拦截） |
| 偏好硬门槛后 | `counters.after_preference_hard_gate` |
| 异性二元性别门闸后（与 `candidatePassesOppositeBinaryGate` 一致） | `counters.after_opposite_gender_gate_final` |

### 过滤原因计数（`drop_reasons`）

- `no_user_image` — 无非本人且无图（扫描到的非 viewer 用户无 `UserImage`）
- `no_relation_profile` — 有图但无 `relationProfile` 行（**与 Prisma baseWhere 直接一致，常见真实根因**）
- `preference_hard_gate` — `passesPreferenceHardGate` 未通过
- `gender_not_opposite_binary` — 候选人非对立 male/female，或 viewer 非二元无法在业务上算作「预览生成成功路径」（仍统计原因）

不包含：phone / email / `reviewNote` / 完整 `detectionScoreJson`；viewer id 仅为 **masked** 片段。

### 扫描上限

默认最多扫描 `PREVIEW_POOL_FUNNEL_MAX_SCAN_USERS`（10000）个**非 viewer** 用户，按 `createdAt` asc。若库中更多用户，`counters.scan_truncated=true`，`drop_reasons` **仅累计该前缀**。

### 运行方式

- **Guard**：生产环境默认禁止；须设置 **`ALLOW_PREVIEW_POOL_FUNNEL_AUDIT=1`** 才可在 `NODE_ENV=production` 下运行。
- **CLI**（需先 `pnpm --filter @peima/api run build`，从仓库根路径）：
  ```bash
  pnpm --filter @peima/api run p75:r4-m-preview-pool-funnel -- --viewerUserId=<你的viewer用户id>
  ```
  可同时读 `mapping.json`（或通过 `P75_R4_TEST_USER_IMAGES_MAPPING` 覆盖路径），输出 **`mapping_json_summary` + `funnel`** 的 JSON。

### 单测

- `apps/api/test/onboarding-photo-preview-pool-funnel.audit.spec.ts`：纯函数折叠 + `mapping` 形 fixture + id mask。

## `mapping.json` 核对（仓库当前）

对 `items[]` 中 `gender` 统计（与本实现 `summarizeDemoMappingGender` 一致）：

| 指标 | 值 |
|------|-----|
| 条目总数 | **6** |
| male | **3** |
| female | **3** |
| 非法性别 | **0** |
| `male≥6 && female≥6` | **否** |

结论：**仅从该 mapping 的资产数量**，无法同时为 **male viewer** 与 **female viewer** 各提供 ≥6 个异性 demo 候选人；要完成 6 人池仍需 **数据库里足够多的「异性 + relationProfile + 图」真实用户**，或扩充 mapping / 批量创建用户。

## 典型「当前约 0 位」根因（推演）

结合漏斗与 **`collectGatedCandidates`** 实现：

1. **`no_relation_profile` 很大**：导入或种子用户若没有 **`UserProfile` / RelationProfile**，即使用户有头像，也会在 **第一层 baseWhere** 消失（与报错「约 0 位」高度一致）。
2. **`gender_not_opposite_binary` 很大**：候选 `User.gender` 非严格男/女或与 viewer 同边；**未放宽** gender gate。
3. **`preference_hard_gate` 很大**：偏好维度过严（与 r4-l 空偏好无冲突；若仍 0 则多半不是主因）。
4. **DB 总用户本来就少**：`non_viewer_users` 或 `base_where_eligible` 已 <6。

## 修复建议（不改产品门闸前提下）

1. 对 demo 候选跑一遍漏斗 CLI，确认 **`no_relation_profile` vs `gender_not_opposite_binary`** 谁占主因。
2. 确保种子 / 导入流程为每个候选用户创建 **`relationProfile`**（与 `relationProfile: { isNot: null }` 对齐）。
3. 保障至少 **6 个** 与 viewer **性别相反** 且 **male/female 词法** 正确的用户（可用 `mapping` 扩展或运营数据）。
4. 若首图 `detectionStatus` 导致「诊断」首张不可用但人数仍够：**可忽略**该诊断；若 **base_where 人数够但最终仍 0**，再回头看 profile / gender。
