# P7.5-r4-h — Candidate image folder ingestion (closeout)

## 本轮目标

在 **dev / staging** 下把 `dev-assets/test-user-images` 中的图片导入为可用的 `User` + `UserProfile` + `UserImage`（含 detection 持久化），使 onboarding **photo preview pool** 能从数据库中的他人候选图取 `imageUrl`。同时保证 **viewer 永不出现在自己的 3+2+1 预览池**。

## 本地 folder 路径

- 仓库内：`dev-assets/test-user-images/`
- 典型内容：`mapping.json` + 若干 `jpg/png/webp`。

## `mapping.json` 结构说明

当前文件为 **v1**，用于把 **文件名** 绑定到 **固定的 candidate `userId`**，并可选给出 `publicBaseUrl`：

```json
{
  "version": 1,
  "publicBaseUrl": "http://127.0.0.1:3000",
  "items": [{ "file": "test-user-images1.jpg", "userId": "…cuid…" }]
}
```

- 每项至少含 `file`、`userId`；可扩展 `nickname`、`styleTags`（导入代码已读取）。
- **`items` 之外的图片**（例如未列入 mapping 的 `NAM0915.jpg`、`test-user-images7.jpg` 等）在 `createMissingUsers=true` 且非 dry-run 时，会为 **每张图新建** demo candidate `User`。
- mapping **不是**完整画像源：未提供的字段用 **demo 默认值**（`User` 列），并确保存在 `UserProfile`，以满足 onboarding preview 的 gated scan。

## 为什么 folder 里的图不会自动进入预览池

预览 API 读取的是 **`UserImage` 数据库行**里的 `imageUrl`（通常为 `/uploads/user-images/...`），并不会扫描仓库静态目录。

## Self-exclusion 修复

文件：`apps/api/src/modules/onboarding/onboarding-photo-preview-pool.service.ts`

- 对 `buildSixNonSelfPreviewSlots` 的产物再过滤并用 **guard** 后才写入 `items`。
- `toViewerBundle` 拉取候选人图片时使用 `AND` 约束 **`userId` 既不能漏选也要显式排除 `pool.userId`**，避免 viewer 自己的 `UserImage` 被映射到任一槽位（含遗留脏数据）。
- shadow 侧的 `gatedCandidates` 仍仅来自已过滤后的 `gAll`（与原 r4-g1 逻辑一致）。

## CLI 命令

脚本注册在 **`apps/api/package.json`**：

`"p75:r4-import-candidate-images": "node dist/dev-cli/p75-r4-h-import-candidate-images-runner.js"`

若 `pnpm --filter @peima/api run p75:r4-import-candidate-images` 仍报 **Missing script**，请确认已保存上述 `package.json`，并在 **仓库根目录**用 filter 执行。

**`--folder` 解析规则（推荐用法）**

| 运行方式 | 推荐 `--folder` |
|----------|----------------|
| 仓库根目录：`pnpm --filter @peima/api run ...` | **`dev-assets/test-user-images`**（相对 **monorepo 根**，不要求当前 shell 在根目录） |
| 在 `apps/api` 里直接 `node dist/dev-cli/...` | **绝对路径**，例如 `C:\Users\...\peima\dev-assets\test-user-images` |
| 必须在 `apps/api` 下使用相对路径 | 可用 **`../../dev-assets/test-user-images`**（相对 **当前工作目录** 解析） |

不建议依赖 `../../...` 作为唯一方式；若以 monorepo 根为基准拼接 `../..`，会与「从根目录写的 `dev-assets/...`」语义混淆。默认更稳妥的是：**filter + `dev-assets/test-user-images`**，或 **`--folder` 用绝对路径**。

```bash
pnpm --filter @peima/api run p75:r4-import-candidate-images -- --folder=dev-assets/test-user-images --dryRun=true
pnpm --filter @peima/api run p75:r4-import-candidate-images -- --folder=dev-assets/test-user-images --dryRun=false
```

可选：`--excludeUserId=<viewerUserId>` 跳过 mapping 绑定到「当前 viewer」的导入行。

需先编译出 `dist`（与其他 dev-cli 一致；若 Windows 上完整 `pnpm` build 触发 Prisma `EPERM`，可在 `apps/api` 目录执行 `pnpm exec nest build` 作为退路）。

## 导入行为概要

1. 解析 `mapping.json`（可选）。
2. 扫描目录：`jpg/jpeg/png/webp`；忽略 `mapping.json`、带点隐藏文件、非图片。
3. **去重**：`imageUrl` 包含稳定标记 `-r4h-import-<slug>` 时已存在则跳过（全局，不限 `userId`）。
4. 非 dry-run：映射或新建用户、`UserProfile` upsert；写 `uploads/user-images`；`UserImage.create`；`runDetection` 时用 `detectFromBuffer`。
5. 单张异常进入 `summary.failed`，不中止整批。

stdout JSON schema：`schemaVersion = p7.5-r4-h-candidate-image-import-v1`。实现侧用 `assertR4HCandidateImportReportPrivacySafe` 阻止输出 `reviewNote`、完整 `detectionScoreJson` 键、`phone`/`email` 等字段。

## Detection 持久化

写入 `detectionStatus`、`detectionReasonCodes`、`detectionScoreJson`（未跑 vision 时为 detection 原生 JSON）、`detectionRulesVersion`、`detectedAt`，以及 `resolveUserImageReviewStateFromDetection` 推导出的 `reviewStatus` / `reviewReasonCodes`。

## dry-run vs write

- `dryRun=true`：不产生 `User`/`UserImage` 写入与文件复制；仍会做 **只读** DB 查询（排除/去重/用户是否存在），需提供 `DATABASE_URL`。
- `dryRun=false`：`copyToUploads` 必须为 `true`（否则服务抛错）。

## Vision（方案 A）

