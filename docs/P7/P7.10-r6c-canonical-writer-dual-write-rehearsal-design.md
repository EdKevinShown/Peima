## 2. Why dual-write rehearsal design is needed

P7.10-r6 delivered a **pure shadow builder** (`buildP76CanonicalWriterShadowPayloadV1`) that compares baseline `MatchResult` vs allowlist sidecar proposal with guardrails aligned to the read-path resolver. **`appliedToMatchResult` is always `false`**; nothing is persisted as a “canonical result.”

P7.10-r6a/r6b and P7.7-r2 proved that a **read-only dev audit** can aggregate shadow payloads into JSON artifacts with **`appliedToMatchResultCount = 0`** and no sensitive fields. That evidence covers **compare / audit safety only**.

[P7.10-r3](./P7.10-r3-p76-canonical-writer-design.md) describes a **future production canonical writer** that would formally own `MatchResult` / `matchInsights` / score / provenance. [P7.10-r5](./P7.10-r5-legacy-pool-bridge-sunset-plan.md) references a **`dual_write_rehearsal`** phase (meta compare only) before disabling the PreviewPool worker. **None of that is implemented for canonical writer yet.**

**Gap:** Shadow compare is ephemeral (in-memory / per-run JSON). The next step toward canonical writer readiness is **not** production write. It is a designed **dual-write rehearsal** phase that:

- **Persists** canonical shadow proposals in a **safe, auditable, rollback-friendly store**
- Keeps **`appliedToMatchResult = false`** everywhere
- Is **ignored by GET**, FinalMatchPage, worker, and percent rollout
- Does **not** update `MatchResult`, `matchInsights`, `candidateUserId`, or `finalScore`

**Terminology guardrail (this doc):**

| Term | Meaning in r6c |
|------|----------------|
| **Dual-write rehearsal** | Baseline row stays on `MatchResult`; rehearsal row stores shadow proposal **elsewhere** (artifact or dedicated sidecar) |
| **NOT** dual-write rehearsal | Writing `MatchResult` + sidecar in one transaction; changing worker winner; enabling read path from rehearsal store |
| **Canonical production write** | Future r3 Phase 3+ — **out of scope** |

**This round:** design only — no implementation.

## 4. Rehearsal options

### Option A — Artifact-only dual-write rehearsal

**Mechanism:** Extend P7.7-r2 / r6a runs to emit versioned JSON under `artifacts/p76/r7r2/` (or `artifacts/p76/r6c/`) per `auditRunId`; no Prisma writes.

| Pros | Cons |
|------|------|
| Lowest risk; matches r6b/r7r2 today | No long-lived Admin query surface |
| No migration | Harder cross-run dedup without discipline |
| Trivial rollback (delete files) | CI / laptop path dependent |
| Already implemented (r6a runner + `p77-r2-local-smoke-artifact-check.mjs`) | |

**Workspace status:** **Partially implemented** (r6a + P7.7-r2). r6c treats repeated artifact runs as **Phase 1 default**.

### Option B — Dedicated rehearsal sidecar table

**Mechanism:** New table e.g. `p76_canonical_writer_rehearsal_meta` (name TBD in r6d) storing one row per `(viewerUserId, matchResultId, sourceVersion, auditRunId)` with embedded or referenced `shadowPayload` JSON.

| Pros | Cons |
|------|------|
| Auditable, queryable, retention policy | Requires migration + implementation gate |
| Clear separation from `p76_allowlist_apply_meta` | Ops must not confuse with “applied” sidecar |
| Supports `supersededAt` / `rollbackToken` patterns | DB write path must stay dev/staging gated |
| Aligns with [P7.10-r3](./P7.10-r3-p76-canonical-writer-design.md) Option B (`p76_canonical_writer_meta`) concept | |

**Workspace status:** **not found in this workspace** (schema/migration). Design in §5; implementation **BLOCKED** until r6d + gates.

### Option C — `matchInsights` shadow block

**Mechanism:** `UPDATE MatchResult` SET `matchInsights` JSON containing `p76CanonicalWriter` rehearsal block; **do not** change `candidateUserId` / `finalScore`.

| Pros | Cons |
|------|------|
| No new table | **Touches `MatchResult` row** — violates r6 no-write invariant spirit |
| Colocated with baseline | Easy to misread as canonical production write |
| | Complicates rollback (snapshot previous `matchInsights`) |
| | GET / clients may surface unknown keys |
| | Conflicts with [P7.10-r5](./P7.10-r5-legacy-pool-bridge-sunset-plan.md) “meta compare only” without MatchResult mutation |

**Workspace status:** **not recommended** for first rehearsal. [P7.10-r3](./P7.10-r3-p76-canonical-writer-design.md) lists `matchInsights` extension as a later, explicitly gated option.

### Recommendation

| Phase | Option | Rationale |
|-------|--------|-----------|
| **Phase 1 (now → next implementation)** | **A — artifact-only** | r6b/r7r2 already PASS; zero DB risk |
| **Phase 2 (after schema review)** | **B — dedicated sidecar** | Durable audit + Admin read-only; still `appliedToMatchResult=false` |
| **Defer** | **C — matchInsights** | Higher ambiguity; requires separate DB review and PM/Ops signoff |

## 5. Recommended dual-write rehearsal contract

**Design-only.** Table name illustrative; **not** created this round.

### 5.1 Future table: `p76_canonical_writer_rehearsal_meta`

```text
p76_canonical_writer_rehearsal_meta {
  id                          TEXT PK
  viewerUserId                TEXT NOT NULL
  matchResultId               TEXT NOT NULL
  batchId                     TEXT?          // from MatchResult.batchId if filtered
  baselineCandidateUserId     TEXT?
  proposedCandidateUserId     TEXT?          // from shadow.proposal.selectedCandidateUserId
  baselineFinalScore          FLOAT?
  proposedScore               FLOAT?         // shadow v1 mirrors baseline score
  wouldChangeCandidate        BOOLEAN NOT NULL
  guardrailReason             TEXT NOT NULL  // shadow.guardrails.reason
  eligible                    BOOLEAN NOT NULL
  sourceType                  TEXT NOT NULL  // "p76_canonical_writer_shadow"
  sourceVersion               TEXT NOT NULL  // e.g. p7.10-r6-p76-canonical-writer-shadow-v1
  pipelineVersion             TEXT NOT NULL
  shadowPayload               JSONB NOT NULL // full P76CanonicalWriterShadowPayloadV1
  appliedToMatchResult        BOOLEAN NOT NULL DEFAULT false
  rehearsalMode               TEXT NOT NULL  // "artifact_only" | "sidecar"
  auditRunId                  TEXT NOT NULL  // correlates artifact file / CLI run
  readPathSourceVersion       TEXT?          // cohort key used for sidecar lookup
  generatedAt                 TIMESTAMP NOT NULL
  expiresAt                   TIMESTAMP?
  supersededAt                TIMESTAMP?
  rollbackToken               TEXT?          // null in rehearsal; reserved for future ops flows
  createdAt                   TIMESTAMP
  updatedAt                   TIMESTAMP
}
```

**Suggested indexes (r6d):** `(viewerUserId, matchResultId, sourceVersion)`, `(auditRunId)`, `(generatedAt)`, `(supersededAt)` where null.

### 5.2 Invariants (must hold in any future implementation)

| Rule | Detail |
|------|--------|
| `appliedToMatchResult` | **Always `false`** in rehearsal rows and embedded `shadowPayload` |
| GET / `resolveMatchResultDisplay` | **Must not read** rehearsal table by default |
| FinalMatchPage | **Unchanged**; no rehearsal consumer |
| Worker / batch-match | **Must not read** rehearsal for ranking or writes |
| `p76_allowlist_apply_meta` | **Not replaced**; rehearsal is downstream compare of baseline + existing sidecar |
| Production env | Rehearsal writer **disabled** unless explicit staging-like gate (separate from r9f percent) |
| Sensitive data | No `rawPrompt`, `transcript`, `imageFeatures`, `rawImage`, `fullPrompt` in stored JSON — reuse [r6a privacy guard](./P7.10-r6a-canonical-writer-shadow-dev-audit-runner-closeout.md) (`p76-canonical-writer-shadow-audit-json.ts`) |

### 5.3 Artifact contract (Option A — already live)

Align with r6a:

- `sourceType`: `p76_canonical_writer_shadow_audit`
- `sourceVersion`: `p7.10-r6a-canonical-writer-shadow-audit-v1`
- `mode`: `dev_audit`
- `appliedToMatchResultCount`: **0**

Optional r6c extension (artifact-only): top-level `auditRunId`, `rehearsalMode: "artifact_only"`, `readPathSourceVersion` (e.g. `p7.6-r7j3-staging-cohort-v1` from r6b).

## 7. Rehearsal write safety rules

Hard rules for any future implementation (artifact or DB):

1. **No** `MatchResult` `create` / `update` / `upsert`.
2. **No** `candidateUserId` update.
3. **No** `finalScore` update.
4. **No** `matchInsights` update (including shadow blocks on `MatchResult`).
5. **No** worker / `batch-match.processor` integration.
6. **No** GET read-path integration (`p76-read-path-display-resolver`, `matching.service` unchanged).
7. **No** FinalMatchPage / frontend changes.
8. **No** production environment writes without staging-like reverify (r9e3 still `NEED_MORE_PROD_REVERIFY`).
9. **No** percent rollout (`r9f` blocked).
10. Every rehearsal record: **`appliedToMatchResult = false`**.
11. Every rehearsal record: **deletable** or **supersedeable** (`supersededAt`, `auditRunId` scope delete).
12. Rehearsal store **ignored by default** — no feature flag that routes display to rehearsal.
13. **Do not** disable PreviewPool writer ([P7.10-r5](./P7.10-r5-legacy-pool-bridge-sunset-plan.md)).
14. **Do not** conflate rehearsal with `p76_allowlist_apply_meta.applied=true` semantics ([P7.6-r8g](./P7.6-r8g-admin-review-ui-api-design.md) `sidecarWritten ≠ productApplied`).

| Action | Effect |
|--------|--------|

Would require storing previous `matchInsights` snapshot per row before update; higher operational risk. **Do not use** until separate design + gate 15 signoff.
