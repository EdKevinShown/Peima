# P7.5-r4-a — VisualRankingShadow 持久化设计（只设计，不实现）

> **状态**：设计稿 · **不**含 migration / 代码 / APPLY_TO_POOL  
> **前置**：P7.5-r3 已实现 `VisualRankingShadowV1` 计算与 `generate()` 旁路 `computeShadow()`  
> **目标**：让运营与回归脚本可观察「若启用视觉增强排序，哪些槽位会变」，**仍不**改变真实 3+2+1 与用户可见结果

---

## 1. 一句话结论

**推荐方案 B**：新增 `OnboardingPhotoPreviewPoolShadow` 独立表存 `payloadJson`（`shadowType=visual_ranking_shadow`），r4-b 只写 shadow、不应用排序；**继续 fire-and-forget 异步写入**；r4-c 用 DB 聚合 + CLI 报表；**APPLY_TO_POOL 留在 P7.5-r5**，且需 shadow 覆盖率与变更率门槛 + staging signoff 后才允许小流量。

## 2. 持久化位置方案比较

| 维度 | A：`OnboardingPhotoPreviewPool.metadataJson` | B：`OnboardingPhotoPreviewPoolShadow` 独立表 | C：不入库（日志 / 文件 / CLI stdout） |
|------|---------------------------------------------|---------------------------------------------|--------------------------------------|
| **Migration 成本** | 低：单列 `Json?` | 中：新表 + 索引 + FK | 无 |
| **查询方便性** | 差：需 JSON 路径扫描或拉全表 | 好：按 `poolId` / `userId` / `createdAt` / `shadowType` 索引 | 差：需解析日志 |
| **回归统计** | 中：SQL `jsonb` 聚合（Postgres）可行但重 | **优**：`payloadJson->summary` 或落盘扁平列（可选） | 仅适合单次本地 |
| **污染主表** | 会：pool 行变大、读写耦合 | **不会**：主表不变 | 无 |
| **多 shadow 类型** | 差：单 JSON 膨胀、版本混杂 | **优**：`shadowType` + 唯一约束 | 差：多文件格式 |
| **Admin / Dev 查看** | 中：需 join pool + 解析 JSON | **优**：专用列表 API / 后台表 | 差 |
| **历史清理** | 难：与 pool 同生命周期 | **优**：按 `createdAt` 批量删 shadow 行 | 易删文件 |
| **与现有模式** | 无先例于 onboarding pool | 类似 `finalSourceShadow`（job 侧 JSON 列）但 onboarding 更适合「一对多 shadow 版本」 | staging harness 可 stdout |

### 方案 A 细节

```prisma
model OnboardingPhotoPreviewPool {
  // ...existing
  metadataJson Json?  // { visualRankingShadow?: VisualRankingShadowV1, ... }
}
```

- **优点**：实现最快；按 `poolId` 一次读取；与 P7.5 主设计文档 §9 表述一致。
- **缺点**：未来若有 `rankingExplainShadow`、`applyAudit` 等，JSON 嵌套变复杂；跨 pool 统计需全表扫描；`findLatestActiveForViewer` 若误 `select metadataJson` 会增大响应面（需 DTO 剥离）。

### 方案 B 细节

```prisma
model OnboardingPhotoPreviewPoolShadow {
  id            String   @id @default(cuid())
  poolId        String
  userId        String   // viewer，冗余便于按用户统计
  shadowType    String   // "visual_ranking_shadow"
  sourceVersion String   // payload 内 sourceVersion 镜像，便于筛选
  payloadJson   Json     // VisualRankingShadowV1
  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt

  pool OnboardingPhotoPreviewPool @relation(...)
  user User @relation(...)

  @@unique([poolId, shadowType, sourceVersion])
  @@index([userId, createdAt(sort: Desc)])
  @@index([shadowType, createdAt(sort: Desc)])
}
```

- **优点**：r4-c 报表、r5 灰度审计、多版本 shadow（如算法迭代 `p7.5-r3-...` vs `p7.5-r4-...`）最清晰。
- **缺点**：多一张表、写入多一步；需定义 pool 删除时 cascade。

### 方案 C 细节

- 仅适合 **本地调试** 或 **一次性 staging**；无法满足「运营持续观察」「历史对比」「覆盖率趋势」。
- 可作为 r4-c CLI 的 **辅助输出**（`--jsonl out/shadows.jsonl`），**不作为主存储**。

### 推荐

| 阶段 | 选择 |
|------|------|
| **P7.5-r4-b** | **方案 B（主推荐）** |
| **若排期极紧** | 可临时 A，但应在 r4-c 前迁 B，避免双轨 |
| **C** | 仅作 CLI 导出副本，不替代 DB |

**理由简述**：Peima 已在 matching 链路用 `finalSourceShadow` 做「真实结果 vs hypothetical」审计；onboarding pool 未来除 visual ranking 外，还可能增加 explain / apply 审计类 shadow，**独立表 + `shadowType`** 与 worker/MatchResult 隔离，且利于 r4-d signoff 指标 SQL化。

## 3. 推荐 schema

### 3.1 表结构（推荐 B）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | cuid | PK |
| `poolId` | FK → `OnboardingPhotoPreviewPool.id` | 关联当次 generate |
| `userId` | FK → `User.id` | viewer，冗余 |
| `shadowType` | string | 固定 `visual_ranking_shadow` |
| `sourceVersion` | string | 如 `p7.5-r3-visual-ranking-shadow-v1`（与 payload 一致，便于过滤） |
| `payloadJson` | Json | 完整 `VisualRankingShadowV1` |
| `createdAt` / `updatedAt` | DateTime | 写入 / 更新（r4-b 通常 insert-only） |

**唯一约束**：`@@unique([poolId, shadowType, sourceVersion])`  
- 同一 pool、同一算法版本只保留一行；算法升级时 `sourceVersion` 变更可并存多行做 A/B 对比。  
- 若只希望「每 pool 最新一条」，r4-c 用 `ORDER BY createdAt DESC LIMIT 1`，或 r4-b 写入前 delete+insert（**不推荐**，破坏历史）。

### 3.2 payloadJson 内容（已有 r3）

保持 `VisualRankingShadowV1` 不变，关键字段：

- `appliedToPool: false`（r4-b/r4-d 恒 false）
- `slots[]`：`baselineCandidateUserId` / `shadowCandidateUserId` / `wouldChange` / scores / `reason` / `reasonTags`
- `summary`：`changedSlots`、`changedTiers`、`candidatesWithVision`、`candidatesMissingVision`、`viewerVisionAvailable`、`applyToPoolIgnored?`

### 3.3 方案 A 备选 schema（仅作对照）

```typescript
type OnboardingPhotoPreviewPoolMetadataV1 = {
  visualRankingShadow?: VisualRankingShadowV1;
  // future: other keys
};
```

### 3.4 可选扁平列（r4-b+1 优化，非必须）

若 r4-c 报表 SQL 压力大，可在 shadow 表增加 **生成列或冗余标量**（第二迭代）：

- `changedSlots Int`
- `viewerVisionAvailable Boolean`
- `candidatesWithVision Int`

r4-a **不强制**，优先从 `payloadJson` 读取。

## 4. Migration 影响

| 项 | 说明 |
|----|------|
| **是否需要 migration** | **是**（A 或 B 均需；C 不需要） |
| **建议名称** | `20260516_p75_r4_onboarding_photo_preview_pool_shadow`（B）或 `..._pool_metadata_json`（A） |
| **历史 pool** | 旧行 **无 shadow 行 / metadata 为 null**；读取逻辑视为「无 shadow」，**不回填**（除非 r4-c 单独 backfill 脚本且仅 staging） |
| **回填** | **默认不做**。原因：历史候选 vision 可能未写入；回填分数无意义。可选：staging 对最近 N 天 active pool 跑 **offline recompute**（独立脚本，非 migration） |
| **现有 pool 读取** | `findLatestActiveForViewer` / `toViewerBundle` **不得** join shadow；items DTO **零变更** |
| **Onboarding 预览页** | **无影响**（前端不读 shadow） |
| **回滚** | 删表或删列 + 部署回滚；shadow 为附加数据，回滚不影响 items |

## 5. 写入时机

### 当前 r3

```text
generate() → create pool + items → void computeShadow().catch()
```

### r4-b 建议

```text
generate() → create pool + items → return bundle（同步）
              └→ void persistShadowAfterGenerate(poolId, ...).catch(log)
```

| 决策 | 建议 |
|------|------|
| **同步 vs 异步** | **继续 fire-and-forget**（与现网一致，不增加 generate 延迟） |
| **成功路径** | `computeShadow` → `persist` insert（B）或 `update metadataJson`（A） |
| **失败** | 记录 `Logger.warn` + 可选 metric；**不**抛到 `generate()` |
| **APPLY_TO_POOL** | 仍为 true 时：**只** `warn` + `summary.applyToPoolIgnored`；**不写** items |
| **SHADOW_ENABLED=false** | 跳过 compute + persist |
| **VISION_ENABLED=false** | 可仍写 shadow（fallback 为主）；或跳过 persist——**推荐仍写**，便于观察 fallback 占比 |

### 幂等

- B：`upsert` on `(poolId, shadowType, sourceVersion)` 或 insert + catch unique violation → update `payloadJson`（重试安全）
- A：`metadataJson.visualRankingShadow` merge 覆盖

### 一致性

- shadow 基于 **generate 时刻** 的 `baselineItems` + 当时 gated candidates；若之后 items 被手动改（当前无此路径），shadow 与 items **可不一致**——payload 已含 baseline 快照，**以 shadow 内 baseline 字段为准** 做审计。

## 7. 观察指标

### 7.1 指标定义（r4-c / signoff）

| 指标 | 计算 | 用途 |
|------|------|------|
| `totalPoolsWithShadow` | count(shadow rows) / count(pools in window) | 持久化覆盖率 |
| `shadowCoverageRate` | `totalPoolsWithShadow / totalPoolsGenerated` | 写入成功率（含 fire-and-forget 丢失） |
| `avgChangedSlots` | mean(`summary.changedSlots`) | 整体冲击面 |
| `changedSlotsDistribution` | histogram 0..6 | 识别「全槽洗牌」异常 |
| `changedTiersFrequency` | count by tier in `changedTiers` | 哪一档最敏感 |
| `candidatesWithVisionRatio` | mean(`withVision / (with+missing)`) | vision 侧车质量 |
| `candidatesMissingVisionRatio` | mean(`missing / total`) | fallback 比例 |
| `viewerVisionAvailableRatio` | mean(boolean) | style_similar 可信度 |
| `topReasonTags` | aggregate `slots[].reasonTags` | 产品解释与调参 |
| `aestheticFitChangeRate` | P(change in tier aesthetic slots) | 3 槽稳定性 |
| `styleSimilarChangeRate` | P(change in style_similar slots) | 2 槽稳定性 |
| `reflowChangeRate` | P(change rank 6) | 探索位是否被误伤 |

### 7.2 可作为 APPLY_TO_POOL（P7.5-r5）前置的指标

| 门槛 | 建议阈值 | 说明 |
|------|----------|------|
| `shadowCoverageRate` | **≥ 80%**（staging 7 天） | fire-and-forget 丢失率可控 |
| `candidatesMissingVisionRatio` | **< 20%**（均值） | 否则 shadow≈baseline，无意义灰度 |
| `viewerVisionAvailableRatio` | **≥ 60%** | style_similar 依赖 viewer passing vision |
| `avgChangedSlots` | **0.3 – 2.5** | 过低=无收益；过高=产品风险 |
| `aestheticFitChangeRate` | **< 40%** | 3 槽大面积换人需产品确认 |
| `styleSimilarChangeRate` | **< 50%** | 同上 |
| `reflowChangeRate` | **< 15%** | 探索位应稳定 |
| `changedSlots = 6` 占比 | **< 1%** | 防全体洗牌 bug |

**非充分条件**：staging signoff、人工 spot-check reasonTags、env 一键回滚验证。

## 8. APPLY_TO_POOL 前置条件（P7.5-r5 设计，r4 不实现）

1. **数据**：满足 §7.2 全部阈值（连续 7 天 staging）
2. **产品**：PM 确认 aesthetic / style_similar 换人样例可接受；reflow 语义不变
3. **工程**：
   - `PEIMA_ONBOARDING_VISION_APPLY_TO_POOL` 默认 **false**；灰度用 **allowlist userId** 或 **百分比**（新 env，r5 设计）
   - 应用时 **新 `sourceVersion`**（如 `onboarding-photo-preview-v2-vision`），便于回滚识别
   - **仅**改 `OnboardingPhotoPreviewPoolItem` 的 candidate/score/reasonTags；**不改** tier/displayMode 结构
4. **隔离**：worker / `finalScore` / `MatchResult` / 旧 `PreviewPool` **零接触**
5. **回滚**：关 env → 用户 regenerate 或切回 v1 pool；保留 shadow 行审计
6. **r4-d**：`p7-r4-visual-ranking-shadow-staging-signoff.mjs` 通过

## 9. 风险

| 风险 | 缓解 |
|------|------|
| **payload 过大** | 单条约 2–6 KB；6 slots 固定上限；禁止写入 `rawProviderMeta` / 全图 URL |
| **candidateUserId 泄露** | shadow **不进** viewer API；Admin/CLI 需 RBAC；日志脱敏 |
| **fire-and-forget 失败不可见** | `shadowCoverageRate` 告警；抽样对比 `pools` vs `shadows` 计数 |
| **shadow 与 items 不一致** | payload 内嵌 baseline 快照；审计以 shadow 为准 |
| **migration 回滚** | shadow 附加表可整体 drop；items 不受影响 |
| **APPLY_TO_POOL 误开** | r4-b/r4-d **硬编码忽略** apply；r5 才读 env + allowlist |
| **JSON 查询慢** | B 表索引 + r4-c 离线聚合；必要时加扁平列 |
| **多版本 shadow 堆积** | 保留策略：90 天 archive pool 的 shadow 可 TTL 删除（运维脚本，非 r4-b） |
