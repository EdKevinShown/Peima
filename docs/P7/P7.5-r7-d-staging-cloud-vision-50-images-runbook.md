## 3. Staging env

在 **staging API 进程** 与 **backfill CLI** 使用的 `.env` 中设置（示例值用 `***` 占位，实际由运维注入）：

```env
# —— Staging live cloud vision（仅 50 张 image allowlist）——
PEIMA_ONBOARDING_VISION_ENABLED=1
PEIMA_ONBOARDING_VISION_PROVIDER=cloud
PEIMA_ONBOARDING_VISION_CLOUD_VENDOR=zhipu
PEIMA_ONBOARDING_VISION_CLOUD_DRY_RUN=0
PEIMA_ONBOARDING_VISION_CLOUD_HTTP_ENABLED=1
PEIMA_ONBOARDING_VISION_API_KEY=***
PEIMA_ONBOARDING_VISION_BASE_URL=https://open.bigmodel.cn/api/paas/v4/chat/completions
PEIMA_ONBOARDING_VISION_MODEL=***
PEIMA_ONBOARDING_VISION_CLOUD_ALLOWLIST_IMAGE_IDS=<id1>,<id2>,...<id50>
PEIMA_ONBOARDING_VISION_CLOUD_ALLOWLIST_USER_IDS=
PEIMA_ONBOARDING_VISION_TIMEOUT_MS=8000
PEIMA_ONBOARDING_VISION_CLOUD_MAX_CONCURRENCY=2
PEIMA_ONBOARDING_VISION_CLOUD_RETRY=0
PEIMA_ONBOARDING_VISION_CLOUD_ASYNC=1

# —— 保持关闭（与 r7-d 边界一致）——
PEIMA_ONBOARDING_VISION_APPLY_TO_POOL=0
PEIMA_ONBOARDING_VISION_APPLY_PERCENT=0
PEIMA_ONBOARDING_VISION_APPLY_ALLOWLIST_USER_IDS=
```

| 变量 | r7-d staging 值 | 说明 |
|------|-----------------|------|
| `ENABLED` | `1` | 开启 vision |
| `PROVIDER` | `cloud` | 走 cloud facade（`zhipu` legacy 等价 gate） |
| `CLOUD_VENDOR` | `zhipu` | `real-zhipu` adapter |
| `CLOUD_DRY_RUN` | `0` | **必须** `0` 才发真实 HTTP |
| `CLOUD_HTTP_ENABLED` | `1` | HTTP 硬闸开启 |
| `CLOUD_ALLOWLIST_IMAGE_IDS` | 50 个 id | **与 CLI `--imageIds` 对齐** |
| `CLOUD_ALLOWLIST_USER_IDS` | **空** | 禁止 user 级放量 |
| `TIMEOUT_MS` | `8000` | 单次请求超时 |
| `CLOUD_MAX_CONCURRENCY` | `2` | backfill 进程内并发（建议 staging 保守） |
| `CLOUD_RETRY` | `0` | 首轮不自动重试，便于 audit 解释 |
| `BASE_URL` | **完整** `.../chat/completions` | **勿**仅配到 `/api/paas/v4`（见下） |

### 常见误配：BASE_URL 缺少 /chat/completions

当前 `ZhipuCloudVisionAdapter` 会将 `PEIMA_ONBOARDING_VISION_BASE_URL` **原样**作为 `fetch` URL，**不会**自动追加 `/chat/completions`。

**错误配置**：

```env
PEIMA_ONBOARDING_VISION_BASE_URL=https://open.bigmodel.cn/api/paas/v4
```

**正确配置**：

```env
PEIMA_ONBOARDING_VISION_BASE_URL=https://open.bigmodel.cn/api/paas/v4/chat/completions
```

**影响**：如果只配置到 `/api/paas/v4`，live HTTP 可能返回非 2xx，并在 audit / vision `fallbackReason` 中表现为：

- `cloud_zhipu_http_404`
- `cloud_zhipu_http_400`
- 或旧版本中的 `cloud_zhipu_http_error`

**处理**：修改 `.env` 后**必须重启 API 进程**（backfill CLI 亦需重新加载 env），例如：

```bash
pnpm dev:api
```

**边界**：本修正只影响 Cloud Vision live HTTP endpoint 配置；**不改** worker / MatchResult / finalScore / RRM；**不启** APPLY_TO_POOL / percent。

### 生产默认仍关闭

**生产**（及未审批环境）保持基线，**不得**复制 staging live 配置：

```env
PEIMA_ONBOARDING_VISION_ENABLED=0
PEIMA_ONBOARDING_VISION_PROVIDER=rules
PEIMA_ONBOARDING_VISION_CLOUD_DRY_RUN=1
PEIMA_ONBOARDING_VISION_CLOUD_HTTP_ENABLED=0
PEIMA_ONBOARDING_VISION_CLOUD_ALLOWLIST_IMAGE_IDS=
PEIMA_ONBOARDING_VISION_CLOUD_ALLOWLIST_USER_IDS=
PEIMA_ONBOARDING_VISION_APPLY_TO_POOL=0
```

## 4. 执行步骤

| Step | 动作 | 写库 | HTTP |
|------|------|------|------|
| **0** | 备份 / 记录 50 个 `imageId`（CSV 或工单附件）；记录执行人、时间、env 快照（**不含** apiKey） | — | — |
| **1** | `dryRun=true` 全量 audit（`limit=50`，`onlyMissingVision=false`） | **否** | 是（gate 通过时） |
| **2** | 检查 audit JSON（§6）；确认 `cloudHttpAttemptedCount` / `Skipped` / `Failed` 合理 | — | — |
| **3** | `dryRun=false` **先跑 5 张**（`limit=5`，同一 `--imageIds` 子集） | **是**（5 条 vision） | 是 |
| **4** | SQL 抽查 `detection_score_json.vision`（§4.1）；确认 **未改** `review_status` / `detection_status` | — | — |
| **5** | `dryRun=false` **跑满 50 张**（`limit=50`） | **是** | 是 |
| **6** | 保存 stdout audit JSON 为 `r7-d-staging-50-audit-<date>.json` | — | — |
| **7** | PM spot-check **10–15 张**（§7 表格） | — | — |
| **8** | 填写 signoff 记录（通过标准 §8）；归档 audit + PM 表 | — | — |

### 4.1 Step 4 — SQL 抽查示例

```sql
-- 仅 vision 块 + 门控字段（勿 SELECT 全文进工单）
SELECT
  id,
  review_status,
  detection_status,
  detection_score_json->'vision'->>'provider'       AS vision_provider,
  detection_score_json->'vision'->>'sourceVersion' AS vision_source_version,
  detection_score_json->'vision'->>'visionStatus' AS vision_status,
  detection_score_json->'vision'->'photoVisualTags' AS photo_visual_tags,
  detection_score_json->'vision'->'qualityTags'     AS quality_tags,
  detection_score_json->'vision'->'sceneTags'      AS scene_tags
FROM user_images
WHERE id IN ('<id1>', '<id2>', '<id3>', '<id4>', '<id5>');
```

**期望（live 成功路径）**：

- `vision_source_version` = `p7.5-r7-cloud-zhipu-v1`
- `vision_provider` = `cloud`
- `review_status` / `detection_status` 与 Step 3 前 **一致**

## 5. 命令示例

在仓库根目录或 `apps/api` 下执行（需 `DATABASE_URL`、`UPLOAD_DIR`；建议 `dotenv-cli` 加载 staging `.env`）。

将 `<ids>` 替换为 50 个逗号分隔 `imageId`（**无空格** 或 CLI 解析一致即可）。

### Step 1 — dryRun audit（不写库）

```bash
pnpm --filter @peima/api run p75:r4-backfill-vision -- --provider=cloud --dryRun=true --limit=50 --onlyMissingVision=false --imageIds=<ids>
```

或：

```bash
cd apps/api
npx dotenv-cli -e ../../.env.staging -- node dist/dev-cli/p75-r4-f-backfill-onboarding-vision-runner.js --provider=cloud --dryRun=true --limit=50 --onlyMissingVision=false --imageIds=<ids>
```

### Step 3 — 小批量写库（5 张）

```bash
pnpm --filter @peima/api run p75:r4-backfill-vision -- --provider=cloud --dryRun=false --limit=5 --onlyMissingVision=false --imageIds=<first-5-ids>
```

### Step 5 — 全量写库（50 张）

```bash
pnpm --filter @peima/api run p75:r4-backfill-vision -- --provider=cloud --dryRun=false --limit=50 --onlyMissingVision=false --imageIds=<ids>
```

**注意**：

- CLI `--imageIds` 与 env `CLOUD_ALLOWLIST_IMAGE_IDS` **应对齐**；gate 以 env allowlist 为准，CLI 用于 DB 行过滤。
- `onlyMissingVision=false`：允许覆盖已有 `vision`（staging 验证常需重跑 live）。
- stdout 为 audit JSON；**禁止**将 apiKey / baseUrl / prompt / base64 贴入工单。

## 6. Audit 检查项

执行 Step 1 / 5 后，逐项核对 audit JSON（schema `p7.5-r7-c3-cloud-vision-backfill-v1`）：

| 字段 | 检查要点 |
|------|----------|
| `scannedImages` | 应等于传入 allowlist 命中行数（≤50） |
| `eligibleImages` | 与可处理行一致；异常偏少查 `skipReasonDistribution` |
| `skippedImages` | 可解释（`image_file_missing`、`cli_allowlist_miss` 等） |
| `updatedImages` | Step 1：`0`（dryRun）；Step 5：应接近 `eligibleImages` |
| `dryRun` | Step 1 `true`；Step 5 `false` |
| `provider` | `cloud` |
| `sourceVersionDistribution` | live 成功应以 **`p7.5-r7-cloud-zhipu-v1`** 为主；若仍为 `p7.5-r7-cloud-dry-run-v1` → gate 未 live |
| `visionStatusDistribution` | `ok` 为主；`failed` 需对照 `fallbackReasonDistribution` |
| `fallbackReasonDistribution` | 无 **单一原因 >50%** 的异常集中（除非已知 outage） |
| `photoVisualTagDistribution` | 封闭 taxonomy 内标签；无空分布 |
| `qualityTagDistribution` | 同上 |
| `sceneTagDistribution` | 同上 |
| `unknownTagDroppedCount` | 可解释；突增检查 vendor 输出是否漂移 |
| `cloudHttpAttemptedCount` | live staging 应 **>0**（与 c3 local mock 不同） |
| `cloudHttpSkippedCount` | gate mock / 无 imageRef 的行 |
| `cloudHttpSuccessCount` | 与 `sourceVersion=zhipu` 且非 fallback 一致 |
| `cloudHttpFailedCount` | 每次应有 `fallbackReason`；可接受但需记录 |

**隐私**：audit 与工单 **不得** 出现 `imageUrl`、apiKey、prompt、base64、`detectionScoreJson` 全文。

## 7. PM spot-check 表格模板

抽检 **10–15 张**（含至少 2 张 `cloudHttpFailed` 若有）。在 staging 后台或受控 SQL 看图，填表：

| imageId | old provider / sourceVersion | new sourceVersion | photoVisualTags | qualityTags | sceneTags | PM verdict | reason | sensitive issue | action |
|---------|------------------------------|-------------------|-----------------|-------------|-----------|------------|--------|-----------------|--------|
| | e.g. `rules` / `p7.5-r2-rules` | `p7.5-r7-cloud-zhipu-v1` | | | | pass / borderline / fail | | yes / no | keep / re-run rules / exclude |
| | | | | | | | | | |
| | | | | | | | | | |

**PM 禁止通过项**（任一命中 → **fail**）：

- 出现性别判断、颜值评分、身份识别表述
- 标签明显与图片内容不符（幻觉）
- 敏感字段写入 `vision` 或工单

**verdict 统计**：`pass` + `borderline`（可接受）≥ **80%** → 满足 §8。

## 8. 通过标准（Signoff）

| # | 标准 |
|---|------|
| 1 | **50 张** allowlist 执行完成（Step 5 audit `eligibleImages` = 50 或已记录 skip 原因） |
| 2 | `cloudHttpFailedCount` **可解释**（每条有 `fallbackReason`；无未捕获批量失败） |
| 3 | `unknownTagDroppedCount` **可解释**（vendor 新词 / mock 漂移已记录） |
| 4 | **无** sensitive field 泄露（apiKey、prompt、base64、PII 不进 DB 块 / 日志 / 工单） |
| 5 | **无** gender / beauty / identity 类输出（parser strip + PM 表确认） |
| 6 | PM spot-check **通过率 ≥ 80%**（§7） |
| 7 | `fallbackReasonDistribution` **无异常集中**（见 §6） |
| 8 | `reviewStatus` / `detectionStatus` **未被 backfill 修改**（SQL 前后对比） |
| 9 | **未启** `APPLY_TO_POOL` / **percent**；PreviewPool 实际写入策略 **未变** |
| 10 | **无** DB migration；worker / `MatchResult` / `finalScore` / RRM **未改** |

**Signoff 记录模板**（粘贴至工单或 `P7.5-r7-e` 前置）：

```text
P7.5-r7-d staging 50 images — PASS / FAIL
Date:
Executor:
Audit file: r7-d-staging-50-audit-<date>.json
cloudHttpAttemptedCount / Success / Failed:
unknownTagDroppedCount:
PM pass rate: __/15 = __%
Blockers:
```

## 9. 回滚方式

| 动作 | 说明 |
|------|------|
| 关闭 HTTP | `PEIMA_ONBOARDING_VISION_CLOUD_HTTP_ENABLED=0` |
| 恢复 provider | `PEIMA_ONBOARDING_VISION_PROVIDER=rules` |
| 关闭 vision | `PEIMA_ONBOARDING_VISION_ENABLED=0`（可选） |
| 清空 allowlist | `PEIMA_ONBOARDING_VISION_CLOUD_ALLOWLIST_IMAGE_IDS=` |
| 恢复 dry-run | `PEIMA_ONBOARDING_VISION_CLOUD_DRY_RUN=1` |
| 重启 staging API | 使 env 生效 |

**数据回滚原则**：

- **不**批量删除历史 `detectionScoreJson.vision`，除非另有专门脚本与 **书面审批**。
- 单张恢复：对该 `imageId` 跑 **rules** backfill（`--provider=rules --dryRun=false --imageIds=<id>`），merge 覆盖 `vision` 为 rules 输出。
- r7-d 失败图可保留 `fallbackUsed=true` 的 cloud 块作排查，不必立即删。
