# P7.4-r1b — 人脸存在性检测设计方案（仅方案，无代码）

> 前置：P7.4-r1a 已落地 `detectionStatus` / `detectionReasonCodes` / `detectionScoreJson` / 极暗·极糊·不可读检测 / `hasPassingPhoto`。  
> 本轮：**是否至少有一张可识别的人脸**；不做身份、比对、颜值、美化。

---

## 1. 一句话结论

**推荐在现有后端同步检测流水线中（sharp 质量检测之后）增加轻量「人脸存在性」步骤，复用 `UserImage` 检测字段、新增 `FACE_NOT_FOUND` 硬拦与 `detectionRulesVersion=p7.4-r1b-v1`，多人脸仅 warning 不 hard fail，检测异常仍 `skipped`，历史 `skipped` 图继续兼容。**

---

## 2. 推荐方案

| 维度 | 选择 |
|------|------|
| **检测位置** | **后端同步**（`POST /images/upload` 落盘后，与 r1a 同一事务化体验） |
| **技术** | **后端轻量人脸检测库**（如 `@vladmandic/face-api` + 小体积 SSD/Tiny 模型，或 `opencv4nodejs` + Haar/DNN 人脸检测器）；**不**作为第一步上云 API |
| **规则** | `faceCount >= 1` → 通过人脸门；`faceCount === 0` → `failed` + `FACE_NOT_FOUND`；`faceCount > 1` → **warning only**（写入 `detectionScoreJson.warnings`，不 `failed`） |
| **数据** | **不新增 DB 列**；扩展 `detectionReasonCodes` / `detectionScoreJson` / `detectionRulesVersion` |
| **门禁** | `FACE_NOT_FOUND` **阻止**进入 `/onboarding/photo-preference`（与 r1a `failed` 一致）；`skipped` 仍视为可用图 |

---

## 3. 为什么不直接做人脸比对 / 身份认证

| 能力 | P7.4-r1b | 身份认证 / 人脸比对 |
|------|----------|---------------------|
| 目标 | 照片里**有没有脸**，能否支撑「第一印象预览」叙事 | 证明**是不是本人**、是否与证件/底库一致 |
| 输出 | `faceCount`、可选框与置信度 | 1:1 相似度、活体、证件 OCR |
| 合规与预期 | 低敏感：质量门槛，非生物特征主键 | 高敏感：需明确授权、留存策略、审计 |
| 产品文案 | 「请上传含清晰人脸的本人照片」 | 「请完成真人认证」 |
| 与匹配链 | **不**写入 `finalScore` / `MatchResult` | 可能影响信任与风控主链 |

**结论**：r1b 是 **onboarding 准入的质量门**，不是 KYC；避免与「真人认证」混用同一套 UI 与法律表述。

## 4. 技术方案比较

### A. 是否需要做人脸存在性检测

**为什么需要**

- 风景、宠物、纯文字截图等可通过 r1a（格式/极暗/极糊）但仍**无人脸**，会污染「审美预览池」产品预期。
- 减少用户到 `photo-preference` 后才发现「预览不像人」的挫败感。
- 与运营/客服口径一致：「配吗第一印象基于你的**人像**与审美偏好」。

**解决什么问题**

- 无脸 / 完全不可辨人脸的 uploads → 明确 `failed` + 可理解文案。
- 为 r1c（单人照）预留 `faceCount` 信号。

**不解决什么问题**

- 是否本人、是否同一人、性别年龄、颜值、是否 AI 生成脸、是否戴口罩遮挡（r1c+）、是否合规（P7.6）。

**与本人认证的区别**

- **存在性**：「图里有没有脸」→ 产品可用性。  
- **认证**：「脸是不是你」→ 身份与风控；需比对、活体、证件，**不在 r1b 范围**。

---

### B. 检测位置比较

| 方案 | 用户体验 | 准确性 | 隐私 | 部署 | 性能 | 误伤 | 与 sharp 衔接 | MVP 适合度 |
|------|----------|--------|------|------|------|------|---------------|------------|
| **1. 前端** | 即时反馈，少一次往返 | 受设备/浏览器差异大；易绕过 | 脸在端上处理，不上传前可知 | 需打包模型，包体大 | 占用户 CPU | 低端机慢/失败多 | 与 r1a 前端校验并列，逻辑分裂 | 中 |
| **2. 后端同步** | 上传后 0.5–2s 内给结果；与现 r1a 一致 | 环境统一、可测、可版本化 | 图已上传，与现网一致 | 模型随 API 部署，一次配置 | 占 API CPU，可限分辨率 | 可控阈值+skipped 兜底 | **自然接在** `UserImageDetectionService.detectFromBuffer` 之后 | **高** |
| **3. 后端异步** | 需轮询或推送，流程复杂 | 同后端 | 同后端 | 需队列/任务（易触 worker 禁令误解） | 峰值好 | 用户已进入下一步才失败，体验差 | 与 onboarding 同步门禁冲突 | 低 |

**推荐**：**2. 后端同步**（与 r1a 同一 `createFromUpload` 路径）。

---

### C. 技术方案候选

| 候选 | 优点 | 缺点 | r1b 建议 |
|------|------|------|----------|
| **1. browser MediaPipe / face-api.js** | 零服务端算力 | 包大、兼容性、可绕过、双人策略难统一 | **不作为主路径**；可作 r2 可选预检 |
| **2. backend 轻量库** | 与 r1a 同栈；可单测；无外链隐私协议 | 需装 native/模型文件；冷启动 | **推荐第一步** |
| **3. 云服务 API** | 准 | 成本、延迟、合规、强依赖 | **不推荐第一步** |
| **4. 仅预留状态** | 零成本 | 问题未解 | 仅当排期极紧；**当前建议做 r1b 最小检测** |

**第一步具体倾向（实现时再选型）**

- **优先**：Node 侧 `@vladmandic/face-api`（TinyFaceDetector）或 **OpenCV DNN face_detector**（Caffe/ONNX 小模型），输入为 r1a 已生成的 **downscale 灰度/RGB 图**（如长边 320–640），避免重复解码。
- **阈值**：`minConfidence` 保守（如 0.5–0.6），宁 `FACE_UNCERTAIN`/`skipped` 也不大量误杀。
- **禁止**：生成式模型、美颜、embedding 比对、年龄性别属性作为主逻辑。

## 5. 数据结构影响

**判断：r1a 字段足够，r1b 不需要新 migration。**

| 字段 | r1b 用法 |
|------|----------|
| `detectionStatus` | 仍 `passed` / `failed` / `skipped`；**不新增** `passed_with_warning`（warning 时仍为 `passed`） |
| `detectionReasonCodes` | 新增 **`FACE_NOT_FOUND`**（仅 hard fail）；**不**把 `MULTIPLE_FACES_WARNING` 写入 codes（或写入非阻断的 `warnings` 数组，见下） |
| `detectionScoreJson` | 扩展：`faceCount`、`faces[]`（可选 `box`、`score`）、`warnings[]`（如 `MULTIPLE_FACES`）、`quality`（r1a 已有指标）、`pipeline: ["quality","face"]` |
| `detectionRulesVersion` | 升级为 **`p7.4-r1b-v1`**（含 r1a 质量 + r1b 人脸规则版本） |
| `detectedAt` | 全流程结束时间，不变 |

**可选（非必须）**：若未来 warning 需持久化查询，可把 `warnings` 放在 `detectionScoreJson`；**不必**新增 `reviewStatus` 列（留给 P7.4-r1d）。

## 6. 后端流程设计

```
POST /images/upload
  → 写盘
  → detectFromBuffer(buf)  [现有 UserImageDetectionService]
       1) sharp 解码 + UNREADABLE
       2) meanLuma → TOO_DARK
       3) laplacianVar → TOO_BLUR
       4) [r1b] faceDetector.detect(downscaled) → faceCount
       5) merge → detectionStatus / reasonCodes / scoreJson
  → prisma.userImage.create(...)
  → 返回完整 UserImage（含检测字段）
```

**规则合并顺序（短路）**

1. 解码失败 → `failed` + `UNREADABLE_IMAGE`（不再跑人脸，省算力）  
2. `TOO_DARK` / `TOO_BLUR` → `failed`（保持 r1a，避免极暗/极糊上跑人脸）  
3. 人脸检测异常 → **`skipped`**（整图或仅人脸段 skipped，见兜底）  
4. `faceCount === 0` → `failed` + `FACE_NOT_FOUND`  
5. `faceCount >= 1` → `passed`；若 `faceCount > 1` → `detectionScoreJson.warnings += ["MULTIPLE_FACES"]`  

**与 r1a 衔接**

- 逻辑集中在 `user-image-quality-detection.ts`（纯函数）+ `user-image-detection.service.ts`（sharp + face 编排）。  
- **复用** `detectionStatus` / `detectionReasonCodes`；**升级** `detectionRulesVersion`；r1a 三码**不变**。

## 7. 前端流程设计

**上传页（`OnboardingPhotoUploadPage`）**

1. P7.3 本地校验（格式/大小/可解码）不变。  
2. 上传成功 → 读 `detectionStatus` / `detectionReasonCodes` / `detectionScoreJson.warnings`。  
3. **`failed` + `FACE_NOT_FOUND`**：停留本页，展示固定中文（见 G），展示失败条目（可选展示当前图缩略图）。  
4. **`passed` + warnings 含 `MULTIPLE_FACES`**：展示黄色提示条，**仍允许**「上传并继续」或「继续选择审美偏好」（若已有 passed/skipped 图）。  
5. **`skipped`**：与 r1a 一致，可进 `photo-preference`。  
6. 保留说明区：「用于第一印象预览池、不 AI 美化、不生成虚假头像」。

**文案映射（新增）**

- `FACE_NOT_FOUND` → hard block 文案（G）  
- `FACE_UNCERTAIN` → 若后端未来用于低置信单脸，按 hard block 或 warning（r1b 可先映射为与 NOT_FOUND 相同或 warning，实现时二选一）  
- `MULTIPLE_FACES`（warning）→ 建议文案（G），不阻断  

**`hasPassingPhoto` / status API**

- 逻辑不变：`passed` + `skipped` 计入；`failed`（含 `FACE_NOT_FOUND`）不计入。  
- 仅 failed 图时仍 `nextStep = photo_upload`。

## 8. 门禁策略

| 问题 | 建议 |
|------|------|
| 1. 无人脸是否 fail？ | **是** → `failed` + `FACE_NOT_FOUND`，阻止 `photo-preference` |
| 2. 多张脸是否 fail？ | **否（r1b）** → warning only；hard fail 放 **P7.4-r1c** |
| 3. 模型不确定？ | **倾向 `skipped`**（与 r1a 检测异常一致），或 `FACE_UNCERTAIN` + warning 不拦（二选一，**推荐 skipped** 减误伤） |
| 4. 老用户 `skipped`？ | **继续兼容**，不 backfill、不阻断 |
| 5. `FACE_NOT_FOUND` 阻止 preference？ | **是** |
| 6. 人工复核？ | **r1b 不需要**；P7.4-r1d 再用 `reviewStatus` |

**对你倾向的评估**

| 你的倾向 | 评估 |
|----------|------|
| `FACE_NOT_FOUND` failed 拦下一步 | **合理**，与产品叙事一致 |
| 多人照不 hard fail，r1c 再处理 | **合理**，降低误伤（合影、背景路人） |
| 检测异常 skipped | **合理**，与 r1a 一致 |
| 老图 skipped 兼容 | **合理**，必须保留 |

---

## 9. 误伤与兜底策略

- **保守阈值**：低置信不计失败 → `skipped` 或 `FACE_UNCERTAIN` warning（实现时择一，默认 **skipped**）。  
- **小脸/远景**：downscale 时保证短边不低于 320；过小人脸可放 r1c。  
- **侧脸/遮挡**：r1b 只要求「检测到脸」，不要求正脸；正脸规则放 r1c。  
- **黑白/滤镜**：不单独拦；依赖检测器鲁棒性。  
- **性能兜底**：检测超时（如 3s）→ 人脸段 `skipped`，不拖垮上传接口。  
- **Feature flag**：`FACE_DETECTION_ENABLED=0` 时仅跑 r1a，便于回滚。  
- **日志**：记 `detectionScoreJson` + rulesVersion，不记原图到日志。

## 10. 测试计划（实现阶段，本轮不写代码）

### 后端

- 正常含脸照 → `passed`，`faceCount >= 1`  
- 无人脸（风景/物体）→ `failed`，`FACE_NOT_FOUND`  
- 人脸检测抛错/超时 → `skipped`，接口 200  
- 极暗 → 仍 `TOO_DARK`，**不**因无人脸重复失败码混乱（质量先短路）  
- 极糊 → 仍 `TOO_BLUR`  
- 多人脸 → `passed` + `warnings` 含 `MULTIPLE_FACES`（按推荐策略）  
- `onboarding` status：仅 failed 脸 → `hasPassingPhoto=false`，`nextStep=photo_upload`  

### 前端

- `FACE_NOT_FOUND` → 停留 upload，中文提示  
- `passed` → 进 `photo-preference`  
- `skipped` → 可进  
- warning → 展示不阻断（若采用）
