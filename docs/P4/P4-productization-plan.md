# P4：产品化补完（Chat / Summary / Copilot / Feedback / Suggestion 联动）— 规划

> **状态**：**规划文档**。本文件描述 **拟议** 的 P4 阶段，**不代表** 当前仓库已实现；实施前需另起 PR / 任务拆解。  
> **前置**：P0～P3（含关系时间线）按 README 口径 **已完成**。

---

## 1. 标题

**P4 — 感知层产品化补完**：在 **不引入** 独立运营后台、**不替换** 规则引擎为模型的前提下，把聊天页周边的摘要、Copilot、反馈、画像建议等能力 **串成一致的用户体验**，并补齐明显的体验与工程缺口。

---

## 2. 本阶段定位（为什么要有 P4）

P2 / P2.5 已把 **数据与 API** 和 **ChatPage / CopilotPage** 的主要入口接上；P3 完成了 **关系时间线** 只读切片。当前缺口主要在：**同一用户路径上多模块的文案、状态、失败降级、入口一致性**，以及 **跨模块的轻量联动**（例如从 Copilot 回到可操作的建议、反馈后 Copilot 提示刷新等）。P4 专门收这一块，避免与「历史版本 / 大盘治理」（P5）或「真实模型链」（P6）混在同一迭代里扯皮。

---

## 3. 与前一阶段的关系

| 阶段 | 关系 |
|------|------|
| **P3** | P3 交付 **时间线只读切片**；P4 **不扩展** 时间线业务能力边界（不新增时间线类型事件、不改为实时推送），仅可 **修正** 与时间线相关的导航/文案一致性。 |
| **P2.5** | P4 **继承** 已有 Copilot 独立页、摘要手动生成、建议 accept/dismiss；P4 做的是 **体验与联动收口**，不重做 schema 或大改 API 形态。 |

---

## 4. 本阶段核心目标

1. **一致体验**：摘要 / Copilot / 反馈 / 建议在 **成功、空态、失败、未登录** 下的表现可预期，文案与路由与 README 描述对齐。  
2. **可发现的联动**：用户在聊天内完成的动作（反馈、建议处理、摘要更新）能在 **Copilot / 摘要展示** 上 **可感知**（例如提示刷新、短暂状态条），无需用户猜「是否生效」。  
3. **可维护**：前端 API 封装、错误处理、与 `sourceType` / `sourceVersion` 展示规则 **集中约定**，减少各页各写一套。  

---

## 5. 建议纳入范围（做什么）

以下为 **建议清单**，实施时按优先级裁剪；**均属 P4 边界内**。

- **ChatPage**：摘要卡片与 Copilot 卡片、快捷反馈、建议列表的 **布局与信息层级** 微调；加载/重试/只读说明统一。  
- **CopilotPage**：与 `basedOn` 对齐的 **空态说明**；从页内 **深链回 Chat**（已有 query 的延续）；可选 **轻量「刷新 insights」**（仍只读调 API）。  
- **反馈**：提交后的 **即时反馈**（toast 或行内成功态）；与 timeline / Copilot 文案 **不矛盾**（不承诺对方可见等）。  
- **画像建议**：待处理/已处理与 Chat 摘要、Copilot 建议 **话术一致**；边界错误（网络、403）统一 `handleJson` 表现。  
- **跨模块约定**：`resolveUserId`、API `baseUrl`、`authHeaders` 在各相关页的 **使用方式文档化**（可落在 `docs/P4` 子页或本文件附录）。  
- **无障碍 / 基础可用性（可选）**：焦点顺序、按钮禁用态、`role="alert"` 等与现有组件风格一致的小步改进。  

---

## 6. 明确不纳入范围（不做什么）

- **不** 新增 **摘要 / Copilot / 反馈** 的 **历史版本列表**、对比视图、回滚（归 **P5**）。  
- **不** 新建 **独立建议中心后台**、**Analytics 大盘改版**、**RBAC 矩阵**（归 **P5**）。  
- **不** 接入 **真实大模型**、**Worker 自动生成摘要/Copilot**、**多 Agent**（归 **P6**）。  
- **不** 改 **P0 聊天发消息契约**；**不** 为 P4 新增 **时间线专用表** 或改变 P3 API 语义。

## 8. 验收口径 / 完成标准

- 给定测试账号，按 **Chat → 反馈 / 建议 / 摘要 / Copilot** 主路径走通，**无未处理的白屏错误**；预期失败有 **可读说明**。  
- **回归**：P0 主链路、P2.5 清单中的 **高优先级项**、P3 时间线入口 **不被破坏**。  
- **代码**：与现有 ESLint / 构建脚本一致；**不** 引入仅 P4 使用的大型新依赖（除非单独评审）。

## 9. 主要风险与依赖

| 风险 / 依赖 | 说明 |
|-------------|------|
| **范围蔓延** | 容易把「做个后台」或「上模型」塞进 P4；需 **对照 §6** 拒收。 |
| **设计未定** | 纯视觉重设计未在本规划内；若产品要强改版式，需 **单独拍板** 或拆出子里程碑。 |
| **API 稳定性** | 若 P4 需要 **极小** 的 API 字段补充（如多返回一个 `lastUpdatedAt`），应 **向后兼容** 且单独 PR。 |

---

## 10. 推荐实施顺序

1. **盘点**：列出 Chat / Copilot / feedback / profile API 调用点与错误分支（1～2 天量级）。  
2. **统一错误与空态**：`handleJson`、各卡片组件（优先 **用户可见频率最高** 的路径）。  
3. **联动与文案**：摘要更新后 Copilot 提示、反馈成功态等 **低成本高收益** 项。  
4. **文档与 checklist**：补手动验收表；再开 PR 更新 README 状态。
