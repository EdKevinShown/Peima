## 三、结论

**M4.0 第一轮真实 DB 验收通过。**

- RRM readonly proposal 已能按 `poolId` 生成；本例中 `wouldChangeStaticResult = true`（静态 shortlist 头名与 RRM-only 头名不一致），且 **`appliedToMatchResult` / `appliedToFinalScore` / `appliedToDisplayCandidate` 均为 `false`**，与「只读提案层」设计一致。
- **`GET /matching/result`** 保持 **M3.8 enabled-mode** 读路径与字段语义不变；正式展示与冻结侧车仍以 `candidateUserId` / `displayCandidateUserId` / `finalMatchDecisionMeta` 为准，**未**被 RRM proposal 改写。

---

## 四、补充说明（语义边界）

**`staticTop1CandidateUserId` 的含义**

在 M4.0 中，`staticTop1CandidateUserId` 来自 **当前 RRM proposal 所依赖的 `AiSimulationV1Job` 上的 `shortlistBinding`（静态 shortlist 基准顺序的第一位）**，用于与 `rrmTop1CandidateUserId` 对比得到 `wouldChangeStaticResult`。

**不应**将 `staticTop1CandidateUserId` **直接等同于** `MatchResult.candidateUserId`：后者由 worker 匹配与后续 M3.8 侧车/冻结逻辑决定；本验收中亦可看到 RRM top1、static top1 与 `MatchResult.candidateUserId` 之间可能不一致，而只读接口 **不** 回写任何一行 `MatchResult`。

**M4.1 预告（未在本轮实现）**

进入 **M4.1 三路对照** 时，建议在观测 UI 或文档中将 **Static 20 维 Top1**、**`MatchResult` 原始候选**、**Pairwise frozen `selectedCandidateUserId`**、**RRM top1** 分栏并列展示，避免单一字段名混读。

## 五、边界（继续有效）

本轮及本验收 **不涉及** 以下变更；后续里程碑亦须在各自 PR 中单独评审：

- **不改** `displayCandidateUserId`

- **不改** `FinalMatchPage` 展示对象
- **不改** pairwise finalize 逻辑
- **不改** RRM 公式、`evaluateRrmSimFromSimulationV2`、`extractDPre` 等核心评估链
