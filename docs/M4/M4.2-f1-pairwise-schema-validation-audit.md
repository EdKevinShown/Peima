# M4.2-F1 — Pairwise `schema_validation` 失败原因审计（只读）

本文档对 **`ai_pairwise_decision_jobs`** 中 **`status = failed`** 且 **`failureDetail.code = schema_validation`** 的条目做 **聚合审计**，用于判断失败形态来自 LLM / JSON / normalizer / validator / prompt / 模型哪一侧，**不包含**原始 LLM 文本、**不包含**可反查主体的 ID（`viewerUserId`、`poolId`、`candidateUserId`、`pairwiseJobId`、`simulationJobId` 等）。**不**修改业务代码、schema、normalizer、prompt、validator。

**审计方法**：对目标环境数据库做只读查询，统计 `failureDetail.message` / `path` / `reason` 的分布；并结合 `ai-pairwise-decision-job-execution.ts`、`ai-pairwise-decision-generate.core.ts` 中 **`schema_validation` 的写入路径** 解读含义。

**快照说明**：下表为 **单次本地审计** 的计数；随时间与新增失败 job 会变化。复核时可重复同一 SQL / Prisma 聚合，**勿**将含真实 `jobId` 的明细提交入库。

## 2. `schema_validation` 失败阶段分布（按持久化 `message` 分桶）

| 阶段（由 `message` 推断） | 条数 | 说明 |
|---------------------------|-----:|------|
| **`AiPairwiseDecision schema validation failed.`**（`generate.core`：normalizer 之后 **`parseAndValidateAiPairwiseDecision`**） | **12** | LLM 已产出可解析 JSON 并经 **normalizer** 得到 **draft**，仍 **未通过** 最终 schema 校验。 |
| **`Persisted shortlistSnapshot failed contract validation.`**（job 执行：短名单预检） | **0** | 本次快照中 **未出现**；若出现则属于 **入队前短名单 JSON** 与契约不一致，**非** LLM 输出。 |
| **`Post-LLM validation unexpectedly failed.`**（job 执行：`gen.ok` 后二次校验） | **0** | 本次快照中 **未出现**；与上一行在代码中互斥于不同失败分支，语义上亦偏 **「已通过 generate、仍校验失败」** 的兜底文案。 |

**结论（阶段）**：当前库内这 **12** 条均落在 **「normalizer 之后、strict validator 未过」** 路径，**不是** `json_parse_error` / `json_extract_error` 等 **JSON 层** code（那些会带 **不同** `failureDetail.code`，不计入本 `schema_validation` 桶）。

## 5. 可能原因映射（1–6）

| # | 类型 | 与本快照的吻合度 | 说明 |
|---|------|------------------|------|
| 1 | **LLM 输出缺字段 / 类型错** | **高** | `viewerUserId` 缺失或非字符串、`strongRisk` / `fallbackUsed` 非布尔等，多为 **模型未按契约填全**。 |
| 2 | **JSON extract 失败** | **低** | 若为 extract/parse 失败，持久化 code 通常为 **`json_extract_error` / `json_parse_error`** 等，**不在**本 `schema_validation` 12 条内。 |
| 3 | **normalizer 未覆盖某些形态** | **中–高** | 所有失败均在 **normalizer 之后** 的 **`parseAndValidateAiPairwiseDecision`**；若 LLM 给出 **可被 normalize 但未覆盖** 的变体，会表现为 **本阶段** 失败。 |
| 4 | **validator 过严** | **中** | `expected_enum` / `expected_range_0_1` 可能部分属 **合理严格**；需对照 **产品可接受语义** 再判断是否放宽。 |
| 5 | **prompt 约束不足** | **中** | 对 **`strongRisk` 布尔**、**`suggestedAction` 枚举**、**与短名单对齐的 `viewerUserId`** 等，prompt 可 **更强约束** 减少漂移。 |
| 6 | **模型低质量 / 随机格式** | **中** | 与 **§5-1** 并存；需结合 **provider/model** 与 **重试率** 另行观测（本审计 **不**记录模型名以外的敏感信息）。 |

---

## 6. 建议修复方向（优先级 — 仅建议，本轮 **未**改代码）

1. **优先补 normalizer / 契约对齐**：针对 **`candidateA.strongRisk`**、**`fallbackUsed`**、**`candidateA.suggestedAction`**、**`conversationFit` / `dimensions.conversationFit`** 的高频 **`reason`**，核对 **`normalizeAiPairwiseDecisionDraftFromShortlist`** 是否覆盖常见 LLM 变体（字符串 `"true"`、空对象、缺键等）。  
2. **并行加强 prompt**：对 **布尔 / 枚举 / 0–1 维度 / 必须与输入一致的 viewerUserId** 给出 **更明确的 JSON 样例与禁止项**。  
3. **再评估 validator**：在 normalizer + prompt 收紧后仍 **系统性** `expected_enum` 失败，再考虑 **枚举扩展** 或 **错误信息驱动的窄放宽**（避免一次放宽导致 silent bug）。  
4. **不建议**在未做 1–2 前 **先**整体放宽 schema：当前失败 **高度集中于少数 path + 少数 reason**，更符合 **「可修 normalizer / prompt」** 而非 **「validator 全面过严」**。

**是否建议先改 normalizer / prompt / validator**：**先 normalizer + prompt**；**validator** 以 **观测后小步调整** 为宜。
