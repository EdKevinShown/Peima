# M4.1 — Three-Source Decision Comparison（只读对照层）

## 1. 目标

在 **M3.8**（Pairwise 冻结 meta + `GET /matching/result` enabled-mode 读路径）与 **M4.0**（`GET /matching/rrm-ranking-proposal/:poolId` 只读 RRM 提案）之上，新增 **只读** 接口：

**`GET /matching/decision-comparison/:poolId`**

将 **Static shortlist（20 维 contract）**、**`MatchResult` 原始候选**、**Pairwise 冻结侧车 meta**、**M4.0 RRM readonly 子集** 并列于同一 **comparison DTO**，并给出 **四源一致性摘要**（`comparisonSummary`），用于内部观测一致/冲突。**不写库**、**不重跑 LLM**、**不改变** `GET /matching/result` / worker / `FinalMatchPage` / pairwise finalize / RRM 核心公式链。

---

## 2. 为什么叫 “Three-Source” 但 DTO 采用四源分栏？

历史命名 **Three-Source** 强调与「单一静态 Top1」叙事区分；实现上 **必须把 `MatchResult.candidateUserId`（worker 原始落库）单独成栏**，避免与 **`shortlistBinding` / static contract 的 Top1** 混读。因此 HTTP DTO 固定为 **四栏**：`staticShortlist`、`matchResultOriginal`、`pairwiseFrozen`、`rrmReadonly`。

---

## 3. 四个来源分别来自哪里

| 栏位 | 数据来源 | 说明 |
|------|----------|------|
| **`staticShortlist`** | `PreviewPoolService.buildShortlistContractV0ForPool(viewerUserId, poolId)` | `source = preview_pool_shortlist_contract_v0`；Top1/Top2 来自 `shortlist.candidateUserIds[0/1]`，`shortlistSize` 为数组长度。无法构建时 **`null`**，`notes` 含 **`STATIC_SHORTLIST_MISSING`**。 |
| **`matchResultOriginal`** | `match_results`：`findFirst({ where: { userId: viewerUserId }, orderBy: { createdAt: "desc" } })` | 返回 **`matchResultId` / `candidateUserId` / `finalScore` / `createdAt`**。无行时 **`null`**，`notes` 含 **`MATCH_RESULT_MISSING`**。 |
| **`pairwiseFrozen`** | `pairwise_pool_finalize_meta`：`findUnique({ viewerUserId, poolId })` | 仅当 **行存在且 `frozen === true`** 且 **`parseFinalizeMetaV1Loose(meta)`** 成功时 **`present: true`** 并展开 meta 字段；否则 **`{ present: false }`**，`notes` 含 **`PAIRWISE_META_MISSING`**。解析复用 **`matching-result-display.ts`** 中的 **`parseFinalizeMetaV1Loose`**（与 `GET /matching/result` 侧车解析一致，**不** 改 display 语义）。 |
| **`rrmReadonly`** | **`MatchingRrmRankingProposalService.getReadonlyProposal`**（M4.0） | 子集字段；**不** 复制 RRM 计算链。若底层抛出 **`NO_SUCCEEDED_SIMULATION_JOB_FOR_POOL`**：**整接口仍 200**，**`rrmReadonly = { present: false, code: ... }`**，`notes` 含 **`RRM_PROPOSAL_MISSING`**。 |

**`sourceVersion`**：`m4.1-three-source-decision-comparison-readonly-v1`。**`mode`**：`readonly`。

---

## 4. `MatchResult` original 不按 `poolId` 外键绑定的语义

**`MatchResult` 表当前没有 `poolId`。** 本接口中的 **`matchResultOriginal`** 表示 **该 viewer 最新一条** `MatchResult`（按 `createdAt` 降序），用于与 **当前预览 `poolId`** 上下文做 **并列对照**，**不是** SQL 级「按池过滤的 MatchResult」。产品/观测上应理解：可能与某次 pool 侧车 **时间对齐**，但 **无外键保证**。

---

## 5. M4.1 与 M4.0 的关系

- **M4.0**：按池返回完整 RRM ranking proposal（含 `ranking[]` 等）。  
- **M4.1**：在同一鉴权与池归属下，**聚合** static / MatchResult / pairwise / **M4.0 子集**（`simulationJobId`、`rrmTop1CandidateUserId`、`wouldChangeStaticResult`、三枚 `appliedTo*`），并计算 **`comparisonSummary`**。RRM 部分 **仅调用** M4.0 service，**不** 调用 `evaluateRrmSimFromSimulationV2` 等底层链。

---

## 6. M4.1 不做批量指标（M4.2）

M4.1 **仅** 提供 **单 viewer + 单 pool** 的只读对照响应；**不做** 跨用户/跨池聚合、大盘、报表。批量指标与观测大盘归属 **M4.2 / M4.4**（本仓库尚未实现）。

---

## 7. 安全边界（与强约束一致）

- **不写** `MatchResult`；**不改** `MatchResult.candidateUserId`、**`finalScore`**  
- **不改** `displayCandidateUserId`；**不改** **`GET /matching/result`** 实现与契约  
- **不改** worker `batch-match`；**不改** `FinalMatchPage`；**不改** pairwise finalize 写路径  
- **不改** RRM 公式、`evaluateRrmSimFromSimulationV2`、`extractDPre` 等  
- **不做** M4.3 用户端解释产品化、M4.4 Admin 大盘  

---

## 8. API 摘要

- **路由**：`GET /matching/decision-comparison/:poolId`  
- **鉴权**：`JwtAuthGuard`；`token.userId` = `viewerUserId`；**池必须属于该 viewer**，否则 **404**。  
- **响应**：见实现类型 **`MatchingDecisionComparisonHttpDto`**；**`comparisonSummary`** 中含 `allSelectedIds`、`uniqueCandidateCount`、若干 **`...Equals...`**（任一侧缺失则为 **`null`**）、`notes`（英文大写枚举式常量字符串）。

---

## 9. 真实 DB 验收记录（M4.1 第一轮收口）

**结论（摘要）**

M4.1 第一轮 **真实 DB 验收通过**。验收明细（四源字段、`comparisonSummary`、`GET /matching/result` 回归）见 **[M4.1-three-source-decision-comparison-run-record.md](./M4.1-three-source-decision-comparison-run-record.md)**。

**四源不可混读**

`staticShortlist.top1CandidateUserId`、`matchResultOriginal.candidateUserId`、`pairwiseFrozen.selectedCandidateUserId`、`rrmReadonly.rrmTop1CandidateUserId` 语义不同，不可混用；说明见 run-record **§四**。

**边界（验收后仍维持）**

不写 `MatchResult`；不改 `MatchResult.candidateUserId`；不改 `finalScore`；不改 `displayCandidateUserId`；不改 **`GET /matching/result`**；不改 worker；不改 `FinalMatchPage`；不改 pairwise finalize；不改 RRM 公式 / evaluator / `extractDPre`；**不进入 M4.2**。
