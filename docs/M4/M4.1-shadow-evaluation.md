# M4.1 — Shadow evaluation（报表脚本）

## 1. 定位

**M4.1 是 shadow evaluation**，只读聚合已完成 AI simulation job 的 **`rrmSimMultiCandidateDiagnostic`** 与 **`rrmRankingProposal`**，用于观察 RRM 与现有 simulation 排序的差异分布。**不是**正式 M4 生产排序融合；**不改变** `finalScore`、worker 主排序、`MatchResult.finalScore`，**不写** `MatchResult`，**不重跑** LLM。

## 2. 脚本路径与模式

- 脚本：`packages/database/scripts/m4-shadow-evaluation-report.mjs`
- 当前实现 **`mode`: `api_readonly`**：用 Prisma **只读**枚举/筛选 job，再对每个 job 调用 **`GET /admin/ai-simulation/v1/jobs/:jobId`** 复用 API 已计算的 diagnostic + proposal（避免在 scripts 包内再搭一套 TS 编译链）。

## 3. 运行命令

在**仓库根目录**（需已 `pnpm install`，且本地 API 可访问 admin 路由）。仓库 **Node >= 20**，推荐用内置 `--env-file`（Windows 上参数会稳定传到脚本；避免部分环境下 `pnpm exec dotenv` 与 `--jobId` 组合异常）：

```bash
node --env-file=.env packages/database/scripts/m4-shadow-evaluation-report.mjs --jobId cmodwumhj000a6z3ke20zbrdr --pretty
```

若未通过 `--env-file` / `dotenv` 注入 `DATABASE_URL`，脚本会**尝试读取仓库根 `.env` 一次**（不打印变量值）。

批量（默认 `limit=20`，按 `updatedAt` 降序，仅 `completed` 且 `items>=3`）：

```bash
node --env-file=.env packages/database/scripts/m4-shadow-evaluation-report.mjs --limit 20 --pretty
```

写入文件：

```bash
node --env-file=.env packages/database/scripts/m4-shadow-evaluation-report.mjs --limit 20 --out ./m4-shadow-report.json --pretty
```

仍可使用（与仓库其他脚本一致）：

```bash
pnpm exec dotenv -e .env -- node packages/database/scripts/m4-shadow-evaluation-report.mjs --limit 20 --pretty
```

单 job 验收时若 `--jobId` 未生效，可用 **`--jobId=<id>`** 或环境变量 **`M4_SHADOW_JOB_ID=<id>`**。

**依赖环境变量**（勿打印到日志/报告正文）：

- `DATABASE_URL` — Prisma 只读查询
- `JWT_SECRET`、`PEIMA_ADMIN_USER_IDS`（至少一个 id）— 签发 admin JWT 调 admin GET
- `VITE_API_BASE_URL` 或 `API_PUBLIC_BASE_URL` — API 根地址（默认 `http://localhost:3000`）

## 4. 参数

| 参数 | 说明 |
|------|------|
| `--limit <n>` | 批量模式下最多处理的 **items≥3** 的 completed job 数，默认 **20**，上限 **500**（与 Prisma `take` 窗口配合） |
| `--jobId <id>` / `--jobId=<id>` | 只处理该 job；**不**应用「batch 下 rrmAvailableCount≥3」剔除，便于单 job 验收；也可用 `M4_SHADOW_JOB_ID` |
| `--out <path>` | 将 JSON 写入文件；不传则 stdout |
| `--pretty` | 格式化 JSON |

## 5. 输出字段（摘要）

- 顶层：`schemaVersion`、`sourceVersion`、`generatedAt`、`mode`、`summary`、`jobs[]`、`skipped[]`
- **`summary`**：`jobCount`（Prisma 扫描窗内行数）、`usableJobCount`、`skippedJobCount`、`totalCandidateCount`、fallback 与 spread 统计、`scoreFlagDistribution`、`recommendationDistribution`、各类 **examples**（截断列表）
- **`jobs[]`**：每 job 的候选数、RRM 诊断计数、`scoreRange`、`scoreDistributionFlag`、`recommendation`、双 top、`topCandidateChanged`、`confidenceLevel`、`warnings`
- **`skipped[]`**：`jobId`、`skippedReason`、`detail`

## 6. `skippedReason` 枚举

| 值 | 含义 |
|----|------|
| `not_completed` | `jobStatus !== completed` |
| `too_few_items` | `items.length < 3` |
| `no_diagnostic` | Admin GET 非 200 或响应缺少 diagnostic/proposal |
| `too_many_fallbacks` | 预留枚举（当前脚本未单独用作 skip 条件） |
| `no_rrm_ready_items` | **仅批量模式**：`rrmAvailableCount < 3`（非 fallback 不足） |
| `malformed_payload` | 找不到 job 等 |

## 7. 如何解释 `recommendation`

与 M4.0 `buildRrmRankingProposal` 一致（由 API 返回的 `rrmRankingProposal.recommendation`）：

- `too_many_fallbacks` → `do_not_use_for_ranking`
- `too_narrow` → `insufficient_separation`
- top 变且 spread≥8 → `review_manually`
- top 不变且双 top 一致 → `supports_existing_rank`
- 其余 → `diagnostic_only`

## 9. 本轮 shadow 结果如何解释（closure）

1. **当前 shadow report 链路可用**：Prisma 只读列 job + admin `GET .../jobs/:jobId` 聚合 diagnostic / proposal，脚本退出码与输出结构稳定，满足 M4.1 只读观测目的。
2. **当前 fallback 不是主要问题**：上述批量跑数中 `fallbackCount = 0`，瓶颈不在 fallback 堆积。
3. **当前最大问题是 usable job 太少**：`usableJobCount = 3`，相对 `jobCount = 16`，大量 job 在批量规则下因 `no_rrm_ready_items`（`rrmAvailableCount < 3`）或 `too_few_items` 被跳过，**样本不足以支撑任何生产排序结论**。
4. **当前 3 个 usable job 全部为 `too_narrow`**：`scoreFlagDistribution` 全落在 `too_narrow`，即模拟分数分离度不足，proposal 侧一致落在 `insufficient_separation`。
5. **`changedTopRate` 虽高，在 `insufficient_separation` 前提下不能作为排序融合依据**：top 变化可能反映噪声或窄分布下的不稳定比较；**不得**把高 `changedTopRate` 单独当作「RRM 更准」或「可以合入主排序」的信号。
6. **当前仍不进入正式 M4**：在分离度与样本量未改善前，仅维持 shadow 报表与文档记录，**不**把 RRM-Sim proposal 写入生产路径。

## 10. 进入正式 M4 的最小数据门槛建议

在动生产排序或写 `MatchResult` 之前，建议至少满足（与 `docs/M4/M4.0-readonly-rrm-ranking-proposal.md` 第 7 节互补，**偏可操作的 shadow 侧门槛**）：

- **`usableJobCount >= 10`**（且 preferably 持续增长），避免被个位数样本误导。
- **多数 job 的 `scoreDistributionFlag = ok`**，而不是 usable 子集清一色 `too_narrow`。
- **`no_rrm_ready_items` 明显下降**：批量扫描下有足够 completed job 满足「≥3 条 rrm-ready」等脚本 batch 规则。
- **`fallbackRate` 可控**：即使当前为 0，也应在更大样本上观察 fallback 是否抬头并设上限预期。
- **`topCandidateChanged` 的样本可人工解释**：能对应到具体 job / 候选差异，而不是仅看比率。
- **至少出现一批 `supports_existing_rank` / `review_manually`**，而不是 usable 子集 **全部** `insufficient_separation`，否则仍只能当诊断噪声带。
- **先做 shadow mode**，不直接写 `MatchResult`；任何生产融合需单独设计与回滚。

## 11. M4.1-data-expansion（样本扩展计划，不实施）

本小节为 **仅设计、不实施** 的小计划，用于指导后续如何**合法扩大观测样本**，而不是改代码或伪造数据。

**目标**：降低 `no_rrm_ready_items` 占比，使更多 **completed** 的 ai-simulation-v1 job 在批量脚本下具备 **≥3** 条 rrm-ready（非 fallback）行，从而让 `scoreDistributionFlag` 有机会从「全 `too_narrow`」走向更可分辨的分布。

**可选动作（A–F）**：

| 步骤 | 说明 |
|------|------|
| **A** | 对**已有**旧 completed job **不做** retroactive 伪造 rrm-ready 或改写历史 payload。 |
| **B** | **新生成 5～10 个**真实 ai-simulation-v1 jobs（正常产品/测试流程）。 |
| **C** | 每个 job **至少 3 个 candidate**（items），满足脚本与 batch 语义下限。 |
| **D** | **仅在明确测试时**开启 `AI_SIMULATION_V1_WORKER_ENABLED=1`（以仓库/env 文档为准），避免误在生产环境放大队列。 |
| **E** | 生成并完成后，再跑 `m4-shadow-evaluation-report.mjs`（`--limit` 可调大）做对照。 |
| **F** | 观察 `scoreDistributionFlag` 是否从「usable 子集全 `too_narrow`」改善，以及 `recommendationDistribution` 是否出现其他桶。 |

执行轮批次、成本控制与停止条件等 **M4.1-data-expansion 执行计划** 见：`docs/M4/M4.1-data-expansion-execution-plan.md`。

## 12. 明确不做什么

- 不改 **finalScore** / **worker 主排序** / **`MatchResult.finalScore`**
- **不写** `MatchResult`，**不让 RRM-Sim 参与真实排序**
- **不写库**（无 Prisma `create/update`）
- **不** `POST /run`、**不**调用 LLM
- **不把 `changedTopRate` 直接当作上线依据**
- **不**为了报表好看而手写、篡改或伪造 rrm-ready item / 诊断字段
- 首版 **不**新增 HTTP API（仅脚本 + admin 只读 GET）
- **不进入正式 M4** 生产排序融合，直至第 10 节门槛与 M4.0 产品侧条件共同满足

当前 **too_narrow** 成因分析与 **evaluator calibration** 规划见：`../M1/M1.3-evaluator-calibration-planning.md`。
