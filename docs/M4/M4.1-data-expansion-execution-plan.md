## 二、数据扩展目标（执行轮需满足）

每个新 job（由真实 LLM + validator 产生，**禁止手写 / 伪造**）目标：

- `items.length` ≥ **3**
- succeeded 且 `transcriptLite` 满足：**`schemaVersion` = 2（JSON 数字，文本 `'2'`）**、`sourceVersion` = **`ai-match-simulation-rrm-ready-v2`**、`fallbackUsed` = **`false`**（根 payload，与 `AiSimulationLlmPayloadV2` 一致）
- `jobStatus` = **`completed`**
- **不写** `MatchResult`；**不让 RRM-Sim 参与真实排序**；**不改** `finalScore` / worker 主排序 / `MatchResult.finalScore`；**不恢复** `shortlistScenariosV0`；**不改** RRM 公式

## 三、方案 A / B / C 比较与推荐

| 维度 | **A：现有编排 + preview pool → enqueue → worker** | **B：reset + 重跑已有 job** | **C：新建测试 viewer + 全量数据再跑链路** |
|------|----------------------------------|-----------------------------|----------------------------------------|
| 成本（执行轮） | 中：每 item 一次 LLM | 低 | 高 |
| 样本多样性 | **中–高**：可选用 **第二个 active viewer**（上表）减轻单 viewer 偏置 | 低：易与历史同源 | 最高 |
| 真实性 | **最高**：与生产路径一致 | 中：仍是真实链路，但时间/版本切片单一 | 高 |
| 污染 `MatchResult` | **否**（侧车设计） | 否 | 否 |
| 触发真实 LLM | **执行轮会**；规划轮不跑 | 执行轮会 | 执行轮会 |
| 回滚 | 停 worker、不再 `POST /run`；已写库 job 保留作样本或后续清理策略（产品决策） | 同左；历史 job 已存在 | 同左；可能多出血缘用户需治理 |

**推荐：以 A 为主路径。**

**理由摘要：** 在**不伪造数据**、**不重跑 LLM 的规划轮**前提下，A 最贴近真实编排与校验；当前库已有 **2 个 active pool、各 6 个 item**，足以在执行轮用 **不同 `viewerUserId`**（至少 `cmo7ksq8s00006znosryc9k0n` 与 `cmocgepyl00006zzcs7is9eoq`）各跑若干 job，**明显改善样本多样性**，而不必立刻上 C。B 仅适合「快速补跑同一 shortlist」的局部实验，**不适合**作为 M4.1 扩展主策略（与「降低单 viewer 偏置」目标冲突）。

## 四、执行批次计划（建议）

### Round 1（先小步验证）

- **目标**：`usableJobCount` **+2**（shadow 批量口径下可核对）
- **规模**：**2 个新 job**；每 job **3 个 candidate（item）** 即可触达脚本 batch 下限，成本控制最优
- **完成后**：立即跑  
  `node --env-file=.env packages/database/scripts/m4-shadow-evaluation-report.mjs --limit 20 --pretty`
- **若 usable 子集仍全 `too_narrow`**：暂停 Round 2，先做分布/队列/provider 分析（见「七」）

### Round 2

- **前提**：Round 1 完成且 shadow 指标有可读变化（例如出现 `ok` 或 recommendation 非全 `insufficient_separation`，或至少确认 narrow 来自数据而非系统性故障）
- **目标**：`usableJobCount` **+3～5**
- **规模**：**3～5** 个新 job；每 job **3～6** item（按 pool 与 orchestration 实际上限）

### Round 3

- **目标**：shadow 口径 **`usableJobCount` ≥ 10**
- **完成后**：再做一轮 **M4.1 shadow closure**（更新 `M4.1-shadow-evaluation.md` 的 run record 由人工执行）

## 五、成本控制（执行轮操作清单）

- **每轮最多 job 数**：Round 1 **≤2**；Round 2 **≤5**；Round 3 累计控制总 token，建议单轮新增 **≤5** job。
- **每 job 最多 candidate**：与 pool / orchestration 合同一致；建议默认 **3～6**，避免无谓放大 item 数。
- **避免 worker 狂消费队列**：
  - enqueue **前** `AI_SIMULATION_V1_WORKER_ENABLED=0`（或停掉 worker 进程），**仅**放入本计划允许的 job 数；
  - 确认队列深度后再 `=1` 启动单 worker；处理完再关掉或恢复日常值。
- **Docker**：若本机同时存在 **Docker worker** 与 **本地 `pnpm dev:worker`**，应**只保留一个 consumer**，否则重复 claim / 双消费风险（以 M3.3 设计为准）。
- **记录新 `jobId`**：每 enqueue 成功后在团队清单 / issue / 本文档附录表格登记 `jobId`、`viewerUserId`、`poolId`、item 数、时间戳（**勿**贴 JWT / API key）。
- **避免重跑已成功 item**：依赖 orchestration 的幂等与「新 job」策略；**不要**对 succeeded item 做手工 reset 除非明确走产品支持的 retry 路径（本计划默认 **只新建 job**）。

**Env 开关（执行轮）：**

| 变量 | 建议 |
|------|------|
| `AI_SIMULATION_V1_WORKER_ENABLED` | 准备队列时 **0**；确认只跑目标 job 后 **1**；跑完再 **0** 或恢复团队默认 |
| `AI_SIMULATION_V1_WORKER_POLL_MS` | 可保持默认或略增大，降低空转日志（非必须） |
| `DATABASE_URL` / `JWT_SECRET` / admin 相关 | 仅本地/受控环境；**不**把密钥写入文档或报告 JSON |

## 七、停止扩展并分析的条件

出现任一情况即**停止 enqueue / 停 worker**，转入排障而非继续加样本：

- Provider 侧 **`schema_validation`** 频率异常升高
- **`too_many_fallbacks`** 在 shadow 分布中明显抬头
- **`usableJobCount` 增长但 score 仍全 `too_narrow`**（分离度系统性不足）
- Token / 费用超预算
- Worker **长时间 `running`** 或卡死（结合 `AI_SIMULATION_V1_STUCK_TIMEOUT_MS` 等现有配置排查）
- **`changedTopRate` 高但 spread 低**（与 M4.1 closure 结论一致：不能当融合依据，应停步分析）
- 队列、权限、admin / viewer 响应边界异常
